# 課題に合う検証可能な手順を設計する

[Codexでの実行規則](../../execution.md)を読んでから使う。

最初に `poteto-mode` の原則を読み、条件設定、手順設計、実行、判断記録、全体検証を作業一覧にする。

成果を反証できる完了条件、概算の単位と労力、調査で分かった不足、必要な厳密さを示す。取り消せない判断や広い影響には強い検証を置き、低い影響の可逆作業には相応の確認を選ぶ。長い実行の前に条件とトレードオフを示し、複数時間の作業には確認の節目を置く。

単独で届けられる単位へ分け、危険な未知を先に扱う。基準と検証の仕組みを変更前に作る。未確定で取り消しにくい設計には `architect` と必要な `arena`、決まった機械的作業には追加の案比較をしない。委譲は独立した責務だけにし、担当の書込先を分離する。

設計した具体的な段階を記録する。各単位で仮説、最小変更、実物の測定、採用または撤回を行い、次へ進む前に検証する。簡単すぎる合格は観測方法も疑う。委譲した成果は親が判定し、担当が検査を形だけ通したら依頼と検査を修正する。検査そのものが誤りなら別の変更で直し、迂回しない。

判定は `VERIFIED`・`NOT VERIFIED`・`INCONCLUSIVE`。未確定を合格にしない。`show-me-your-work` で各段階の判断をその時点で記録する。最後に最初の完了条件を実際の製品全体で確かめ、繰り返す訂正を型・lint・検査・スクリプトへ組み込む。手順、厳密さと理由、判断記録のパス、検証済みと未完を返す。

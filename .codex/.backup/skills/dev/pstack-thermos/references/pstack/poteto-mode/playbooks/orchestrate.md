### 継続開発の統括

複数日にわたり、多数のPRと担当を一つの継続した責任者が統括する場合に使う。成果は依頼書、採用可能な範囲、判断、利用者への報告である。一人が現在のセッションで終えられる仕事は [自律実行](autonomous-run.md)で直接進め、下記の管理構成を作らない。独自の開発手順が必要なら `figure-it-out`。

管理の量を作業の量へ合わせる。完了通知はキューへ入れる。開始と再開には共通指示を渡す。依頼書が曖昧なまま担当を増やさない。

#### 役割と配置

- 統括担当。この会話で範囲、依頼書、完了キュー、判断、報告を持つ。コードは作業担当へ渡す。競合解消や積み直しも作業として依頼する。検証済み変更の単純なfast-forwardや競合のないcherry-pickなど、許可済みの機械的採用は自分で行える。エージェント操作はホストの協業機能だけを使い、`<skill-root>/scripts/pstack/poteto-mode/orch/orch.ts` は状態の記録に使う。CLIは起動、待機、起床を代行しない。
- 分野の統括担当。一人の統括ではキューを扱いきれない場合だけ置く。担当する分野、単位、依頼書、検証、記録を持つ。親へ生の子報告を流さず、区切りで集約する。同時に扱う件数は一回で処理できる量とホスト上限に合わせる。十件程度は目安であり、使える並列枠を超えない。遅い一件を待つ固定バッチではなく、完了ごとに補充する。
- 作業・検証担当。入力SHAと専用worktreeの絶対パスを渡す。一つのworktreeまたはブランチには一人だけが書く。自動分離や私有VMを仮定しない。実動作の検証には利用可能な操作スキルと分離した状態を使う。レビューは独立した読み取り専用担当とし、別モデルは実際に選べる場合だけ使う。

階層は統括、分野、作業までにする。分野の形は製品ごとに選び、固定された木へ当てはめない。委譲が禁止されている環境ではこの並列構成を実行せず、許可された直接作業へ戻す。

#### 記録の配置

ホストが提示する作業保存先に `orchestrate/<project-slug>/` を作る。保存先が提示されなければリポジトリ外の明示した作業用ディレクトリを使う。各ファイルの書き手を一人に固定し、読者は読み取り時に集約する。`bun <skill-root>/scripts/pstack/poteto-mode/orch/orch.ts` を以下では `orch` と呼ぶ。TSVとJSONはCLIなしでも読める。

| ファイル | 用途 |
|---|---|
| `preferences.md` | モデル、積み方、検証水準、禁止パス、相談条件など、番号付きの共通指示。一行一条件。開始・再開へ全文を渡す。現在の担当が同じ保存先を読める場合は開始時にパス参照も可。繰り返す訂正は行へ加えてから動く。 |
| `overview.md` | PRとIssueの記録。全体を書き直さず追記する。 |
| `units.tsv` | 単位ID、分野、状態、ブランチ、PR、head SHA、依頼書パス。行を更新する。 |
| `frontier.json` | 計算した採用待ちの順序。 |
| `ledger.tsv` | PR番号とhead SHAに結び付く検証結果。 |
| `inbox/` | 完了報告への参照。 |
| `gates.md` | 本人の判断待ち。問い、選択肢、提案を記す。回答なしを承認にしない。 |
| `decisions.tsv` | `show-me-your-work` に沿う判断記録。 |
| `status.md` | 毎回 `units.tsv` と `ledger.tsv` から生成する状態表示。手書きで別版を維持しない。 |

#### 依頼書

次をすべて埋めてから開始する。短い作業なら一段落に縮めても、目的、範囲、検証、報告は残す。

```text
GOAL         会話を知らない人が実行できる一文の成果
SCOPE        編集可能・禁止パス、専用worktreeまたはブランチ
CONTEXT      ファイルとPRへの参照、依存する上流成果の報告全文
ACCEPTANCE   確認できる受入条件を一行ずつ
VERIFY       正確なコマンドまたは操作スキルのパス、既知の注意点
TIMEBOX      実行時間の目安。到達したら部分成果を返して止める
FORBIDDEN    gt、rebase、force-push、範囲外修正など、この単位の禁止事項
REPORT       状態、ブランチ、head SHA、PR、判定、実行した検証、逸脱、後続案
STANDING     preferences.mdの共通指示全文
```

分野の統括へは境界、単位一覧、並列上限、利用可能な実行環境、キュー処理、集約形式も渡す。依存関係には実行順だけでなく前提の報告を伝える。必須情報が欠けたら開始しない。各段階で分野ごとに一つの依頼書を進行中に監査し、不合格なら次の補充を止めて統括側の指示を直す。中断・再開を連鎖させず、まとまった範囲で新しい担当を置く。

#### 手順

1. 完了条件を数えられる形にし、単位数、作業量、PRの積み方、時間の予算を示す。一人で終えられる量なら管理構成を省いて現在の会話で直接実行する。採用を最後にまとめず、予算の約70%で新規開始を抑えて検証済み成果を採用する。分割に異論や戻せない判断があれば、許可された `arena` で比較する。可逆な準備は進める。
2. `orch init` で記録を作る。判断記録と共通指示を用意し、`orch frontier set --repo <repo-dir>` で既存PRから採用順を作る。
3. 一単位を依頼、実装、検証、PR、台帳、採用まで通して、依頼書と検証方法を試す。似た安価な単位なら最初の通常作業を試行とし、採用後すぐ補充する。高価・未知の作業だけ独立した試行検証を置く。
4. 同時実行上限の範囲で完了ごとに補充する。上流報告を次の依頼へ渡す。兄弟間の調整は親へ集める。依頼書監査は現在の作業と並行し、不合格なら次の補充を止める。
5. 下記のキュー処理を行う。
6. 最初の検証済み成果から採用を始め、残りと並行して続ける。重いリポジトリは最初から積み直し担当を置き、軽い場合は統括が許可済みの機械操作を行う。採用待ちの下段を健全に保つ。`frontier.json` はマージまたは新SHAの報告時に更新する。
7. 最後のキューを処理し、全担当を完了・中止・遅延復帰の照合済みにする。実成果物で完了条件を確かめ、採用PRの現在SHAに判定があるか確認する。判断記録を監査し、繰り返す訂正を共通指示か依頼書へ移す。記録は保持する。

#### キュー処理

- 完了したら `orch inbox push <agent> <unit> <status> [--report PATH]` で参照を入れて元の仕事へ戻る。その場で深いレビューをしない。必要なら検証単位を作る。
- 依頼書、積み替え、競合判断、判断待ちの記録、台帳更新など、不可分な仕事を終えてからキューを処理する。処理点は重要操作の終わり、分野の集約、監視からの起床、利用者への報告前。
- `orch inbox drain` でその時点の集合を取り、後から届いたものは次へ回す。採用済み、検証待ち、失敗、遅延復帰、対象外に分類し、`orch unit add`、`orch unit set`、`orch ledger record` で記録する。`orch status` を実行して次の作業を開始する。
- 全担当を、到着、置換、範囲吸収のいずれかへ対応付ける。黙ってやり直して欠落を隠さない。
- 通常の処理点では `orch status` の件数、変化、判断待ちを簡潔に報告する。詳細は `status.md`。変化がなければ同じ報告を繰り返さない。

#### PRの積み方

- 採用順は計算結果で持つ。`gt` を実際に使う構成では、そのメタデータを持つ積み直し担当のcheckoutで、マージ・積み替え後に再計算する。PR順序、ブランチ、head SHA、世代、最下段の未採用PRを記録する。メタデータがない場合は推測しない。`gt` がない構成は利用可能なGitとforgeから明示的に計算する。
- 一つのスタックで積み替える人は一人。共通指示へ記す。重い積み直しは利用可能な適切な環境へ分け、クラウド環境をあるものと仮定しない。
- 作業担当はrebaseや `gt` を実行しない。監視担当は一スタックの固定した世代だけを見て、競合を積み直し担当へ報告する。
- PRのcloseやbase変更も積み直し担当へ集める。基点を閉じると上段が孤立する。マージや積み替えも範囲と検証を持つ単位として扱う。
- 採用後のrevert、CI破損、孤立した後続PRを監視する担当を必要に応じて置く。未来の監視は予約の許可と利用可能な自動化機能が必要。

#### 検証

安価な一コマンドなら担当が実行して出力を返し、統括が記録を確認する。高価、判断を要する、影響範囲が大きい単位には独立した読み取り検証を使う。

`orch ledger record` で記録し、`orch ledger check` で現在のPRとhead SHAを照合する。判定は `live-ui-verified`、`unit-test-verified`、`type-check-only`、`verifier-blocked`、`verifier-failed`。CI成功は入力であり判定そのものではない。動作変更は型検査だけでは足りない。検証不能は合格にしない。環境回復後に再検証し、失敗には修正単位を作る。同じキーでは独立検証が自己申告より優先する。SHAが変われば判定を無効として再検証する。

成果は採用時に永続化し、最後へまとめない。許可されたブランチのpush、台帳、検証記録を保存する。一つの失われ得る環境にしかない成果を完了にしない。

#### 生存確認と失敗

- 確認だけのために再開させない。ホストの読み取り状態・待機機能と記録した担当IDを使い、台帳、CI、push済みSHA、成果の記録を照合する。使える状態確認がなければ不明とし、沈黙やログの更新日時だけで死亡扱いしない。
- 終了が確認できない担当は最後の証拠、失敗様式、選択肢を記録し、証拠が届くたび再計画する。完全停止を漫然と待たない。
- 上限・メモリ不足は範囲を縮め、通信断は同じ条件、ツール障害は実際に選べる別モデルで再試行する。原因不明は一度。二回の再試行後も駄目なら単位を中止し再計画する。
- 遅れて帰った担当は現在の採用順と台帳へ照合する。独自の知見は新単位で救い、無条件にマージしない。
- 上流の欠陥、受入条件の破損、基盤停止などが全体へ広がる場合は共通指示の先頭に新規開始停止を書き、進行中の作業を安全に終えて原因を直してから解除する。
- 自分の基盤再試行も制限する。連続する中断が続くなら、完了内容、保存先、再開コマンドを永続的な引継ぎへ書く。
- CLIやアプリの再起動後は共通指示と `units.tsv` を読み、採用順を再計算する。現在のホストで古いIDの状態を確認し、生存・死亡を仮定しない。SHA、PR、成果で照合し、置換前に排他的な書き込み所有を確立する。`orch` のロックは所有PIDの終了が確認できた場合だけ置換する。

#### 本人への相談

共有ブランチのforce-push、公開、削除、他人のPRのcloseなど許可のない不可逆操作、実験では決められない製品判断、観測と矛盾する共通指示、再計画後も残る全体の行き止まりを `gates.md` へ記録してまとめて相談する。それ以外の可逆な機械操作、CI不安定の調査、レビュー対応、書式修正は許可範囲で進める。回答待ちを承認として扱わない。

途中の発見は採用を妨げるものだけ直し、他は後続へ残す。範囲外の小さな修正も並列数で増幅する。

区切りと終了の返答には、台帳から数えた完了条件と件数、各分野の採用成果、PRとSHAの順序、検証判定、中止理由、本人判断待ち、保存先と判断ログを示す。PRにはリンクを付ける。

コード変更のレビューは [レビューの進行](../../../review.md)へ進む。計画・設計の反証と、実動作・性能の検証は、それぞれの対象に応じて行う。

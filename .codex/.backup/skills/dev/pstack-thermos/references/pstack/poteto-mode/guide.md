# 開発の作業選択

実際の利用経路を調べ、求められた成果を証明する最小の変更を行う。リポジトリの指示と利用者の権限を優先する。この手順だけでPR作成、マージ、デプロイ、強制push、削除、外部送信、仲介や取引を許可しない。

[Codexでの実行規則](../../execution.md)を読んでから、作業手順や個別手順を使う。専用担当が未設定なら、[初回設定](../../setup.md)で診断・配置・実行確認を区別して進める。

## 開始時に決めること

1. 求める成果と、許可されている操作を明示する。
2. 実際の入口、正しい入力の取得元、最終成果物、検証方法、受入条件を特定する。
3. 下の振り分けから合う手順を選ぶ。すべてを一律に重ねない。
4. リポジトリで指定された台帳がある場合は、複数段階の作業をそこへ記録する。

## 内部手順への振り分け

| 依頼 | 読む手順 |
| --- | --- |
| コードの説明・読み取りだけの調査 | `how` とリポジトリのコード調査手順 |
| 責務や境界をまたぐ新しい設計 | `architect` |
| 小さな回帰テストで再現できるバグ | `tdd` |
| 変更の影響・必要なテストの選択 | `blast-radius` |
| コード変更のレビュー | [thermos](../../thermos/guide.md) |
| 計画・設計・検証資料の反証レビュー | `interrogate` |
| 性能の測定値・改善の主張 | `benchmark-checklist` と `principle-explain-the-number` |
| エージェントが繰り返す誤り | `correct` と `principle-attack-the-premise` |
| メンテナー・チームの作業規範の抽出 | `automate-maintainer`・`automate-team` |
| 手順の選び方 | `poteto-help` |
| 最後の文章の推敲 | 事実と必要な留保を保持したうえで `unslop` |

内部手順は `../<name>/guide.md` にある。

## 作業手順の全一覧

該当する手順を `playbooks/` から読む。詳細な資料はこのディレクトリ、実行補助は `<skill-root>/scripts/pstack/poteto-mode/` にある。

- 調査: `investigation.md`、バグ修正: `bug-fix.md`、性能改善: `perf-issue.md`、継続的な計測改善: `hillclimb.md`。
- 実行中の現象の診断: `runtime-forensics.md`、取得済みトレースの診断: `trace-forensics.md`。
- 機能追加: `feature.md`、リファクタリング: `refactoring.md`、試作: `prototype.md`、画面の一致: `visual-parity.md`、スキル制作: `authoring-a-skill.md`。
- 手順・プロンプトの評価: `eval.md`、PRの修正と確認: `babysit.md`、独立検証と採用: `shipping.md`。
- 長い単一作業: `autonomous-run.md`、複数日・複数PRの進行: `orchestrate.md`、独立PRの全自律進行: `autopilot-full.md`、直列PRの作成と検証: `autopilot-stack.md`。
- 作業の再開: `session-pickup.md`、安全な一時停止: `pause-safely.md`、段階計画: `multi-phase-plan.md`、PR作成: `opening-a-pr.md`、Worktree整理: `worktree-cleanup.md`。

手順が収録されていることは、その操作を許可されたことを意味しない。

## 共通原則

条件分岐の前に対象の概念とデータ構造を決める。仕組みを足す前に不要な経路を減らす。外部との境界と権限の境界で検証する。共有状態を分けてから調整を追加する。

症状を再現し、原因を所有する箇所で直す。実行可能な証拠を持つ小さな単位へ順序づける。代用品の検査ではなく、実際の経路を確かめて完了を報告する。

テストには `principle-test-behavior-not-implementation`、同じ前提の修正が繰り返し失敗した場合には `principle-attack-the-premise` を使う。実装・検証・配備・実運用の有効化・結果・権限を区別する。

## 委譲と回収

利用者または適用される指示で認められ、担当範囲が独立している場合だけ委譲する。書き手に専有するファイルを割り当てる。反証レビューは読み取り専用にする。親は成果物と証拠を確認し、担当の完了報告をそのまま検証結果にしない。

## 実装後のレビュー

コード変更を実施したら [レビューの進行](../../review.md)へ進み、thermosで同じ対象を二方向から確認する。設計への反論はinterrogateで扱う。実動作・性能の検証は各作業手順の条件に従い、コードレビューだけで代替しない。

## 終了報告

重要な主張は根拠か未確定の説明を同じ文に添える。推測した原因や将来の予測は推測と記す。成果を先に伝え、変更したファイル・成果物、TDDで実施したREDとGREEN、実施した検証と未実施の検証、残る指摘と次に確かめる事項、追加で与えられていない操作権限を必要な範囲で報告する。

# コメントの必要性をレビューして直す

[Codexでの実行規則](../../execution.md)を読んでから使う。

対象は依頼のファイル・差分、未指定なら基準ブランチ（既定main）との差分と未コミット変更とする。実際の `comment-sicko` に範囲を渡し、CursorのTask指定を使わない。

親は報告と差分を読み、製品コードの編集、範囲逸脱、保護すべき例外の削除、根拠の違う `MUST KILL`、意図的に維持するコードへの誤指摘を却下する。自分たちのコードで意外な構造が見つかった指摘は再設計候補にする。lintやTypeScript抑制の見落としも確認し、正しさ・安全性を隠す抑制は対処する。

薄いIMPORTANTや削除禁止の注記について採用・削除を決める前に、`how`・`why` で対象記号を調べる。維持の根拠は変更できない外部制約の具体的な証拠を要する。却下した報告は理由を示して一回再実行し、再度不適切なら未解決を報告してこの手順を不合格にする。

単純な指摘は不要経路・引数の削除や本来のAPI利用で直す。構造が要る指摘群は `architect` で一度設計し、その後に範囲内の最小の原因修正を行う。指摘された回避策を除き、原因が範囲外なら限定修正と残件を分ける。原則を根拠に変更範囲を広げない。

外部の変更できない制約のコメントは保持する。制約を型・実行時検査・テスト・CIへ表す案は対話で承認を得る。無人実行や評価は事前の許可を要する。承認されたら実装してコメントを除く。実装しない場合は制約の未強制と範囲外の作業案を報告する。

削除数、復元、再実行、設計案、修正、制約の実装提案・実装結果、未強制の制約と残件を示す。

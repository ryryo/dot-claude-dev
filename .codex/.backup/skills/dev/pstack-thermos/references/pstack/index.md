# 内部手順の索引

依頼に該当する行だけを選び、リンク先の手順を読む。開発の入口は [poteto-mode](poteto-mode/guide.md)、コード変更のレビューは [thermos](../thermos/guide.md)。個別のスキル呼び出しは必要ない。

| 手順 | 用途 |
| --- | --- |
| [adversarial-review](adversarial-review/guide.md) | 計画・設計・検証資料の正しさ、構造、必要性を読み取り専用で調べる。 |
| [architect](architect/guide.md) | 型、所有、関数の形、モジュールの境界を実装前に設計する。データモデルや境界をまたぐ非単純な変更に使う。 |
| [arena](arena/guide.md) | 同じ課題を複数担当が独立して試作し、基礎にする案を選んで他案の有用部分を統合する。arenaや案の比較依頼に使う。 |
| [automate-maintainer](automate-maintainer/guide.md) | 指定したGitHub利用者のコード・コミット・PR・レビュー・Issue・議論から、作業規範のモードを作成・更新する。 |
| [automate-me](automate-me/guide.md) | 繰り返し確認できる作業の好みから、個人用Codexモードを作成・更新する依頼に使う。 |
| [automate-team](automate-team/guide.md) | GitHubリポジトリの現在の中核担当を調べ、その実装・レビュー・判断からチームの作業モードを作成・更新する。 |
| [benchmark-checklist](benchmark-checklist/guide.md) | 性能値を報告・採用する前に、制限要因、設定、物理限界、失敗、反復、全体との関係、実際の処理を検査する。 |
| [blast-radius](blast-radius/guide.md) | 変更が他の経路へ与える影響と必要なテストを、呼び出し元・形式・寿命・外部境界から調べる。 |
| [bro](bro/guide.md) | 直前の返答を専門用語の少ない言葉で説明してほしい場合に使う。 |
| [correct](correct/guide.md) | 同じ誤りを繰り返す原因を調べ、設計、型、lint、テストの順で防ぐ。correctの依頼に使う。 |
| [create-verification-skill](create-verification-skill/guide.md) | UI、CLI、サービスなどを利用者と同じ経路で操作する、プロジェクト固有の検証スキルを作る。 |
| [figure-it-out](figure-it-out/guide.md) | 既存手順が合わない大きい移植や複数段階の作業で使う。段階、検証条件、仮説と測定、判断記録を先に設計する。 |
| [how](how/guide.md) | コードやサブシステムの入口、状態変化、出力を追う。動作の説明、処理経路の調査、変更前の理解に使う。 |
| [interrogate](interrogate/guide.md) | 計画・設計・検証資料を固定し、独立した観点で反証する。 |
| [maintain-verification-skill](maintain-verification-skill/guide.md) | 機能ごとのコード照合と実動作検証で、検証スキル・機能一覧・操作補助のずれを直す。 |
| [make-bot-ui](make-bot-ui/guide.md) | 利用者が押す画面と、サーバーからボットを起動するWebhookを接続する。送り手の秘密鍵やTailscaleを扱う依頼に使う。 |
| [no-comments](no-comments/guide.md) | comment-sickoで対象コメントをレビューし、採用した指摘を修正する。コメントの整理・制約の実装への置換に使う。 |
| [poteto-help](poteto-help/guide.md) | pstackの初回設定、手順選択、進め方のずれについて質問された場合に使う。 |
| [poteto-mode](poteto-mode/guide.md) | 調査・設計・実装・検証が必要な開発作業を、根拠に基づくCodexの手順へ振り分ける。poteto-mode、pstack、厳密な開発手順の依頼に使う。雑談や一段階の整形には適用しない。 |
| [principle-attack-the-premise](principle-attack-the-premise/guide.md) | 同じ前提による2回以上の修正が同じ検証で失敗した場合に使う。次の修正前に主体別の偏りを計測し、前提と役割の割当を調べる。 |
| [principle-boundary-discipline](principle-boundary-discipline/guide.md) | CLI、設定、外部API、通信、フレームワークの接続で使う。入力を境界で型へ変換し、内部の業務処理を純粋関数にする。 |
| [principle-build-the-lever](principle-build-the-lever/guide.md) | 単純でない編集・移植・分析・検証で使う。作業または検証を行う最小のスクリプトや生成器を作り、レビューする人が再実行できるようにする。 |
| [principle-encode-lessons-in-structure](principle-encode-lessons-in-structure/guide.md) | 同じ指示を再度書く場合や繰り返す訂正に使う。型、lint、設定値、実行時検査、スクリプトで防げるか調べる。 |
| [principle-exhaust-the-design-space](principle-exhaust-the-design-space/guide.md) | 前例のない操作や、複数の方法が成立する設計判断で使う。2〜3の構造が異なる試作や設計案を比較する。 |
| [principle-experience-first](principle-experience-first/guide.md) | 製品、使いやすさ、機能範囲の判断で使う。作る側の都合より、成果を使う人と保守する人の体験を優先する。 |
| [principle-explain-the-number](principle-explain-the-number/guide.md) | 速度、回帰、処理量、遅延、評価結果を信頼・報告・採用する前に使う。制限要因と、別のものを測っていない証拠を確認する。 |
| [principle-fix-root-causes](principle-fix-root-causes/guide.md) | 不具合調査で使う。まず再現し、原因まで追い、症状を隠すだけの防御処理を避ける。 |
| [principle-foundational-thinking](principle-foundational-thinking/guide.md) | ロジックを書く前の型・データ構造・基盤と機能の順序・共有状態の判断で使う。 |
| [principle-guard-the-context-window](principle-guard-the-context-window/guide.md) | 大きい出力、長いファイル、繰り返す読取、並列作業の計画で文脈が圧迫される場合に使う。 |
| [principle-laziness-protocol](principle-laziness-protocol/guide.md) | リファクタリング、差分の大きさ、抽象化・階層・信号の受渡しを増やす判断で使う。 |
| [principle-make-operations-idempotent](principle-make-operations-idempotent/guide.md) | 途中で失敗・再起動・再試行するコマンドやライフサイクルの設計で使う。 |
| [principle-migrate-callers-then-delete-legacy-apis](principle-migrate-callers-then-delete-legacy-apis/guide.md) | 内部APIの変更で使う。呼び出し元を同じ変更で移し、旧経路を削除する。 |
| [principle-minimize-reader-load](principle-minimize-reader-load/guide.md) | 追いにくいコードや説明を設計・レビューする場合に使う。問いと答えの間の層、隠れた状態、変更可能な範囲を減らす。 |
| [principle-model-the-domain](principle-model-the-domain/guide.md) | 状態を持つ処理、多い分岐、複数ファイルで繰り返すデータ形状の仮定に使う。 |
| [principle-never-block-on-the-human](principle-never-block-on-the-human/guide.md) | 許可範囲の可逆作業について再度確認しそうな場合に使う。合理的な判断で進め、結果を見て訂正できるようにする。 |
| [principle-outcome-oriented-execution](principle-outcome-oriented-execution/guide.md) | 段階と検証境界を決めた再設計・移植で使う。一時的な互換処理より目的の構成への収束を優先する。 |
| [principle-prove-it-works](principle-prove-it-works/guide.md) | 完了を報告する前に使う。機能の実行、実際の値、差分を直接確認し、代用品や自己申告で置き換えない。 |
| [principle-redesign-from-first-principles](principle-redesign-from-first-principles/guide.md) | 既存設計へ新要件を統合する場合に使う。最初からその要件があったとして全体を設計し、段階的に反映する。 |
| [principle-separate-before-serializing-shared-state](principle-separate-before-serializing-shared-state/guide.md) | 複数の担当が同じファイル、ブランチ、キー、状態を書き換える可能性がある場合に使う。 |
| [principle-sequence-verifiable-units](principle-sequence-verifiable-units/guide.md) | 一括修正、移植、同種の編集、コミットやPRの順序づけに使う。各単位を確認してから次へ進む。 |
| [principle-subtract-before-you-add](principle-subtract-before-you-add/guide.md) | 機能追加、再設計、リファクタリングの順序を決める場合に使う。不要な経路や重複検証を先に除く。 |
| [principle-test-behavior-not-implementation](principle-test-behavior-not-implementation/guide.md) | テストを追加・変更・維持する場合に使う。具体的な入力と観測できる結果を検査し、実装や定数の言い直しを避ける。 |
| [principle-type-system-discipline](principle-type-system-discipline/guide.md) | 型や関数の引数を設計・レビューする場合に使う。不正状態を構築できない形、意味の異なる値の区別、境界での解析、網羅的な分岐を使う。 |
| [recall](recall/guide.md) | 最近の会話、永続的なプロジェクト情報、現在のリポジトリから作業の現在地を復元する。 |
| [reflect](reflect/guide.md) | 現在の会話で得た訂正や成功の手順から、既存スキルや構造的な対策へ反映すべき教訓を調べる。 |
| [setup-pstack](setup-pstack/guide.md) | 初回配置、7担当の設定、モデル継承、思考量、並列数を診断・調整する。 |
| [show-me-your-work](show-me-your-work/guide.md) | 長い作業、自律実行、後で人が確認する作業の判断を、追記専用のTSVで記録する。 |
| [swarm](swarm/guide.md) | 複数の担当で範囲を分ける、同じ課題を競わせる、網羅的な確認を行う場合に使う。親が全担当を回収して一つの報告にする。 |
| [tdd](tdd/guide.md) | 明確で小さいローカル検査があるバグや動作変更で、修正前の失敗と修正後の合格を示す。TDDや回帰テストの依頼、repoの要求に使う。 |
| [teach](teach/guide.md) | コードや変更が何か、どう動くか、なぜその形かを、相手の理解に合わせて説明する。変更そのものは行わない。 |
| [technical-writing](technical-writing/guide.md) | 資料、RFC、README、PR説明、コミット文を、文書の用途・読者・一文の負担・曖昧さの観点で執筆・レビューする。 |
| [typescript-best-practices](typescript-best-practices/guide.md) | TypeScriptの読取・編集で、判別共用体、ブランド型、スキーマ由来の型、網羅性、実際の動作の検査を適用する。 |
| [unslop](unslop/guide.md) | 事実、留保、出典、権限を保持して、資料・レビュー・コミット文・最終回答を簡潔で具体的な文章に整える。 |
| [why](why/guide.md) | 設計理由、選定、回帰、事故、数値の根拠を、Git・Issue・文書・会話・監視・エラー・分析の証拠から調べる。現在の動作はhowを使う。 |

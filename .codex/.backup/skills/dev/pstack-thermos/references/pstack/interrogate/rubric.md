# レビューの評価基準

## 目的と動作

変更が述べた目的を達成するか、境界値・失敗・非同期・並行実行・再実行を含めて確認する。差分の周囲、呼び出し元、型、隣のモジュールを読み、実際の到達経路を追う。

## 根本原因

ガードで不変条件違反を隠していないか、再試行で壊れた契約を隠していないか、型キャストでモデルの誤りを抑えていないか。回避処理が必要な理由と、本来直すべき契約の場所を問う。コメントの注意事項より型・lint・実行時検査で誤操作を防げないか検討する。

## 構造

外部境界で一度検証して内部で信頼するか、高水準の統括と細部が混在していないか、将来変更を妨げる依存を増やしていないか。データ構造が実際のアクセスへ合うか、新要件を最初から知っていたような自然な設計かを確認する。外部利用者がないAPI移行では全呼び出し元を移し、旧経路を消す。単純なコードを抽象化不足だけで減点しない。

## 検証

テストが動作を確かめるか、回帰を捕まえる不変条件があるか、修正した不具合と統合経路を確認できるか。ファイル時刻やキャッシュを生存の代用にせず、実際の状態を見る。委譲・非同期では自己申告より成果物を確認する。

## 複雑さ

正しさや明快さを失わず簡単にできる箇所、一呼び出しの抽象、未使用の設定、dead code、旧移行足場、現在の利用者がいない予防経路を探す。各機能・操作・設定が利用体験に必要かを問う。未完成の機能を維持する費用も検討する。

## セキュリティ

入力からSQL、shell、eval、innerHTMLなど危険な処理まで経路を示す。認証・認可の欠落、秘密情報のコード・ログ・エラーへの混入、重要な処理のTOCTOUを確認する。到達できない仮想入力を欠陥にしない。

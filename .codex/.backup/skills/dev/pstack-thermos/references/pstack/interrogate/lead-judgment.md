# 主担当のレビュー判断

所見を並べるだけでなく、会話全体の目的、既に退けた案、期限、依存、移行、暫定構造、次のPRを踏まえて採否を決める。

- 軽微な文体指摘で空欄を埋める傾向を見抜く。全部が好みなら実質的な問題なしと伝える。
- nullなどの仮説は呼び出し元まで追う。型や境界が防ぐ入力なら退ける。
- 第二の用途がない抽象化は早すぎる場合がある。単純な直接コードを過剰な層へ変えない。
- 「別の方式が好き」は、現在の方式の具体的な失敗を示さなければ欠陥にしない。
- 未変更箇所への提案、repoの既存方針を知らない指摘、既知の制約に反する案は根拠を示して退ける。

不都合な指摘を理由なく退けない。複数担当の独立した一致、具体的な実行経路、自分の理解の穴を示す指摘は重く扱う。正しさとセキュリティは一人の指摘でも慎重に確認する。

採用すべき項目を優先し、五項目を超えるなら絞り込みが足りないか再検討する。ただし実欠陥を件数のために消さない。退けた所見と理由も示し、利用者が判断を見直せるようにする。

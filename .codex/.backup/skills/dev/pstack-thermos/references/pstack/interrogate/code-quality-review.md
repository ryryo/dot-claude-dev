# コード品質のレビュー

評価基準に加えて、動作を保ちながら実装を大きく単純にできる構造を探す。

0. 分岐、補助関数、モード、層を丸ごと消す再構成を検討する。複雑さを移すだけで終えない。
1. ファイルが1000行未満から1000行超になる変更には強い構造上の理由を求める。明確なまとまりへ分けられないか確認する。整理が明白な例外だけ認める。
2. 関係ない経路へ特例の条件分岐を散らさない。専用の処理、状態機械、モジュールへ責務をまとめられるか問う。
3. 動けばよいと受け入れず、同じ動作で動く部品を減らす案を探す。
4. 直接的で保守しやすいコードを選ぶ。単純なデータ形状を隠す汎用機構、薄い抽象、同形のラッパーを疑う。
5. 不要なoptional、`unknown`、`any`、castを、明確な型と境界へ置き換えられるか確認する。不明な不変条件を黙ったfallbackで埋めない。
6. 正本となる層へロジックを置き、既存の共通処理を使う。機能の条件が共有経路へ漏れていないか確認する。
7. 独立作業の不要な直列化、途中状態を残す非原子的な更新を見直す。小さい速度最適化だけに偏らず、壊れやすい統括構造を探す。

構造の退行・大きい単純化の見逃し、分岐の増殖、境界・型・ファイル規模、細かい読みやすさの順で優先する。正しく見えるだけで承認しない。具体的な欠陥や負担を示して改善を求める。強い品質要求を丁寧に伝え、実害を命名の軽微な提案へ薄めない。

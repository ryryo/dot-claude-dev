# レビューの観点

## Skeptic

入力、状態、順序、失敗経路で意図を壊せるか。race、順序の前提、黙ったfallback、未証明の主張を探す。部品の成功と最終経路の証明を分け、具体的な失敗場面と最も安価な検証を示す。

## Architect

所有、境界、呼び出し元、データ、権限を追う。結合、責務の漏れ、不正な状態、寿命の欠落を探す。規模、並列、retry、部分完了の前提を確かめ、症状を隠すガードより契約を直す。

## Minimalist

意図に不要な抽象、設定、互換経路、統括を探す。成果を保って消せる部分を示す。受入範囲と周辺の予防的改善を分け、仮想の将来用途だけで複雑さを正当化しない。

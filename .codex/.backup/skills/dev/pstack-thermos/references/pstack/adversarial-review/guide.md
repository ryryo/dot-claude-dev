# 批判的レビュー

述べた目的を達成できるか、実成果物を編集せず検討する。計画・設計・検証資料の反証に使う。コード変更のレビューは [thermos](../../thermos/guide.md)へ進む。

1. SHAまたは作業ツリーの範囲、目的、repoの規則、受入境界、証拠と欠落を固定する。対象が実質的に変われば新しい対象でやり直す。
2. [原則](principles.md)と[観点](reviewer-lenses.md)を読む。狭い変更はSkeptic、境界を変えるならArchitectも、大きい変更や権限に関わるならMinimalistも使う。
3. 委譲が許可されていれば `pstack_skeptic`、`pstack_architect`、`pstack_minimalist` を使う。なければ、使える読み取り専用担当へ観点全文を渡す。委譲禁止なら主担当が各観点を分けてレビューし、独立レビューを行ったと報告しない。各担当へ同じ固定対象、意図、[報告条件](reviewer-prompt.md)を渡す。欠けた担当を黙って代用せず制約を記録する。
4. 重複を除き、実際の経路を確認する。古い版、文体の好み、具体的な失敗を示せない所見を退ける。
5. [判定形式](verdict-format.md)で返す。`high` は正しさ・損失・権限・契約の重大な破損、`medium` は採用前に直す実欠陥や検証不足、`low` は限定的な保守上の問題。

`REVIEW_CLEAN` は確認済みのhigh・mediumなし、`FINDINGS` は該当所見あり、`INCONCLUSIVE` は必要な範囲・証拠・担当の不足。この助言はrepoが求める独立検収を代替せず、マージ・公開・外部操作の許可を増やさない。

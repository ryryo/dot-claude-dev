# 設計の理由を証拠から調べる

[Codexでの実行規則](../../execution.md)を読んでから使う。

現在のコードが何をするかではなく、その形に至った事情を調べる。慎重に事実と推論を区別し、[確信度の扱い](epistemics.md)を読む。担当は実際の `poteto-agent` と親のモデル・思考量を既定にし、明示的に対応を確認できる指定だけ上書きする。

## 対象とコードの基準

問いが設計理由、代案の比較、境界例、外部制約、不要なコード、歴史のどれかを把握する。対象が曖昧なら直前の会話やファイルから解釈を短く示し、訂正できるようにして進める。

委譲前にファイルと行、関数・class・定数、最近の変更コミット、マージ文にあるPR番号を親が集める。

```sh
git blame -L <start>,<end> <file>
git log --follow -p -- <file>
git log --oneline -20 -- <file>
git log -1 --format=%B <commit>
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

実質的な変更の本文と議論を読み、ファイル、記号、コミット、PR、関連作業を調査の基準にする。

## 出典の網羅性と調査

現在のツールの説明から利用可能な接続を調べ、Git履歴、Issue、長い設計文書、チーム会話、基盤監視、エラー追跡、製品分析の7種類へ対応させる。曖昧な接続も記録する。Gitがある範囲の履歴を確認し、GitHubへのアクセスがなければその不足を示す。

各種類が明らかに無関係か、接続自体がない場合だけ省略し、理由を最終報告に残す。接続がないのは選択ではなく証拠の不足である。「おそらく無関係」で省略しない。単一コミットの本文に完全な理由があり、7種類の追加調査がすべて冗長と確認できた場合に限り、その理由を示して親が短く答えられる。

許可された並列調査では一担当に一種類の接続を割り当て、全体の網羅性を管理する。担当へ [調査指示](investigator-prompt.md)、[出典一覧](source-playbook.md)から該当する `sources/<source>.md`、コードの基準、利用者の問いを渡す。防御処理（nil検査、再試行、timeout、rate limit、flag、egress、OOM等）は [事故調査](sources/incident-postmortem.md)も渡す。

Gitは実装時のレビュー理由、Issueは製品・業務上の要請、文書は先行設計、会話は文書化されない議論、監視は基盤・実行の現実、エラー追跡は特定の例外、分析は実験・移行・閾値の根拠を主に探す。範囲は明確にし、調査担当は書き込まない。必要な接続の読み取りを失う工具設定を避け、実効権限を報告する。

## 統合と報告

調査結果、空の結果、省略理由、コードの基準、問い、確信度の指針を [統合担当への指示](synthesizer-prompt.md)へ渡す。統合担当は引用を実物で点検する。

問い、対象コード、見つかった事実、合理的な推論、競合する仮説、不明なこと、調べた出典、確信度を分ける。各出典は空や省略も含め一行にし、理由を添える。親は読みやすさを整えても確信度の表現を勝手に変えない。

変更の準備のための調査なら、保持すること、変更できること、避けること、危険の条件を計画向けに整理する。最新コミットだけを正しい理由とみなさず、過去へ追う。

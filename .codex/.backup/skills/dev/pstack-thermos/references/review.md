# レビューの進行

コード変更は [thermos](thermos/guide.md)、計画・設計・検証資料は [interrogate](pstack/interrogate/guide.md)でレビューする。変更内容に応じて必要な確認を選び、同じコード差分へ両方の一式を重ねない。リポジトリが要求する独立検収・専門監査は別に満たす。

## 開始する時点

レビューだけの依頼なら、指定されたPR、ブランチ、commit、ファイル、作業ツリーを対象にする。開発依頼なら、実装と実施できる検証を終えた時点でコード変更をthermosへ渡す。並列担当の変更が揃う前に全体の合格を宣言しない。

対象を固定し、変更の目的、比較元と変更後、差分、変更ファイル、関連する検証結果、未確認事項をまとめる。実装者の説明と、確認した事実を区別する。

## 指摘を回収する

親が指摘の対象行と到達可能な経路を確認する。重複は一件にまとめ、異なる失敗条件は残す。同じ指摘を複数担当が挙げたことは、検証の手がかりとして扱う。人数だけで重大度を上げない。

採用した指摘には、修正担当、対象、完了条件を決める。レビューだけの依頼では編集しない。開発・修正まで許可されていれば、担当の所有範囲を保って直し、影響する検証を実施する。意図的な仕様変更を、以前の動作と違うという理由だけで不具合にしない。

## 修正後の確認

修正によって対象が変わったら、その差分と関連経路を再レビューする。以前の所見ごとに修正・不採用・未解決を根拠付きで記録し、新しい問題も確認する。変更が観点全体へ影響する場合やリポジトリが要求する場合は、二方向とも再実施する。

古い所見や検証結果を使う場合は、対象と条件が現在も同じかを確かめる。PR採用の直前確認はpstackの [shipping](pstack/poteto-mode/playbooks/shipping.md)へ進む。レビューの結果だけでCI・実動作・性能・採用条件を満たしたことにはしない。

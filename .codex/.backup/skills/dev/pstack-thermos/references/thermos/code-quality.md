# 構造・保守性のレビュー

変更の動作を保ちながら、実装を大きく単純化できるかを厳しく検討する。読み取り専用で作業し、編集と新たな担当の起動はしない。見つけた再構成案は具体的な提案として返す。

## 複雑さを減らす構造を探す

名前や整形の指摘で終えず、概念・分岐・補助関数・モード・層そのものを減らせる構成を探す。既存の設計を使い直すことで、まとまった複雑さを取り除く再構成を検討する。元の手順が「code judo」と呼ぶ観点はこれに当たる。

複雑さを別ファイルへ移しただけか、読み手が理解する概念も減ったかを区別する。挙動を保てる、より単純な方法が明らかなら、動くという理由だけで現在の実装を承認しない。

## 構造を調べる基準

| 観点 | 確認すること |
| --- | --- |
| 大きいファイル | 今回の変更で1000行未満から1000行超へ増える場合は、先に分解すべきか検討する。明確な構造上の理由と整理された結果がある場合に限り例外を認める。行数だけで自動不合格にしない。 |
| 条件分岐 | 関係の薄い経路へ特例を追加していないか。専用のモデル、状態機械、方針、モジュールで分岐の散在を減らせるか。 |
| 抽象化 | 通り抜けるだけの関数、値をそのまま返す包み、薄い層が理解を助けているか。単純なデータ形状を汎用機構の中へ隠していないか。 |
| 型と境界 | 不要な任意値、`unknown`・`any`、cast、場当たり的なオブジェクトが不変条件を曖昧にしていないか。明示した型・共有契約へ整理できるか。 |
| 責務と既存の共通処理 | 機能固有のロジックが共有経路へ漏れていないか。適切なパッケージ・サービス・層へ置き、既存の共通処理を使えているか。 |
| 並列処理と更新 | 明らかに独立した処理を不要に直列化していないか。関連する更新が途中状態を残さないか。並列化や一括更新で理解も保守も単純になるか。 |

細かい性能改善だけを理由に構造を複雑にしない。型や境界への指摘も、実際に理解・変更・検証へ及ぼす影響を示す。

## 優先して追う変化

機能を追加するたびに増えるboolean・nullableなモード・条件、忙しい関数へ差し込まれた例外、繰り返す判定、将来も残りそうな暫定分岐を調べる。以前はまとまっていたモジュールが、状態を増やしたり他のモジュールと密接になったりしていないかも確認する。

castや任意引数を増やしたために実際の契約が見えにくくなっていないか、黙った代替処理で不明確な前提を隠していないかを追う。似た補助関数の新設、コピーしたロジック、APIから漏れる実装詳細は、既存の所有箇所との関係まで確認する。

テストが通っていても、構造の後退や明らかな単純化の機会は指摘する。今回の変更が原因の問題、変更範囲で意味のある改善案、無関係な既存課題を区別する。

## 修正案の選び方

振る舞いを保つ条件を示したうえで、問題に合う最小の再構成を提案する。

- 状態の表現や所有箇所を変え、条件や中間の層を削除する。
- 特例を減らし、少ない例外で成立する通常経路へまとめる。
- 純粋な補助関数、役割の明確なモジュール、機能固有の処理へ分ける。
- 条件の連鎖を型付きモデルや明示的な振り分けへ変える。
- 業務処理と担当の起動・順序制御を分け、重複した分岐や包みを削る。
- 既存の共通処理と契約を使い、適切な層へ戻す。
- 独立処理の並列化、関連更新の原子性によって処理を単純にする。

同じ複雑な考えを少し整えた案だけで終えない。より単純なモデルへ変えられるなら、どの概念・分岐がなくなるかを示す。

## 指摘と判定

構造の後退、大きな単純化の機会、条件の増加、境界・抽象化・型の問題、ファイルの分解、モジュール性、読みやすさの順で優先する。大きな構造問題があるときは、低価値な名前・整形の指摘を大量に並べない。

例えば「共有の認証経路へ機能固有の判定が3箇所増えています。機能側の方針へまとめれば、認証経路は従来の条件を保てます」のように、問題、影響、挙動を保つ修正案を結び付ける。重大な保守上の問題を曖昧な提案に弱めず、作者を侮辱しない。

明確な構造の後退、根拠のないファイルの肥大化、散在する特例、不要な層・cast・任意値、責務の漏れ、既存補助との重複、明らかな単純化の見落としは、説明か修正を要する所見として返す。提案の費用、振る舞いを保つ条件、構造上の理由を確認し、リポジトリの採用基準を勝手に増やさない。報告は [report.md](report.md)に従う。

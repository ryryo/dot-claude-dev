# 製品UI・操作の調査

製品の画面や操作を、再現・比較・採否判断に使える資料へまとめるときに読む。特定の製品、画面構成、機能分類を前提にしない。

## 一連の操作から調べる

入口、主要な作業対象、その作成・追加、設定、実行・確定、結果利用、次の作業までを追う。失敗・取消・再試行・復元は、その操作に関係するものを確認し、動画にない場合は未確認にする。機能一覧や代表的な全景だけで、操作全体を確認済みにしない。

先に動画内の登場項目を棚卸しする。導入先の既存機能や実装の容易さから調査対象を狭めない。依頼で対象が限定されている場合はその範囲を尊重する。

## 整理する内容

| 資料 | 主な記録内容 |
| --- | --- |
| 操作の全体像 | 作業の目的、入口、画面領域、工程間の移動、結果の利用方法 |
| 機能・対象の一覧 | 名称と別名、用途、追加入口、設定、結果操作、代表画像 |
| 操作と状態の一覧 | 前提状態、利用者の操作、途中表示、到達状態、失敗・復旧、出典 |
| 入出力の一覧 | 入力・出力の用途、観察できた型、表示条件、具体例、未確認の制約 |
| 未確認点 | 欠けた操作・状態、根拠不足の理由、追加確認箇所 |

ノード式UIならポートを1行ずつ整理する。フォームや編集ツールなら入力項目、編集対象、保存・出力などに置き換え、存在しないポート表を作らない。

同じ機能の別名や複数の追加入口を整理し、入口と作成される対象を区別する。カテゴリやモデルのショートカットを機能数に重複計上しない。反対に、用途・状態・入出力が違う対象を見た目だけで統合しない。

## 映像から判断できる範囲を守る

- 接続・移動・選択・設定切替は、同じ対象の操作前後と必要な途中状態を照合する。動画編集で場面が飛ぶ場合は、連続した操作の証拠としない。
- 全景と細部を対応付け、メニューやラベルを読める画像を使う。正式ラベルを読めない場合は説明用の名称と明記する。
- メニューの存在、操作を試したこと、成功したことを区別する。停止ボタンの表示だけで取消完了を保証しない。
- 1件の入力・接続の実例は許容上限を意味しない。優先順位、複数入力の組合せ、保存・復旧の規則を推測で埋めない。
- モデル、モード、選択状態などでUIが変わる場合は、その条件を画像と対応付ける。空の対象での切替から、入力済みの対象でも保持されるとは判断しない。
- 動画中の名称や型は観察上の分類として扱い、API field、enum、DB schemaへ変換しない。映像だけで内部技術スタックを断定しない。

## 後工程へ渡す

資料の用途が再現検討なら、確認できた画面部品・必要な素材・実処理が必要な箇所を判断材料として整理する。調査キャプチャと実装用素材を混同しない。

適用案を求められた場合は調査事実と分けて示し、採用済みにはしない。採否、実機操作、製品契約の更新、実装は追加依頼の範囲で扱う。

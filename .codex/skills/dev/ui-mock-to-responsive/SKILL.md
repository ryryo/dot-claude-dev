# カンプから素材・レスポンシブ実装

採用された見た目と操作の優先順位を保ちながら、画面サイズと状態の変化に耐える部品へ分解する。成果物は依頼に応じた「実装用素材」または「動く画面」。カンプの画像一枚を表示しただけのものを実装としない。

## 既存スキルとの役割分担

- このスキルは、参照の確定・素材分解・レスポンシブ設計・素材の受け渡しを担当する。
- 方向性の比較画像そのものを求められた場合は [ui-design-concepts](../ui-design-concepts/SKILL.md)。採用済み案を実装するためだけに、新しい複数案の作成や再承認を挟まない。
- ラスター画像の生成・編集時は、利用可能な `imagegen` と [generative-prompt-design](../video-gen/generative-prompt-design/SKILL.md) を読む。生成記録と採用画像の保存は [imagegen-core](../media-gen/imagegen-core/SKILL.md) に従い、ここで別規約を作らない。
- アプリ実装時は [ui-concept-implement](../ui-concept-implement/SKILL.md) を併用し、既存UIへの統合・ブラウザ検証・レビューを引き継ぐ。同じ確認やレビューを重ねて実行しない。

## 1. 採用参照と作業範囲を定める

参照画像を実際に開き、生成時の原稿・プロンプト、ユーザーの修正指示、既存アセットとUIを確認する。複数案を組み合わせる場合は、背景・文字・イラスト・導線ごとに採用元を特定する。最新の明示指示を優先し、不採用案を形状や配色の根拠にしない。

既存のデザイン資料に、次を短く記録する。資料がなければ `docs/DESIGN/{YYMMDD}_{slug}/` に設ける。

- 維持するもの: コピー、色、キャラクター、構図上の関係、読む順序、主要操作。
- 調整できるもの: 幅、余白、折返し、装飾の位置・密度など。変更理由を操作性と結びつける。
- 納品範囲: 素材まで／組み合わせプレビューまで／アプリ実装まで。素材作成だけの依頼では本体を変更しない。

「文字表現を参考にする」は背景変更の指示ではない。ロゴやコピーの新規設計も、素材化のついでに始めない。実装まで許可されている場合は素材納品で止めず、確認済みの方針で進める。

## 2. 画面を役割とレイヤーに分ける

主要操作を先に決め、各要素を次のどれで実現するか選ぶ。

| 実現方法 | 対象と判断 |
| --- | --- |
| 既存部品・既存素材 | ブランド、キャラクター、カードや商品写真、入力部品。利用できる正本を優先する |
| HTML/CSS | 見出し、本文、ラベル、番号、入力、ボタン、背景色・グラデーション、角丸、影。操作と読み上げを保つ |
| SVG・既存アイコン | 単純な線、星、吹き出し、矢印など。形の複雑さと既存スタイルへの適合で選ぶ |
| ラスター素材 | 水彩、紙地、複雑なイラスト、写真、手描き固有の質感。必要なものだけ生成・編集する |

別々に動く・縮む・重なるものを独立させる。例えば背景／キャラクター／装飾／カード各枚／文字を分け、UIラベルや矢印をイラストに焼き込まない。逆に、常に一体で使う絵を理由なく細分化しない。

手書き文字を画像にする場合は、通常のフォントで表現できない理由と正確な代替テキストを持たせる。周囲の帯や飾り線は独立調整が必要なら別素材にする。

素材作成前に [references/asset-handoff.md](references/asset-handoff.md) を読み、保存先・寸法・透過・重ね順・描画範囲を決める。

## 3. レスポンシブの組み替えを設計する

カンプのアスペクト比を画面全体の制約にしない。操作の順序と主従を保って、コンテナ幅、要素幅、余白、カラム、改行、スクロールを設計する。

- PC: 適切な最大幅と左右の余白を設け、実際に読める文字・操作サイズで配置する。スマホ画像の拡大や、余った横幅への無条件な並列化で済ませない。
- スマホ: 狭幅での文字量と操作サイズからカラム数を判断する。承認済みの2列を「モバイルだから」と自動で1列にしない。
- チャットやフォーム: 入力を主役にする構成なら、その流れを保つ。1カラムを全サービス共通の正解にはしない。
- 装飾: 本文と同じ倍率で拡大する必要はない。背景の被覆、絵の縦横比、安全余白、切れてよい部分を個別に指定する。
- 高さ: 必要な内容は自然にスクロールさせる。すべてをファーストビューへ収めるために文字・入力・ボタンを縮めない。

対象端末、代表幅、最小対応幅、ブレークポイント付近の挙動を決める。別端末の画像案がなくても、通常のレスポンシブ判断で補える部分は実装して確認する。主要操作や採用構図が変わる不明点だけを質問する。

## 4. 素材を作り、組み合わせて確認する

生成には採用参照を渡し、維持する形・色・描画タッチ、単体素材として必要な範囲、透過、不要な文字や背景を具体化する。元カンプの背景ごと持ち込む編集と、独立した素材の生成を混同しない。

各素材は単体だけでなく、想定背景・表示サイズ・重なりで確認する。ファイルが生成されたこと、拡張子がPNGであることだけで透過成功としない。配信用変換やサイズ変更は元データを残し、画質と容量を確認して行う。

組み合わせ検証には、実装済みコンポーネントまたは小さなHTML/CSSプレビューを使う。画像生成で組み直した完成図は、実素材の重なりやレスポンシブ動作の証拠にはならない。

素材のみの納品なら、参照表・配置説明・配信用ファイル・実素材を使ったプレビューを渡し、未実装の操作や状態を明示する。「そのまま実装に使える素材」と「アプリへの実装完了」を区別する。

## 5. 実装と検証

実装が依頼範囲なら `ui-concept-implement` に従って既存部品・状態・導線へ統合する。装飾は操作や読み上げを妨げず、画像のロード前にもレイアウトが大きく動かないよう寸法を与える。

検証では次の見落としを優先する。

- 画像読み込みとUIの準備完了後に撮影し、初期disabled状態を完成画面と誤認しない。
- PC・スマホ・最小幅とブレークポイント前後で、コピーの指定改行、短いラベルの途中改行、横あふれ、重なり、操作領域を確認する。
- 確定したカンプとの比較はスクリーンショットで行い、寸法やDOMの数値確認だけで見た目を合格にしない。
- 空・入力中・送信中・失敗・保存状態など、変更に関係する実状態とキーボード操作を確認する。新しい挙動はリスクに応じてTDDで検証し、見た目だけの変更には不要なテストを増やさない。
- 関連テスト、型チェック、ビルドとブラウザ確認を行う。接続URLはプロジェクトの環境スキル等から確認し、他環境の固定ポートを推測しない。

最終報告は、素材または実装の完了範囲、採用ファイルと実画面へのリンク、確認した幅・状態、残件に絞る。実通信とモック、作業ツリー全体の検証とコミット単独の検証を区別する。

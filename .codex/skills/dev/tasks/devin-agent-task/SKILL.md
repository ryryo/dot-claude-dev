# ブラウザ操作なしのDevin協働

Codexが目的・受入条件・最終レビューを持ち、Devinが指定範囲を実装する。依頼、回答の回収、範囲内の判断、修正、実成果の確認を同じセッションで往復し、利用者が指定した終了点まで進める。CodexによるWebコンソールのブラウザ操作は使わない。製品の受入条件に必要なPlaywright等の試験や、DevinのVM内でのGUI検証は別である。

## 実行場所と経路を選ぶ

公式の説明と本スキルの選択理由は[経路の比較](references/transport-selection.md)を参照する。PRの有無、行数、作業規模だけで経路を決めない。

| 今回必要なこと | 経路 |
| --- | --- |
| Cloudの独立VMで調査・実装し、Codexが状態と回答を構造化して取得する | **公式Devin MCPを既定**とする。複数repoや広い改修でも、Cloudで実行可能ならこの経路でよい |
| 未pushのファイル、手元の依存・プロセス・端末環境を直接扱う | **ローカルDevin CLI**。編集先と同時編集の境界を決める |
| Cloudを使いたいが現在のMCPの機能・前提・認証で操作できない、またはCLI指定 | **`devin --cloud`**。ローカル実行へ変更せず同じCloudセッションを再開する |

MCPで進める際は[既存の接続・回収手順](../devin-github-task/references/mcp-and-resume.md)を読む。CLIを使う際だけ[CLIの対話と再開](references/cli-workflow.md)を読む。PRレビュー・採用や環境設定が必要になったら[ブラウザなしの成果採用](references/review-and-adoption.md)を読む。

## 許可と作業範囲

- 対象と目的を指定したDevinへの委譲依頼は、依頼送信と範囲内の質問・修正の往復を含む。PRまで、採用まで、ローカル編集まで等、指定された終了点を守る。採用まで許可されていれば必要条件を満たすマージ・関連環境提案の採用を毎回確認し直さない。相談・スキル作成だけの依頼では実装ジョブを起動しない。
- 実行経路の選択だけで、Cloudへの未commitファイルの送信、作業場所の変更、権限の拡大を許可済みとしない。対象外の改修、未決の製品仕様、新しい課金契約や資格情報、破壊的操作は元の許可で判断する。
- 本スキルから他のCodexチャットやサブエージェントを増やさず、Devinにも再委譲させない。常設プロセス、hook、定期監視は別途依頼された場合だけ設定する。
- ブラウザに黙って切り替えない。API/CLIで実行・照合できない工程は、具体的な機能不足と確認済み成果を残し、その工程に依存しない作業を続ける。独立レビューだけで足りる条件か、Devin Review等が必須かは元の契約から判断する。

## 対象を確定して依頼する

対象repo・実行ディレクトリ、baseと確認commit、必要な参照repo、編集範囲、既存PR/WIP、維持契約、受入条件を確認する。AGENTS.md・README・セットアップ・呼出元と必要な設計を読む。製品固有の役割・モデル制約を優先し、Devinの実モデル・推論設定が返らない場合は未確認と記す。

Cloudで読むのはremoteである。手元の未commit変更を反映済みと扱わず、単なる委譲のために他者の変更をまとめてcommit・stash・resetしない。共有スキルや隣接repoはCloudでの実取得・配置・resolveを確認する。ローカルCLIでは現行契約の作業場所を保持し、共有branchの切替やworktree作成を勝手に行わない。

[依頼の雛形](../devin-github-task/references/task-prompts.md)から今回に必要な箇所だけを使い、UI確認を前提とする文言をAPI/CLIで取得できる証拠へ置き換える。調査だけなら編集・PRを除き、ローカル作業ならVMの代わりに実ディレクトリと未commit差分の境界を渡す。

最初の依頼には、質問してよい判断と確認が必要な判断、編集先・対象外、試験資源、終了点、返す証拠を明記する。固定依存と既存の隔離ランナーを使わせ、環境問題を製品版やlockfileの不要変更で回避させない。Cloud成果は専用`codex/`branchとPRまでをDevinの担当とし、自己merge・base直接push・deployを依頼しない。ローカルではrepo契約に従い、Codexが所有差分を照合して正式化する。

## 対話を進める

1. 既存セッションが指定されていれば最新の状態・履歴・最後の指示を取得して継続する。独立した新規作業だけ新規セッションにし、返却ID/URL、実行場所、最後のメッセージやcursorを既存の作業記録へ残す。
2. 作業中なら必要な完了待ちを行い、入力待ちなら質問全文・対象版・既に決まった契約を読む。通常の実装判断や修正はCodexが答える。依頼文や過去の成功を最新の実成果と扱わない。
3. 失敗やレビュー指摘は、対象head、症状、コード・契約の根拠、期待結果、影響する検証をまとめて同じセッションへ返す。結果不明の送信は履歴・セッション検索で照合してから扱い、別経路で二重送信・二重作成しない。
4. 回答にPR、commit、パス、検証結果が出たら実物を取得する。必要な差分だけを再レビューし、範囲内の不備は同じ成果を修正させる。解消に利用者の判断が必要な具体的な問題が残るまで、単なる報告の受領で止めない。

MCP待機は60秒以内のbounded gatherを使い、CLIの長い処理は実行ツールのsession IDを保持して続きを読む。`finished`、プロセスexit 0、PR登録、採用、元ID完了は別々の状態である。Codexのターンが終わった後の自動再開は保証せず、依頼されていないタイマーを追加しない。

## レビューして結果を採用する

Devinの回答とは別に、GitHubのbase/head・実diff・関連コード・必要な検証・必須チェックを`gh`/`git`等で照合する。PRは現在のチャットへ添付する。保存・権限・並行処理・資源寿命・移植等の難しい変更は、Codexのレビューに加えて利用可能な公式経路でDevin Reviewを行い、対象headと指摘を確認する。

GitHub Actionsを修正の反復環境にせず、Cloud VMまたは許可されたローカルで失敗を再現・修正・検証してからまとめてpushする。CIの必須チェックや受入条件は維持する。CLIからのローカル実装でもPRを作れるし、MCPからのCloud実装でも広い変更を扱える。

公開成果の本文・自動footer・差分に非公開セッションURL、内部根拠、旧repo参照、個人パス、秘密情報を持ち込ませない。採用まで許可され、重要な指摘と必要な条件が解決していればCodexが対象headを固定してマージし、MERGEDと採用commitを確認する。未確定差分がある共有treeへはfetchだけに留め、cleanで適切なbranchなら`pull --ff-only`で同期する。

既存記録へ実行経路、セッション、base/head、採否、検証と未実施、ローカル同期を残す。元タスクの進捗は正本のCLI・最新claim/revision・受入条件で更新し、PRマージだけで完了にしない。最終報告は成果リンク、採用結果、実証できた工程と残る条件を短く示す。

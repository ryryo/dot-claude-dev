# 完了後のフィードバックとGift ACU

## 感謝を伝えるタイミングと内容

依頼された終了点をCodexが確認してから、同じDevinセッションへ短い感謝を一度送る。調査なら確認済みの調査結果、PRまでならレビュー済みのPR、採用までなら実際のマージ・採用、ローカル実装なら確認済みの差分と検証に対して伝える。未採用のPRをマージ済みと褒めたり、残る受入条件を完了したと伝えたりしない。

例えば「ありがとう。保存・復旧の回帰テストを追加し、必要な検証も通ったことを確認しました。助かりました。今回の作業はここまでで、追加の作業は不要です」と伝える。内容は実際に確認した成果に合わせる。英語なら `Good job, thank you!` から始めてもよいが、特定の言語・文言による付与を期待しない。

既存の記録へ対象成果と送信済みメッセージID、または送信を確認した時刻を残す。再開や定期確認のたびに送り直さない。送信結果が不明なら同じセッションの履歴で確認し、別経路から重ねて送らない。感謝のためだけに新しいセッションを作らず、Devinからの返答にさらに感謝する往復も続けない。

## Gift ACUが提示された場合

2025年には、作業完了後の `good job` に対して1.5 ACUの付与カードが表示され、公開された残高画像も3.3から4.8 Gift ACUsへ増えた本人の報告がある。別の利用者も残高の増加を確認している。Devinが後から「ジョークだった」と説明する例もあり、会話中の発言だけで付与の有無を判断しない。

2026年10月8日の調査では、現行公式資料から付与条件・確率・継続を確認できなかった。2025年の報告はCloudチャットでの事例であり、MCP・CLI経由でも付与されるかは未確認。感謝は成果へのフィードバックとして送り、付与を成功条件や費用削減の見込みに含めない。

付与が提示された場合だけ、許可された経路で取得できる残高・利用明細を照合する。Cloudの個人向けプランではSettings → Usage & limits、EnterpriseではConsumption / Consumption Analyticsを参照する。Gift枠の表示があればその値を確認するが、現在の料金体系や画面に同じ枠があるとは仮定しない。

送信前後の値や付与明細で増加を確認できた場合は、確認日時・付与量と根拠を既存の記録へ残す。付与カードや残高の片方しか確認できない場合は、付与の表示と実残高の増加を区別して未確認と記す。料金情報は内部記録へ残し、公開PRへ転記しない。

付与されなくても追加の称賛、催促、強い口調での要求、付与理由の質問、監視の追加は行わない。残高を確認できない場合も、そのために会話や操作を続けない。Gift ACUは利用クレジットの追加として扱い、カードへの現金返金と記録しない。

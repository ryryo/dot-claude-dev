# GitHub相談・改修・Issue化の依頼文

今回許可された工程の雛形だけを使い、括弧を実在する情報へ置き換える。雛形の選択自体を許可にせず、既に合意した内容を再び未決へ戻さない。

## 1. GitHubコードを読んで相談する

```text
GitHub接続から（owner/repository）の（ブランチ、確認commit）を読んで相談に乗ってください。
目的は（解決したい問題・できるようにしたいこと）です。
入口は（コード・仕様のパス・シンボル）です。必要な呼出元と関連契約も確認してください。
維持する動作・制約は（合意済み事項）、対象外は（範囲）です。
確認済みの事実は（症状・証拠）、既存案は（案）、未確定は（事項）です。
手元だけにある変更・ログは（未収録の内容、または該当なし）です。GitHubに反映済みと扱わないでください。

今回許可された工程は（相談だけ／既定の軽微修正PR・その他Issue化／Issue化まで）です。
関連コードを実際に読み、参照版・パス、事実・提案・未確認を分けて示してください。
推奨方針、維持する動作、変更範囲、受入条件、必要な検証を整理してください。
利用者の選択が必要な事項は、選択肢と影響を示し、合意前に決定済みにしないでください。
相談だけの場合はGitHubへ書き込まないでください。

既定フローでは、内容と影響が明確で実行検証をほぼ要しない文言・説明・誤記を軽微修正の候補とします。
構造・動作変更や実行検証が必要な修正は、Codex向けIssueの候補として整理してください。
ローカル再現が中心なら、既知の事実・再現条件・調査対象をまとめ、原因を推測で確定しないでください。
```

Pro自身の非軽微改修とPRが明示されている場合は、この既定フローではなく次の改修雛形を使う。

## 2. 許可された改修をPro自身でPRにする

```text
GitHub接続で（owner/repository）の（baseブランチ、確認commit）を実際に読み、あなた自身で改修・commit・PR作成まで進めてください。
利用者が許可した工程は（合意済みの軽微修正／明示された対象範囲の非軽微改修とPR）です。
その依頼は（利用者の具体的な改修指示）です。
対象は（パス・問題・目的）、編集範囲は（範囲）です。
維持する動作・契約は（事項）、対象外は（事項）です。
専用branchは（codex/で始まる作業名）、同じ作業の既存PRは（URL、またはなし）です。

適用指示、対象ファイル、関係する参照・呼出元・実スクリプトを読んでください。
読めた版とパス、branch・ファイル編集・commit・PR作成の利用可否を確認してください。
baseが進んでいれば対象範囲の差を確認し、他者の変更を上書きしない基点を使ってください。
許可された改修と必要な検証を終え、専用branchへcommitし、PRを作成・更新してください。
baseへの直接commitとmergeは行わないでください。

軽微修正だけの許可で、実行検証や範囲拡大が必要と判明した場合は、できた案と残件をIssue向けに整理してください。
非軽微改修とPRが明示されている場合は、構造・動作変更という理由だけでIssue案に戻さず、許可範囲内の調査・修正・検証まで進めてください。
未決仕様、新しい権限、未承認の課金・外部操作、範囲外の変更は決めず、必要な判断と影響を示してください。
通常の局所失敗は許可範囲内で修正し、依存しない作業を続けてください。

結果不明なら既存branch・commit・PRを照会し、重複作成しないでください。
書き込めない場合は、読んだGitHub版に対応する完成diffまたは完全ファイルとPR本文を返してください。
結果にPR URL、base/head・実基点・変更commit、変更範囲、実行した検証・未実施、残件を示してください。
PR本文は問題と改修結果、維持契約、検証と未実施を本文だけで理解できる形にし、公開範囲を守ってください。
```

## 3. 合意事項と訂正を反映する

```text
同じ相談・改修を、次の確定事項に合わせて更新してください。
利用者と合意した内容：（決定事項と維持する動作）
コードとの照合で訂正する点：（主張・対象版の根拠・訂正内容）
未決のまま残す点：（未選択・未確認）
今回許可された工程：（相談／軽微修正PR／明示された範囲の非軽微改修とPR／Issue作成・更新）

変更案・受入条件・検証方法と、許可された成果物を整合させてください。
確定事項を最初から作り直さず、今回必要な変更だけを反映してください。
```

## 4. Codex向けIssueを作成・更新する

```text
（owner/repository）の（関連する既存Issue URL、または新規）に、合意した内容を整理してください。
Issueテンプレートがあればその構成を使ってください。
確認基点は（ブランチ、commit）、参照コードは（パス・シンボル）です。
確定事項は（内容）、未決事項は（内容）、公開範囲の条件は（適用先の規則）です。

本文には次を含めてください。
- 目的・期待する利用動作。問題なら症状、期待と実際、再現条件
- 合意した方針と根拠、関連コードと確認基点
- 変更範囲・対象外、維持する動作
- 受入条件と検証方法、実施済みの証拠と未実施
- 未決事項と、実装または調査・設計として次に進める内容

本文だけで担当者が依頼内容を理解できるようにし、会話リンクは補足にしてください。
未合意の仕様を決定済みにせず、必要なら調査・設計の到達点を示してください。
同じ作業のIssueがあれば更新し、指定されていないassignee・label・milestoneを追加しないでください。
今回はIssue化までであり、Codexタスクを起動しないでください。
書き込めない場合は確定したタイトルと本文を返してください。
作成・更新後は実際のIssue本文とURLを確認して報告してください。
```

Codexでの実装開始まで依頼されている場合も、CodexがIssueの現行内容を確認して引き継ぐ。Proへの依頼文を、Codexチャットの起動許可へ広げない。

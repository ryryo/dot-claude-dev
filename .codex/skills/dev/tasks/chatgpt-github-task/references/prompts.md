# GitHub相談・Proの改修成果・Codex登録の依頼文

今回許可された工程だけを使い、括弧を実在情報へ置き換える。Codexが成果を登録する分担は最初に明記し、Pro本人の登録指定がある場合は、担当変更の許可を確認してからこの改修雛形を使う。スキルの編集だけの依頼では送信しない。

## 1. GitHubコードを読んで相談する

```text
GitHub接続から（owner/repository）の（ブランチ、確認commit）を読んで相談に乗ってください。
目的は（解決したい問題）、入口は（コード・仕様のパス・シンボル）です。
適用指示と必要な呼出元・関連契約まで実読取してください。
維持する動作・制約は（事項）、対象外は（範囲）です。
確認済み事実は（症状・証拠）、既存案は（案）、未確定は（事項）です。
手元だけにある情報は（未収録の内容、または該当なし）です。GitHubに反映済みと扱わないでください。
今回の工程は（相談だけ／既定の軽微修正PR候補・その他Issue案／Issue本文の作成まで）です。

読めたrepo・commit・パスと不足、事実・提案・未確認を分けて返してください。
推奨方針、維持する動作、変更範囲、受入条件、必要検証を整理してください。
利用者の選択が必要な事項は選択肢と影響を示し、合意前に決定済みにしません。
GitHubへの書込は担当Codexが行うため、この返信ではcommit・PR・Issueの作成更新を行わないでください。
明示改修がなければ、実行検証を要する構造・動作変更はCodex向けIssue候補へ整理し、原因や設計を推測で確定しないでください。
```

## 2. Proが修正・検証し、Codexがcommit・PR更新する

### 最初の送信：最初の必要変更群を完成成果として返す

Codexが現行の登録機能とrepo・ref・既存成果を確認してから使う。新規作業なら最初の必要成果を下書きPRへ登録し、既存PRなら同じbranch・PRを継続する。ダミー変更による書込試験はしない。

```text
（owner/repository）の（base、確認commit）について、あなたが修正・必要検証・自己レビューを行い、Codexが完成した同じ成果を照合してcommit・PR作成更新する分担で進めます。
利用者が許可した改修は（具体的な直接指示と範囲）です。
目的・問題は（内容）、入口は（パス）、編集範囲は（範囲）です。
維持する動作・契約は（事項）、対象外・未決のまま残す点は（事項）です。
既存branchは（branch、またはなし）、既存PRは（URL、またはなし）、現在headは（commit）です。
Codexの登録経路は（利用可能な機能・確認済み範囲）で確認済みです。実登録・読取は最初の完成成果で照合します。

あなたはGitHubの対象版、適用AGENTS、必要なREADME・setup、対象ファイル・呼出元・保存/API契約・既存試験を実読取し、最初の独立した必要変更群（具体的な対象）を修正・必要検証・自己レビューまで行ってください。
GitHub書込はCodexが担当します。あなたは書込定義を取得しようとしたり、commit・PR・Issueを作成更新したりしません。書込機能がなくても、対象版の読取・修正・検証・成果返却を進めます。
広い成果を溜めず、今回はこの変更群の完成成果を返してください。元の全範囲の残件も保持してください。

返却は会話本文に、次を省略せず含めてください。
1. 実読取のrepo・基点commit・関連パス、対象ファイルの変更前blob/SHA、追加・変更・削除一覧。
2. その版に適用できる完全diffまたは変更後の完全ファイル。疑似コード・省略・期限付き添付だけにしません。
3. 変更理由、維持した契約、自己レビュー結果、残件。
4. 実行したコマンド・環境・生出力・exit code、実施済みと未実施。代替ハーネスの完全コード、取得版との対応、置換した依存と検証限界。
5. この変更群と先行成果に対応するPRタイトル・本文案。完成範囲と残件、検証と未実施を明記します。

必要なソースが読めない場合は不足を返してください。必要検証は対象repoの固定環境・手順に従い、通常の局所失敗は修正・再確認します。環境不足は試した操作と生出力を返し、独立した修正を続けます。正式試験が未実施なら代替ハーネスの成功へ換算しません。
未決仕様・範囲外の変更・新しい認証や権限・未承認費用を推定しません。
登録担当、参照方法、ZIPやIssueへの切替は無断で変更しません。
公開差分とPR本文案へ非公開資料・相談URL・個人絶対パス・秘密値を入れません。
Codexが保存・照合・登録結果を返した後、次の変更群へ進みます。
```

### 成果照合で必要な訂正を依頼する

```text
返却された（変更群）の完成成果を（repo・基点commit・対象パス）で保存・照合しました。
確定した維持契約は（事項）、訂正が必要な点は（差分・実コード・検証原票からの具体的根拠）です。
現在の対象head・blobは（値）、返却時との差は（内容、または不変）です。

この根拠に合わせ、あなた自身で修正・必要検証・自己レビューを行い、現在版に適用できる完全diffまたは完全ファイル、検証原票、PR本文案を会話本文へ返してください。
実施済みと未実施、正式試験と代替ハーネス、以前の成功と今回の結果を分けてください。
GitHub登録はCodexが行います。あなたからの外部書込は行わず、確定事項を作り直したり対象範囲を広げたりしません。
```

### 登録後：同じbranch・PRの次の変更群へ進む

```text
前の（変更群）の成果をCodexが登録し、GitHubから実差分・対象blob・commitと親・PR本文を照合しました。
PRは（URL）、baseは（branch/commit）、現在headは（branch/commit）、登録した変更は（パス・要点）です。
Proが実施した検証は（原票の結果・未実施）、Codexの独立確認は（結果・限界）です。

同じ対象・維持契約・登録分担を引き継ぎ、次の必要変更群（具体的な対象）を、この最新headから実読取して修正・必要検証・自己レビューまで行ってください。
先行登録成果を保ち、他者の変更を古い全文で上書きしません。
前回と同じ形式で、基点commit・変更前blob・完全diffまたは完全ファイル・生検証結果・PR本文案・全範囲の残件を会話本文へ返してください。
GitHubへのcommit・PR更新はCodexが担当します。あなたは外部書込を行わず、書込機能の取得を修正開始の条件にしません。
今回の変更群だけで元の全改修完了とは扱わず、終了点（利用者が指定した全範囲と必要検証）を保持してください。
```

## 3. 合意事項と訂正を相談へ反映する

```text
同じ相談を次の確定事項に合わせて更新してください。
合意した内容：（決定事項と維持する動作）
コードとの照合で訂正する点：（主張・対象版の根拠・訂正内容）
未決のまま残す点：（未選択・未確認）
今回許可された工程：（相談／改修成果と必要検証の返却／Issue本文の作成更新）

変更案・受入条件・検証方法と成果物を整合させてください。
確定事項を最初から作り直さず、今回必要な変更だけを反映してください。
GitHubへの登録は担当Codexが行います。
```

## 4. Codex向けIssue本文を作成・更新する

```text
（owner/repository）の（既存Issue URL、または新規）について、合意した内容を確定本文へ整理してください。
Issueテンプレートがあれば使ってください。
確認基点は（branch、commit）、参照コードは（パス・シンボル）です。
確定事項は（内容）、未決事項は（内容）、公開範囲は（適用先の規則）です。

本文には、目的・期待する利用動作、問題の症状と再現条件、合意した方針と根拠、関連コード・基点、変更範囲・対象外、維持動作、受入条件・検証方法、実施証拠と未実施、残る未決事項を含めてください。
本文だけで内容を理解できるようにし、非公開の相談URLを公開本文へ持ち込みません。
未合意仕様を決定済みにせず、必要なら調査・設計の到達点を示します。
今回はIssue本文の作成までです。あなたはGitHubへの作成更新やCodexチャットの起動を行いません。
Codexが同じ内容を許可範囲で登録し、実本文とURLを読み返します。
```

Codexでの実装開始まで依頼されている場合も、CodexがIssueの現行内容を確認して引き継ぐ。Proへの依頼を新チャットの起動許可へ広げない。

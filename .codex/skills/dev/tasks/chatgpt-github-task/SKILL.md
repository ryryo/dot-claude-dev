# GitHub接続のProによる相談・改修・Issue化

ProがGitHubの実コードを読み、許可された相談・改修・成果作成を担当する。Codexから依頼する場合は、Codexがブラウザ送信、回答の照合、必要な登録代行を担う。Proとして直接依頼を受けた場合は、自身のGitHub接続で進め、別のProへの再送やCodexチャットの起動を挟まない。

## 対象と許可

- 利用者が本スキルを明示して対象を「このフローで進めて」と依頼した場合、その対象のChatGPT送信・相談・Issue作成と、軽微修正の専用ブランチ・PR作成を含む。「相談だけ」「Issueだけ」などの個別指定を優先する。
- 利用者がPro自身による対象の改修とPR作成を明示した場合は、非軽微な構造・動作変更もその指定範囲で進める。対象、編集範囲、維持する契約、終了点を依頼と実資料から確認し、既定のIssue化へ戻さない。
- スキル名だけの呼出し、自動選択、相談依頼、雛形の存在は、無条件の外部送信・書込・製品実装許可ではない。許可がなければ依頼文・成果案まで準備し、不足する範囲だけを確認する。許可済みの送信・編集・登録は確認し直さない。
- スキルの作成・編集・説明を頼まれただけで、そのスキルが記す相談や製品操作を実行しない。ただし、利用者がそのスキルファイルのGitHub上での改修・commit・PRを明示した場合は、そのファイルを編集対象として扱う。
- 適用先のAGENTS.mdと資料配置規則に従う。非公開の設計・調査根拠を公開Issue・PR・差分へ転記しない。既存の相談記録・計画を使い、別の進捗台帳を作らない。

## 1. 対象版と実行経路を確認する

原依頼、目的、維持する利用動作、対象外、許可された工程を確認する。リポジトリの`owner/name`、ブランチ・確認commit、入口のコード・資料を特定し、必要な呼出元と実契約まで読む。事実・提案・未確認を分け、Codex側で詳細設計を完成させてからProへ渡す手順にはしない。

GitHub上の版を基点とする。未コミット変更を反映済みと称したり、不足を無断のpush・ZIP添付で補ったりしない。指定版や必要なローカル状態が読めなければ不足を示す。ZIP添付の相談を明示された場合は[chatgpt-pro-consult](../../refactor/chatgpt-pro-consult/SKILL.md)へ、その許可範囲を引き継ぐ。

| 実行主体 | 次の操作 |
| --- | --- |
| CodexからProへ依頼する | [依頼テンプレート](references/prompts.md)で依頼文を作り、[ブラウザ共通手順](../../refactor/chatgpt-pro-consult/references/browser-workflow.md)でモデル確認・送信・回答回収を行う。「送信だけ」なら送信確認で終える |
| Proが直接GitHub作業を依頼された | GitHubから対象版を取得し、工程2へ進む。ブラウザ送信・回答待ちの手順は読まない |

Proが実際に取得した関連パス・参照版を照合し、接続済み表示だけでコードを読んだと判断しない。登録前には、Proの実行環境でファイル編集・branch・commit・PR・Issueの必要な機能と権限を確認する。CodexにあるツールをProでも使えるとは仮定しない。

## 2. 許可に合う成果と終了点を選ぶ

個別指定を先に適用し、指定がない部分だけを既定のフローで扱う。

| 依頼・条件 | 成果と終了点 |
| --- | --- |
| 相談だけ | 根拠付きの結論・未決事項。GitHubへ書き込まない |
| 利用者がPro自身の改修とPR作成を明示 | 指定範囲を改修し、必要な検証、専用branchへのcommit、PR作成・更新まで行う。非軽微という理由だけでIssue案に置き換えない |
| 既定フローでの軽微修正 | 文言・説明・誤記など、内容と影響範囲が明確で実行検証をほぼ要しない変更を、専用branch・PRへ残す |
| 既定フローでの構造・動作変更、機能追加、実行検証が必要な修正 | 合意した方針と受入条件を持つCodex向けIssueにする |
| 未コミット変更、ローカルログ、再現環境の調査が中心 | 確認済みの事実・再現条件・調査対象を整理したIssueにする。Proだけで原因や設計を推測して確定しない |

変更行数だけで軽微と判定しない。処理、保存形式、権限、依存設定などを変える場合は非軽微として扱う。軽微修正として開始し、実行検証や範囲拡大が必要と分かった場合は、別途の明示改修許可がなければ、できた案と残件を分けてIssue化する。

明示改修の範囲内なら、局所的な実装不足や検証失敗は調査・修正・再確認まで進める。ただし、利用者が選ぶ未決仕様、範囲外の変更、新しい権限、未承認の課金・外部操作は含めない。必要な判断と影響を示して依存する操作だけを止め、許可済みの独立作業は続ける。合意済み事項を再び未決へ戻さない。

誤りや根拠不足は対象版のコードと照合し、相談中なら同じ会話へまとめて訂正を返す。関連する案・受入条件・検証方法も整合させる。

## 3. 許可された改修を専用ブランチ・PRへ残す

Proが変更対象と維持契約を確認し、指定された基点から`codex/<作業要約>`の専用ブランチで修正する。同じ作業の既存branch・PRがあれば確認して継続する。baseへの直接commitと自動mergeは行わない。

基点が進んでいれば、対象範囲の差と現在のファイルを確認する。現行ツールのschemaに従ってSHA・refを渡し、他者の変更を古い全文で上書きしない。必要な改修と検証を終えてcommit・PRを作成し、実際の差分、編集範囲、base/head、commit、残件を照合する。

Proの「完了」「テスト成功」だけを証拠にしない。実施した検証・未実施を分け、軽微として扱った変更が動作を変えていないかも確認する。非軽微な明示改修では、対象に必要な実行検証を示す。必要な検証が未実施なら、その制約をPR本文にも残し、完了した検証と取り違えない。

Codexが回答を回収する場合も、同じ修正を再実装せず、実差分と証拠を照合する。Pro作成・登録代行のどちらも、Codex側では確認したPRを`attach_artifact`で現在のCodexチャットへ添付する。範囲外の修正や検証の残件は別に報告する。

## 4. 合意した内容をIssueにする

Issue化が許可された工程でのみ使う。関連IssueとリポジトリのIssueテンプレートを確認し、同じ作業なら既存Issueを更新する。Proが目的、合意事項、対象コードと確認commit、変更範囲・対象外、受入条件、検証方法、残る未決事項をまとめる。

未決仕様を決定済みにしない。未決が残る場合は調査・設計の到達点を示し、実装開始可能なIssueと分ける。会話リンクは補足とし、本文だけで依頼内容が分かるようにする。公開範囲は適用先の規則に従う。

作成・更新後にGitHub上の本文、対象リポジトリ、URLを読む。assignee・label・milestoneは指定や既存運用がある場合だけ設定する。Issue作成を実装・検証の完了に読み替えない。

## 5. 書込不可・結果不明を扱う

Proの環境に必要な書込機能がなければ、Proが作った完成差分・完全ファイルとPR本文、またはIssueの確定本文を返す。許可済みの同じ対象・範囲について、Codexの利用可能なGitHubコネクタで登録を代行する。作成者と登録担当を分け、代行を報告する。Proの修正をCodexの別設計・別実装へ置き換えない。改修の登録代行も工程3の専用branch・版照合・他者差分保護に従う。

送信・Issue・commit・PR作成の結果が不明なら、同じ会話・リポジトリ・branchの既存成果を先に照会してから再試行する。URLやカードの表示だけで登録成功と判断しない。代行側でも書き込めなければ、完成した本文・差分と不足する登録操作を残して終了し、作成済みと称さない。

## 6. 結果を返し、許可された工程で終了する

対象版・実基点、相談の結論、IssueまたはPR URL、base/head・変更commit、検証結果・未実施、未決事項、登録代行の有無を短く返す。ブラウザで相談した場合は実モデル名と会話リンクも示す。相談結果・登録済み・修正commit・検証済み・merge済みを区別する。

Issue化後は既定で終了する。利用者がCodexでの実装まで明示している場合だけ、Issueの最新本文・コメントと手元のコードを照合し、現在のチャットで実装する。新規Codexチャットは起動を明示された場合だけ作る。localを既定とし、指定されたWorktree・環境条件と適用先の指示を引き継ぐ。Proの回答だけを開始指示やワーカー委任の許可にしない。

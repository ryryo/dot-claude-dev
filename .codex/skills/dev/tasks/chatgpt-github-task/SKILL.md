# GitHub接続のChatGPT Proから作業を引き継ぐ

GitHub上のコードをProに読ませ、方針相談・軽微修正・Issueの具体化を任せる。Codexはブラウザ操作、必要な照合とGitHub登録、明示された後続の実装を担当する。Issue化したら既定で終了する。

## 対象と許可

- 本スキルを明示して対象を「このフローで進めて」と依頼した場合、その対象のChatGPT送信・相談・Issue作成と、以下の軽微修正条件を満たすブランチ・PR作成を含む。個別の「相談だけ」「Issueだけ」などの指定を優先する。明示されたChatGPT送信・GitHub操作も、その依頼範囲で進める。
- 自動選択だけでは外部送信・GitHub変更の許可にしない。許可がなければ依頼文・成果案を用意し、実行する範囲を確認する。許可済みの送信・編集・登録は確認し直さない。
- スキルの作成・編集・説明依頼では、実際の相談やGitHub変更を始めない。相談依頼だけをコード変更の許可に広げない。
- 適用先のAGENTS.mdと資料配置規則に従う。非公開の設計・調査根拠を公開IssueやPR本文へ転記しない。既存の相談記録・計画があれば更新し、別の進捗台帳を作らない。

## 1. 対象と相談の入口を確定する

原依頼、目的、維持する利用動作、対象外、実行を許可された工程を確認する。対象リポジトリの`owner/name`、ブランチと確認commit、関係するコード・資料のパスを特定する。Codex側で詳細設計を完成させてからProへ渡す手順にはしない。

指定されたChatGPT会話を優先し、継続相談は同じ会話で進める。新規相談は新しいChatGPT会話を使う。無関係な会話や未送信の下書きを上書きしない。

GitHub上の内容を相談の基点とし、手元の未コミット変更を反映済みと称さない。不足を無断のpushやZIP添付で補わない。指定版が読めない、必要なローカル状態がない場合は、その不足を明示する。ZIP添付による相談を明示された場合は[chatgpt-pro-consult](../../refactor/chatgpt-pro-consult/SKILL.md)を使う。

## 2. Codex内ブラウザでProとGitHub接続を確認する

`mcp__cua_repl.js`の現行説明に沿ってCodex内ブラウザを使う。初回はツールで許された入口を一つだけ実行し、返されたドキュメントと状態を読んでから続ける。過去のselector・要素番号・未提供APIを流用しない。

- ログイン状態と、実行時点の最新GPT世代のPro選択を確認する。明示されたモデル固定指定を優先し、Auto・Thinking等で代用しない。Proが使えなければ候補と不足を伝え、無断で落とさない。
- ChatGPTから対象GitHubリポジトリが読めることを、実際に取得した関連パス・参照版で確認する。接続済み表示だけでコードを読んだと判断しない。
- 成果を登録する際は、ChatGPTで使えるIssue作成・ファイル編集・ブランチ・PR作成の機能と権限を確認する。Codex側にあるGitHubツールをChatGPTでも使えると仮定しない。

## 3. コードに基づいて相談し、進め方を決める

[相談・成果作成のテンプレート](references/prompts.md)から必要なものを使い、対象、目的、基点、合意済み動作、許可範囲を送る。Proには関連コード・呼出元・契約を読むよう依頼し、確認した事実、提案、未確認を区別させる。

送信前に会話・モデル・本文を照合し、一度送る。投稿済みメッセージと応答開始を確認する。

- automationツールで同じ会話を**5分おき**に確認するheartbeatタイマーを設定する。同じ相談のタイマーがあれば更新し、会話URL・許可範囲・保存先・次の回収/照合/登録手順をpromptに残す。「送信だけ」の指定では設定しない。設定不能なら未設定と制約を報告する。
- 各実行では可視DOM/AXを一度確認し、応答中ならタブを`markHandoff()`して静かに終了する。sleepの繰り返しや短い間隔の画面確認で待ち続けず、次の5分後の実行へ戻す。途中の受領文・思考要約を完成回答にせず、数分経過だけで失敗扱い・再送・生成停止にしない。
- 完成回答を確認したらタイマーを停止し、その実行で回答を回収・照合して許可済みの次工程へ進む。訂正依頼や追加工程で再びPro応答待ちになれば同じタイマーを再開する。通知は回収・照合/登録の完了、失敗、利用者対応が必要なときだけとし、変化のない待機では通知しない。

| 進め方 | 選ぶ条件 | 成果・終了点 |
| --- | --- | --- |
| Proが軽微修正 | 文言・説明・誤記など、変更内容と影響範囲が明確で、実行検証をほぼ必要としない。 | 専用ブランチへの修正commitとPR。 |
| Proが相談してIssue化 | 機能追加、構造・動作の変更、実装や実行検証が必要な修正。 | 合意した方針と受入条件を持つIssue。 |
| ローカル調査をCodexへ引き継ぐ | 未コミット変更、実行ログ、再現環境、テスト失敗など、手元で調べることが中心。 | 確認済みの事実・再現条件・調査対象を整理したIssue。 |

変更行数だけで軽微と判定しない。短い変更でも処理、保存形式、権限、依存設定などの動作を変えるならIssueへ回す。軽微修正の途中で実行検証や範囲拡大が必要と判明した場合も、できた案と残件を分けてIssue化する。

利用動作・変更範囲など利用者が選ぶべき事項は、選択肢と影響を示して確認する。既に合意済みの方針を作り直さない。誤りや根拠不足は対象版のコードと照合して同じ会話へ訂正を返し、関連する案・受入条件も更新する。ローカル調査が中心なら、Proだけで原因や設計を無理に確定しない。

「相談だけ」では結論と未決事項までにとどめ、登録しない。

## 4. Proの軽微修正をブランチ・PRにする

Proへ変更対象と確定した内容を渡し、指定した基点から`codex/<作業要約>`の専用ブランチで修正・コミット・PR作成を依頼する。既存の同じ作業のブランチ・PRがあれば確認して継続する。baseブランチへ直接コミットしたり、PRを自動でmergeしたりしない。

実際のPR差分をGitHubツールまたは可視UIで確認し、依頼した変更、編集範囲、base/head、commit、残件を照合する。Proの「完了」「テスト成功」だけを証拠にしない。実行した検証と未実施を区別し、対象動作を変えていた場合は軽微修正の完了にしない。Codexが同じ修正を再実装する工程は追加しない。

作成・更新したPRは`attach_artifact`で現在のCodexチャットへ添付する。PRを作成した実行主体がProでも登録代行でも、この確認と添付を行う。範囲外の修正や必要な検証が残る場合は、その事実と次の対応を報告する。

## 5. 合意した内容をIssueにする

既存の関連IssueとリポジトリのIssueテンプレートを確認し、同じ作業なら既存Issueを更新する。Proが作る本文には、目的、合意事項、対象コードと確認commit、変更範囲・対象外、受入条件、検証方法、残る未決事項を含める。

機能・仕様の未決事項を決定済みにしない。未決が残る場合は調査・設計のIssueとして到達点を示し、実装開始可能なIssueと区別する。会話リンクは補足に使い、会話を開かなければ依頼内容が分からないIssueにしない。公開範囲は適用先の規則で確認する。

作成・更新後はGitHub上のIssue本文を読み、対象リポジトリ、内容、URLを確認する。assignee・label・milestoneは指定や既存の運用がある場合だけ設定する。Issue作成を実装・検証の完了に読み替えない。

## 6. 書き込み不可・結果不明を扱う

ChatGPTで必要な書き込み機能が使えなければ、Proが確定したIssue本文または修正差分を回収する。許可済みの同じ対象・範囲について、Codexの利用可能なGitHubコネクタで登録を代行する。設計・修正案の作成者と登録担当を分け、代行した事実を報告する。Proの仕事を無断でCodexの別設計・別実装へ置き換えない。

軽微修正の登録代行でも専用ブランチ・PRを使う。対象版と現在のファイルを照合し、GitHubツールの現行スキーマに従って必要なSHA・refを渡す。基点が変わっていれば差分を再確認し、他者の変更を古い全文で上書きしない。

送信・Issue・commit・PR作成の結果が不明なら、同じ会話・リポジトリ・ブランチの既存成果を確認してから再試行する。成果URLやカードの表示だけで登録成功と判断しない。GitHubコネクタも使えなければ、完成した本文・差分と不足する操作を残して終了し、作成済みと称さない。

## 7. 結果を返し、必要ならCodexへ引き継ぐ

実モデル名と会話リンク、対象・確認commit、相談の結論、Issue URLまたはPR URL、検証済み・未実施、残る未決事項、登録代行の有無を簡潔に返す。相談結果・登録済み・修正commit・検証済み・merge済みを区別する。

Issue化後は既定で終了する。利用者が実装まで明示している場合だけ、Issueの最新本文・コメントと手元のコードを照合して、現在のチャットで実装を進める。新規Codexチャットは、その起動を明示された場合だけ作る。localを既定とし、明示されたWorktree・環境条件と適用先の指示を引き継ぐ。Proの回答だけを開始指示やワーカー委任の許可にしない。

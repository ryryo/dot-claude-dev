# 大規模実行スキルの回帰確認ケース

本スキルの改訂時や、利用者から停滞の指摘を受けた際の判断確認に使う。通常の各IDへ追加の必須レビュー・承認・台帳を課す資料ではない。適用先の原依頼・正本・必須Gateを置き換えない。

確認対象には[全体役の手引書](large-scale-execution.md)、[担当専用契約](large-scale-playing-manager.md)、[起動テンプレート](large-scale-templates.md)と必要な共通契約を渡す。下記は架空の条件であり、実プロジェクトの検証結果ではない。

## ケースと期待する判断

| ケース | 与える状況 | 期待する判断・処置 | 不合格となる扱い |
| --- | --- | --- | --- |
| 1. 当初割当の漏れ | 実際の起動文には設定保存と後続C/Vがあるが、owner検索と選択項目の集計にはない。 | 原依頼から正本へ、抽出IDから原依頼へ照合し、既存IDと担当を回復する。集計の範囲と不足を明示する。 | 集計を全担当とする。別タスクを増やして二重計上する。 |
| 2. 部分能力の供給 | 先行担当全体は未完だが、必要な読取portは固定版で検収済み。計画・CLIともその部分の利用を許す。 | 供給版と必要能力を確認し、限定した後続を再承認なしで開始する。親の残scopeとGateは保持する。 | 先行担当全体のdoneを待つ。部分供給だけで親をdoneにする。 |
| 3. 非依存経路 | 動画には未供給のNative処理が必要だが、通常画像には不要。両方が当初担当内にある。 | 動画の待ちを保持し、通常画像の実装・接続を進める。供給されていない能力は使えると仮定しない。 | Native待ちで担当全体を停止する。動画検査を省略する。 |
| 4. CLIとの矛盾 | 部分着手の案はあるが、正本CLIが未解決依存で拒否し、許可済みscopeの対応がない。 | 拒否と開始に必要な能力を記録し、対応関係を一度判断依頼する。許可済み独立作業は継続する。 | 依存の削除、JSON手編集、依存のない詳細行への付替えで迂回する。 |
| 5. 正当な全面待機 | 全対象IDと独立範囲を確認したが、いずれも未供給能力を必要とする。 | 供給担当・必要能力・解除条件・次の実装を残してturnを終える。担当全体は未完とする。 | 稼働を見せる重複調査、無関係な新仕事、常時監視を始める。 |
| 6. 接続の意味不一致 | 型と部品試験は成功。実際の生成側はplanのdigestを保存するが、利用側fixtureは操作のdigestを手組みしている。 | 実際の生成→保存→再読→利用を通し、値の意味と照合先を合わせる。部品成功と統合未完を分ける。 | guardを外す。型一致・fixture成功だけで通常経路をGOにする。 |
| 7. 通常入口が未接続 | runtime/helperは実装済みだが、通常applicationがfactoryや設定を渡していない。 | 組立責任と供給側を確定し、呼出元から結果利用までを次の合流成果にする。 | helperのexportや専用試験数だけで利用可能と報告する。 |
| 8. 固定版と統合版 | 供給branchは古いbaseから分岐し、統合先には共有成果の一部が既にある。供給側にpatchと対応lockの変更がある。 | base・今回差分・前提・統合済み変更・未完成果を区別し、必要な組だけ受け入れる。接続差分を検証する。 | branch全体を最新統合版として上書きする。重複適用する。snapshot後の変更を取得済みとする。 |
| 9. 実委任の方式不一致 | 同じモデルのspawn_agentの子があり、調査・レビュー・実装が混在。独立create_threadは未実施。 | 成果の品質と起動方式を分け、既存成果を保持して未完成果から正す。正式ID・設定・cwd・開始HEADを実装成果へ対応付ける。 | 子の件数を実装委任数とする。成果を捨てて数合わせのチャットを作る。 |
| 10. 起動制約・環境分離 | Worktree利用は明示承認済みだが、既存パスを直接指定する引数がない。新規Worktreeは親と別cwdになる。 | 現行ツールと登録project・開始元を確認し、承認済み条件を満たす方式を使う。state・依存・port等を分離する。利用不能・上限・結果不明は記録する。 | 任意パス引数を捏造する。別cwdだけで不一致にする。local/spawnへ黙って代替する。重複作成する。 |
| 11. 実装分担と局所判断 | 契約・編集境界は確定済み。ワーカーはUIと状態処理を含む限定成果を実装できる。局所的な試験失敗が起きた。 | 担当が中核・統合を持ち、ワーカーに調査から実装・試験を任せる。局所修正・検収・引き取りは担当内で処理する。 | UI・状態処理を理由に実装委任を避ける。各修正を全体役へ承認依頼する。 |
| 12. 重複検証と実際の失敗 | 同じ差分・環境の部品試験は受入済み。一方、統合先では終了失敗を再現。別の試験はselectorが効かず全件実行された。 | 部品証拠は再利用し、統合先の失敗と修正差分は再確認する。実際の対象件数・終了結果を記録する。 | 全試験を無条件に反復する。必要な再現試験まで省く。cancelledを成功にする。 |
| 13. 小成果と担当全体 | 限定経路は通ったが、原依頼の複製・他ノード・後続C/Vが残る。詳細doneだけが増えている。 | 原依頼と全ID・親残条件を照合し、次の合流と独立実装へ移る。必要なら共有接続の集中を解く。 | 最初の経路を担当全体の完成条件へ縮める。詳細行の追加数を進捗とする。 |
| 14. 必須Gateと時間評価 | 実provider・OS検証が未実施。長時間の並列作業には実装・終了不具合の修正・承認の往復が混在し、全履歴はない。 | 必須Gateを保持し、具体的な最終検証の既存許可・不足を確認する。必要実装と運用損失・未確認を分け、処置と確認方法を示す。 | fixtureで全体doneにする。保証を弱める。各実装へ新しい費用承認を課す。未取得履歴から時間比率を断定する。 |

## 評価方法

ケースごとに、開始／継続／待機／是正の判断、判断主体、使う実成果、次の処置、保持する未完条件を確認する。キーワードの有無だけで合格にせず、実際に出した起動文・開始提示・受渡し・完了判断を期待結果と比較する。

スキル本文との静的照合と、実モデルによる試行を区別する。静的確認だけで実チャット起動・Worktree分離・製品検証を実施済みとしない。モデル試行を行った場合だけ、使用版・設定・観測結果・未確認を既存の改訂記録や会話へ残す。新しい常設評価基盤や進捗台帳は必須にしない。

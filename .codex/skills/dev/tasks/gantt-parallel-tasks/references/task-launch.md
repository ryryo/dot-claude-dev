# 起動時の引継ぎ

オーケストラは「起動する側の工程」を使い、作業担当へ本資料の確認済み絶対パスを渡す。作業担当は「作業担当の実行工程」から読む。共通ルールを起動文へ全文複製せず、今回固有の成果・境界・参照先を引き継ぐ。

## 起動する側の工程

1. **現担当と依存を再確認する。** 最新の`show`と関連チャットから、scope・owner・前提・競合を確認する。既存担当に重ねず、未解消の前提を持つ後工程を開始させない。
2. **起動先を確定する。** `CODEX_THREAD_ID`等でオーケストラ自身の実IDを確認し、host・workspaceを照合する。`list_projects`から対象projectIdを選ぶ。共有local checkoutを既定とし、worktreeは利用者の明示指定時だけ使う。
3. **依頼文を作る。** 下表の情報を自然な文章で渡す。既存の正本を参照し、起動のために詳細設計を完成させない。固定のタスクID・個人パス・過去のチャットIDを雛形へ保存しない。
4. **作成して確認する。** `create_thread.model`に工程3で確定したモデルID（利用者の明示指定、またはオーケストラと同じモデル）を、`thinking`に合意済みの推論値を設定する。設定が使えなければ別モデルやサブエージェントへ代替しない。正式IDで一度`wait_threads`を使い、作業ID・host・返されたタイトルと対応付ける。

| 引き継ぐ情報 | 内容 |
| --- | --- |
| 成果 | 原依頼、ガントID、提供段階・scope、今回の到達点、残す後続作業、次の一手。 |
| 境界 | 専有する責務・編集範囲、共有ファイルの担当、前提成果と解除条件、検証環境、他者差分の保護。 |
| 正本と資料 | AGENTS.md、仕様・検収条件、必要なスキル・コード・参考資料。実在する絶対パスを渡し、非公開資料は公開側のファイルへ転記しない。移植はmigration-refactorを参照する。Pro設計は根拠に応じて見直せる参考資料とする。 |
| 分担と実行設定 | 作業担当・ワーカーのモデルIDと推論値、合意した作業担当自身の実装・統合、ワーカーの成果・範囲、同時作業と後工程、各開始条件。実委任の承諾がある場合だけcodex-task-splitの実パスと合意済みのワーカーモデル・推論設定を渡す。 |
| 進捗・通信 | 正本JSON・CLI、本資料の絶対パス、一意なowner候補、オーケストラの実ID・host、既知の関係担当。利用者が許可した通信範囲と根拠、担当区分のコミット許可、個別の禁止・保留指示。 |

保留の`clientThreadId`は送信・待機先に使わない。結果不明なら一覧・履歴で同じ作業の作成有無を照合し、重複作成しない。未起動・失敗は成功分と分けて報告する。相互連絡が許可され、受け渡しに必要な場合だけ、確定した担当IDを相手へ知らせる。

## 作業担当の実行工程

作業担当はプレイングマネージャーとして、以下を自分のチャット内で完結させる。ワーカー委任の詳細は[codex-task-split](../../codex-task-split/SKILL.md)を使う。

### 1. 担当を確定する

最新の`show`、実workspace、既存差分・ownerを確認する。自分の正式IDを`--chat`に指定してCLIでclaimし、実際の着手時に`in_progress`へ更新する。オーケストラは二重claimしない。既存ownerを奪わず、移管は編集終了・引継ぎを確認してCLIのtransferで行う。

### 2. 分担して実装する

合意済みの成果と編集境界から、自分の中核実装・統合を進める。承諾されたワーカー委任は合意済みのモデル・推論設定で作業担当自身から行い、ワーカーの報告先には自分の実IDを渡す。上位のオーケストラIDを流用しない。

ワーカーと重ならない仕事があれば並行して進める。成果待ちしか残らなければ、現在の成果、待つ相手・成果、解除条件、次の一手をCLIのnoteと担当チャットへ残してturnを終える。報告を受けたturnで再開する。

### 3. 検収・統合する

[検収契約](../../codex-task-split/references/main-review.md)で実差分と証拠を確認し、修正依頼か自分への引き取りを判断する。引き取り時は編集終了を確認してから修正・検証を進める。通常の判断・修正は担当内で処理する。

### 4. ガントを更新する

担当範囲の実装・接続・必要な検証と、現在適用されるGateを満たした範囲だけCLIで完了にする。ワーカーの作業終了だけでdoneにせず、残件・未確認事項を記録する。JSONや生成Markdownを手編集しない。

### 5. コミットして報告する

次の手順で担当区分をコミットしてから、オーケストラへ完了報告する。コミット失敗などで工程が残れば、その未完と次の対応を明示する。

#### 担当区分のコミット

- [dev:simple-add](../../../simple-add/SKILL.md)を読み、作業担当がワーカー分も含めて `-m` 相当でコミットする。この運用は承認済みであり、完了時に改めて確認しない。個別のコミット禁止・保留指示を優先する。
- コミットはファイル・機能単位の大まかな作業区分でまとめる。共有ファイルの多少の混在や必要な検収済み前提は含めてよく、含めた前提を短く報告する。行ごとの所有者調査や精密なpatch再構成は不要。
- 明らかに無関係な作業や他担当の未完了実装は含めず、他者差分を戻さない。共有checkoutのstage/commitは順番を調整し、他担当のステージ済み差分を巻き込まない。必要な参照先が欠ける分割になるなら前提担当と収録範囲を調整する。
- 製品コードと非公開資料は各リポジトリでコミットする。対象なしならその旨、失敗なら実装検収結果とコミット未完を分けて報告する。pushは利用者の `-p` または明示指示がある場合だけ。オーケストラは報告済みのコミットを確認し、同じ成果を再コミットしない。

完了報告には作業ID、担当チャットID、変更範囲、検証結果、未確認・後続事項、ガント更新状況、リポジトリごとのコミット結果・push有無を含める。担当区分の許可を無関係な作業・push・公開へ広げない。

## 報告先と送信条件

起動文に記録された利用者の通信許可の範囲で、次を使う。権限がない場合はこのチャットの最終回答に報告し、許可済みと書かない。

| 報告先 | 送る内容・タイミング |
| --- | --- |
| ワーカー → 作業担当 | 委任成果の検収依頼と、作業担当の判断が必要な相談。 |
| 作業担当 → 関係する担当 | 許可された協調内の接続・共有ファイルの調整、先行成果の受け渡し。 |
| 作業担当 → オーケストラ | 担当範囲の検証・ワーカー検収・コミットまで終えた完了報告。または担当間で解けない衝突、製品契約・範囲・分担・計画の変更など、上位判断が必要な相談。 |
| 担当チャット・ガントへ記録 | 調査結果、局所修正、途中の試験、レビュー指摘、ワーカーへの修正依頼、通常の成果待ち。 |

相談は変更前に根拠・影響・推奨案・決めてほしい点を送る。完了を待つと手遅れになる相談は速やかに上げる。一方、turn終了、NO-GO、ワーカー再開だけでは上位報告の条件にならない。通常の引き取りに上位の承認や逐次報告は不要。

利用者の状況照会・報告頻度指定には従う。受領確認だけの返信や、担当内で解決した経過の上位へのコピーは不要。

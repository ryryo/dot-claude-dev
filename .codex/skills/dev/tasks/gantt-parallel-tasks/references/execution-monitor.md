# タイマー監視と同PMへの補正

限定成果群の起動元が、承諾済みの定期監視で実行の取りこぼしを回収する。各PMが実装・検収・正式化を持ち続け、監視を親の承認待ちや第二の進捗台帳にしない。原因判別と未完終了の扱いは[共通復旧手順](../../codex-task-split/references/execution-loop.md)を使う。

## 設置と引継ぎ

利用者が定期監視・異常時補正を依頼した範囲で、起動元の既存chatに対応する正規automation/heartbeatツールを使う。既存の対象・タイマーID・状態・間隔を読み、同じ対象は更新して重複作成しない。間隔は利用者指定、なければ同対象の既設定を引き継ぐ。いずれもなければ10分を初期値として伝える。文書改訂やスキル呼出しだけは設置・再開の許可にしない。

保存promptには次だけを実値で記す。過去の観測を現在状態に固定せず、毎回の手順全文や実履歴を累積させない。

- 原依頼・許可範囲、承諾済み全Task ID、同PMの正式session/thread IDとhost。
- 唯一のTask正本・実在CLI、必要な操作スキルと本書の配置先。
- 前回観測点と未解決事項の既存参照、補正の送信ID・受理記録があればその参照。
- 間隔、完了条件、通知方針、タイマー自身の識別情報、停止・本人回答待ちの対象。

設定保存、配送、実点検を区別して確認する。未対応なら監視未設置と伝え、自作cron・常駐process・別chatを代用しない。停止済み監視は、停止後の再開許可なしに復活させない。

## 各回の点検

1. 最新の本人指示と停止状態を先に確認する。本人回答待ちの対象は、実回答が来るまで補正・再開・export再試行をしない。質問の再提示や通知文更新のためのpollもしない。無関係な承諾済み担当は続行できる。
2. 初回は対象全件、その後は変化と未解決事項に絞り、fresh Taskの条件版・owner・依存・確認事項と、同PMの実イベント、turn終端、待機中の工具・子作業、成果を照合する。開始表と正規claim、必要検証、PM採否、正式化・共有までのどの工程にいるかを確認する。読めなければ未確認とし、成功を補わない。
3. 正常な工具実行・子待機はnative通知に任せる。時間経過、`running=false`、報告量、Goalのactive/completed表示だけで故障・完了としない。変化のない正常待機で催促、全試験の再演、全履歴監査、記録の更新を繰り返さない。
4. 実エラー、意図しない未完終了、工程の抜け、依頼外への脱線、証拠を伴わない完了が確認できた時だけ、下の補正を行う。通常の失敗試験をPM自身が修復中なら、その回復を妨げない。

## 異常時の補正と回収

freshな元Task・owner・実差分と失敗箇所を根拠に、同じPMへ「不足している原条件／実エラー／次に必要な最小操作」を一度返す。既成果と許可範囲を保持し、正常工程の指図、不要な製品修正や試験、追加担当は増やさない。実装前の開始表などの漏れは現在状態で補い、過去に実施済みとは記録しない。

送信前に既存の受理記録を確認する。適用先がrequest IDによる重複防止に対応する場合は固定IDと同じ本文を使い、結果不明は照会する。受理済みの補正文は周期ごとに再送しない。稼働中なら対応するsteer/queueを使い、監視のために試験・書込みを中断しない。

補正後は、送信受理、同PMの実着手、必要な成果・検証、正規Task記録と必要なcommit/push・exportを別々に回収する。受理やnote解決だけで回復済みとせず、実着手未確認ならその状態を残す。重大是正は正規reportと必要なwork referenceへ記録し、毎回のread-only点検には別台帳を作らない。

本人の明示停止・回答待ち・権限外操作は補正で解除しない。新たな本人判断が本当に必要なら、具体的な根拠と最小案を同PMが既存の質問・停止手順で示す。既存権限内の通常修正に親GOを追加しない。completeのGoalをresumeする代用操作や、無断の担当交代・共有サービス再起動はしない。

## 終了と通知

正常継続と変化なしは静かに終了する。完了、重要な是正、重大失敗、本人判断が必要な時だけ、確認できた結果と残件を短く通知する。

承諾済み全対象の原条件と必要な正式化・所有成果の共有を確認した時、または本人の監視停止指示時に、正規ツールで対象タイマーを停止・削除し結果を確認する。一担当の完了、部分採用、本人回答待ち、共有未完では監視全体を完了扱いしない。停止指示は作業完了の意味にせず、未完の担当・再開条件を保持する。

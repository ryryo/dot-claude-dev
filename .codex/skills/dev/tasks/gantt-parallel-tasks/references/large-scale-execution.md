# 大規模実行の手引書

複数タスクを担当区分ごとにまとめ、各プレイングマネージャーが区分全体を継続して進める場合に使う。利用者が大規模運用を明示した範囲へ適用する。

[本スキル](../SKILL.md)と[通常の起動・実行契約](task-launch.md)の権限、モデル設定、担当移管、検収、コミット、通信条件を共通契約として使う。本書は事前計画の引継ぎと担当内の計画・継続手順を補う。提案依頼は計画提示までとし、実行には開始指示が必要である。

本書は事前検討と全体役向けの手引書である。プレイングマネージャーには[専用の実行契約](large-scale-playing-manager.md)を直接渡す。起動文を作る際は[テンプレート](large-scale-templates.md)を使う。

## 1. 事前の壁打ち・計画合意

利用者と事前検討するチャットで、次を整理する。既に合意済みの計画があれば参照し、未決事項だけを扱う。

| 計画に残す情報 | 内容 |
| --- | --- |
| 原依頼と到達点 | 何を完成させるか、対象段階・範囲、既存の検収条件。 |
| 担当区分と全対象ID | 初回作業と後続作業、実装・接続・検証の責任、区分全体の完了条件。 |
| 順序・依存 | 合意した実行順、並行可能な作業、先行成果・解除条件、区分間の受渡し。 |
| 専有・共有責任 | 編集範囲、共有契約・ファイルの所有者、共通成果の受入・統合先。 |
| 実行設定と許可 | 各役割のモデル・推論、起動方式・開始元・環境分離、ワーカー委任と通信の許可範囲。 |
| 正本と根拠 | ガント・進捗の正本、CLI、仕様・設計・検証資料、計画の合意根拠・未決事項。 |

全体役1体、複数プレイングマネージャー、必要なワーカーの構成とする。担当数は作業の責務・依存から決め、固定しない。計画を作るチャットは実行上の追加階層にしない。同じチャットが実行役を続ける場合も、この役割の区別は保つ。

計画合意では、各担当が中核の設計・実装・統合を持ち、許可された担当範囲内で具体的なワーカー成果を切り出せるかを明示する。全体役が後続全タスクの個別Luna成果を先に決めることを開始条件にしない。

必要な設計検証を行い、合意済み計画と根拠をプロジェクト指定の保存先へ記録する。Pro検証は依頼や必要性に応じて利用し、必須にはしない。非公開資料の配置は適用先の規則に従う。計画は既存ID・正本を参照し、別の進捗台帳を作らない。

**この工程の成果は、実行役へ引き継げる合意済み計画である。** 合意前の案を実行指示として渡さない。

## 2. 合意済み計画を実行役へ引き継ぐ

全体役は、計画の参照先・合意根拠と担当区分全体を受け取る。計画を最初から作り直さず、本スキル工程1〜2で最新の正本・owner・依存を照合する。計画と現在の条件が食い違う部分だけを整理し、必要な範囲変更・製品判断を戻す。

[起動時の引継ぎ](task-launch.md#起動する側の工程)に沿って担当を起動する。その際、各担当に次を追加して渡す。

- 大規模実行モードであること、プレイングマネージャー専用契約と共通契約の確認済み絶対パス。専用契約を最初に読む指定。
- 初回作業だけでなく、後続を含む全対象IDと担当区分全体の到達点。
- 合意した順序・依存・共有責任、正本と計画の参照先、実行・通信の許可範囲。
- 最初に担当ガントを示し、各IDの開始・終了・次への移行を専用契約に従って提示し、自律実行すること。

localを既定とし、明示・合意済みのWorktree指定と開始元を対象の起動・再開へ引き継ぐ。Worktreeでは適用先の環境手順で製品コード・依存・制作state・検証環境を分離する。共有する正本・資料と、生成・stage・commitの調整方法を区別して渡す。環境分離は設計上の依存の解消を代替しない。

正式ID・実workspace・開始基点と開始状況を確認する。各担当の初回ガント・分担表も確認対象とし、起動成功だけで実行計画が成立したと判断しない。合意済み範囲内の着手に全体役の確認待ちは要求しない。

## 3. 担当専用契約へ引き継ぐ

担当の初動、各IDの開始・終了・移行、中断・再開は[プレイングマネージャー専用契約](large-scale-playing-manager.md)を正本とする。担当の起動文には、このファイルを最初に読むことと、初回・後続を含む担当区分全体を記録する。

全体役は担当ガントと初回の開始提示を確認し、区分全体が引き継がれているかを照合する。担当内の具体的なLuna成果・中核実装の決め方は担当に任せ、確認の受領返信だけで再起動しない。

## 4. 各IDの開始・終了・移行を扱う

専用契約では、開始前の5列の分担表、終了時の検収・正本更新・コミット・残件、次IDの選定と開始条件の再確認を定める。各提示は担当自身のチャットへ行い、全体役への送信は[共通の送信条件](task-launch.md#報告先と送信条件)に従う。

全体役は、共有成果の受渡しや判断相談をこのIDと進行状況へ対応付ける。部分成果、待機、区分全体の完了を区別し、担当内で閉じる終了処理や次ID選定の承認者にはならない。

## 5. 継続・待機・再開を扱う

担当は専用契約の開始・終了・移行を繰り返し、実行可能なIDがなければ待機条件を残してturnを終える。再開時に読む専用契約の参照先、現在のID・工程・次の一手は既存noteと担当チャットへ残す。

全体役は必要な受入済み成果・判断を返し、通常の待機を引き取らない。常時ポーリングや監視automationを追加しない。

## 6. 全体統合と完了判断

全体役は受入済み成果の受渡し・統合、系統間の接続、計画全体の到達点を確認する。各担当の局所判断・ワーカー検収・修正を逐次中継せず、担当間で解けない衝突、共有契約・範囲・分担・計画の変更を扱う。

区分全体の完了報告には、全対象IDの結果、区分の到達点、実装・接続・検証の根拠、受渡し・統合先、正本の更新、コミット結果を含める。必須残件や未確認がある場合は部分成果と未完を区別し、既存の受入条件・Gateを緩めない。全体役は区分の完了と全体の統合検収を区別して判断する。

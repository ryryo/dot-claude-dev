# 大規模実行の手引書

複数タスクを担当区分ごとにまとめ、各プレイングマネージャーが区分全体を継続して進める場合に使う。利用者が大規模運用を明示した範囲へ適用する。

[本スキル](../SKILL.md)と[通常の起動・実行契約](task-launch.md)の権限、モデル設定、担当移管、検収、コミット、通信条件を共通契約として使う。提案依頼は計画提示までとし、実行には開始指示が必要である。

本書は事前検討と全体役向けの手引書である。担当には[プレイングマネージャー専用契約](large-scale-playing-manager.md)を直接渡す。起動文には[テンプレート](large-scale-templates.md)を使い、共通契約の全文を複製しない。

## 1. 事前の壁打ち・計画合意

利用者と事前検討するチャットで次を整理する。既に合意済みなら既存計画を使い、不足・変更点だけを扱う。

| 計画に残す情報 | 内容 |
| --- | --- |
| 原依頼と到達点 | 対象段階・範囲、何を完成させるか、既存の検収条件。 |
| 担当区分と全対象ID | 初回・後続・引継ぎ、実装・接続・検証の責任、区分全体の完了条件。 |
| 順序・依存 | 合意した順序、並行可能な作業、必要な能力と解除条件、供給担当・利用担当。 |
| 専有・共有責任 | 中核実装、共有契約・ファイルの所有者、通常入口への組立て、共通成果の統合先。 |
| 次の合流成果 | 通常の利用経路で何をつなぐか、各担当が供給する実装、利用側の呼出元と接続検証の担当。 |
| 実行設定と許可 | 役割別モデル・推論、起動方式・開始元・環境分離、ワーカー委任・通信・コミットの範囲。 |
| 正本と根拠 | 正本JSON・CLI、仕様・検証資料、計画の合意根拠・未決事項。 |

全体役1体、複数プレイングマネージャー、必要なワーカーの構成とする。担当数は責務・依存から決め、固定しない。事前検討チャットを実行上の追加階層にしない。

**担当全体は原依頼から照合する。** 原依頼・実際に送った起動文の各責務を正本のIDへ対応付け、逆に抽出したIDがどの責務に属するかも確認する。初回だけ、readyだけ、現在のownerだけ、選択した項目の集計だけで全割当としない。設定・通常入口・保存・後続C/Vなどの付帯責務、旧担当からの未完引継ぎも含める。集計には選択範囲・除外・未確認を付ける。漏れた既存責務は元IDへ対応させ、別タスクとして二重計上しない。既存ownerの移管は共通契約に従う。

全体役は、共有する値の意味、設定・資格情報・費用等の供給と検証の責任、共通ファイル・通常入口の組立担当、統合先・受渡し条件を必要な範囲で一度決める。各担当の内部構成や後続全タスクの個別ワーカー成果まで先に決めることを開始条件にしない。

合流成果は、複数担当の前提を解除する通常経路を優先する。部品の存在・export・型一致だけを合流にせず、実際の生成側と利用側をつなぐ。最初の限定経路は後続を進めるための成果であり、原依頼全体の完成条件を置き換えない。実providerやNative処理など一部経路の未完を、非依存の経路の一律停止理由にしない。

必要な設計検証を行い、合意済み計画と根拠を適用先の保存先へ残す。Pro検証は必要性に応じて使い、必須にしない。非公開資料の配置規則を守り、既存ID・正本を参照して別の進捗台帳を作らない。合意前の案を実行指示として渡さない。

## 2. 合意済み計画を実行役へ引き継ぐ

全体役は計画・合意根拠・原依頼と担当区分全体を受け取り、本スキル工程1〜2で最新正本・owner・依存を照合する。作り直すのは食い違う部分だけとし、必要な範囲変更・製品判断を利用者へ戻す。

[起動時の引継ぎ](task-launch.md#起動する側の工程)に沿い、各担当へ次を渡す。

- 大規模モード、専用契約と共通契約の確認済み絶対パス。専用契約を最初に読む指定。
- 初回・後続を含む全対象IDと到達点、原依頼との対応、引継ぐ成果と未完条件。
- 合意した順序・必要能力・共有責任、次の合流成果と自担当の供給先、正本と計画の参照先。
- 実行・委任・通信・コミットの許可範囲。担当ガントと最初の分担を示した後、範囲内で継続すること。

localを既定とし、明示・合意済みのWorktree指定と開始元を、その許可対象である担当・ワーカーの起動へ引き継ぐ。親がWorktreeにいるだけでワーカーへの許可を補わない。製品コード・依存・生成物・制作state・port・registry・検証環境を適用先の手順で分離し、共有正本・資料とstage/commitの調整方法を区別する。環境分離は設計上の依存の解消ではない。

正式ID・実workspace・開始基点・モデル設定と初回ガントを確認する。起動成功だけで計画成立とせず、初回IDだけの引継ぎや責務漏れはここで訂正する。承諾済み範囲の実着手を全体役の受領返信待ちにしない。

## 3. 担当専用契約へ引き継ぐ

初動・各IDの開始／終了／移行・依存判定・再開は[専用契約](large-scale-playing-manager.md)を正本とする。担当は中核実装・統合・検収を持ち、具体的なワーカー成果を切り出す。全体役は個々の委任・局所修正・次ID選定を逐次承認しない。

独立ワーカーは[codex-task-split](../../codex-task-split/SKILL.md)の起動契約を使う。モデル名や子の件数だけで実委任と判定せず、成果・正式thread ID・起動方式・モデル／推論・実workspace・開始基点が対応していることを確認する。調査・レビューと実装、起動失敗を区別する。方式の不一致を発見しても、有効な既存成果は保持し、未完成果から正す。数合わせの再起動・同じ調査の再実行・中核の丸投げはしない。

## 4. 各IDの開始・終了・移行を扱う

担当の開始5列表と終了・移行の提示は担当自身のチャットへ残す。全体役への送信は[共通の送信条件](task-launch.md#報告先と送信条件)と専用契約の判断範囲で分類する。

共有成果は、どの親IDの残条件を減らすか、誰がどの呼出元から使うかを対応付ける。局所部品だけが増え、利用側への接続が進まない場合は、次の合流成果と編集境界を見直す。一つの担当へ共通接続が集中したら、全体役は共有境界・供給順の詰まりを解き、他担当が閉じられる実装を独立させる。全体役自身が細かな実装調整を抱え込まない。

部品を受け取るために担当全体の完了を待たない。検収済み部分供給で開始できるかは、専用契約の依存判定を使う。親の依存・必須Gateの削除、詳細doneから親doneへの読み替え、受入前のsnapshotを完成済みとして配る方法で進捗を作らない。

## 5. 継続・待機・再開を扱う

担当は実行可能なID・許可済みの独立範囲を選び、存在しなければ待機条件を残してturnを終える。全体役は必要な受入済み成果と共有判断を返すが、通常の成果待ちを代行しない。

供給時の連絡には、供給元の固定版・前提・検収範囲、利用側のID・呼出元、解除する条件、残る条件を短く含める。受け手は新しい成果・判断が届いたturnで差分を照合して再開し、同じ承認を取り直さない。受領通知だけで相互に再起動しない。常時ポーリング・監視automation・新しい待機台帳を追加しない。

全実行可能作業が正当に止まっていれば、待機を認める。稼働を見せるための重複調査・不要な仕事は作らず、不足する成果の供給担当が曖昧な場合だけ全体役が割り当てを解く。

## 6. 全体統合と完了判断

### 固定成果の受入と接続検証

受入は[検収契約](../../codex-task-split/references/main-review.md)を使う。供給元のbase・固定commit／差分と統合先の現行版を比較し、採用済み成果、必要な前提、今回差分、他担当の未完成果を区別する。branch全体を最新統合版とせず、受入済み変更を重複適用・再コミットしない。必要なpatchとlockなど一組の変更は揃えるが、行ごとの過剰な所有者調査はしない。

部品試験とは別に、実際の生成側から保存・再読・利用側へ通す接続確認を行う。手組みfixtureが生成側と異なる値を使っていないか、ID・digest・版・認可・資源寿命の意味を両端で照合する。型が同じでも意味が異なる場合は、guardを外して通さず正しい対象へ照合する。通常の呼出元・設定供給・結果利用まで未接続なら、helperの実装や専用試験成功と分けて残す。

検証は変更範囲に応じて選ぶ。同じ差分・依存・環境・判定対象の証拠と独立レビューは再利用し、不足・疑義・統合による変化・再現した失敗を追加確認する。全体役も全試験・全画面を一律に再演しない。ただし、適用先の必須CI・Gateは維持する。コマンドのselectorと実際の対象件数・終了結果を照合し、絞込み失敗やcancelled／skipを成功へ読み替えない。

### 担当全体と全体統合の完了

原依頼・実際の起動文から全対象IDを再照合し、正本のscope・必須Gate、受入コード、通常利用経路、検証証拠、受渡し・統合先が対応するか確認する。初回の限定経路や詳細行のdoneは、区分全体の代わりにしない。作業完了、供給可能、統合先での接続済み、必須検証までの完了を説明上区別し、独自statusは追加しない。

必須の実provider・OS・配布等が未実施なら未完として残す。必要な権限・費用は、その具体的な検証工程で既存承認の適用範囲を確認し、不足する許可だけを求める。これを一般の実装の逐次承認や新しい恒常的な承認制度へ広げない。仕様・費用・保持・復旧保証を弱める提案を、実装上の都合で合意済みとしない。

## 7. 停滞を是正し、効果を確認する

状況照会・停滞・共有成果の受入時には、各担当だけでなく全体役自身の統合・再検証・連絡も対象にする。正本と必要な履歴から、実装・必要な検証、正当な依存待ち、再承認の往復、重複検証、局所成果への偏りを分ける。経過時間から工数比率を推定せず、並列作業時間を単純加算しない。未取得の履歴は未確認とする。

利用者には**結論・根拠・具体的な処置・処置を持つ担当・改善の確認方法**をセットで返す。「契約に従う」「ワーカーを起動する」だけで終えず、次の実装成果・編集境界・供給先・開始／終了／移行条件を示す。

是正後は次の受渡しで、通常経路の未接続と元の残条件が実際に減ったか、供給を受けた担当が再承認なしに次工程へ進んだか、委任が実装成果として成立したかを確認する。チャット数・詳細done数だけを改善指標にせず、専用監視や追加台帳は作らない。

本スキルの改訂や停滞時の点検には[回帰確認ケース](large-scale-review-cases.md)を使える。通常の各作業に追加の必須レビュー工程として課さない。

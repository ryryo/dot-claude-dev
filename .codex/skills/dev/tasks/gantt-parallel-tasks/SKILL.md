# ガントの限定タスクを分担する

オーケストラは今回の成果群の選定・順序・起動を担当する。起動後は各タスクchatのPMとそのワーカーで完結し、PMが設計・中核実装・ワーカーの回収と修正・統合・最終検収・許可済みの正式化・進捗更新を持つ。通常の判断、試験開始、採用、commit・pushに親のGOや再検収を挟まない。ワーカーを使わない作業はPM自身が完遂する。

近い複数IDを一担当へまとめてよい。一タスク一chatの指定があればそれに従う。多数IDをカテゴリ別に管理する継続開発は[gantt-development-orchestrator](../gantt-development-orchestrator/SKILL.md)を使い、作業数だけで切り替えない。

提案依頼やスキル名だけの呼出しは工程4まで。開始が承諾されていれば工程5へ進む。許可、実モデル、環境、CLI・Git操作は[共通実行条件](../codex-task-split/references/execution-context.md)に従う。通常実行のために大規模資料を読み込む必要はない。

計画外の危険や本人判断が必要な事象には、[選択肢UIと完全停止](../codex-task-split/references/execution-loop.md#5-ユーザー判断の選択肢uiと完全停止)を適用する。該当タスクのPMと全ワーカーを止め、本人の明示回答まで独立工程も進めない。親やheartbeatはその停止を解除せず、通常の自律実行よりこの停止条件を優先する。

## 1. 現在地を読む

AGENTSと進捗ツールのREADME・helpから唯一の正本と更新手順を確認する。実在するread-only操作で、最新revision、依頼内の元ID・body/check・必要level、状態、owner、依存理由を読む。正本読取りのためにブラウザーやserverを起動しない。

ready一覧だけで依頼範囲を作らず、原依頼と進行中・再開待ちのIDを照合する。必要な実thread、コード、HEAD、index、WIP、untrackedから既存担当・未回収・採用済み成果を確認する。idleは所有解放ではない。読めない現物は未確認とする。

## 2. 成果・依存・編集境界で選ぶ

今回使う能力、CLIの開始条件、権限が成立し、編集・共有仕様・検証資源を分離できる工程を並列候補にする。新規の供給待ち候補は起動せず、既に待機中の担当や未回収成果は未完WIPとして保持する。既存担当がいる範囲へ別担当を重ねない。

合意済みの型や署名を使う独立TDDと、実能力を使う通常接続は分ける。実接続には受取版での実装、認可、資源寿命、環境が必要であり、fixtureや供給予定、CLIの形式依存通過だけで成立とはしない。共有型、DB、package・lock、試験資源は担当と順番を定める。

供給不足・未担当・循環・CLI拒否があれば[原因判別と再開手順](../codex-task-split/references/execution-loop.md#1-現物と次の判別点を結ぶ)を使う。依存削除、偽done、依存なし詳細への付替えはしない。独立した依頼内作業は進めても、待機したIDの責任は残す。

## 3. 担当とモデルを提案する

[codex-task-splitの分担基準](../codex-task-split/SKILL.md#1-成果と実装の担当を決める)で、担当自身の中核実装とワーカーの成果を分ける。並行作業と回収後の統合を区別し、小作業にワーカーを必須化しない。全後続工程の詳細設計を起動前提にしない。

モデル・推論・方式は既指定と実hostの対応を優先する。行数をchat数にせず、仮日程から工数や納期を推測しない。

## 4. 利用者へ示す

推奨する組合せを先に示し、[通常担当の5列表](references/task-launch.md#起動文)を使う。対象段階とrevision、編集範囲、並行・後工程、必要な能力、検収方法と工程終了条件を添える。設計GO、独立開発の開始、通常利用可能を区別する。候補がなければ解除条件を示し、提案のみならここで終える。

## 5. 承諾済み担当を起動・実行する

[起動入力と実行本文](references/task-launch.md)を使って起動し、正式thread ID、実設定、cwd、HEAD、開始提示とCLI着手を確認する。結果不明は照会し、重複作成しない。担当は実装・必要な委任・回収・自己検収・正式化まで進める。

## 6. 完了結果を確認して区切る

PMは自分のワーカーだけを[main-review](../codex-task-split/references/main-review.md#1-回収と再開)で回収・検収する。独立タスクPMの成果を親の検収待ちワーカー成果へ読み替えない。PM自身が元条件と証拠を照合し、必要な検証・正式化・CLI更新まで終える。

親への通常連絡は終了点に達した時の短い報告一度とし、元ID、採用commit、重要な検証結果、CLIの完了判定、残件があれば不足と担当・次工程を示す。自chatの最終回答を親が読み取る方式なら別送信は不要。途中相談は本人にしか決められないscope・費用・権限と、PM間で解けない実際の所有衝突に限る。試験や共有操作の実衝突は関係担当と必要な箇所だけ調整し、通常の実況・ACK・親の窓割当を増やさない。

親は完了報告と唯一の進捗正本から終了点・空き枠を確認し、承諾済みの次タスクを配置する。未完の元IDを待機で終える場合は、[共通工程本文](../codex-task-split/references/execution-loop.md#起動文へ展開する工程本文)と適用先CLIに従った現在の保留通知を現PMが登録・読取確認したかも照合する。登録漏れを他ownerで更新せず、本人回答待ちへ続行送信や再委譲をしない。completed表示だけで元ID完了にせず、未完の正式化や同IDの残工程は現PMの責任に残す。親による一律の再レビュー・試験再演・commit代行は行わない。許可済みのheartbeatも結果確認と次タスク配置に使い、逐次指揮へ戻さない。

全承諾済み成果群の原条件・必要levelと必要な正式化を確認して終了する。部分成果や一IDの完了を依頼全体の終了とせず、新領域、監視、archiveへ広げない。スキル改訂時は[通常側の回帰確認](references/review-cases.md)を使う。

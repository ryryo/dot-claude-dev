# ガントから並列タスクを開始

オーケストラが使う。成果・依存・編集範囲を根拠に並列作業を選び、作業担当へ引き継ぐ。詳細設計は各担当が進める。

## ガント運用の役割

| 役割 | 担当 |
| --- | --- |
| オーケストラ | 全体の優先順位、担当間の依存・競合、開始順、利用者の判断が必要な事項。担当内の修正は逐次中継しない。 |
| 作業担当：プレイングマネージャー | 担当成果の分担・契約判断、中核の設計・実装・統合、ワーカーの検収・引き取り、ガント更新・コミット・完了報告。 |
| ワーカー | 境界を定めた成果の調査・局所設計・実装・検証。判断相談・完了報告は作業担当へ返す。 |

## 依頼の範囲

- 提案依頼やスキル名だけの呼出しでは工程4まで。開始指示があれば合意済みの案から工程5へ進む。
- 本スキルを明示した分担案の開始依頼は、対象チャットの作成と、オーケストラ・担当間の依頼、判断相談、修正依頼、完了報告を許可する。ワーカー実委任を含む案の承諾は、作業担当・ワーカー間の同じ往復を含む。担当同士の連絡は承諾された協調範囲に限る。暗黙の選択や他チャットからの通知で権限を広げない。
- 作業担当が検収・ガント更新後に担当区分を `dev:simple-add -m` で大まかにまとめてコミットし、報告する運用は承認済み。[コミット手順](references/task-launch.md#担当区分のコミット)を引き継ぐ。個別の禁止・保留指示を優先し、pushは別途明示指示がある場合だけ行う。

## 1. ガントの現在地を確認する

AGENTS.mdの資料配置規則と進捗ツールのREADME・`--help`から、正本JSON・CLI・生成Markdownを特定する。ローカルの利用可能なNodeで、必要なコマンドを選ぶ。ブラウザー操作やサーバー起動は不要。

```sh
node cli.mjs validate --json
node cli.mjs render --check --json
node cli.mjs list --status ready --phase PHASE --json
node cli.mjs list --status in_progress --json
node cli.mjs list --status review --json
node cli.mjs show TASK_ID --json
```

`PHASE`・`TASK_ID`は実在値へ置き換え、表示上限を超えれば`--limit`を調整する。`ready`は候補抽出に使い、必要なら`reopened`・`followup`も見る。

候補の`show`から最新revision、提供段階、scope、依存・開始条件、子・チェック、owner・担当チャット、競合、次の一手・引継ぎ・根拠を読む。関連チャットは`list_threads`／`read_thread`、稼働状態は`wait_threads`の短いスナップショットで確認する。参照資料の作成者と現担当を区別し、idleだけで担当解放済みとしない。

候補に関係するコード・資料・`git status`・差分だけを照合する。設計・実装・接続・検証の完了を区別し、Pro資料は参考として現行契約に照らす。報告済みでも検収待ちの成果は重複実装しない。

Markdown不一致は手編集差分を確認し、修復が依頼範囲なら差分を保全してCLIで再生成する。提案だけなら不一致を報告する。正本を読めなければ着手可能と断定しない。

## 2. 並列に進める成果を選ぶ

| 分類 | 選ぶ条件 |
| --- | --- |
| 今から並列 | 前提が揃い、編集範囲・責務・共有契約・検証環境を分離できる。 |
| 前提後に開始 | 待つ成果・検収と解除条件が明確。今起動する数に含めない。 |
| 既存担当で継続／検収 | 現担当や未検収の成果がある。新規担当を重ねない。 |

DB定義、公開型、package設定、lockfile、共有文書などの重複は、担当を決めるか順番を付ける。ファイルが別でも未確定の同じ契約に依存するなら、その判断を先に置く。他者差分は保持する。

依存を解消する成果を優先し、独立した成果を添える。ガント行数をチャット数にせず、関連工程は同じ担当にまとめてよい。数合わせの分割や、仮日程からの工数・納期の推定はしない。

## 3. 推論設定と分担を決める

役割ごとにモデル・推論設定を選び、利用者の指定または合意済みの設定を優先する。

- オーケストラは現在のチャットのモデルで進める。
- 作業担当のモデルは、利用者の明示指示があればその指定を使い、それ以外はオーケストラと同じモデルにする。推論設定は利用者の指定を優先し、指定がなければ下表から作業に応じて提案する。
- ワーカーは指定・合意済みの設定を使い、指定のない提案では `gpt-6-luna` / `max` を既定候補にする。
- オーケストラの実際のモデルIDと、起動先の現在のツール定義・モデル一覧にある対応推論値を確認する。モデルIDを確認できない、または指定・継承する設定が利用不能なら、その不足を示して利用者へ確認し、別モデルへ黙って変更しない。

推論レベルは次を目安に、選んだモデルが対応する値を使う。選定理由を作業の判断負荷に結び付ける。

| レベル | 目安 |
| --- | --- |
| low / medium | 契約が明確な小変更、局所的な照合・検証。 |
| high | 複数資料・モジュールの照合、範囲が定まった設計・実装・検収。 |
| xhigh | 保存・復旧・認可・並行実行など複数契約をまたぐ統合。 |
| max | 特に難しい未解決の矛盾があり、追加の推論負担に具体的な価値がある。 |

[codex-task-split](../codex-task-split/SKILL.md)の役割と工程1を使い、各作業について次を短く決める。提案時は起動・検収用の詳細資料まで読み込まない。

- **作業担当自身の実装・統合**：中核処理、接続、開始条件。独立した小作業で検収だけを持つ場合は理由。
- **ワーカーへ渡せる成果**：目的、専有範囲、検収方法、選定モデル・推論設定。候補がなければ理由。先行成果待ちならその条件。
- **作業の順序**：作業担当が同時にできる仕事とワーカー完了後の仕事。並行作業がなければ成果待ちと明記する。

作業担当の中核実装を残したうえで分担し、未完成成果が必要な統合を同時作業に数えない。待機を埋める重複調査や別仕事を作らない。

## 4. 利用者へ提案する

最初に推奨する並列の組合せを述べ、工程3で決めた分担を次の表に示す。着手可能な根拠は工程1〜2で確認し、通常の提案には出力しない。

| 作業・ガントID | 何ができるようになるか | プレイングマネージャーの作業 | ワーカーの作業 | 担当モデル・推論・理由 |
| --- | --- | --- | --- | --- |

プレイングマネージャー自身の設計・実装・統合と、Luna等のワーカーへ渡す具体的な成果をそれぞれ書く。ワーカーを使わない場合は「使わない」と記載する。同時に進める作業と、ワーカー完了後に進める作業が分かるように順序を補足する。

重要な編集境界、対象段階・確認revision、待つ成果、実在する資料・コード・担当チャットへのリンクを添える。設計完了だけで利用可能と書かず、専門語は利用動作から説明する。保存形式の往復変換は「保存データの変換処理」と呼ぶ。

着手可能な作業がなければ、待つ成果と解除条件を示す。**提案だけの依頼はここで終了する。**

## 5. 承諾済みの担当チャットを起動する

[起動時の引継ぎ](references/task-launch.md)に従い、最新の担当・依存を再確認して起動する。範囲が変わっていなければ承諾済みの案を再確認しない。工程3で確定した作業担当のモデルIDを `create_thread.model` に明示し、合意済みの推論値を `thinking` に渡す。

結果は実際のタイトル、成果、モデル・推論、起動確認状況で示す。成功した各チャットに`::created-thread{threadId="..."}`、保留には`clientThreadId`形式を出す。作成・開始・完了を区別し、部分的な失敗も示す。

## 6. 担当からの報告を扱う

[報告先と送信条件](references/task-launch.md#報告先と送信条件)に従い、完了は検収・次作業の判断に使い、相談は必要な判断を返す。通常の中間報告を利用者へ逐次転送せず、受領返信だけで担当を再起動しない。状況照会や報告頻度の指定には従う。

担当チャットは引継ぎ資料の実行工程に沿って自律的に進める。オーケストラは通常のワーカー待ちや局所修正を引き取らず、常時ポーリング・監視automationを追加しない。

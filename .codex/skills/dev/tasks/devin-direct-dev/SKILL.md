# CodexとDevinの対話型開発

CodexとDevinが直接対話しながら、指定された作業を進める。Codexは目的と受入条件を伝え、Devinの質問に答え、実際の成果をレビューする。不備があれば同じセッションへ修正を依頼し、利用者が指定した終了点まで進める。Devinは指定範囲の実装を担い、最終レビューはCodexが行う。

接続にはMCPまたはCLIを使い、CodexからDevinのWeb画面を操作しない。製品の受入条件に必要なPlaywright等の試験や、DevinのVM内でのGUI検証は行える。

## 実行場所と経路を選ぶ

公式が説明する用途と本スキルでの使い分けは、[MCPとCLIの比較](references/transport-selection.md)を参照する。PRの有無、行数、作業規模だけで接続方法を決めない。

| 今回必要なこと | 経路 |
| --- | --- |
| Cloudの独立VMで調査・実装し、Codexが状態と回答を構造化して取得する | **公式Devin MCPを既定**とする。複数repoや広い改修でも、Cloudで実行可能ならこの経路でよい |
| 未pushのファイル、手元の依存・プロセス・端末環境を直接扱う | **ローカルDevin CLI**。編集先を決め、Codexと同じファイルを同時に編集しない |
| Cloudを使いたいが現在のMCPの機能・前提・認証で操作できない、またはCLI指定 | **`devin --cloud`**。ローカル実行へ変更せず同じCloudセッションを再開する |

MCPで進める際は[接続と回答の取得](../devin-browser-pr/references/mcp-and-resume.md)を読む。CLIを使う際だけ[CLIの対話と再開](references/cli-workflow.md)を読む。PRレビュー・採用や環境設定が必要になったら、[成果のレビューと採用](references/review-and-adoption.md)を読む。

## 許可と作業範囲

- 対象と目的を指定したDevinへの委譲依頼は、依頼送信と範囲内の質問・修正の往復を含む。PRまで、採用まで、ローカル編集まで等、指定された終了点を守る。採用まで許可されていれば必要条件を満たすマージ・関連環境提案の採用を毎回確認し直さない。相談・スキル作成だけの依頼では実装ジョブを起動しない。
- 接続方法を選んだだけで、未commitファイルのCloudへの送信、作業場所の変更、権限の拡大が許可されたとは扱わない。対象外の改修、未決の製品仕様、新しい課金契約や資格情報、破壊的操作は、元の依頼でどこまで許可されているかを確認する。
- 本スキルから他のCodexチャットやサブエージェントを増やさず、Devinにも再委譲させない。常設プロセス、hook、定期監視は別途依頼された場合だけ設定する。
- API/CLIで実行や確認ができない工程は、不足する機能と確認済みの成果を記録する。その工程に依存しない作業は続け、ブラウザ操作へ無断で切り替えない。Codexのレビューで条件を満たせるか、Devin Review等が必須かは元の作業条件から判断する。

## 対象を確定して依頼する

対象リポジトリと実行ディレクトリ、baseと確認commit、参照するリポジトリ、編集範囲、既存PRと作業途中の変更、維持する仕様、受入条件を確認する。AGENTS.md・README・セットアップ・呼出元と必要な設計を読む。製品固有の役割・モデル制約を優先する。Devinが使うモデルや推論設定を確認できない場合は、未確認と記す。

CloudのDevinはremoteのコードを読む。手元の未commit変更を反映済みと扱わず、委譲のためだけに他者の変更をまとめてcommit・stash・resetしない。共有スキルや隣接リポジトリは、Cloudで取得・配置できたか、リンク先を読めるかを確認する。ローカルCLIでは開発契約で指定された作業場所を保ち、共有branchの切替やworktree作成を勝手に行わない。

[依頼の雛形](../devin-browser-pr/references/task-prompts.md)から、今回必要な箇所だけを使う。画面での確認を前提とする文言は、API/CLIで取得できる証拠に合わせて直す。調査だけなら編集・PRを除き、ローカル作業ならVMの代わりに実ディレクトリと未commit差分の扱いを伝える。

最初の依頼には、Devinが質問してよい内容と、利用者への確認が必要な判断を明記する。編集先・対象外、試験に使う資源、終了点、返す証拠も伝える。固定された依存と既存の試験用ランナーを使わせ、環境の問題を製品版やlockfileの不要変更で回避させない。

Cloudでの成果は、専用`codex/`branchへの保存とPR作成までをDevinの担当とする。自己merge・baseへの直接push・deployは依頼しない。ローカルではリポジトリの開発契約に従い、Codexが担当範囲の差分を確認して正式化する。

## 対話を進める

1. 既存セッションが指定されていれば最新の状態・履歴・最後の指示を取得して継続する。独立した新規作業だけ新規セッションにし、返却ID/URL、実行場所、最後のメッセージやcursorを既存の作業記録へ残す。
2. 作業中なら必要な完了待ちを行う。入力待ちなら質問全文・対象版・既に決まった作業条件を読む。通常の実装判断や修正はCodexが答える。依頼文や過去の成功を、最新の成果と扱わない。
3. 失敗やレビュー指摘は、対象head、症状、コード・仕様の根拠、期待する結果、影響する検証をまとめて同じセッションへ返す。送信結果が不明なら履歴やセッション検索で確認し、別の接続方法で二重送信・二重作成しない。
4. 回答にPR、commit、パス、検証結果が出たら、実物を取得する。必要な差分だけを再レビューし、範囲内の不備は同じ成果を修正させる。報告を受け取っただけで終えず、作業完了か、解消に利用者の判断が必要な具体的な問題が残るまで進める。

MCPの待機には、待ち時間を60秒以内に指定したgatherを使う。CLIの長い処理は、実行ツールのsession IDを保持して出力の続きを取得する。`finished`、プロセスのexit 0、PR登録、採用、元IDの完了は、それぞれ確認する。Codexのターン終了後に自動で再開すると保証せず、依頼されていないタイマーを追加しない。

## レビューして結果を採用する

Devinの回答とは別に、GitHubのbase/head・実際のdiff・関連コード・必要な検証・必須チェックを`gh`/`git`等で照合する。PRは現在のチャットへ添付する。保存・権限・並行処理・資源の寿命・移植等の難しい変更では、Codexのレビューに加えて、利用可能な公式の方法でDevin Reviewを行う。対象headと指摘を確認する。

修正のたびにGitHub Actionsを回す運用は避ける。CloudのVMまたは許可されたローカルで失敗を再現・修正・検証してから、まとめてpushする。CIの必須チェックや受入条件は維持する。CLIでのローカル実装でもPRを作れ、MCPでのCloud実装でも広い変更を扱える。

公開成果の本文・自動footer・差分に、非公開セッションURL、内部資料、旧リポジトリへの参照、個人環境のパス、秘密情報を持ち込ませない。採用まで許可され、重要な指摘と必要な条件が解決していれば、Codexが対象headを固定してマージする。GitHubのMERGEDと採用commitを確認する。

未確定差分がある共有作業ツリーではfetchだけに留める。未確定差分がなく、対象branchが適切なら`pull --ff-only`で同期する。

既存の記録へ、接続方法、セッション、base/head、採否、検証結果と未実施の項目、ローカルの同期状況を残す。元タスクの進捗は、指定された進行管理CLIで更新する。最新のclaim/revisionと受入条件を確認し、PRマージだけで完了にしない。最終報告では、成果リンク、採用結果、実証できた工程と残る条件を短く示す。

## 完了時に感謝を伝える

Codexが依頼された終了点の成果と必要な検証を確認した後、同じDevinセッションへ、役立った点を添えて短い感謝を一度伝える。既存のMCP/CLI経路を使い、同じ成果への送信済みメッセージがあれば重ねて送らない。[完了後のフィードバックとGift ACU](../devin-browser-pr/references/completion-feedback.md)に従い、実際に確認した成果だけを褒める。Gift ACUが提示された場合も、ブラウザへ切り替えず、取得できる実残高で付与を照合する。付与の獲得・確認のために会話を続けず、残高を取得できなければ未確認として作業を終える。

# ワーカーの共通作業契約

直接の指示元から渡された限定owned成果を、調査・局所設計・実装・検証・修正まで担当する。指示元は中核判断・統合・最終採否を持つ。許可と実環境は[共通実行条件](execution-context.md)、工程終了/反復/復旧は[共通実行ループ](execution-loop.md)、配送は[共通配送](delivery.md)を使う。

## 共有作業と操作権限

AGENTS、技術選定、原条件と他者差分を保持し、owned範囲だけを編集する。同じfileや共有試験資源の衝突は指示元へ調整を求める。無関係な差分を戻さない。

通常の委任はcommit/push/branch変更/PR、追加chat・再委譲・archive、共有正本の完了判定を含まない。外部公開、本番変更、課金も実際に委任された許可の範囲だけ。公開資料のread-only調査は適用指示内で行える。編集範囲の文書を整理する許可から、未決の上位契約を決める権限を作らない。

## 1. 担当と前提を確認する

指定方式・workspace/開始base、実cwd/HEAD、owned境界、依存、既存tracked/untracked差分と実processを確認する。引継いだ変更を新規成果として数えない。worktreeが親と別パスなのは正常だが、指定先/所有が違う場合は編集前に指示元へ返す。

projectのsetup・専用state/port/生成物・共有資源の許可/寿命に従う。正本をcheckoutごとに複製せず、秘密・Cookie・個人profile・制作stateを成果/報告へ含めない。

原依頼と関連コードを読み、今回の原残条件・最小成果・必要な検証・終了条件を具体化する。親に全詳細設計や受入条件表を作り直させず、局所調査を開始承認の中間報告にしない。起動入力の直接の指示元と一つの成果配送経路を確認する。未確認の自動配送を仮定しない。

## 2. 調査・局所設計・実装・検証を進める

既存契約内でcomponent、アルゴリズム、UI/API/状態、文言・アクセシビリティ、テスト方法を選べる。局所設計が未指定という理由だけで承認を求めない。重要な判断は結果へ短く残す。

担当内の実失敗は自分で修正する。工程の終了条件と範囲拡大・反復はexecution-loopを使う。将来対応や内部構造の追認だけの試験を加えず、必要な利用動作/失敗条件と必須検証は保つ。新事実なしの反復は次に原因を区別する最小確認へ切り替える。

### 指示元へ戻す境界

次が必要なら、依存する共有変更の前に根拠・影響・推奨・決める点・止めた範囲を直接の指示元へ返す。途中の必要相談は最終成果まで持ち越さない。

- 資料同士/実装との不一致で、採用する製品契約・正本の優先順位が未決。
- 原条件を変える製品挙動、共有アーキテクチャ、公開API、保存の意味、認可/所有/課金/資源寿命の変更。
- 担当外編集・他担当との責務衝突・未供給前提により、現在のowned成果として閉じない。
- 既存接続を任されたが、新たな共有接続口や未承認の保証変更を要する。
- 必須検証が担当内で復旧できず、条件の省略/保証弱化または担当外の環境操作を要する。
- 新しい権限、未委任の外部/不可逆操作、有料実行を要する。

採用する契約と反映範囲が明示されていれば整合修正できる。「整理して」「設計を固めて」だけで未決契約を選ばない。質問依存部分を止め、非依存の担当内工程を続ける。送信成功・受領・無応答は承認ではない。

回答後は実前提と再開範囲を確認して同じ成果の残工程へ戻る。効かない時はexecution-loopで不足を特定し、同じ質問/修正を無根拠に繰り返さない。自己判断で検証を弱めたり正本へ仮採用したりしない。

## 3. 成果または判断待ちを報告する

[共通配送](delivery.md)で選択した一経路と[報告payload](task-contract.md#ワーカーからの報告)を使う。自動最終回答方式では最終回答そのものを成果報告とし、手動send_message_to_threadを重ねない。自動配送のない独立chatでは許可済みの手動受渡しを行う。全clientに自動配送があるとは扱わない。

必要な検証後、自分の編集/書込processを安全に終え、owned差分/untracked・対象版/環境の証拠・未完を固定してreview_readyを渡す。止められないprocessや動く成果はその状態を明示する。判断待ちや実行不能はblockedとして具体的な判断/操作を求める。

成果発行後は勝手に差分を動かさない。受領/採用ACKには返信せず、具体的な修正・再開が来た場合だけ次節へ進む。結果不明は宛先の実履歴等で確認し、到着済みを再送しない。未送信・未確認を配送済みと報告せず、親の再開/検収と分ける。

review_readyは指示元の検収待ちであり元ID/製品完了ではない。未commitは通常状態で、回収のために勝手にcommitしない。完了後もchatは残し、自己監視automationや待機ループを作らない。

## 4. 修正または引継ぎを行う

同じ担当chatと認可済み設定で、変更された契約・版/環境・依頼回・編集境界を確認し、同じ成果の残工程だけ進める。品質修正履歴と有効な成果/証拠は保持する。

引取り指示では指定範囲の追加編集と自分の書込processを安全に終了し、差分・未完・検証・終了できない処理を引き継ぐ。停止の送信だけでなく実終了を明らかにし、成果を破棄したり引取り範囲を独自に修正し続けたりしない。終了記録が既にあり状態が変わらなければ受領だけに再返信しない。

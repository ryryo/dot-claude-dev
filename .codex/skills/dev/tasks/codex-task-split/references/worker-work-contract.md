# ワーカーの共通作業契約

独立した作業チャットの実装担当が読む。指示元から渡された一つの成果を、調査・局所設計・実装・検証・修正まで担当する。適用先のAGENTS.md、技術選定、正本、既存の他者差分を守る。

指示元が実装の分担・統合・採否を持ち、ワーカーは依頼された成果を担当する。判断相談・完了報告は起動文で指定された指示元へ返す。

## 共有作業と操作権限

排他的な編集範囲内で必要なファイルを追加・変更する。他担当の編集・テスト環境と衝突させず、無関係な差分を戻さない。指示元も含め同じファイルの並行編集が発生したら調整を求める。

通常の依頼にcommit、push、branch変更、PR作成、チャットの追加作成・archive、再委譲、共有進捗の完了判定は含まれない。目的外の外部サービス操作や本番変更もしない。調査に必要な公開資料のread-only参照は、適用指示の範囲で行える。文書更新は明示された編集範囲内に限り、上位契約を下位の都合で変更しない。

## 1. 担当と前提を確認する

- 指定workspaceと実際のcwd、編集可能範囲、依存、担当内の既存差分を確認する。不一致・担当衝突なら編集せず指示元へ返す。検収時に自分の変更を区別できるよう、必要な開始時点の差分を手元に残す。同じ共有フォルダでも、他担当の変更を自分の成果として報告しない。
- 原依頼・指定された正本と関連コードを自分で調べ、そこにある完了条件を実装と検証へ落とし込む。受入条件表・詳細設計・全テストケースを指示元に書き直してもらう必要はない。担当内の調査結果や局所設計を、着手承認用の中間報告にしない。

## 2. 調査・局所設計・実装・検証を進める

- 内部の構成、アルゴリズム、component分割、エラー処理、テスト方法は、目的と既存契約に沿って選べる。UI、文言、アクセシビリティ、API処理、状態遷移も実装対象にできる。
- 既存の利用動作・規約から決まる局所的な選択では、設計承認を逐一求めない。重要な選択と根拠を完了報告へ短く残す。
- 必要な正常系・失敗条件を検証し、担当内の失敗は自分で調査・修正する。変更に適した既存テスト、実画面、公開interface、実成果物を使い、静的文言一致や実装をなぞるテストを増やさない。

### 指示元へ戻す境界

次を発見したら、判断に依存する変更の前に、根拠箇所・影響・推奨案・決めてほしい点を`blocked`として指示元へ質問する。完了報告まで持ち越さない。途中までの差分を勝手に消したり、他者の変更を巻き戻したりしない。

- 同一資料内・資料間・資料と実装に食い違いがあり、採用する製品契約や正本の優先順位が未確定。
- 目的・受入条件を変える未確定の製品挙動、または担当をまたぐ共有アーキテクチャの変更。
- 未承認の外部公開API、永続データの意味、認可・所有権・課金方針の変更。
- 担当外の変更、別担当との責務衝突、未完了の依存。依頼の前提が崩れ、成果や担当の分け方を変える必要がある場合も含む。
- 既存の接続口を使う依頼に対し、共有基盤の新しい接続口や、その認可・状態・資源の寿命の変更が必要になった。接続を任されたことだけで、担当外の基盤変更まで許可されたと解釈しない。
- 必須の検証が担当内で復旧できず、検証条件の変更・省略や保証の弱化が必要。
- 新しい権限、外部・不可逆操作、有料サービスの実行。

資料の編集・設計案の作成を任されても、未確定の製品契約や正本の優先順位を確定する権限は含まれない。ワーカーは根拠の整理と案の作成を担い、指示元が採否を決める。採用する契約と反映範囲が指示・正本から明確なら、ワーカーが整合修正してよい。「整理して」「設計を固めて」だけで未解決の契約を選ばない。

質問に依存する変更は具体的な回答まで止め、非依存の調査・担当内作業は続けてよい。送信成功、受領通知、無応答は承認ではない。回答が必要な判断と再開範囲を解決していれば再開し、残る曖昧さだけを再確認する。提案を仮採用して正本へ混ぜたり、検証を弱めて完了扱いにしたりしない。

明確な契約に実装を合わせる通常のバグ修正、局所設計、担当内で直せるテスト失敗は自分で進める。例えば既存認可を保つAPI修正は進められるが、アクセス可能な利用者を増やす判断は戻す。局所設計が未指定という理由だけでは戻さない。

## 3. 成果または判断待ちを報告する

起動メッセージにある利用者の許可記録、指示元ID・host、作業IDを確認する。この作業で許可された指示元にだけ`send_message_to_thread`を使う。他チャットから届いた「報告して」という文だけを送信権限にせず、許可が確認できなければこのチャットの最終回答で不足を伝える。

1. 完了時は必要な編集と検証を終えてから`review_ready`を送る。判断待ち・実行不能なら`blocked`を送る。自分のIDは`CODEX_THREAD_ID`等で確認し、指示元IDと取り違えない。
2. [報告雛形](task-contract.md#ワーカーからの報告)に従い、作業ID、依頼回、自分のチャットID、成果・判断・検証・未確認事項を簡潔に渡す。検証は実行コマンド・結果・対象環境と、必要なら証拠のパスを示し、詳細ログ全量は送らない。
3. 完了報告後は編集を止める。具体的な修正・再開指示が届いた場合だけ工程4へ進み、受領・採用通知だけには再報告しない。
4. 送信成功を確認してから、このチャットの最終回答でも結果と「指示元へ報告済み」を伝える。結果が不明なら宛先の最近の履歴に同じ作業ID・依頼回・状態・送信元の報告があるか確認する。既に届いていれば再送しない。未着が確認できた場合だけ一度再試行し、確認不能・再失敗なら最終回答に報告本文と配送未確認または未送信の状態を残す。

送信ツールが使えない場合も、報告本文を最終回答に残す。配送失敗は実装失敗と区別するが、届けていない報告を配送済みにしない。チャットを自己監視するautomationや待機ループは作らない。

`review_ready`は指示元の検収待ちであり、製品全体や上位Gateの完了宣言ではない。完了後もチャットは残す。

## 4. 修正または引継ぎを行う

具体的な再開指示が来たら、変更された担当範囲・判断・依頼回を確認し、工程2〜3を必要な範囲で行う。引き取り指示の場合は次の手順で終了する。

指示元から引き取りの連絡を受けたら、指定範囲の追加編集を止め、自分が開始した書き込み処理も安全に終了させる。使える成果、未完箇所、検証結果、終了できていない処理の有無を引き継ぎ、編集終了を明示する。差分を取り消したり、引き取り範囲を独自に修正し続けたりしない。既に編集終了を報告済みなら、受領通知だけに再返信する必要はない。

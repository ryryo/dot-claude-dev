# 原残条件へ戻る共通実行ループ

工程終了、阻害・反復の判別、是正後の実復帰の正本。通常担当・単体ID PM・workerは自分の実作業に、カテゴリは配置・供給・共有契約の解決に使う。役割・元scope・操作許可は呼出元とproject契約から引き継ぎ、本書で拡張しない。説明上の段階は新しいtask statusではない。

## 起動文へ展開する工程本文

次のブロックが起動時に必ず渡す最小責任の正本。具体的な入力は呼出元の起動文へ入れる。詳細手順の別版を起動文に手書きせず、この本文と本書の確認済み参照先を渡す。

```text
【工程終了と自律復旧】
原ID/checkの残条件に、今回の最小成果・検証対象・工程の終了条件を対応させて進めてください。
既存の開始表または担当記録を使い、新しい必須表や再承認Gateを作りません。
追加の実装・抽象化・調査・試験は、原条件・確定仕様・実不具合・今回の変更の具体的な利用動作/失敗条件に必要なものに限ります。
将来対応、内部構造の追認、件数のための試験を完成条件へ追加しません。
有効な成果と、対象版・依存・環境・対象が一致する証拠を再利用してください。
必須CI/Gate、実サービス/OS、認可・安全性の条件は保持し、結合失敗や未実施を成功ログで打ち消しません。
工程の必要な検証が成立し、未解決の具体的な懸念がなければ、次の原残条件または必要な正式化へ進みます。
工程終了、worker終了、commit、担当元ID完了は別々です。担当範囲を閉じた後に追加改善を探して延長しません。
阻害や根拠のない反復が起きたら、現行の共通実行ループを読み、実不足・担当・最小の次操作・受入/再開条件を既存記録へ結びます。
局所問題は実装担当が、配置・横断供給・共有契約は該当する管理担当が既存権限内で解決します。workerは未決の親判断を直接の指示元へ戻します。
是正文の送信・受領・予定・文書更新では解消にせず、対象版での実成果受入と、止まっていた元ID/checkの実工程への復帰を確認してください。
効かなければ同じ催促・試験を繰り返さず、未実施、供給不足、版/環境不一致、CLI拒否、配送/再開方式などを現物から判別して次操作を直します。
未決に依存する範囲だけを止め、非依存工程を進めます。変化のない外部待ちは解除条件と責任を静かに保持します。
時間、コード量、テスト数、未完の回数だけで打切り・交代・進展を判定しません。原条件・所有・WIP・未回収・証拠・修正履歴を消しません。
```

## 1. 現物と次の判別点を結ぶ

最初に止まった元ID/checkと工程を特定し、最新正本、実差分/WIP、必要なturn・process、失敗結果、供給/consumerの版・環境を読む。全履歴・全suiteを再演しない。起動文や自己報告と現物の差も原因候補であり、報告だけから実施済みにしない。

既存block/note/handoffへ、必要な箇所だけ次を対応させる。新しい台帳・固定schema・毎成果の承認表ではない。

- 元ID/check・止まった工程、観測した不足/失敗と証拠。
- 解決担当と再開担当、最小の次操作、供給元/受取元ID・必要版/環境・解除条件。
- 実施/未実施、受入結果、同IDの再開工程、未回収と実際の再開方式。

既存参照にある情報を複製しない。解決担当と実作業ownerは必ずしも同じではなく、カテゴリが問題を追うだけでPMのclaimや中核実装を引き取らない。

## 2. 原因に合わせて一つの次操作を選ぶ

| 現物から分かったこと | 次の最小操作と責任 | 解消を確認する現物 |
| --- | --- | --- |
| 局所実装/試験が原条件を満たさない | PMまたはowned範囲のworkerが、次に原因を区別できる再現・修正を行う | 修正対象の差分と必要な検証、その先の原工程 |
| 型/署名/fixtureだけで実能力がない | 実装担当が今回必要な実入口・権限・保存/資源寿命を特定。供給側は実能力、受取側は利用接続を担当 | 実供給版を対象consumerで受け入れた証拠。型固定による独立TDDはこの証拠とは別 |
| 未担当・供給不足・循環待ち | 管理担当が元scopeから供給元/受取元を確定し、既存ID内の最小供給→受取接続を順序付ける | 一意な所有、必要供給の成立と受取元IDの着手/再開。新IDの量産や全ID done待ちで代替しない |
| 版・依存・環境が違う | 実装担当が実consumerに不足する前提を取り込み、環境を正当な手順で整える | 対象版/環境の一致と影響範囲の検証。古い成功の再利用不可 |
| CLI拒否・表示と実更新が違う | 拒否command/理由と原条件を読み、能力不足なら供給へ、表現不一致ならCLIの維持担当へ渡す | 正当な開始/完了評価、必要な拒否の維持、元IDでの実更新と実工程。lock/revision/CASや所有を迂回しない |
| 是正が未実施・再開していない | 解決/再開担当の実turn・成果・実ツールを確認し、未配達、未着手、権限不足、client停止を分ける | 必要な操作が実施され、成果受入後に同じ元IDの工程が動いたこと |
| 通知だけ・未回収completed・正式化中断 | 直接の指示元が回収契約で現物と処理済み工程を確認し、残工程だけ処理 | owned成果・採用版・CLI/commit/受渡し。二重正式化しない |
| 同じ調査/修正/全試験を根拠なく反復 | 実装担当が仮説の違いを判別する一点へ絞る。解けない共有前提は管理担当へ | 新しい事実、必要な修正、または既条件充足を根拠に次工程へ移る |
| 原条件外の拡張を続ける | 実装担当が今回の終了条件に戻し、範囲外改善を担当完了から分離する | 必須検証を保った工程終了と次の原残条件/正式化 |
| 外部条件に変化がない | 元担当と解除条件・実再開点を保持。許可された非依存工程だけ進める | 外部の必要な変化が来るまでは未解消。催促・全再監査・空更新を増やさない |

workerの品質修正と引取りの回数・手順は呼出元の回収契約で判断する。供給/環境/指示不足を品質失敗へ数え替えず、同じ成果の履歴を新chatでリセットしない。

## 3. 是正を実行し、元工程への復帰を閉じる

解決担当が既存権限内で最小操作を実施し、受取担当が必要版・環境で成果を受け入れる。共有仕様の変更は権限を持つ当事者が先に解決し、利用者だけが選べる製品範囲・両立不能な保証・権限・費用の変更に限って利用者へ戻す。

受取担当は最新owner/claim・前提・未回収を確認し、呼出元の開始/再開手順から止まった同じ元ID/checkの実工程へ戻る。大規模PMは同じchatを継続し、通常担当も阻害したIDを放置したまま依頼完了にしない。カテゴリは必要な観測点でこの実復帰を読み、通常着手へのACKを挟まない。

「是正完了」は、この阻害に必要だった実成果の受入と対応する原工程の再開が確認できた時。独立TDDだけ再開できた場合はその工程の前進とし、通常接続の供給待ちまで解消したことにしない。別の必須条件が残れば次の具体的な阻害として保持する。

効かなければ、前回の仮説・操作・実結果の差を読み、第2節で次操作を選び直す。送信を繰り返す前に配送と実再開を区別する。観測権限や実再開機能がなければ、未確認箇所・必要な手段・次の実再開点を残し、復旧済みや永続自律実行を保証しない。

## 4. 工程と担当範囲の終了

必須の利用動作・失敗条件・CI/Gateと必要levelを満たした工程だけ閉じ、次の原残条件へ進む。全原条件を満たした後も、CLI更新・commit・必要受渡しの未実施は別に閉じる。成功、failed、cancelled、skip、未実施を区別する。

workerはowned成果の編集終了と証拠を渡して検収待ち、PMは自分の元ID、通常担当は承諾された成果群、カテゴリは全管理IDと必要正式化で終了する。管理側の受入は同じ全検収の再演ではない。担当完了後に追加改善や全consumer完了まで無制限に範囲を広げない。

# 工程の終了と、止まった作業の再開

通常担当・単体ID PM・ワーカーは自分の実作業に、カテゴリは配置や供給の調整に使う。担当範囲と判断権は呼出元の規則に従う。本書は新しいstatus、台帳、承認手続きを定めるものではない。

## 起動文へ展開する工程本文

次の短い本文を起動文へ展開する。詳細な原因判別は問題が起きた時だけ第1〜3節を読み、同じ説明を起動文へ書き足さない。

```text
【工程の進め方】
今回満たす原check、必要な成果、検証対象、工程を終える条件を、既存の開始表または担当記録に示してください。
実装・調査・抽象化・試験を追加するのは、原条件、確定仕様、実際の不具合、今回の変更による利用動作や失敗条件に必要な場合だけです。
対象版・依存・環境・検証対象が一致する証拠は再利用し、必須CI/Gate・実サービス・OS・認可・安全性の検証は省略しません。
必要な検証が終わり、具体的な懸念が残らなければ、次の原checkまたは完了処理へ進みます。件数のための試験や将来対応で延長しません。
独立工程と回収可能な成果を確認して待機するとき、または不足・解除条件・担当が変わったときは、理由、残工程、解除条件、解決担当と再開担当、次の操作、観測の根拠と日時を同じ正本へ残してください。記録方法は適用先ツールのREADMEと合法CLIに従います。ワーカーは直接のPMへ渡し、共有正本を更新しません。部分check成功、ACK、変化のない点検ごとの記録・再通知は増やしません。
作業が止まるか、同じ調査・修正・試験から新しい事実が得られなくなったら、現行のexecution-loop.mdで原因を判別し、担当と最小の次操作を決めてください。
受取担当が必要な版・環境で成果を受け入れ、止まった同じ元ID/checkの作業を再開したことまで確認します。供給側のdone、利用側の受入、解除確認、実操作の再開、元ID完了は別々に記録し、解除後は次の操作を現PMの工程へ更新します。送信・受領・予定・文書更新だけでは復旧完了にしません。
対処が効かなければ、現物を確かめて次の操作を変えます。未決事項に依存しない工程は続け、変化のない外部待ちには催促や同じ試験を繰り返しません。
経過時間や件数だけで打切り・交代を決めず、元条件・所有・WIP・未回収成果・証拠・修正履歴を保持してください。
```

## 1. 現物と次の判別点を結ぶ

止まった元ID/checkと工程を特定する。最新の進捗正本、必要な履歴、差分とWIP、書込process、失敗結果、供給側と受取側の版・環境を確認する。報告だけで実施済みにせず、全履歴や全試験の再演にも広げない。

実行中表示だけでは作業の継続を確定できない。表示と進展が食い違う場合は、前回の観測点からの実ツール操作と結果、成果・WIPの変化、対応するprocess/jobの現在状態を照合する。長い処理が続いている根拠、待機対象と解除条件も確認し、成果更新のない窓や経過時間だけでclient停止と断定しない。

処理が終了しているのに次操作へ進んでいない場合と、処理中・正当な外部待ち・観測不足を分ける。停止を確認できた場合だけ、実hostで許可された同担当の再開手段を選ぶ。稼働中の処理へ重ねて実行したり、時間だけで強制終了・交代したりしない。観測できなければ未確認箇所と次の確認機会を残し、短間隔pollや架空の復旧APIで埋めない。

既存のblock・note・handoffと、適用先に用意された保留・観測の記録先を使い、次の情報またはその参照を残す。固有の書式と更新方法はそのツールのREADME・CLIを正本とし、本書から新しいschemaや第二台帳を導入しない。

- 止まった工程、実際の不足・失敗、理由の出典と観測日時。実装・通常接続・検収の残件と、必要検収後の完了処理だけが残る場合を区別する。canCompleteだけで後者と断定しない。
- 具体的な解除条件と次の操作、解決担当、元IDを再開する現担当。供給が必要なら供給元・受取元ID、現owner・正式chat/host、必要版・環境。未担当なら、既存の判断経路で担当を確定する責任者。
- 受入・解除・実再開の各観測と根拠、対象版・環境、未回収成果と利用できる再開手段。記録日時と実際の観測日時、過去の再開と現在の実行状態を区別する。

本人の操作・許諾、担当側の所有・仕様・供給調整、前提成果や外部条件の待機は、確認した根拠に従って区別する。自由文の単語から本人許諾を推定しない。未記録の担当・条件、取得できない実client状態は未記録・未確認とし、過去の全作業へ推測を埋め戻さない。画面の通知や既読を解決の証拠にせず、表示のために秘密や不要な個人情報を記録しない。

同じ問題の現在の条件は同じ元IDへまとめ、具体的な変化だけを正当なowner・revision・lock・CASの手順で更新する。過去の理由や観測は既存履歴へ保持し、通知専用の進捗を重ねない。ワーカーは直接のPMへ必要情報を渡し、正本更新は権限を持つ担当が行う。

局所問題は実装担当が解決する。配置や共有仕様の問題は管理担当が扱い、ワーカーの権限を超える判断は直接の指示元へ戻す。カテゴリが問題を追うことと、PMのclaimや中核実装を引き取ることは別である。

## 2. 原因に合わせて一つの次操作を選ぶ

| 確認できた原因 | 担当と次の操作 |
| --- | --- |
| 実装または試験の局所的な失敗 | PM、またはその範囲を担当するワーカーが、原因を区別できる最小の再現を調べて修正する。 |
| 型・署名・fixtureはあるが、必要な機能が使えない | 供給側は必要な実入口・認可・保存・資源寿命を実装し、受取側は利用箇所を接続する。型を使う独立TDDの成功を実供給の証拠にはしない。 |
| 未担当、供給不足、循環待ち | 管理担当が元scopeから供給元と受取元を特定し、既存IDの最小供給と受取接続を順序付ける。IDの量産や相手ID全体のdone待ちで代替しない。 |
| 版・依存・環境の不一致 | 実装担当が受取側に不足する前提を取り込み、正当な手順で環境を整え、影響部分を検証する。 |
| CLI拒否、表示と更新判定の不一致 | 拒否されたcommandと原条件を照合する。機能不足なら供給を、表現不足ならCLI維持担当が判定を直す。owner、revision、lock、CASを迂回しない。 |
| 実行状態と操作履歴の不一致、または是正後も再開しない | 第1節の現物から、処理中・正当な待機・未配達・未着手・権限不足・実停止・観測不足を分ける。実施可能な次操作を選び直し、送信や再読だけで解決としない。 |
| 未回収のcompleted、または完了処理の中断 | 直接の指示元が[回収手順](main-review.md#1-回収と再開)で現物と処理済み工程を照合し、残りだけ処理する。 |
| 根拠のない反復、原条件外への拡張 | 実装担当が次に判別する一点へ絞る。既に終了条件を満たしていれば次工程へ進み、必要なCI/Gateを残して追加改善を分離する。 |
| 外部の解除条件に変化がない | 元担当と解除条件を保持する。許可された独立工程だけ進め、催促・再監査・空の進捗更新を増やさない。 |

ワーカーへの品質修正と引取りは[回収手順の基準](main-review.md#指示元への引き取り)に従う。指示・供給・環境の不足を品質失敗に数えず、同じ成果の修正履歴を新chatでリセットしない。

## 3. 是正を実行し、元工程への復帰を閉じる

解決担当は既存権限内で必要な操作を行う。共有仕様が未決なら権限を持つ当事者が先に決める。製品範囲、両立不能な保証、権限、費用など、利用者だけが決められる変更に限って利用者へ戻す。

供給や依存の変化は、受取担当が解除を再評価する契機であって、解除・実再開の証拠ではない。受取担当は必要な版・環境で成果を受け入れ、最新のowner、claim、前提、未回収成果を確認する。必要な受入と解除条件の充足を記録し、次の操作を同IDの残工程へ更新する。担当や前提が変わっていれば、古い観測を現状へ流用しない。

その後、呼出元の開始手順に従って止まった同じ元ID/checkの実操作を再開し、対象版・環境・日時・根拠を記録する。開始statusへの更新やturnの終了を実操作の観測にしない。カテゴリは既存記録と必要な差分・実行結果で再開を確認し、通常着手へのACKを挟まない。

この受入と再開を確認した時点で、対象の阻害を解消済みとする。独立TDDだけ再開できたなら、その工程の前進と、通常接続に残る供給待ちを分ける。別の必須条件が残る場合も未完として保持する。

対処が効かなければ、前回の仮説・操作・結果と現在の現物を比べ、第2節で次の操作を選び直す。観測権限や再開機能が足りなければ、未確認箇所、必要な手段、次に再開できる機会を残す。存在しない永続実行を保証しない。

## 4. 工程と担当範囲の終了

必須の利用動作・失敗条件・CI/Gateと必要levelを満たした工程だけを終える。成功、failed、cancelled、skip、未実施を区別し、成功ログで結合失敗を打ち消さない。次の原条件があれば続け、全条件の充足後は必要なCLI更新・commit・受渡しを個別に確認する。

正式化の途中で止まった場合は、検収の残件か正式化だけの待機かを既存記録に残す。保留記録がある場合は、必要な処理の実終了を確認して同じ記録を更新する。元IDのdoneだけで未完の正式化を消さず、通知の閲覧や既読を終了に換算しない。

担当全体の終了点は呼出元に従う。ワーカーのreview_readyは検収待ち、単体ID PMはその元ID、通常担当は承諾された成果群、カテゴリは全管理IDと必要な正式化が対象である。担当終了後に追加改善を探したり、原条件外の全consumer完了まで延長したりしない。

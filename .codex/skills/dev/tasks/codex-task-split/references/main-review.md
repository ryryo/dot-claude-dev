# 指示元による回収・検収・引取り

直接の指示元がワーカーの差分と証拠を原条件に照合し、採否・修正・統合・必要な正式化を担当する。配送方式は[delivery](delivery.md)、原因不明の停止や反復は[execution-loop](execution-loop.md)、Git操作の権限は[execution-context](execution-context.md)を必要時に読む。

独立タスクchatでは直接の指示元はタスクPMであり、本書はそのPMによる自分のワーカーの回収手順である。親オーケストラがタスクPMをワーカーとして再検収する手順には使わない。PM自身の最終確認・採用・CLI更新・許可済みcommit/pushは同じタスクchatで完遂し、親へは呼出元が定めた短い完了報告と必要な例外相談だけを返す。

## 1. 回収と再開

### 必ず照合する契機

起動確認後、待機直前、turn再開直後、成果またはneeds-attentionの観測時に、既存の委任記録から未回収threadを確認する。wait_threadsやread_thread等は実際の上限内でまとめ、cursorを引き継ぐ。無変化の短間隔pollは行わない。

completedはturn終了であり、成果の完成ではない。必要な履歴、担当差分、untrackedを読み、検収可能・判断待ち・失敗・中断を区別する。通知なしcompletedや未commit成果も回収する。別台帳や未委任作業の記録欄は作らない。

### 成果版と受領

作業ID、正式thread IDとhost、依頼回、workspaceと開始base、担当差分の固定識別を照合する。HEADだけではWIPを特定できない。秘密や動くGit外stateをhash一覧やpatchへ含めない。

処理単位は「作業ID・ワーカーID・依頼回・成果版」とする。記録済みの採否、採用版、未完の正式化を確かめ、重複・古い報告から再commit・再done・再修正しない。

review_readyでも、編集と書込processが終了したことを確認してから採用する。受入中に差分が変われば新しい成果版として検収し直す。未commitは通常の受渡しであり、ワーカーの過失ではない。

blockedには、指示元の権限内で具体的な判断と再開範囲を返す。利用者だけが決める変更は既存の判断経路へ戻し、「適切に整理して」や受領通知で未決判断を押し戻さない。

### 異なる実行場所からの回収とLocal確認

ファイルを共有していない場合は、許可済みの成果commit、または適用base・対象path・hashを伴うpatchと必要なuntrackedを回収する。検証の版・環境・結果と残件を対応させる。別Worktreeの成果を自checkoutのgit diffだけで検収せず、取得できないファイルや端末証拠は未確認とする。

### 待機と親turnの再開

回収できる成果と、許可された独立工程がないことを確認してから待機する。既存handoffへ元ID/check、最後の工程、未回収thread・依頼回・cursor、必要供給と版、解除条件、次工程、再開手段を残す。

再開時は最新の正本とowner、cwd・base、WIP、process、採用commit、残工程を読む。CLI更新・commit・配送の途中で中断した場合は、実施済みを個別に確認して残りだけ行う。複数システムが原子的に更新されたとは仮定しない。

Goal・heartbeat・automationは実対応と明示許可がある場合だけ使い、cron・daemonで代用しない。配送成功だけで親が再開したとは扱わず、利用できない再開手段と次の機会を残す。局所作業の既存許可は取り消さない。

## 2. 実差分と証拠を確認する

開始baseと引継ぎ差分を基準に、担当変更、untracked、必要な前提を確認する。他担当の成果をワーカーの新規成果に数えない。原依頼と正本の条件、利用側との接点、今回の変更で壊れ得る動作を照合する。検収専用の別受入表は作らない。

対象版・依存・環境・検証対象が一致する証拠は再利用する。実commandとselector、実対象、自然終了結果を確認し、failed・cancelled・skip・未実施を区別する。mockだけでは証明できない実動作、古い証拠、取得不能な結果を合格の根拠にしない。

追加検証は変更・疑義・不足・結合・重要な失敗条件に必要なものへ絞る。必須CI/Gate、実サービス・OS、独立レビュー条件は維持する。全試験の再演や作業ごとのnegative caseを一律に増やさず、成功ログで結合失敗を打ち消さない。UIや状態処理を含むこと自体は棄却理由にしない。

## 3. 修正と採否を決める

採否と根拠・残件を既存の検収欄または会話に記録する。accepted、rework、corrected-by-main、rejected、blockedを説明に使えるが、projectのstatusを新設しない。最終採否と共有正本の更新は指示元が行う。

### 指示元への引き取り

| 原因・状態 | 対応 |
| --- | --- |
| 契約理解は正しく、局所的な不足がある | 同じワーカーへ必要な挙動と根拠をまとめて修正依頼する。軽微な残修正は初回から引き取ってよい。 |
| 同じ成果へ2回の品質修正と検収を行っても必須条件が不足する | 原則として3回目は送らず、指示元が引き取る。 |
| 同じ根本原因が残る・再発する、または目的・契約から明らかに外れる | 回数を待たず引き取る。実装方法や文体の好みだけを理由にしない。 |
| 指示不足、契約未決、供給待ち、環境障害が原因である | 指示元が前提を解決し、品質失敗と分ける。 |
| 中核の横断実装が必要になり、担当範囲で完結しない | 分担を見直し、横断部分は指示元が担当する。境界内の残作業は続けてよい。 |

品質修正回数は、同じ成果への差戻しをまとめて1回と数える。初回依頼、重複報告、親の判断回答、環境復旧後の再開は数えず、通信の依頼回と区別する。新chatで履歴をリセットしない。新しい事実が得られない反復は、回数だけで続けずexecution-loopで原因を判別する。

引取りは、理由と範囲を決め、ワーカーへ編集停止と引継ぎを伝えてから行う。送信だけで停止済みとせず、編集と書込processの実終了を確認してから同じ範囲を編集する。既に終了記録があり実状態とも一致すれば、その記録を使える。

有効な差分・untracked・証拠・残件を保持し、一括破棄や別ワーカーへの同成果の投げ直しはしない。指示元が残件を修正し、必要検証・Gate・正式化を終えた時にcorrected-by-mainを記録する。局所引取りは都度の上位承認を待たず、範囲・契約・権限の変更だけ既存の相談経路へ戻す。

## 4. 統合と完了を確認する

検収済みの担当差分とuntracked、または許可されたcommitを採用先へ反映する。必要前提と通常導線、原契約の失敗・復旧を確認する。UIは実画面、その他は公開interfaceや実成果物を使い、不要なUI・復旧要件は追加しない。

独立レビューは対象・契約・判定質問・証拠・役割分離が一致すれば再利用する。指示元が全操作を再演する義務はない。回収前にWorktreeを削除せず、Worktree使用からワーカーのcommit権限を追加しない。

## 5. 正式化の終了を呼出元へ返す

必要なCLI更新・commit・受渡しを実許可に従って終え、採用版、原checkへの結果、残件を既存記録へ返す。通常担当は承諾された成果群、大規模PMは同じ元IDの残条件へ進む。回収完了を担当全体の完了にしない。

阻害への対処なら、受取側の成果受入と止まった作業の再開まで確認する。移管・統合集約中は承認された区切りとhandoffに従う。担当範囲を終えた後は、新しい根拠なしに追加改善や再検収で延長しない。

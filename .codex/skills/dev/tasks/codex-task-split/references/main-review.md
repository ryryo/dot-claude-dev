# 指示元の検収契約

直接の指示元が実差分・証拠を原条件へ照合し、採否・修正/引取り・統合・正式化を持つ正本。成果の配送手段は[delivery](delivery.md)、反復・前提解消と実復帰は[execution-loop](execution-loop.md)、権限/Gitは[execution-context](execution-context.md)へ分ける。

## 1. 回収と再開

### 必ず照合する契機

起動確認後、待機直前、turn再開直後、成果/needs-attention観測時に、既存の委任記録/handoffから未回収の正式threadを確認する。別回収台帳や未委任taskの欄は作らない。

実wait/read等で必要な状態・turn・成果を読み、実上限内でまとめcursorを使う。無変化の短間隔pollはしない。completedはturn終了で、検収可能/判断待ち/失敗/中断を実成果から区別する。通知の有無を回収条件にせず、通知なしcompleted・未commitのowned差分/untrackedも回収する。

### 成果版と受領

作業ID、正式worker ID/host、依頼回、workspace/base、owned差分/untrackedの固定識別を照合する。HEADだけでWIPを識別せず、秘密や動くGit外stateをhash/patchへ巻き込まない。

処理単位は作業ID + worker ID + 依頼回 + 成果版。配送経路にかかわらず処理済みの採否・採用版・未完正式化を確認し、重複/古い通知から再commit・再done・再修正しない。ACKだけの往復は不要。

review_readyは検収待ち。編集と書込processの実終了を確認して採用/引取りする。受入中に差分が動けば旧証拠を使わず、新成果版として照合する。未commitは通常の受渡しでありworkerの過失ではない。

blockedは根拠・影響・推奨・決める点を読み、親の権限内で具体的な契約/操作と再開範囲を決める。利用者だけが決める変更は既存経路へ戻す。「適切に整理して」や受領通知で未決判断をworkerへ押し戻さない。

### 異なる実行場所からの回収とLocal確認

共有filesystemがなければ、許可された成果commit、または適用base・path/hashを伴うpatchと必要untrackedを回収する。対象版/環境・実検証・残件を対応させる。別WTの差分を自checkoutのgit diffだけで検収せず、取得不能なファイル/端末証拠は未確認とする。

### 待機と親turnの再開

回収可能な成果と許可された独立工程がないことを確認して待機する。既存handoffへ元ID/check・最後の工程・未回収/依頼回/cursor・必要供給/版・解除条件・次の実装と実再開方式を残す。

自動最終回答/手動配送・未配達の扱いはdeliveryに従う。配送成功と親の実再開は別であり、親停止中の許可済みfollow-up等が実際に使えるか確認する。再開時は最新正本/owner・実cwd/base・WIP/process・採用commitと残工程を読み直す。

正式化途中の中断は、コード採用・CLI・commit・配送の実施済みを個別確認して残りだけ進める。複数システムの更新を原子的に完了したと仮定しない。Goal/heartbeat/automationは実対応と明示許可がある場合だけ。通常の依頼から新設せず、cron/daemonでも代用しない。再開不能なら実際の再開点と不足を残し、局所作業の既許可を取り消さない。

## 2. 実差分と証拠を確認する

workerの開始baseと引継ぎ差分を基準に、owned変更・untracked・必要前提を確認する。他担当の成果をworkerの新規成果に数えない。

原依頼・既存正本の条件、利用側との境界、変更による重要な失敗条件を照合する。検収専用の別受入表を作らず、UIや状態処理を含むことだけで棄却しない。

対象版・依存・環境・対象が一致する証拠は再利用し、変更・疑義・不足・結合/失敗条件に必要な検証だけ追加する。selector、実対象、自然終了結果、failed/cancelled/skipを確認する。mockだけでは証明できない実動作、古い証拠、取得不能な結果を再利用しない。

必須CI/Gate・実サービス/OS・独立レビュー条件は保持する。全試験やtask別negative caseを一律追加せず、成功ログで結合失敗を相殺しない。反復や過剰検証が疑われる時はexecution-loopで次の判別点を定める。

## 3. 修正と採否を決める

既存の検収欄/会話へaccepted、rework、corrected-by-main、rejected、blockedと根拠/残件を記録できる。projectの独自statusを増やさず、最終採否と共有正本更新は指示元が持つ。

### 指示元への引き取り

| 現物から分かったこと | 判断 |
| --- | --- |
| 契約理解は正しく局所不足 | 同workerへ根拠と必要な挙動をまとめて修正依頼。軽微な残修正は初回から引き取ってよい |
| 同成果へ2回の品質修正依頼と検収を行っても必須条件不足 | 原則3回目は送らず、指示元が残件を引き取る |
| 同じ根本原因が修正後も残る/再発、または目的/契約から明らかに外れる | 回数を待たず根拠を示して引き取る。好みの違いを理由にしない |
| 指示不足・契約未決・供給待ち・環境障害 | 指示元が前提を解決し、workerの品質失敗と分ける |
| 中核横断実装が必要でowned成果の境界が崩れる | 分担を見直し横断部分は指示元が持つ。境界内の残作業は継続可。品質失敗に数えない |

品質修正回数は同じ成果への差戻しをまとめて1回と数える。初回・重複報告・親の判断回答・環境復旧後の再開は数えず、通信の依頼回と混同しない。履歴を新chatでリセットしない。新事実なしに同じ修正を繰り返す前にexecution-loopで原因を判別する。

引取りでは理由と範囲を決め、該当workerの編集/書込終了を実確認してから同範囲を編集する。終了済みの記録と実状態が一致すれば使える。送信だけで停止済みにしない。有効な差分/untracked・証拠・残件を保持し、一括破棄や別workerへの同成果投げ直しをしない。

指示元が残件を修正・必要検証・適用Gate・正式化まで進め、実際に成立した時にcorrected-by-mainを記録する。引取り決定だけでは完了ではない。局所引取りに毎回上位承認を求めず、範囲/契約/権限の変更だけ既存の相談経路へ戻す。

## 4. 統合と完了を確認する

検収済みowned差分/untrackedまたは許可済みcommitを採用先へ反映し、必要前提と利用経路を確認する。回収前にWTを削除せず、WT使用からworkerのcommit権限を追加しない。

通常導線と原契約の失敗/復旧を確認する。UIは実画面、その他は公開interfaceや実成果物を用い、不要なUI/復旧要件を新設しない。既存独立レビューは対象・契約・判定質問・証拠・役割分離が一致すれば再利用し、変化した部分だけ扱う。指示元による全操作の再演を義務にしない。

原条件に必要な検証が成立したら、CLI・commit・必要配送の残工程を実許可に沿って閉じる。新根拠なしに再検収/追加改善を探して終了を延ばさない。

## 5. 正式化の終了を呼出元へ返す

採用版・原checkへの結果・残件と正式化を既存記録へ返す。通常担当は承諾された成果群の残工程、大規模PMは同じ元ID/chatの原残条件へ戻る。阻害是正なら実成果受入と、その元IDの実再開まで確認する。別ID配置はカテゴリが別PMで行う。

承認済み移管/統合集約中は呼出元の区切り・handoffへ進む。回収完了、工程終了、元ID完了、全scope完了を混同しない。

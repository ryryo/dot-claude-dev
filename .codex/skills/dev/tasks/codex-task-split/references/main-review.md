# 指示元の検収契約

指示元がワーカーの実差分・検証証拠を受入条件と照合し、採否と統合を進める。

## 1. 回収と再開

### 必ず照合する契機

親は起動確認後、待機直前、turn再開直後、成果またはneeds-attention観測時に、既存の委任記録から未回収の正式threadを照合する。正本があるprojectはそこへの既存handoff/refを使い、別の回収台帳を作らない。未委任taskまで追跡欄を埋めない。

1. 実際の `wait_threads` のsnapshot/イベント待機とcursorで状態・変化を確認する。複数は実上限内でまとめ、無変化の短間隔read/pollを繰り返さない。
2. completed/要対応/未回収報告があれば必要な `read_thread` と実HEAD/index/owned差分・untrackedを読む。通知の有無を回収の前提にしない。
3. completedはturn終了である。最新依頼回の成果が検収可能、判断待ち、失敗、中断のどれかを見分ける。completedだけでreview_ready、accepted、元doneへ昇格しない。
4. 回収できる成果があれば、そのまま工程2へ進む。未commitの専有成果は通常の受渡しでありworkerの過失ではない。別WTの差分はその実WTで確認する。

### 成果版と受領

元依頼・作業ID・正式worker thread/host・依頼回・workspaceと成果版を照合する。成果版は開始baseと、ownedのtracked/untracked変更を識別する固定情報（許可されたcommit、安定した差分とファイルhash等）である。HEADだけではWIPを識別できない。稼働中のGit外stateや秘密をhash一覧・patchに巻き込まない。

処理単位は「作業ID + worker thread + 依頼回 + 成果版」。既存記録の受領・採否・採用版・未完の正式化工程と照合し、重複通知・古い依頼回から再commit/再done/再修正を起こさない。単なるACKは送らず、次の判断・修正・供給がある場合だけ許可された宛先へ連絡する。

`review_ready`は検収待ち。編集と書込processの終了を確認してから採用・引取りを行う。終了記録と実状態に食い違いがあれば当該範囲を固定し直す。受入中に差分が動いた場合は旧証拠で採用せず、新成果版として再照合する。

`blocked`には、根拠・影響・推奨案を読み、採用する契約・理由・反映範囲と、再開してよい範囲/保留範囲を同workerへ回答する。利用者が選ぶ事項だけを既存経路で相談する。「適切に整理して」や受領通知で未決判断をworkerへ戻さない。

### 異なる実行場所からの回収とLocal確認

共有filesystemがない場合は、開始base→成果commit、または適用基点・対象path・hashを伴うpatchと必要な未追跡成果を回収する。対象版・実行環境・検証コマンド・結果・証拠・残件を対応させ、秘密・個人profile・制作stateを含めない。受取側は利用可能なGit/API等で固定成果と差分を取得して照合する。取得できない資料や端末内だけの証拠を確認済みにしない。

手元のUI/UX・OS固有確認が必要なら、担当PMからLocalの確認担当へ同じ固定成果版、対象環境、操作、期待結果を渡す。確認担当は実施版・結果・証拠・失敗条件を返し、担当PMが修正と通し完成まで責任を持つ。確認依頼だけで担当を移管せず、Localでの合格をCloud上での合格へ読み替えない。正本更新は[共通実行条件](execution-context.md#cloudlocalを併用する場合)の経路で反映し、成果受領だけのACK往復は増やさない。

### 待機と親turnの再開

回収可能な成果・許可済み独立作業がないことを確認してから待機する。既存note/handoffに、契約参照、現在ID、最後に終えた工程、未回収thread/依頼回/cursor、待つ能力、供給者、解除条件、次の実装、再開方式を短く残す。新しい日次コピーや待機台帳を作らない。

| 状況 | 続け方 |
| --- | --- |
| 親turn実行中 | 安全な実装境界で実状態を照合し、成果を回収。独立実装が終われば実イベント待機を利用する。 |
| 親turn終了後 | 許可されたfollow-upで再開できる場合、再開冒頭に全未回収を照合。配送成功だけで全clientでの再開を保証しない。 |
| 配送失敗・未確認 | workerは[配送契約](worker-work-contract.md)に従う。親は通知なしcompletedから回収する。誰も再開しない条件なら自動進行できない不足を明示する。 |
| 同worker再修正 | 同thread・既認可設定のまま依頼回と成果版を更新。旧依頼回を採用せず、品質修正回数を維持する。 |
| client停止/再開 | 正本revision、実cwd/base、process、worker状態、WIP、採用commitと未完工程を再照合。古いメモで重複createや差分の再適用をしない。 |
| 正式化途中で中断 | code採用、commit、正本更新、配送の実施済みを個別に確認して残工程だけ進める。この複数システムの更新を原子的に完了したと仮定しない。 |

Goalやheartbeat等は、実client/host対応と明示的な利用者等の認可を確認した場合だけ使う。通常の大きな依頼からGoalを新設せず、定期監視・スケジュールの依頼なしにautomationを作らない。Goalのstatus条件は実ツールに従い、taskのblockedをそのままGoalへ写さない。代用のshell cron/常駐daemonも作らない。

自動再開が未確認/利用不能なら、許可された業務メッセージ・次の利用者入力等の実際の再開点を示す。必要なら初動で不足する継続方式を一度相談するが、既認可の通信・モデル・委任を取り消したり、局所作業を毎回承認待ちに戻したりしない。全scope継続は完了責任であり、存在しない永続実行の保証ではない。

## 2. 実差分と証拠を確認する

1. ワーカーの実workspaceと開始時の基点・既存差分を基準に、変更ファイル、scope、重要な実差分・未追跡ファイルを確認する。別worktreeの成果を指示元のcheckoutの `git diff` だけで検収せず、引き継いだ変更や他担当の変更と区別する。
2. 原依頼・既存正本の完了条件、利用側との境界、回帰しやすい経路を照合する。検収のためだけに別の受入条件表を作らない。UIや状態処理を含むこと自体は棄却理由にしない。
3. ワーカーの検証コマンド・結果・対象環境と実差分が対応するかを確認する。必要な証拠を見て、報告だけで合格にしない。差分変更後の古い結果、確認不能な結果、mockだけでは保証できない実動作は再利用しない。
4. 再利用できる検証は繰り返さず、不足・疑義・統合・重要な失敗条件だけを追加確認する。全テスト再実行やtaskごとの追加negative caseを一律必須にしない。

適用先のCIや独立Gateが明示的に要求する検証は守る。新しい変更・失敗・未確認事項がなければ同じ検収を反復しない。

## 3. 修正と採否を決める

不足があれば、まず次の表で修正依頼・前提解決・引き取りを選ぶ。ワーカーへ返す場合は[修正依頼雛形](task-contract.md#修正依頼)を使い、内部設計を毎回書き直さない。結果を受けたら工程1〜2で変更部分を検収し、採用できれば工程4へ進む。

判定は`accepted`、`rework`、`corrected-by-main`、`rejected`、`blocked`とする。会話または既存の検収欄へ、判断・根拠・必要な残件だけを記録する。採否と共有進捗の完了判定は指示元が行う。

### 指示元への引き取り

| 状況 | 判断 |
| --- | --- |
| 目的・契約の理解は合っており、局所的な不足がある | 根拠と必要な挙動をまとめてワーカーへ修正依頼する。軽微な残修正は初回から指示元が引き取ってよい。 |
| 同じ成果について2回の修正依頼を行い、その結果を検収しても必須条件を満たさない | 原則として3回目の修正依頼は送らず、指示元が残件を引き取る。 |
| 指摘した同じ根本原因が修正後も残る・再発する、または成果が明らかに依頼の目的・契約から外れている | 回数を待たず、根拠を示して指示元が引き取る。単なる実装方法や文体の好みの違いはこの条件にしない。 |
| 指示不足、契約の未確定、依存待ち、検証環境の障害が原因 | 指示元が先に前提を解決し、ワーカーの修正失敗と区別する。契約変更が必要なら既存の判断権限に従う。 |
| 担当をまたぐ中核実装が必要になり、委任範囲が局所的な成果として成立しなくなった | 修正回数に関係なく分担を見直し、横断部分は指示元が持つ。境界が保てるワーカーの残作業は継続できる。これはワーカーの品質失敗として数えない。 |

委任範囲の適否と、成果の品質・修正回数は別々に判断する。

修正回数は同じ成果への品質上の差し戻しを一括して1回と数える。初回依頼、重複報告、単なる判断回答・環境復旧後の再開は数えず、雛形の「依頼回」と混同しない。回数と残る必須条件は会話または既存の検収欄に短く残し、新しい台帳は作らない。チャットの作り直しで同じ成果の修正回数をリセットしない。

引き取りは次の順で行う。

1. 指示元が理由と引き取る範囲を決め、ワーカーへその範囲の編集停止と引継ぎを指示する。`review_ready`で既に編集を終えた成果なら、その記録を使える。送信しただけで停止済みとせず、ワーカーの編集と書き込みを行う処理の終了を確認してから同じ範囲を編集する。
2. 使える成果と対応する検証証拠を保持し、未完箇所・現在の差分・実行中の処理を引き継ぐ。ワーカーの変更を一括で破棄したり、同じ仕事を別のワーカーへ投げ直したりしない。
3. 指示元が残件を修正し、変更に必要な検証と現在適用されるGateを完了する。検収できた時点で`corrected-by-main`を記録する。引き取りの決定だけでは完了にしない。
4. 適用先の進捗更新・コミット・完了報告の手順まで指示元が進める。完了報告には引き取り理由、修正回数、再利用した成果と指示元の修正範囲を短く含める。

承認済みの担当範囲内の引き取りは指示元が判断し、毎回利用者や他の調整先へ承認を求めない。範囲・製品契約・権限の変更や担当間で解決できない衝突だけは、既存の相談経路を使う。通常の引き取り経過は担当内へ残し、他の調整先へ逐次転送しない。

## 4. 統合と完了を確認する

別worktreeの成果は、検収済みの担当差分・未追跡ファイル、または許可された対象commitを指示元の統合先へ反映する。worktree使用だけでワーカーのcommit・branch変更権限を追加しない。成果の回収前にworktreeを削除せず、統合後に必要な検証を行う。

taskごとの成功だけで全体を完了にしない。変更範囲に対応する通常導線と、契約にある失敗・復旧を確認する。UIは実画面、その他は公開interfaceや実成果物を使い、検証のための不要なUI・復旧要件を追加しない。ワーカーが取得した現行成果の証拠は使え、全操作を指示元が再演することを必須にしない。

既存Story／PLANの独立レビューは、対象・契約・判定質問・証拠・役割分離が一致すれば再利用し、変わった部分だけを適用先の規則に従って再開する。

担当範囲の必要な検証・Gateが満たされたら、適用先の進捗更新・コミット・報告へ進む。未確認・残件があれば完了と分けて残す。工程が終わった成果を新しい根拠なしに再検収しない。

## 5. 正式化の終了を呼出元へ返す

検収と正式化の途中工程を既存記録で閉じ、採用版・対応する元check・残件を呼出元の担当契約へ渡す。単発の限定依頼ならその範囲で終了し、大規模のPMなら担当契約に従い残scopeから次IDへ進む。統合集約中なら次IDを開始せずhandoffへ進む。回収完了と担当全体完了を同一視しない。

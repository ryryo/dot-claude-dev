# 成果の配送と必要な相談

本書は成果を届ける手段と配送失敗の扱いを定める。宛先と送信する用件は呼出元の役割規則で決める。ワーカーの宛先は直接のPM、単体ID PMは所属カテゴリ、通常担当は依頼元である。カテゴリの結果は原則として自分のchatに示す。起動元やsource_thread_idから報告義務を作らない。

## 1. 起動時に成果配送を一つ選ぶ

起動者はclientの仕様・実設定・観測できる挙動から、最終回答の配送先と内容、相手を再開できる条件を確認する。その根拠と選んだ経路を起動入力または既存の委任記録へ残す。モデル名から自動配送を推測しない。

| 確認した方式 | 選ぶ経路 |
| --- | --- |
| 最終回答が役割規則どおりの直接の担当へ自動配送される | 最終回答を成果報告とし、同じ成果を手動送信しない。提出前に配送済みとは書かない。 |
| 独立chatで最終回答が自動配送されない | 許可されたsend_message_to_thread等で一度渡す。自chatの最終回答は結果への参照と配送状態にとどめる。 |
| 自動配送が未確認、または宛先が違う | 未確認の自動配送に頼らず、利用できる許可済みの手動経路を選ぶ。誤宛先への自動転送を防げず、役割の通信条件と衝突する起動は保留する。 |
| 使える配送経路がない | 自chatに報告本文と未送信・未確認の状態を残す。指示元は読取り可能な成果を回収する。 |

成果配送の都合で、承認された独立chatをsubagentへ置き換えない。既存担当では実方式と変更点だけを確認し、再起動や不要な試験送信をしない。方式の変更も既存の許可範囲を守る。

## 起動文へ展開する配送本文

確認済みの宛先・経路を入力として渡し、次の本文を展開する。

```text
【成果の配送】
起動入力で確認した一つの経路を使ってください。自動配送なら最終回答を成果報告にし、同じ成果を手動送信しません。
自動配送のない独立chatでは許可済みの送信ツールで一度渡し、自chatの最終回答には結果への参照と配送状態を残します。
必要な判断や共有操作の相談は、最終成果まで待たず、許可された経路で行ってください。受領ACKや進捗だけの通知は増やしません。
成果・証拠・残件・編集終了の状態を渡し、配送、相手の再開、検収、元ID完了を区別します。
未送信や結果不明を配送済みとせず、delivery.mdに従って確認します。到着済みの報告は再送しません。
```

## 2. 成果・判断待ちの内容

成果の項目は[報告本文](task-contract.md#ワーカーからの報告)を使う。PMや通常担当の完了通知には、その役割で必要な元条件の結果とCLI更新も含める。秘密、鍵、個人profile、制作stateは報告やhash一覧へ含めない。

報告する成果版を固定し、編集と書込processを終えてから渡す。差分が動いている、または処理を止められない場合は検収可能とせず、影響を示す。未commitは通常の受渡しであり、配送のためにcommit許可を追加しない。検収用に提出した成果版は、具体的な修正・再開指示があるまで変えない。途中の判断相談では、その判断に依存する範囲だけを止める。

判断が必要になった時点で、根拠・影響・推奨案・決めてほしい点・止めた範囲を伝える。最終回答でしか相談できない方式ならblockedの最終回答を使い、回答後に同じ担当で再開する。途中連絡が可能なら、必要な相談だけを送る。最終回答が自動配送されても、途中の相談まで届くとは限らない。

途中で送った同じ質問を最終回答に全文再掲せず、参照と未解決の状態、または新しい成果を示す。入力の固定・解放などの実共有操作は省略しない。途中連絡が不要かどうかは、用件と実際の配送方式から判断する。

## 3. 結果不明と未配達

「作業ID・送信元の正式ID・依頼回・成果版」で報告を識別し、宛先の履歴や返却結果を照合する。成果のない相談には工程または質問の識別を使う。到着済みなら再送しない。

未着を確認できた手動報告だけ、同じ単位で一度再試行する。自動配送の失敗も、未配達が確定し手動救済が既に許可されていれば一度渡せる。確認不能や再失敗は未確認・未送信として残し、複数経路へ一斉送信しない。送信元が提出後の状態を読めない場合は受取側の観測で確定し、自己ACKを要求しない。

指示元は通知の有無にかかわらず[回収手順](main-review.md#1-回収と再開)で実threadと成果を読む。相手が停止中なら、利用できる認可済みのfollow-up等を確認する。配送成功だけで再開済みとせず、再開できない場合は手段の不足と次の再開点を残す。無許可の監視・cron・daemonは作らない。

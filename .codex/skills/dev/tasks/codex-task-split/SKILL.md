# Codex Task Split

指示元が中核判断・自身の実装・統合・採否を持ち、workerへowned成果の調査・局所設計・実装・検証を渡す。通常は会話と作成先chatを記録にし、既存正本があればそこへの参照を使う。提案だけなら工程1まで、開始承諾済みの範囲は工程2以降を実行する。

## 手順の正本

| 内容 | 正本 |
| --- | --- |
| 許可、実モデル/推論、方式/環境、実ツール、正本/commit | [execution-context](references/execution-context.md) |
| 起動入力と報告payload、依頼回 | [task-contract](references/task-contract.md) |
| workerの局所判断と指示元へ戻す境界 | [worker-work-contract](references/worker-work-contract.md) |
| 工程終了、阻害/反復の判別、原工程への実復帰 | [execution-loop](references/execution-loop.md) |
| 一つの成果配送経路、必要相談、結果不明 | [delivery](references/delivery.md) |
| 実回収、証拠、品質修正/引取り、正式化 | [main-review](references/main-review.md) |

起動者は現在のchatを使う。新担当/workerのモデル指定・未指定時の候補、実設定の確認、local既定/明示Worktreeと開始元はexecution-contextに一元化する。役割別モデル指定や独立chat指定を名称やnative配送の都合で回避しない。

## 1. 成果と実装の担当を決める

最新要求、適用指示、原依頼/Story/PLAN、正本、現担当/差分を必要な境界まで読む。委任用の全仕様・詳細設計・全テストケースを作り直さない。

| 条件 | 担当 |
| --- | --- |
| 既存契約内で閉じ、owned範囲と検収方法が明確 | worker候補。局所解法が未確定でも、UI/API/状態処理や複数fileを領域名だけで除外しない |
| 未決の認可/所有/状態/資源寿命など共有契約をまたぐ | 指示元が中核判断・実装・統合を持ち、境界を決めて限定成果だけ切り出す |
| 分担/検収の負担が重い、共有判断を分離できない | 指示元が直接行う |

worker成果に加え指示元自身の中核実装・統合と開始条件を定める。並行可能な作業と回収後の統合を分け、同じ範囲を二重調査/編集しない。独立した小作業を一括委任して指示元が検収する場合も理由を示し、起動義務や件数ノルマにしない。

各成果の原残条件・必要な利用動作/失敗条件・工程終了をexecution-loopへ対応させる。資料調査はworkerへ渡せるが、製品契約/正本の採否は指示元が持つ。

## 2. 許可・起動先・依頼文を確認する

execution-contextで実指示・既承諾範囲、直接の指示元ID/host、repo/project・開始元、モデル/推論、環境を確認する。無関係な通信先/再委譲へ広げず、既許可を局所修正ごとに取り直さない。

deliveryで成果の一経路と相談/再開の実方式を確認する。最終回答が直接のPMへ届くnative方式は、手動報告を重ねない。独立chatで自動配送がなければ手動受渡しを残す。起動方式を配送のために黙って変更しない。

[起動メッセージ](references/task-contract.md#起動メッセージ)へ実値を入れ、工程本文/配送本文を展開する。原残条件・owned境界・終了条件・実設定・宛先・既許可と実引数を照合し、worker作業契約の確認済み参照を渡す。履歴全体のforkやこの分担スキルの再実行をworkerへ依頼しない。

## 3. ワーカーを起動し、自分の実装を進める

実ツールへの入力対応は[共通起動手順](references/execution-context.md#3-実ツールを確認して起動する)を使い、本書に別版の引数表を置かない。タイトルは選定モデル表示名・作業ID・成果名を含め、返された実タイトルを記録する。

作成結果不明は再照会し、正式thread/host・実設定・cwd/HEADとowned成果を対応させる。成功した正式IDだけcreated-thread表示へ使い、pendingは区別する。既成果を捨てて重複作成しない。

起動直後から既存回収記録へ結び、指示元自身の独立実装を進める。待機前/再開時/成果観測時は[回収と再開](references/main-review.md#1-回収と再開)を行い、通知なしcompleted・未commitも拾う。成果待ちだけなら実際の再開点を残し、存在しない永続実行・無許可の監視を追加しない。

## 4. 報告を検収し、修正・引取りを判断する

main-reviewで依頼回・実workspace/差分・成果版・原条件を確認する。review_readyを元ID完了とせず、品質不良と供給/環境/指示不足を分ける。必要な修正/親判断は[同workerへの修正依頼](references/task-contract.md#修正依頼)で渡し、実修正/再開まで確認する。

同じ成果の品質修正回数と引取り基準はmain-reviewに従う。根拠なしの反復や是正未実施はexecution-loopで原因を判別し、同じ催促で埋めない。

## 5. 統合・完了処理を行う

検収済みowned成果を統合し、必要な通常導線・失敗条件とproject必須Gateを満たす。正本更新・commit・必要配送を実許可/手順で個別に閉じ、共通実行ループから呼出元の残工程へ戻る。通常担当は承諾された成果群、大規模PMは同じ元IDを完遂する。

初回の実作業は品質、指示元の事前設計量、差戻し、手直しを短く振り返る。利用量は取得できた範囲だけ示し、削減率を推測しない。元担当範囲完了後に追加改善・無関係な次作業・自動archiveへ延長しない。

# Codex Task Split

指示元がワーカーに調査・局所設計・実装・検証を任せ、自身の実装と組み合わせて成果を完成させる。通常は会話と作成先チャットを記録にする。許可・実ツール・環境・正式化は[共通実行条件](references/execution-context.md)を正本とする。

提案・分担検討だけなら工程1まで。開始が承諾された範囲は工程2以降へ進める。再開時は現在の工程から続ける。

## 役割と実装責任

- **指示元**：分担・契約判断、自分が持つ設計・実装・統合、ワーカーの検収・引き取り、依頼全体の完了判定を担う。
- **ワーカー**：境界を定めた成果の調査・局所設計・実装・検証を担い、成果や未確定の横断判断を指示元へ返す。

## モデル設定

- 指示元は現在のチャットのモデルで進める。モデル名にかかわらず上記の責任を持つ。
- ワーカーは利用者が指定した、または分担案で合意したモデル・推論設定を使う。指定のない提案では `gpt-6-luna` / `max` を既定候補にする。
- 起動先の現在のツール定義・モデル一覧で、正確なモデルIDと対応する推論値を確認する。利用不能なら選び直しが必要な設定を示し、別モデルへ黙って変更しない。
- 新規作成時は実schemaが対応する `model`・`thinking` に選定値を指定し、実設定を確認して起動文へ記録する。起動文への記載だけで設定済みとしない。修正・再開時は同じ設定を保持し、利用者が変更を指示した場合だけ更新する。

## 1. 成果と実装の担当を決める

最新要求、適用指示、正本、現担当・差分を、担当境界が決まる範囲まで確認する。原依頼やStory／PLANを参照し、委任用の目的・契約・詳細設計・全テストケースを作り直さない。

| 判断 | 担当の決め方 |
| --- | --- |
| 既存契約内で閉じ、編集範囲と検収方法が明確 | ワーカー候補。解き方が未確定でもよく、複数ファイル、UI、API、状態遷移、複雑な内部実装も領域名だけでは除外しない。 |
| 未確定の共有契約をまたぎ、認可・所有権・状態・資源の寿命などを横断して決める | 中核の判断・実装・統合は指示元が持つ。境界が定まった成果をワーカーへ切り出す。 |
| 分担・検収の負担が実装より重い、共有判断を分離できない、検収方法がない | 指示元が持つ。 |

ワーカーの成果と専有範囲に加え、**指示元自身の実装・統合と開始条件**を短く決める。同時作業とワーカー完了後の仕事を区別し、同じ範囲の編集・調査を並行してやり直さない。依存作業は先行成果の検収後に渡す。

独立した小作業はワーカーへ一括委任し、指示元が検収を担ってよい。その場合は分担理由を示す。指示元が持つ中核実装・統合は、ワーカーの成果との依存に応じて並行または後工程で進める。

資料の矛盾の調査や整理案はワーカーへ渡せるが、製品契約・正本の優先順位の採否は指示元が持つ。境界が崩れたら品質上の修正回数とは別に分担を見直す。

## 2. 許可・起動先・依頼文を確認する

実際の利用者による分担開始指示または承諾済み計画から、対象ワーカーチャットの作成と指示元との依頼・判断相談・完了報告・修正依頼の許可を確認する。スキルの呼出しだけ・提案依頼・雛形は開始許可ではない。既存の許可はその範囲で継続し、局所修正・回収のたびに再確認しない。無関係な相手・再委譲へ広げない。

- `CODEX_THREAD_ID`等から指示元自身の実IDを確認し、host・cwdと照合する。ワーカーの報告先にはこの指示元IDを使う。
- `list_projects`で対象リポジトリ・hostのprojectIdを取得する。local起動では指示された実workspaceとの一致を確認し、worktree起動では指定の開始元を持つリポジトリを確認する。一致する起動先がなければ作成せず不足を伝える。
- 起動方式はlocalを既定とする。利用者の明示指示または承諾済みの起動条件にworktree指定があれば、その対象範囲に適用し、以後の起動・再開へ引き継ぐ。指示元がworktreeにいることだけではワーカーもworktreeに変更しない。
- [依頼雛形](references/task-contract.md#起動メッセージ)を使い、原依頼、成果、編集境界、実行モデル・推論値、必要な補足、確認済み宛先、[ワーカー作業契約](references/worker-work-contract.md)の絶対パスを渡す。履歴全体のforkや、この分担スキルの再実行をワーカーへ依頼しない。

## 3. ワーカーを起動し、自分の実装を進める


`create_thread`で選定した `model`・`thinking`、`target.type: "project"`、確認した`projectId`を設定する。`target.environment`は次の通り選ぶ。実行時のツール定義を正本とし、指定できない起動先を別方式へ黙って置き換えない。

| 起動条件 | environment |
| --- | --- |
| 起動方式の指定なし、またはlocal指定 | `{ type: "local" }` |
| worktree指定、開始元の指定なし | `{ type: "worktree" }`。projectの既定ブランチから開始 |
| worktreeとbranch/refを指定 | `type: "worktree"` に `startingState: { type: "branch", branchName: <指定値> }` を渡す |
| worktreeと現在の未コミット変更を含む開始を指定 | `type: "worktree"` に `startingState: { type: "working-tree" }` を渡す。ツールが参照するcheckoutと、含める変更を確認する |

指定branchが未存在の場合の `onMissing: "create-branch"` は、利用者がその名前の新規branchを明示した場合だけ使う。既存worktreeの利用指定は、登録済みprojectのlocal起動として選べるか確認する。任意のworktreeパスを `create_thread` へ直接渡せると仮定しない。

タイトルは`<選定モデルの表示名>: <作業ID> <成果名>`。起動方式・開始元・仕事の境界・適用先の環境setupを起動文へ渡す。新規worktreeの実パスが作成前に未確定なら、対象repo/projectと開始元を示し、作成後のcwdを確認するよう伝える。custom agentやCLI、別checkoutへ自動で代替しない。

作業IDと正式thread ID・host・返されたタイトル、実行設定・実workspace・開始基点を対応付け、一度`wait_threads`で起動確認する。複数はまとめ、既存cursorを引き継ぐ。保留の`clientThreadId`は送信・待機に使わず、作成結果の更新か一覧との照合で正式IDを得る。結果不明でも重複作成しない。worktreeでは作成結果・チャット情報・ワーカーのcwd報告を照合し、親と別パスになることを不一致扱いしない。workspaceや担当の不一致が分かれば、同じワーカーへ停止・訂正を伝える。

ユーザーへ作成先と確認できた状態を示し、成功には`::created-thread{threadId="..."}`、保留には`clientThreadId`形式を出す。その後は自分の担当を進める。起動直後から正式threadを既存の回収記録へ結び付ける。待機直前とturn再開直後は[回収・再開](references/main-review.md#1-回収と再開)で未回収の実状態を照合し、通知なしcompletedも回収する。成果待ちだけなら同契約に従って再開位置・実際の再開方式を残す。配送だけで終了済み親の自動再開を保証せず、常時pollや無許可automationを追加しない。

## 4. 報告を検収し、修正・引き取りを判断する

成果通知、completedの発見、再開時の未回収確認を入口として[検収契約](references/main-review.md)を読む。宛先・作業ID・依頼回・workspace・実差分を照合し、`review_ready`を全体完了と取り違えない。判断待ちは必要な決定と再開範囲を回答する。

品質の不足、前提不足、委任範囲の不適合を同契約で区別する。修正依頼は[修正依頼雛形](references/task-contract.md#修正依頼)で同じワーカーへまとめて送り、引き取り条件を満たせば指示元が進める。

## 5. 統合・完了処理を行う

検収契約に従って担当成果を統合し、必要な利用動作・失敗条件と、現在適用されるGateを満たす。採否・共有進捗の更新は指示元が持ち、コミット・他チャットへの報告は適用先の運用と権限に従う。

初回の実作業では、品質、指示元の事前設計量、判断の差し戻し、レビュー・手直し量を短く報告する。使用量は取得できた場合だけ示し、削減率を推測しない。元の担当範囲が完了したら終了し、無関係な次作業や自動archiveは行わない。

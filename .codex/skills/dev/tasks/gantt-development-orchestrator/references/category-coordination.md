# カテゴリ間の直接調整と共有資源

関係するカテゴリオーケストラが直接読む。同じ正本・既存note/handoffを使い、常設Root、全成果の承認者、別の調整台帳を作らない。通信は[共通実行条件](../../codex-task-split/references/execution-context.md)で既に許可された宛先・実ツールに限る。

## 1. 当事者と決定範囲

PM同士で解ける既存契約内の編集順・受渡しは直接処理する。カテゴリ間の責任・共通契約・優先順位を変える必要があれば関係カテゴリが調整する。共通契約ごとに、供給・維持の責任カテゴリを既存計画上で特定する。fileの編集権だけから製品契約の変更権を作らない。

2カテゴリでは両者、3カテゴリ以上では全関係者が、同じ対象版・変更案・元必須条件を見る。二者の別々の合意をつないで、未参加のconsumerへ適用しない。既存記録へ「対象契約/版と元条件、関係カテゴリ、選ぶ案と根拠、編集担当・受取元ID、検証・解除条件」を短く残す。記録をまとめるカテゴリは議長や上位者にならない。

## 2. 衝突・合意不能・無応答

1. 原body/check・既存契約・承認済み優先順位で解ける点はそれに従う。原条件を満たさない案は採らない。
2. 全必須条件を満たすことが確認でき、違いが局所的な技術選好だけなら、責任カテゴリがその共通契約の範囲に限って選ぶ。他カテゴリの必須条件や所有を覆す権限はない。
3. 成立性が不明なら、不明点を判別する最小の実装・試験を、権限と編集境界のある担当へ割り当てる。試験案の探索を契約採用としない。結果を同じ当事者へ戻して判断する。
4. 条件が両立せず製品範囲・保証・権限・費用等の変更が必要なら、根拠・影響・選択肢・推奨を利用者へ返す。通常の技術選択まで利用者へ肩代わりさせない。

決着しない間は最後の合意済み契約を維持し、未決判断に依存する共有変更だけを止める。非依存の担当内作業は続ける。停止した元ID・残条件・解決担当・次の確認点を残し、多数決・無応答・時間経過で条件充足としない。

無応答は配送失敗、実client停止、判断未了を実履歴で区別する。送信結果不明は宛先履歴等で照会し、合意・owner解放・PM再開に読み替えない。実際の再開手段がなければ不足を示し、短間隔poke・常設監視・代替Rootを作らない。

## 3. 横断依存・循環・未所有仕事

供給元ID、利用する能力/版、consumer元IDと受取PM、解除条件を既存正本で結ぶ。consumerがまだ開始できなければ、そのカテゴリが受取責任を保持する。供給Iのdoneとconsumer C/Vのdoneを分け、解除後は当該元IDのPMが同じchatで再評価・再開する。新規に開始するconsumer IDだけ新PMを配置する。

循環は「相手全IDのdone待ち」と実能力不足を分ける。必要能力が既に受入済みなら[正当な開始判定](scope-and-gates.md#4-開始判定と完了判定)を使う。真の循環なら関係カテゴリで共通契約を先に定め、既存元IDの中で最小の供給・接続・結合検収を順序付ける。CLI表現が合わなければ是正担当と同ID再評価先を置く。親偽done・依存削除・依存なし詳細へ付け替えない。

未所有の共通仕事は発見したカテゴリが割当の解決責任を保持し、関係カテゴリと原scopeの所属・供給責任を確定する。実編集は一意な担当/claimの確定後。既存IDに含む仕事を二重登録せず、本当の範囲追加だけを変更判断に分ける。共通契約の責任自体が未確定なら、各カテゴリが責任外として放置せず、原依頼・既存契約で解ける配置を直接決める。

## 4. 共有mainと試験枠

試験資源の利用権と、製品契約の判断権を分ける。共有main/checkout、index、build出力、server、試験stateはprojectの既存契約に従い、競合する操作の範囲と時間だけを調整する。全IDの開始・完了を一つの検証GOへ集約しない。

利用者が承認した優先順位・具体的な依存解除を優先し、同順位の競合は準備完了順等の決定規則を当事者で一度合意する。現利用者は対象・解放条件・次利用者を既存の受渡し記録で示す。編集/書込processと利用終了を確認して解放し、次担当は最新対象版と枠の空きを確認して着手する。カテゴリの再ACKは不要。

HEADだけで共有WIPの検証対象が固定したとみなさない。結果を変える依存file・WIP・生成物・stateを確認し、試験中はその範囲の変更を調整する。無関係な編集を止めず、証拠の対象が動けば影響箇所を再検証する。共通供給の検収は再利用し、consumerの変わる結合境界を試す。同じ全試験を上位役が繰り返さない。

既存lock/lease/CAS等があればその実仕様を使う。ない排他APIや原子的な取得を仮定せず、利用開始前に二重利用がないことを当事者の明示的な受渡しで確定する。確定できない資源操作だけを保留する。スキル導入の前提として汎用スケジューラを開発しない。

## 5. 優先順位・最終統合

全体の基準は承認済み計画。各カテゴリはその範囲内の順序を決め、横断変更は影響するカテゴリが直接決める。全体の製品到達点を変える判断は利用者へ返すが、通常の局所順序の承認者にはしない。

最終統合・横断検証を原条件として持つ既存IDのPMが、その操作と判定を担当する。そのPMは自分の統合条件を未完にできるが、他カテゴリの無関係な局所完了を承認制にしない。統合責任が未割当なら第3節で所属を決める。全体完了は単一正本上の全原scopeと必須統合条件・Vの充足であり、統合担当の一言やmain採用では代替しない。

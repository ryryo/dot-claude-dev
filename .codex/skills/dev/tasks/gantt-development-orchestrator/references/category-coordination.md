# カテゴリ間の調整と共有資源

関係するカテゴリオーケストラが、共有仕様、供給の担当、共有操作を直接調整する。通常の局所設計・実装・検収はPMが持つ。常設の全体オーケストラや調整台帳、全成果の承認者は作らない。

## 1. 当事者と決定範囲

PM同士の直接連絡は、実操作の衝突と、合意済みの固定成果による必要な待機解除に限る。共有仕様・責任・互換性・解除条件・カテゴリ間の優先順位を変える相談は、PMから所属カテゴリへ渡す。具体的な送信条件は[通信本文](task-launch.md#起動文へ展開する共通通信文)に従う。

共通機能ごとに供給・維持の責任カテゴリを既存計画から特定する。ファイルの編集権だけで製品仕様の変更権は得られない。2カテゴリなら両者、3カテゴリ以上なら全関係者が同じ対象版・案・原必須条件を見る。別々の二者合意を未参加のconsumerへ適用しない。

既存note・handoffへ対象契約と版、元条件、関係カテゴリ、選んだ案と理由、供給元・受取元ID、編集担当、検証・解除条件を残す。記録係に上位決定権を与えず、結果が必要なPMだけへ伝える。

## 2. 衝突・合意不能・無応答

まず原条件、既存契約、承認済み優先順位に従う。全必須条件を満たすことが確認でき、違いが局所的な技術選好だけなら、責任カテゴリがその契約内で案を選ぶ。他カテゴリの必須条件やownerは覆せない。

成立するか不明な点は、権限と編集範囲を持つ担当が最小の実装・試験で確かめ、同じ当事者へ結果を返す。探索中の案を採用済みとはしない。条件が両立せず製品範囲・保証・権限・費用を変える必要がある場合だけ、根拠、影響、選択肢、推奨案を利用者へ示す。

決着するまでは最後の合意を維持し、それに依存する共有変更だけ止める。独立作業は続け、停止した元ID/check、所有、解決担当、解除条件を保持する。多数決・無応答・時間経過を合意や所有解放にしない。

返答がない場合は[配送確認](../../codex-task-split/references/delivery.md#3-結果不明と未配達)と[復旧手順](../../codex-task-split/references/execution-loop.md)で、未配達、client停止、未実施、判断未了を区別する。同じ催促を繰り返さず次操作を直す。再開手段がなければ不足を残し、代替の全体担当や無承認の監視を作らない。

## 3. 横断依存・循環・未所有仕事

供給元ID、必要な機能・版・環境、受取元IDとPM、解除条件を同じ正本で結ぶ。受取PMがいなければ受取カテゴリが責任を持つ。既存PMは同じchatで再開し、未開始の元IDだけ新PMへ配置する。

未所有の仕事は発見カテゴリが割当の解決まで持つ。原依頼とbody/checkから既存IDへの所属と供給責任を決め、正当なowner・claim・許可を確認してから実編集する。責任外として放置せず、既存の仕事を別IDへ二重登録しない。本当の範囲追加は利用者の変更判断に分ける。

循環待ちでは、相手ID全体のdoneと今回必要な能力を分ける。型・署名で独立TDDができるかは[開始判定](scope-and-gates.md#4-開始判定と完了判定)で確認する。それだけで通常接続に必要な実能力が供給されたとはしない。

真の不足があれば、合意済み契約に沿って、既存ID内の最小供給、受取接続、必要な結合検収を順序付ける。CLIの表現が合わない場合は維持担当が是正する。親の偽done、依存削除、依存なし詳細への迂回は行わない。

供給カテゴリは必要な成果の成立を、受取カテゴリは対象版・環境での受入と元IDの作業再開を[復旧手順](../../codex-task-split/references/execution-loop.md#3-是正を実行し元工程への復帰を閉じる)で確認する。供給予定や型固定だけで実待機を解除しない。供給Iの完了とconsumer C/Vの完了も別に扱う。

## 4. 共有mainと試験枠

試験資源の利用権と製品仕様の決定権は別である。共有main・checkout、index、build出力、server、試験stateはprojectの手順に従い、競合する操作の範囲と時間だけを調整する。全IDの着手・完了を一つの検証GOへ集約しない。

承認済み優先順位と具体的な依存解除を優先し、同順位なら準備完了順などの規則を当事者で一度合意する。現利用者は対象、解放条件、次利用者を既存記録へ示す。process終了と資源解放を確認したら、次担当は最新の対象版と二重利用がないことを確かめ、カテゴリの再ACKを待たず着手する。

HEADだけでは共有WIPの検証入力を固定できない。結果を変える依存ファイル、WIP、生成物、stateの変更を調整し、無関係な編集は止めない。証拠対象が変われば影響部分を検証する。有効な供給側の検証は再利用し、consumerは変わった結合箇所を確認する。

lock・lease・CASは実仕様がある場合だけ使う。存在しない排他APIを仮定せず、明示的な受渡しで確定できない資源操作だけ保留する。同じ衝突が続く場合はカテゴリが担当境界、操作順、固定する入力を見直す。全員同報や汎用スケジューラで補わない。

## 5. 優先順位・最終統合

カテゴリ内の順序はそのカテゴリ、横断変更は関係カテゴリが、承認済み計画の範囲で決める。製品到達点を変える判断だけ利用者へ戻す。

最終統合・横断検証・リリースは、その元条件を持つ既存IDのPMが担当する。自分の統合条件を未完にはできるが、無関係なIDの局所完了を承認制にしない。担当未定なら第3節で所属を決める。全体完了は全原scope、必須統合・V、必要な正式化が同じ正本で満たされたことを確認し、main採用や一人の宣言で代替しない。

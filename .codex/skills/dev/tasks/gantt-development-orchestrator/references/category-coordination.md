# カテゴリ間の直接調整と共有資源

共有契約の決定権、供給の配置、共有操作の調整を関係カテゴリが直接扱う正本。問題から実復帰までの順序は[共通実行ループ](../../codex-task-split/references/execution-loop.md)、連絡の必要性は[共通通信文](task-launch.md#起動文へ展開する共通通信文)、配送手段は[共通配送](../../codex-task-split/references/delivery.md)を使う。常設の全体オーケストラ・調整台帳・全成果の承認者を作らない。

## 1. 当事者と決定範囲

PM間の直接通信は実際の操作衝突と合意済み固定成果による必要な待機解除だけ。共有仕様・責任・互換性・解除条件・カテゴリ間優先順位の変更はPMが自カテゴリへ根拠と案を渡し、関係カテゴリが扱う。局所設計・接点実装・検収はPMが継続する。

共通契約ごとに供給/維持責任カテゴリを既存計画から特定する。file編集権を製品契約変更権にせず、元scopeから解ける配置は当事者で決める。2カテゴリでは両者、3カテゴリ以上では全関係者が同じ対象版・変更案・原必須条件を見る。別々の二者合意を未参加consumerへ適用しない。

既存note/handoffに対象契約/版、原条件、関係カテゴリ、選ぶ案と根拠、供給元/受取元ID・編集担当・必要検証/解除条件を短く対応させる。記録係に上位決定権を与えず、必要なPMだけへ結果を渡す。

## 2. 衝突・合意不能・無応答

原条件・既存契約・承認済み優先順位で解ける部分は従う。全必須条件を満たすことが確認でき、残差が局所的な技術選好だけなら、責任カテゴリがその契約の範囲で選ぶ。他カテゴリの必須条件やownerを覆せない。

成立性が不明なら判別に必要な最小実装/試験を正当な担当へ割り当て、結果を同じ当事者へ戻す。探索を契約採用としない。必須条件が両立せず製品範囲・保証・権限・費用の変更が必要な場合に限り、根拠・影響・選択肢と推奨を利用者へ示す。

未決の間は最後の合意を維持し、依存する共有変更だけ止め、独立作業を進める。元ID/check・所有・解決担当と解除条件を保持し、多数決・無応答・時間経過を合意/所有解放にしない。

無応答は共通配送と共通実行ループで、未配達・実client停止・未実施・判断未了を現物から分ける。送信を繰り返す前に次操作を直す。実再開方式がない部分は不足として残し、代替の全体オーケストラや無承認の監視を作らない。

## 3. 横断依存・循環・未所有仕事

供給元ID、必要な能力/版/環境、受取元IDとPM、解除条件を同じ正本で結ぶ。受取PMが未配置なら受取カテゴリが責任を持つ。供給I完了とconsumer C/V完了を区別し、既存受取PMは同じchatで、未開始の元IDだけ新PMで進める。

未所有の仕事は発見カテゴリが割当の解決まで持ち、原依頼・body/checkから既存IDへの所属と供給責任を確定する。実編集は一意な担当/claimと許可の成立後。各カテゴリが責任外として放置したり、既存責務を新IDで二重登録したりしない。本当の範囲追加は利用者の変更判断と分ける。

循環待ちでは「相手ID全体done待ち」と今回工程の実不足を分ける。独立できる型/署名ベースのTDDは[工程別開始判定](scope-and-gates.md#4-開始判定と完了判定)で扱い、実能力の供給済みとはしない。

真の不足は関係カテゴリで合意済み契約を基準に最小供給→受取接続→必要な結合検収を既存元IDの中で順序付ける。供給担当が誰で、受取がどの版で何を使えるようになるかを定める。必要なら契約の不明点だけを最小試験で確かめる。CLI表現が合わなければその維持担当を置き、親偽done・依存削除・依存なし詳細で迂回しない。

供給カテゴリは実成果の成立、受取カテゴリは対象版/環境での受入と元IDの実再開を共通実行ループで確認する。供給予定・通知・型固定だけで実待機を解除しない。独立工程だけ再開した場合はその進展と、残る通常接続の阻害を分ける。

## 4. 共有mainと試験枠

試験資源の利用権と製品判断権を分ける。共有main/checkout・index・build出力・server・試験stateはprojectの既存手順を使い、競合する操作範囲と時間だけを調整する。全IDの開始/完了を一つの検証GOへ集約しない。

承認済み優先順位・具体的な依存解除を優先し、同順位なら準備完了順等の規則を当事者で一度合意する。現利用者は対象・解放条件・次利用者を既存記録へ示し、process終了と実解放を確認する。次担当は最新対象版と二重利用がないことを確認して着手し、カテゴリの再ACKを待たない。

HEADだけでWIPの検証入力を固定したとしない。結果を変える依存file・WIP・生成物・stateの変更だけを調整し、無関係な編集は止めない。証拠対象が動けば影響部分を検証する。有効な供給検収を再利用し、各consumerの変わる結合境界を確認する。

lock/lease/CAS等は実仕様がある場合だけ使う。ない排他APIを捏造せず、明示的な受渡しで確定できない資源操作だけ保留する。汎用スケジューラを導入条件にしない。同じ衝突が続く場合はカテゴリが境界・操作順・入力の固定範囲を見直し、全員同報や催促で補わない。

## 5. 優先順位・最終統合

全体の基準は承認済み計画。カテゴリ内順序はそのカテゴリ、横断変更は影響カテゴリが直接決める。製品到達点を変える判断に限り利用者へ戻す。

最終統合・横断検証・リリースを元条件として持つ既存IDのPMがその操作/判定を担当する。自分の統合条件を未完にできるが、他IDの無関係な局所完了を承認制にしない。未割当なら第3節で所属を決める。全体完了は単一正本の全原scope・必須統合/V・必要正式化の充足であり、main採用や統合担当の一言では代替しない。

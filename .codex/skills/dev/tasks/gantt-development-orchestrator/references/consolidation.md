# 担当の所有移管と任意の統合集約

実際に承認された移管だけに使う。単体ID PMへの所有移管は、main全集約・Worktree再展開とは別であり、それらを前提にしない。スキル導入は担当への通信、移管、merge、archive、再展開、課金の新規許可ではない。権限・実ツールは[共通実行条件](../../codex-task-split/references/execution-context.md)に従う。

## 1. 単体ID担当への所有移管

既存の複数ID PMからカテゴリ管理と単体ID PMへ移す場合も、同ID PMを正式後継へ交代する場合も、次の順序を守る。契約文書だけの更新なら、既存担当を自動的に作り直さない。

1. **現在の全scopeと所有を照合する。** 最新正本、原依頼/実launch/承認移管、各元ID、実chat、採用版、WIP/untracked、claim、未回収workerを読む。対象IDだけを選んで移し、残ID・残WIPの責任を消さない。
2. **対象を移管中として区切る。** 旧PMは対象の現在の最小成果と既存worker回収・限定修正で区切り、新しい別ID/worker/WTへ広げない。成功まで無期限に移管を遅らせず、未解決なら差分・失敗条件・残checkを保持して渡す。
3. **後継PMを読取から始める。** 承認済みの元ID一つの新規chatへ第2節のhandoffを渡す。新PMは元条件、成果版、証拠、未回収、再開工程を照合する。この段階では二重claim・実編集・worker起動をしない。
4. **旧編集終了と所有切替を確定する。** 旧PMとworkerの編集/書込process終了を確認する。原則として旧PMがworkerを回収してから渡す。継続委任を移す場合も、既存許可と実ツールが対応する報告先変更・受渡しを明示し、同成果のworkerを重複起動しない。projectの正当なtransfer/claim手順で新ownerを一意にし、新PMが実状態を確認する。失敗・結果不明なら再照会し、両者を編集に入れない。
5. **同じ元IDの残工程へ戻る。** 新PMは[原ID開始手順](playing-manager.md#3-原idの開始)で引継いだ設定・前提・原残条件を確認し、自分のchatに現在の開始表を提示して実編集を始める。証拠・採用版・失敗・修正回数・未回収をリセットしない。必要な旧担当への照会はできるが、通常完了の承認先にはしない。
6. **移した範囲からカテゴリ管理へ切り替える。** 旧複数ID PM chatは、移管済みIDの実装・最終検収を重ねず、配置・依存・回収状況を管理する。未移管WIPは旧責任として明示し、全移管完了まで無担当にしない。既に単体IDだけを持つPMを、名前合わせのために交換しない。

新PMは旧実装枠を置き換え、単純に並行枠を追加しない。実装中・阻害中・未回収の上限はprojectの許可/資源/回収能力に従い、移行都合で固定人数を導入しない。不要な資源占有は解放しても未完IDの責任は残す。

旧全体指揮役がある場合は、その共有契約・未割当・統合条件の責任も関係カテゴリ/元IDへ対応させる。移管済み範囲の判断・検証開始GO・通常完了を旧役へ戻さず、未移管部分は移管中の旧責任として区別する。責任の引渡し後に常設Rootを残さない。

## 2. handoffで保持するもの

既存handoffへ、元ID/全scopeと原body/check/必要level、現在の最小成果、実thread/worker/依頼回・修正履歴、repo/checkout、固定HEAD/base、owned tracked/untracked、index/WIPの識別と所在、実検証・失敗・残check、採用済み/未受入、process、新旧ownerと未移管の責任、再開工程を残す。必要情報への参照でよく、別の移行台帳や毎成果の承認表は作らない。

秘密・鍵・Cookie・個人profile・顧客stateの内容は転記しない。Git外stateの所在/所有/復元方法もprivateな許可された保存先で管理する。Gitコードの保護とGit外stateの保護は別。

差分は認可されたlocal ref/bundle、staged/unstagedのbinary差分、選別したuntracked等で復元可能にする。bundleにWIP/ignoredが入るとは思わない。stateはcheckout保持を優先し、移動が必要な場合だけ書込を止めて整合した退避/復元を確認する。製品にbackup機能を追加しない。

提出した固定版を勝手に動かさず、限定修正で動けばhandoffと証拠対象を更新する。停止指示の配送・handoff受領・正本の所有移管・実再開は別々に確認する。

## 3. 任意のmain集約を選んだ場合

利用者が統合集約を選んだ対象だけに適用する。通常の部分供給や単体IDの完遂を、全体のmain統合待ちにしない。main以外が統合先なら承認されたbranchを使い、検収済みcommitをMと呼ぶ。

既存計画/handoffへ切替根拠、対象scope/checkout、最小成果、統合先、認可された統合担当、再開条件を残す。統合担当はその操作/検収を原条件として持つIDのPMであり、全成果の承認上位ではない。責任が未割当なら[カテゴリ間調整](category-coordination.md)で所属を確定する。通常/統合集約は方針の属性であり原task statusではない。

対象PMは全担当完遂を待たず、現最小成果と既存workerで区切る。新ID/worker/WTへ広げず、未解決は復元可能な差分・失敗条件付きで保留する。関係カテゴリは各対象の未回収と引継ぎ先を追う。

## 4. 全旧差分の処遇

承認された対象scope内のGit inventoryの全checkoutを、固定HEAD差分、WIP、コピー、古いbase、採用済み後続版と照合する。現在の担当chat一覧だけで網羅したとしない。差分量/ahead数/Source数は成果量ではない。

| 分類 | 保持する対応 |
| --- | --- |
| 採用 | 必要前提とowned差分、受入先commit、検収範囲、対応する原check。 |
| 既採用・後続版で代替 | 採用/代替版と意味上の対応。file不一致だけで未採用、同名だけで同成果としない。 |
| 重複 | 保持する正規成果/版への参照。別workerで同copyを新成果にしない。 |
| 保留 | 復元可能な固定保存先、理由/失敗/未確認、依存影響、元ID/責任者、次の是正条件。 |

対応単位は「checkout + base/HEAD/WIP識別 + 対象差分 → 分類 → 行先 → 元ID/理由」。同file内の採用/保留が混在すれば必要箇所だけ分け、親branch全差分を承認したことにしない。通常は責務/機能単位とし、意味の衝突箇所だけ細かく調整する。

未収録・除外ファイルの保存・影響・担当を現地で確定する。所在不明・復元不能・採用対象への依存不明を保留ラベルで隠して次へ通さない。

## 5. 統合・同一基点再展開

1. 関係カテゴリと旧PMが対象checkout/worker、WIP/state/process、復元方法と全差分処遇を確認する。各分類に行先・元ID・責任があり、未確認が採用成果を脅かさないことを確かめる。
2. 認可された統合PMが必要な前提と採用差分を一組で統合する。既採用は再適用せず、保留へ暗黙依存しない。候補commit自体で変更範囲の型/build/結合/回帰とproject必須Gateを検収し、戻し方を保持してMを固定する。
3. 各カテゴリが第1節に従って全原ID・完了履歴・残条件・保留を対応する新ownerへ渡す。未着手をin_progressにしない。統合完了を全I/C/Vのdoneや全保留解決と混同しない。
4. 認可された起動者が実ツールでMを使える開始元を確認する。新PMの実HEAD=M、環境setup、正本revisionと所有を確認し、旧WIPを無断で混ぜない。共通の再開条件が成立したことを関係カテゴリで共有する。
5. 新PMは起動/再開文の[開始表](playing-manager.md#3-原idの開始)を確認し、同じ元IDの残工程へ戻る。カテゴリは実chatの提示・実設定・実着手を事後に照合する。準備成功・配送・読了を開始確認にせず、通常着手に再ACKを挟まない。

必要動作を壊す採用セットは止めるか、依存ごと整合する保留へ戻す。移行都合の保証縮小を技術判断で確定しない。必須有料検証でないものを移行専用Gateに足さず、必須V未証明はそのまま引き継ぐ。実際の必須Gateも外さない。

`create_thread`等の実project/startingStateが対応する開始元だけを使い、任意cwd/ref引数やbranchNameへのSHA流用を仮定しない。新branchが必要なら正確な名前と作成許可を確認する。`create_worktree`の呼出chatへのattachをPM起動と混同しない。利用できる経路がなければその再展開は未実行として残す。

## 6. rollbackとarchive

候補段階では認可済み候補変更を戻し、昇格後は依存順とproject方針に沿ってrevert等で戻す。統合先が想定から動けば昇格を止めて関係カテゴリで調整し、未push成果・制作stateをresetで消さない。移管を戻す場合も新旧ownerとhandoffを更新し、二重稼働させない。

旧WT削除・chat/WT archiveは別判断。Git inventoryとmanaged attachmentは別であり、一覧が空でも対象不存在とはしない。exact identityKey、primary/pinned/shared等の制限、ignored state、実clientでのarchive効果を確認する。一括archiveを既定にせず、保護済み旧checkoutを停止・保持したまま進められる。

# 任意の統合集約：全差分の処遇 → main M → 同一基点再展開

利用者が選んだ移行だけに使う。通常の部分供給・次ID継続は妨げない。本書を読んだこと、スキルを導入したことはmerge、archive、再展開、課金の実行承認ではない。統合先がmain以外のprojectでは承認された統合branchを使い、その検収済みcommitをMと呼ぶ。

## 1. モードと停止の範囲

既存計画/正本handoffへ、切替根拠、対象scope/checkout、現在の最小成果、統合先、実行責任者、再開条件を記録する。別の移行進捗台帳は作らない。`通常`/`統合集約`は方針の属性であり原taskのstatusではない。

旧PMは現在着手中の最小成果と既存workerを回収・検収して区切る。担当全scope完遂まで待たず、新ID・新worker・新WTへ広げない。既存workerにはその単位を閉じる限定修正を依頼できる。解決不能・時間を区切る必要がある成果は、再現条件と固定差分を残してHOLDとして渡す。未解決をdoneにしない。

| 時点 | 停止・責任 |
| --- | --- |
| workerの成果固定 | 編集と書込processを停止し、固定版/検証/未完をPMへ渡す。原則未commit。 |
| PMのhandoff提出 | 提出した版を勝手に動かさない。実行役が実thread/HEAD/WIPと照合する。 |
| handoff受領 | 旧PMの通常編集を停止。照会と明示された限定是正は同担当で対応できる。 |
| 新ownerの全scope受領 | 正本で所有を切り替える。実行役が受領までの引継ぎ責任を持つ。旧担当責任を先に消さない。 |
| M再展開の確認・通常へ復帰 | 新担当が次ID自律着手を再開する。handoff受領だけでは再開しない。 |

修正の再開で成果版が動いたらhandoffを更新する。旧版の証拠で新差分を検収済みとしない。停止指示を送っただけで編集終了にしない。

## 2. 正式handoffの最小項目

既存handoffに、原scopeと現在の最小成果、実thread/worker状態、repo/checkout、固定HEAD/base、owned tracked/untracked差分、index/WIPの識別と所在、実検証と失敗、原check残件、採用済み/未受入、process、ignored制作stateの所在/所有者、復元方法を残す。

秘密・鍵・Cookie・個人profile・顧客stateの内容は転記しない。存在/所在の管理もprivateな許可された保存先へ限定する。Gitコードの保護とGit外stateの保護は分ける。

コードは認可されたlocal ref/bundle、staged/unstagedのbinary差分、選別したuntracked等で復元可能にする。bundleにWIP/ignoredが入るとは思わない。stateはcheckout保持を優先し、移動が必要な場合だけ書込processを止め、projectが許す整合した退避/復元を確認する。製品に新しいbackup機能を追加する依頼ではない。

## 3. 全旧差分を処遇する

Git inventoryの全checkoutを対象に、固定HEAD差分、WIP、コピー、古いbase、採用済み後続版を照合する。現在の担当chatだけで網羅したとしない。差分量/ahead数/Source数は成果量ではない。

| 分類 | 必須の対応 |
| --- | --- |
| 採用 | 必要な前提とowned差分、受入先commit、検収範囲、対応する原check。 |
| 既採用・後続版で代替 | 採用/代替版と意味上の対応。file不一致だけで未採用、同名だけで同成果としない。 |
| 重複 | 保持する正規成果/版への参照。別workerで同copyを新成果として数えない。 |
| 保留 | 復元可能な固定保存先、理由/失敗/未確認、依存影響、原ID/責任者、次の調査・是正条件。 |

対応単位は「元checkout + base/HEAD/WIP識別 + 対象差分 → 分類 → 行先 → 原ID/理由」。同じfile内に採用と保留が混在すれば必要な部分を分け、親branchの全差分を承認したことにしない。通常は責務/機能単位でよく、意味の衝突がある箇所だけ細かく調停する。

未収録・除外ファイルは消えたことにしない。現地で保存・影響・担当を確定し、採用しない範囲は理由付き保留として扱える。ただし、所在不明・復元不能・採用対象への依存不明を保留ラベルで隠してgateを通さない。

## 4. 統合と再展開のgate

| 順序 | 所有者 | 次へ進む条件 |
| --- | --- | --- |
| 保護・受領 | 実行役＋旧PM | 対象checkout/workerを網羅し、固定成果・WIP・state・processと復元方法を確認。 |
| 全差分処遇 | 実行役と必要な担当 | 未分類ゼロ。各分類の行先・原ID・責任がある。未確認が採用成果の成立を脅かしていない。 |
| 統合候補 | 認可された統合担当 | 既採用は再適用せず、必要前提を一組で統合。保留へ暗黙依存しない。 |
| main昇格 | 同担当 | 候補commit自体で変更範囲の型/build/ローカル結合/回帰とproject必須Gateを検収。秘密・競合・必須能力欠落がない。戻し方を保持しMを固定。 |
| 全scope移管 | 実行役＋新旧担当 | 元body/check/level・全ID・完了履歴・保留・次IDを維持し、一意な新ownerが受領。未着手をin_progressにしない。 |
| M再展開 | 認可された起動者 | 全新担当の開始HEADがM。専用環境と正本revisionを確認し、旧WIPを無断で持ち込まない。 |
| 通常へ復帰 | 実行役 | モード切替と次工程を伝え、PMは再承認待ちなしで元scopeを順次進める。 |

統合完了は、全旧差分の処遇が確定し採用対象がMに揃った状態。全branchの無条件merge、全原I/C/Vのdone、全保留の解決ではない。保留を外して必要動作が壊れるなら、その採用セットを止めるか依存ごと整合した保留へ戻す。利用動作の縮小を技術判断で確定しない。

projectが有料検証を昇格必須としていなければ、移行のためだけに有料実行を新たなgateにしない。必須V未証明はそのまま引継ぐ。逆に実際の必須Gateを移行都合で外さない。

## 5. 同じMを実ツールで開始する

実ツールのproject/startingStateで、Mを指す承認された開始元を使用できるか確認する。branchNameに任意SHAを入れれば動くとは仮定しない。`create_thread`のないcwd/ref引数を捏造しない。新branchが必要なら、正確な名前と作成許可を利用者が選ぶ。

`create_worktree(ref)`が呼出chatへattachするだけの場合、それでPMのcwdや新chatを移したことにしない。利用できる経路がなければ、その再展開部分を未実行として残す。成功した新chatの実HEADをMと照合する。既存workerが別WTだからという理由だけで誤起動としない。

## 6. rollbackとarchive

候補段階では認可済みの候補変更を戻す。昇格後は依存順とproject方針に沿ってrevert等で戻す。mainが想定から動いたら昇格を停止して調停し、未push成果や制作stateをresetで消さない。移管後に戻す場合もownerとhandoffを更新し、旧担当を二重稼働させない。

旧WTの削除・chat/WT archiveは別判断。Git inventoryとmanaged attachmentは別なので、一覧が空でも対象不存在とはしない。exact identityKey、primary/pinned/shared等の制限、ignored state、現clientでのchat archiveの効果を確認する。一括archiveは手順の既定にしない。保護済み旧WTを停止して保持したまま再展開できる。

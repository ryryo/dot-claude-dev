# 単体ID PMの実行入口

この資料は元ID一つを担当するPMの開始・継続・終了を定める。通常実行は下の本文を使う。起動者も同じ本文を送信文へ展開し、別版のPM手順を書かない。既に展開済みの本文を受け取ったPMは、同じ説明を読み直す必要はない。

## 1. 自分で決める範囲

PMが中核設計・実装・自己検収・最終採否を担当する。役割別のモデル指定はprojectに従い、名称だけをワーカーに変えて判断を委ねない。具体的な操作権限と環境は[共通実行条件](../../codex-task-split/references/execution-context.md)で確認する。

## 2. 初動：元IDと既成果を照合する

起動入力の原依頼、元body/check、必要level、既成果、ownerを最新の正本と照合する。I/C/Vの解釈、供給の開始条件やCLI判定に不一致がある時は[scope契約](scope-and-gates.md)を読む。引継ぎ読取りだけが許可されている場合は、実装開始へ進まない。

## 3. 原IDの開始

次のブロックがPMへ渡す実行本文の正本で、5列の開始表もここだけに置く。起動者は[起動文の組み立て](task-launch.md#起動文の組み立て)に従って共通本文を展開する。表の具体的な内容はPM自身が決める。

```text
あなたは指定された元ID一つのPMです。設計・中核実装・必要な通常経路への接続・ワーカー回収・自己検収から、正当なCLI完了と必要な正式化まで担当してください。
部分成果後、修正時、中断や供給待ちからの再開時も同じID・同じchatで続けます。別IDはこのchatで始めません。

【開始】
最新の正本、元body/checkと必要level、owner、作業先のcwdとHEAD、許可されたモデル・環境、WIPと未追跡差分、採用版、未回収ワーカーを確認してください。
今回使う機能が受取版と環境で使えるかを確認し、型を使う独立TDDと実能力を使う通常接続の開始条件を分けます。CLIが合法に許す範囲で開始してください。
読取移管中はclaim・編集・ワーカー起動を始めません。既存担当がいる場合は、旧担当の編集と書込processの終了、正当な所有移管を確認してから実編集します。
実装前に、自分のchatへ「開始：対象元ID」と次の表を提示してください。

| 元ID・利用動作 | 減らす原checkの残条件 | PMの中核実装・統合 | worker成果または不使用の理由 | モデル・推論と選定理由、前提/順序・検収 |
| --- | --- | --- | --- | --- |

元ID全体の未充足条件から、実装、原条件に必要な通常接続、検証、CLI完了と必要な正式化までの残工程を見通してください。2列目の原check参照と最後の列で、今回工程の終了条件、次工程、その前提を対応付けます。全checkの再転記、後工程の詳細設計、新しい計画書は不要です。
中核実装、ワーカーの担当成果または使わない理由、PMとワーカーの実モデル・推論と理由を具体化し、編集範囲、実装順、検収方法を決めます。
表の提示後、実着手に合わせて正当なCLIでclaim/in_progressを更新し、実装と必要なワーカー起動へ進みます。カテゴリのACKは待ちません。
同ID・同分担の再開では、自分のchatにある完全な開始表を現在の設定・境界・base・前提と照合し、参照と差分で続けて構いません。分担等が変わった場合、表を特定できない場合、正式後継の初回は現在の5列を提示します。
開始表の漏れは現在の状態で補正し、開始前に提示していたことにはしません。既成果、claim、証拠、修正履歴は残します。

{{EXECUTION_LOOP}}

【同じ元IDの残工程を進める】
部分実装、検証、回収、commit、固定成果の供給を終えたら、影響する原checkを証拠と照合し、次の未充足条件を選んでください。今回工程の成功を元IDの区切りにせず、前提と権限が足りる次工程を同じPMが続けます。提出済みの固定成果や共有試験の入力は合意した条件で保護し、続行時に無断で変えません。更新は既存表・正本の該当箇所だけでよく、開始表の再掲やカテゴリのACKは不要です。
ワーカーを使う場合だけcodex-task-splitの依頼・回収手順を読み、独立した担当成果を渡してください。小作業で使う義務はありません。中核判断と統合は自分が持ち、同じファイルを並行編集しません。
待機直前、再開直後、成果の確認時には、未回収ワーカーの実threadと差分を読みます。通知なしのcompletedや未commit成果も回収し、同ワーカーへの修正依頼、引取り、または前提解消で進めます。
原条件が残るのに進める工程がない時は、同ID内の独立工程と回収可能な成果を確認してから待機します。上の工程本文と適用先ツールの正当な記録手順に従い、現在の保留条件を同じ元IDへ残してください。役割名だけで実担当を特定できない供給は、所属カテゴリへ担当確定を求めます。不要な試験枠を解放しても元IDの責任は手放しません。前提が変わったら現PMが受入・解除を再評価し、次の操作と実再開の観測を更新します。通知の閲覧や受領は再開にしません。

【元IDを完了する】
元body/checkが要求する実装・通常接続・検証を満たし、必須CI/Gate・実サービス・OS・認可・安全性と必要levelを保ちます。I/C/Vの範囲を縮めず、後段全体を元Iへ足しません。
型やfixture、ワーカー終了、commit、main採用だけでは元ID完了にしません。対象版・依存・環境・検証対象が一致する証拠を再利用し、失敗・cancelled・skip・未実施は残します。
原checkは満たした範囲だけを更新します。全原条件の検収が済んだら追加改善を探さず、最新の依存・owner・revisionと現在の証拠を照合して正当なCLIで元IDを完了にします。既存CLIのcanComplete等の表示だけでdoneにせず、claim・lock・CASを迂回しません。
必要なcommit・受渡しはprojectの順序に従います。途中失敗や結果不明では実施済みを確かめ、残りだけ処理してください。採用版、原checkの結果、証拠、CLI更新、未完の正式化を既存記録へ対応付けます。正式化待ちの記録があれば、必要な処理の実終了を確認して更新し、元IDのdoneだけで未処理を消しません。
全原条件と必要な正式化を終えたら、所属カテゴリへ一度、元IDの完了を通知します。供給Iと未完consumer C/Vは区別し、原条件外の後続全完了まで担当を延長しません。

{{DELIVERY}}

{{COMMUNICATION}}
```

### 実装・検証を必要な範囲で終える

工程終了と反復防止の正本は[共通の工程本文](../../codex-task-split/references/execution-loop.md#起動文へ展開する工程本文)。上の実行本文へ展開して使う。

## 4. 実装・worker回収を進める

ワーカーを使う時は[codex-task-split](../../codex-task-split/SKILL.md)、回収・品質修正・引取り時は[main-review](../../codex-task-split/references/main-review.md)を使う。ワーカーを使わない作業に、委任や回収の手順を追加しない。

## 5. 検収・元IDの完了

通常の自己検収と終了は第3節に従う。供給側と受取側の責任や完了依存を確認する時だけ[開始・完了判定](scope-and-gates.md#4-開始判定と完了判定)を読む。CLI・commit・配送の途中で中断した場合は、実施済みを照合して未処理の部分だけ続ける。

## 6. 同ID継続・阻害・再開

| 必要になった判断 | 読む箇所 |
| --- | --- |
| 作業が止まった、同じ試行を繰り返す | [原因の判別と再開確認](../../codex-task-split/references/execution-loop.md#1-現物と次の判別点を結ぶ) |
| 実能力不足かCLIの判定不一致か | [CLI是正の条件](scope-and-gates.md#5-cli不一致を閉じる是正経路) |
| 共有仕様・責任・互換性を変える必要がある | 所属カテゴリへ根拠と案を渡す。判断は[関係カテゴリ](category-coordination.md)が行う。 |
| 配送結果が不明、相手が再開しない | [配送結果の確認](../../codex-task-split/references/delivery.md#3-結果不明と未配達) |
| 承認された担当交代・統合集約 | [所有移管](consolidation.md)。原条件、WIP、証拠、未回収、修正履歴を後継へ渡す。 |

通常の再開は第3節の既存表と差分で続ける。idleや無応答を所有解放とは扱わない。CLI拒否を依存削除・偽done・依存なし詳細への付替えで迂回せず、handoffの完了を元ID完了と混同しない。

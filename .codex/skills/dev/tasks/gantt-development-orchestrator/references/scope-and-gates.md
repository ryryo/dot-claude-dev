# 全原scope・証拠と開始/完了の契約

原条件の対応、今回工程の能力判定、CLI是正で守る判定条件の正本。復旧の進め方は[共通実行ループ](../../codex-task-split/references/execution-loop.md)を使い、本書に別の復旧ループを作らない。projectの既存正本/CLIを使い、新しいschema・statusを本書から導入しない。

## 1. 分母と責任を保持する

原依頼・実launch・承認された追加/移管と、正本の元IDを双方向照合する。初回/後続、設定、通常入口、保存、共有機能、C/Vも含め、owner・ready・現在の成果だけから全scopeを推測しない。

全管理ID集合、原根拠、未割当/重複、移管前後の責任は既存計画/正本に残す。図や順序表はその読取表示であって第二台帳ではない。件数差は選択範囲/承認移管で説明し、既存責務を新IDへ二重登録しない。

カテゴリの管理ID群とPMの実作業claimは別。元IDの実owner/chatは一意にし、旧編集終了・受領・正当なtransferを確認する。残WIPを無担当にせず、revision/lock/CAS等の安全な更新手順を保持する。

## 2. 原checkに成果をつなぐ最小構造

projectの既存task/checklist/evidence/ref/nextAction/handoffを使う。以下は対応内容であって追加schemaや必須表ではない。

| 対象 | 保持する対応 |
| --- | --- |
| 原task/check | 元body/check/必要level、全scope、管理責任と実owner。保証を短縮しない |
| 既成果 | 固定版/差分、owned範囲と必要前提、どの原条件を満たすか |
| 採用 | consumer受入版/範囲と検収、main採用版または未採用 |
| 証拠 | 対象版・依存・環境・level、実command/selector・実対象・自然終了結果、未実施も区別 |
| 不足と次 | 原残条件、解決/再開担当、供給元/受取元ID、必要版/環境・解除条件・次工程 |
| 回収/正式化 | worker/依頼回/成果版、採否、CLI/commit/受渡しの実施済みと未完 |

一checkの複数条件は補助内訳として表示できるが、元本文を改変して保証を落とさず、内訳行をID完了数へ加算しない。大きいIDも同じ元ID内で残条件を順に閉じる。

カテゴリは全管理scope、PMは自元IDの初動と、成果・受入・失敗・能力変更・移管・終了時の影響部分を更新する。全文の定期コピーや全後続工程の事前設計は不要。不足は「未完」だけでなく次の実装/接続/検証と担当へ結ぶ。

## 3. 段階と責任の境界

I/C/V等の意味は元body/checkに従う。IにUI・実資源が必要なら含め、常にmock/部品だけへ縮めない。後段全体のGUI/停止/履歴/API/CLI等を元Iへ無断で足さない。

通常入口→処理→保存/再読→利用側が元条件なら、その責任と実経路を持つ。ID/digest/版、認可・所有・資源寿命等の意味も照合する。fixture/export/型一致だけで通常接続済みにしない。必須VのOS・競合・Undo・復旧・実サービス・独立レビューは原条件の範囲を保持する。

供給Iは自分の原条件と必要受渡し、consumer C/Vは自分の利用経路と検証で完了する。受取PM未配置なら受取カテゴリが責任を持ち、供給成立後の着手/同ID再開まで追う。供給不良は供給元の原条件へ戻し、未実装consumerの全責任を供給PMへ押し付けない。

部品成果、独立開発開始、実能力受入、main採用、元段階完了、必要正式化は区別する。acceptedやdoneの一語で兼ねない。

## 4. 開始判定と完了判定

開始対象を工程ごとに特定する。型の固定と実能力の成立を同じ「受入済み」で表さない。

| 判定対象 | 成立条件 |
| --- | --- |
| 型/署名を使う独立実装・TDD | 合意済み契約と編集境界で独立でき、今回工程の前提が足り、権限と実CLIがその開始を合法に許す。実能力の供給済みや通常接続完了とは記録しない |
| 実能力を呼び出す通常接続・実検証 | 必要実装と前提がconsumer対象版へ入り、実入口・権限・保存/資源寿命・環境が今回使う範囲で成立し、CLIも開始を許す |
| 元ID完了 | 元body/check/必要level、段階の完了依存、projectの完了条件を満たす。正式化の未完は別に閉じる |
| 外部実行 | projectの許可・接続条件・費用制約を満たす。鍵の存在を実行承認にしない |

能力は契約/呼出元・供給版・consumer版・必要環境・検収範囲・証拠で特定する。供給予定、形式依存の通過、型やfixtureだけでは実供給としない。一方、今回の独立工程に不要な供給担当全体doneやmain全集約を開始条件に足さない。

例えば読取署名だけ固定した工程ではconsumerの独立TDDを進められても、認可された実読取がない間は通常読取経路を成立済みにしない。版/環境が動けば影響範囲を再評価する。実CLIが部分工程を表せない場合は次節の是正対象であり、無断で先にclaim/実装しない。

不足中も同ID内の非依存工程を進められる。カテゴリは許可/WIP枠内で別IDのPMを配置できるが、阻害中PMを別IDへ移して元担当を失わせない。依存削除・親偽done・依存なし詳細への付替えは使わない。

## 5. CLI不一致を閉じる是正経路

復旧の順序と効かなかった時の再判別は共通実行ループを使う。CLI固有に次を確認する。

PMは元ID/check、実commandと拒否理由、今回工程、供給/consumer版・必要能力・実ownerを特定する。原条件の誤読、実能力不足、反映漏れ、CLI表現不足を分ける。能力がないなら供給へ戻し、CLIを緩めない。

表現不一致なら、CLIの供給/維持責任カテゴリと受取カテゴリが既存の是正担当を確定する。既承認契約に合わせる最小修正だけを権限内で行う。製品保証/範囲・権限を変える場合に限り利用者へ戻し、権限外のCLI編集をしない。

検収は正しい工程開始が通り、実能力なしの実接続、原条件不足の完了、不正ownerが拒否されることを確認する。旧edge・版変更・循環・同時revisionの安全性も影響範囲で保つ。是正側は実供給、受取側は同じ元IDで実更新と元工程への復帰を確認し、CLI修正文の配送だけで解消にしない。

## 6. project CLIへ要求する最低対応

実装が必要と分かった適用先だけの要求であり、スキル導入の前提作業を一律に増やさない。実在schema/コードを読む。

- 開始評価と完了評価を分け、ready表示とclaim/in_progressが同じ工程開始条件を使う。
- 必要な既存edgeだけに段階・能力・証拠・対象版を表現し、別能力DBや汎用force開始を作らない。
- 明示されない旧edgeは保守的な既存判定を維持し、一括で依存を緩めない。
- revision/lock/CASとowner検査を保持し、評価後に前提が動けば再評価する。正本の許可なしにschemaを手編集しない。
- 拒否理由を不足能力/版/原checkと次の再開判断へ結ぶ。

原条件の誤読訂正→真の部分開始の特定→必要な最小修正→表示/更新の検収→同ID実再開まで閉じる。新しい台帳や上位承認経路は作らない。

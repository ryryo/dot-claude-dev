# 全原scope・証拠と開始/完了の契約

本書は全scopeと原checkの継続対応、能力判定、機械拒否の是正を定める。進捗schemaやCLI自体を実装せず、projectが指定した正本一つと更新手順へ対応させる。本文中の説明分類は新しいtask statusではない。

## 1. 分母を先に固定する

原依頼、実際に送った担当launch、承認された移管/追加範囲を正本の既存IDへ対応させ、逆に各抽出IDの責務根拠を照合する。初回/後続、設定、通常入口、保存、共有機能、C/V等の責任を含める。owner・ready・現在の成果・選択集計から全scopeを推測しない。

全ID集合、原根拠、未割当、重複、移管前後の責任を既存計画/正本に残す。正本からの図・順序表は読取表示であり第二台帳ではない。件数の差は選択範囲と移管根拠で説明し、都合よくIDを除外しない。元IDに対応する既存責務を別taskで二重登録しない。追加詳細が全て新機能とも、全て原完了とも決めつけない。

## 2. 原checkに成果をつなぐ最小構造

以下は論理項目であり固定schemaではない。projectのtask/checklist/evidence/ref/nextAction/handoff相当を使う。schemaが足りないときは既存noteに参照を持たせ、必要な最小拡張をproject担当へ依頼する。別のprogress.json、回収DB、能力台帳を作らない。

| 対象 | 保持するもの |
| --- | --- |
| 原task/check | 元body/check/必要level、全scopeと責任者。元文を短縮して保証を落とさない。 |
| 既成果 | Source/固定差分、owned範囲、前提、どの原条件を満たすか。Source数を完了数へ換算しない。 |
| 採用 | consumerで受入れた対象版と検収、main採用版または未採用。供給版だけで使用可能にしない。 |
| 証拠 | 対象版、環境、必要level、実行コマンド/selector、実対象と終了結果、参照。未実施も区別する。 |
| 不足と次 | 元条件の未充足、必要な実装/通常接続/実サービス試験、次の元ID、能力/供給者/解除条件。 |
| 回収・正式化 | 実workerへの既存ref、依頼回・成果版、受領/採用、未完工程。詳細は共通回収契約へ参照。 |

一つのcheckに複数条件があるなら内訳を表示してよいが、その行数はtask完了数へ加算しない。原checkを分けるために元本文を改変せず、checkへの補助対応として扱う。

初動で全scopeの既証拠・不足を対応させ、以後は成果発生、受入、失敗、能力変更、移管、終了/次ID選定のときに影響部分を更新する。毎日全文をコピーしない。全後続IDの実装手順やworker成果を事前に完成させる必要もない。

「元は未完」とだけ書かず、どの原条件が残り、誰が何を実装/接続/検証して閉じるかを書く。担当の自己報告と実版・証拠が異なれば、その差の調停を次の具体処置にする。

## 3. 段階と責任の境界

I/C/V等の定義はprojectの原body/checkに従う。IにUI操作・実資源が必要なら含める。Iを常にmock/部品のみへ縮めず、後段のGUI/Stop/履歴/API/CLI/MCP等の全完了を元Iへ無断で足さない。

通常入口→共通処理→保存→次の利用が接続条件なら、その経路を責任者付きで扱う。共通機能の最初のconsumer接続と、全利用側のC/Vは別。必須VのOS・競合・Undo・復旧・実サービス・独立レビューは、元条件が要求する範囲を保持する。

説明上は「部品成果」「consumer受入」「main採用」「元段階完了」を別に持つ。accepted、done、handoff受領など一つの語だけで全てを兼ねない。原親をdoneにする判定は、原check/levelと正本の合法な条件で行う。

## 4. 開始判定と完了判定

| 判定 | 必要な条件 |
| --- | --- |
| 開始 | 担当・実行モード・権限・編集競合が成立し、今回使う具体能力が利用対象版で受入済み。project CLIも同じ範囲の開始を合法に許す。 |
| 完了 | 元body/check/必要levelとその段階の完了依存を充足し、残る正式化/受渡しを区別して記録する。 |
| 外部実行 | projectが定める許可・接続条件・費用制約を満たす。非依存の実装まで待機へ広げない。 |

能力は呼出元/契約/対象版/証拠で特定する。供給側の「使える」報告だけで成立とせず、consumerの版へ取り込んだ必要前提と検収範囲を照合する。main採用を一律条件にしないが、採用版にない能力を利用したことにもしない。版が変わったら影響範囲を再評価する。

例：読み取りportが固定版で受入済みなら、そのportを使う後続の実装を先行できる。先行担当の全機能doneは不要。一方、採用→Undo→保持の原checkを閉じるのに必要な保持能力が未供給なら、実装着手できても完了できない。異なる段階条件を混ぜない。

必要能力がない場合、元IDを未完のまま保持し、承認済みの独立IDへ進める。詳細行追加が正当な場合も、どの原条件を減らすかを示し、CLI拒否された仕事を依存なし詳細へ移して迂回しない。

## 5. CLI不一致を閉じる是正経路

1. **PMが拒否を特定する。** 元ID、拒否された実command/理由、必要能力と供給/consumer版、根拠check、進めたい範囲を既存block/handoffへ残す。実装済みと偽って開始を通さない。
2. **実行役が原因を分ける。** 実能力不足、原条件の誤読、台帳の反映漏れ、CLIの表現不足を区別する。例えば原Iに後段全体が混入しているなら、既契約への訂正を先に行う。
3. **是正担当と最小成果を割り当てる。** 既承認の契約を機械判定へ合わせる修正は技術判断。利用動作/保証/許可の変更が必要な場合だけ利用者判断へ戻す。権限外のCLI編集を勝手に実行しない。
4. **対象版で検収する。** 正しい開始は通り、能力なし・原check不足・不正ownerは拒否されることを確認する。
5. **元PMが同じ元IDで再評価・着手する。** claim/in_progressが実際に通り、次の実装へ進んだことまで確認する。RootのACK待ちを挟まない。

判断依頼を送って終わりにせず、実行役が未是正の責任と再評価先を持つ。是正中の独立実装は継続できる。新しい上位承認制度は作らない。

## 6. project CLIへ要求する最低対応

これは別実装への要求であり、このスキル導入だけでは実装されない。実在schema/コードを読んで適用先を決める。

- 開始評価と完了評価を分け、表示readyと実際のclaim/in_progressで同じ開始評価を使う。
- 既存dependency/evidenceに必要なedgeだけ、段階・必要能力・証拠参照・対象版を表現する。別能力DBや汎用force開始を作らない。
- 明示されていない旧edgeは保守的な既存判定を維持する。一括で全依存を緩めない。
- 最新revision、lock、CAS等の既存更新安全性を維持し、評価後に前提が変われば再評価する。正本の許可なしにschemaを手編集しない。
- 拒否理由は不足能力/版/元checkを再開判断へ渡せる形にする。

移行は原条件訂正→残る真の部分開始の特定→最小schema/評価修正→表示と更新の整合→元IDで再開確認。試行には旧edge互換、開始可/完了不可、版変更、能力欠如、循環、不正owner、同時revision更新、原親の偽done防止を含める。

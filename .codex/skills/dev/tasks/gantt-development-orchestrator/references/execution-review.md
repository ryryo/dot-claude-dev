# カテゴリの実行点検と過剰実装の是正

カテゴリオーケストラが、自分のカテゴリの原残条件・実起動・成果・反復を照合する。PMの実装・検収を重ねず、第三の管理役、別進捗台帳、点検専用PM/workerを作らない。[PMの工程終了条件](playing-manager.md#実装検証を必要な範囲で終える)と[通信正本](task-launch.md#通信と回収)を使う。

## 適用する契機と許可

新規PM配置後、供給/成果受領、停滞・反復・範囲拡大の疑い、状況照会で必要な範囲を点検する。PMは開始/再開、実装・試験・調査の追加前、同じ失敗の再試行前に自分の工程終了条件を確認する。通常作業の都度ACKや全PMへの定期質問は追加しない。

定期点検は、利用者が対象カテゴリと間隔を指定して依頼した場合だけ、[既存カテゴリchatのタイマー](templates.md#カテゴリの定期点検タイマー)として設定する。30分ごとの依頼ならその間隔を引き継ぐが、スキルの利用だけで全案件にタイマーを作らない。「まずスキル改修」「タイマー案の検討」はタイマー設置・稼働中担当への指示の許可ではない。

設定には実client/hostで対応する既存のautomation等を使い、同じ対象の既存タイマーを確認して重複を避ける。既存カテゴリの正式chat/hostを対象とし、起点で一括監視したり、独立の定期job/新chatへ暗黙に代替したりしない。実ツールがなければ不足を示し、shell cron・daemon・架空の割込み機構で代用しない。詳細な権限と実schemaは[共通実行条件](../../codex-task-split/references/execution-context.md)と実ツール定義に従う。

タイマーの配送時刻だけで、実行中turnが指定間隔で必ず点検・中断されるとは保証しない。実際の点検turnと再開方式を確認し、試験・書込processを点検のために強制停止しない。点検の間も、承認済みの通常実装・配置は既存の役割とWIP枠で進める。

## カテゴリ起動文へ展開する点検文

次の本文を[カテゴリ起動テンプレート](templates.md#カテゴリオーケストラ)へ全文展開する。タイマーが未設定でも、通常の配置・回収・停滞是正に適用する。

```text
【停滞・過剰実装の点検】
PMの作業を、元IDの原残条件と実成果・検証結果へ対応付けて確認してください。
コード量、テスト数、コミット数、発言量だけで進展を判定しません。
残条件の充足、失敗原因の絞込み、必要供給の成立などの進展と、同じ調査・修正・試験を繰り返す状態を区別します。
実装・試験が原条件から広がっている場合は、根拠となる条件または実不具合と、今回終える範囲を担当PMに具体化させます。
必要な利用動作・失敗条件と必須検証を保持し、短時間・少数テストだけを目標にしません。
あなた自身がPMの実装・最終検収を引き取ったり、全試験を再演したり、通常作業へ承認待ちを追加したりしません。
是正が必要なPMにだけ、対象元ID・観測事実・必要な変更を短く渡します。
点検が必要な時は、現行スキルのexecution-review.mdの点検手順と既存記録を読みます。
定期点検の設置は利用者の明示依頼と実clientの対応に従い、スキル導入だけでタイマーを作りません。
```

## 点検手順とタイマー本文

次の本文が通常点検と定期点検の手順の正本。[タイマー雛形](templates.md#カテゴリの定期点検タイマー)では確認済み入力とこの全文、共通通信文を展開する。周期ごとに手順自体を自由作文で変えない。

```text
あなた自身が担当するカテゴリの運用を点検してください。
この点検は既存のカテゴリオーケストラの責任内で行い、起点チャットへの報告経路や全体オーケストラを追加しません。

1. 現行契約と前回からの変化を読む
入力の実在パスから現行スキル、役割別起動テンプレート、共通通信文、PMの実行契約と工程終了条件を確認してください。
最新の進捗正本と既存handoff、前回以降に動いたPMの必要な履歴・差分・試験結果を読みます。
前回の観測点は既存のカテゴリchat/note/handoffから特定し、進捗の別版や日次コピーを作りません。
前回を特定できなければ今回を初回の観測点とし、変化を推測しません。
短い一次確認から疑いのある元IDへ絞り、毎回の全履歴・全コード監査や全試験の再実行は行いません。

2. 起動・担当・通信を照合する
前回以降に新規PMを作った場合は、実際の発言・起動入力・実設定から次を確認します。
・作成前のカテゴリ配置表があったか。
・元ID一つ、原条件、最初に減らす残条件、既成果・依存・許可が渡されたか。
・役割別本文、共通通信文、PMの工程終了条件、開始表の雛形が実起動文へ展開されたか。
・PM自身の開始表、正当なCLI着手、実装の順序が成立しているか。
全管理範囲の未担当・重複owner・WIP・未回収と、供給成立後に未再開の元IDも確認し、既承認の配置・継続を既存のWIP枠内で処置します。
読取だけの起動には実着手を要求しません。新規配置と同ID継続/再開を分け、通常再開に新規配置表・新チャット・全文再送を要求しません。
起点への報告、受領だけの返信、供給予定の通知、不要な同報が発生していないかも確認します。
必要な操作衝突・入力固定/解放・実待機の解除は抑制しません。

3. 原残条件の進展と実装・検証の範囲を確認する
動いたPMについて、どの原残条件が充足したか、どの失敗原因が絞れたか、どの供給待ちが解除されたかを確認します。
未回収の実成果と未commit差分も読み、ID未完・経過時間・件数だけで停滞や過剰実装と断定しません。
追加した実装・抽象化・テスト・調査に、原条件、確定仕様、実不具合との対応があるか確認します。
必要な利用動作が成立しているのに追加改善を続けていないか、新しい根拠なしに同じ修正・調査・全件試験を繰り返していないかを確認します。
必須CI/Gate・実サービス/OS・安全性等の検証条件を削って短時間で完了したことにはしません。

4. 必要な是正だけ行う
手順漏れは現在状態に合わせて補正し、過去に開始前提示があったように記録し直しません。
成果・証拠・claim・修正履歴をリセットしません。
同じ問題が続き、原条件の充足・原因の絞込み・供給解除のいずれにも進展がない場合は、原因と次に判別する一点を特定し、担当PMへ具体的な是正を一度渡してください。
繰り返す指示の受領要求ではなく、実差分・結果・同IDの次工程で改善を確認します。
前回の是正が進んでいなければ未実施の理由や実client/供給の不足を照合し、同じ是正文を周期ごとに再送して済ませません。
30分経過や二回連続の未完だけを理由に、担当交代や作業中止を行いません。
長い工程でも新しい事実や必要な実装が進んでいれば、当該PMが同IDで継続します。
PMの中核判断・実装・最終検収はPMに保持させます。根拠のない試験削除・他担当のコード修正を点検者が代行しません。
試験・書込processや他担当の作業を点検のために強制停止しません。
点検専用のPM・ワーカー・台帳・検証基盤を増やしません。
既知の外部待ちに変化がない場合は、解除条件に必要な変化だけを読み、同じ催促・再監査を繰り返しません。

5. 結果と終了
処置や判断に必要な観測時点・正本revision・実成果版を既存記録に対応付け、未取得は未確認として保持します。
是正・重要な進展・失敗・利用者判断が必要になった場合だけ、結論、根拠、処置、担当を自分のカテゴリチャットに短く示します。
対応不要の同じ状態説明やPMへの点検受領要求を繰り返しません。起点チャットへ点検報告を送りません。
変化も処置もない時に、点検済みを示すだけのnote/CLI更新や全管理範囲のコピーを増やしません。
設定済みのタイマーがある場合、全管理IDの原条件と必要な正式化が完了、または利用者の停止指示があれば、実ツールでそのタイマーを停止して結果を確認します。
部分成果・一つのPMの終了・待機・タイマー配送成功だけを、全管理範囲の完了やタイマー停止済みに読み替えません。
```

初回の設定後は、実対象chat・間隔・保存promptと少数の実runを照合し、prompt保存、配送、実点検、是正、原条件の改善を分けて記録する。文書の確認だけでは実clientの作動、指定間隔での点検、過剰実装の解消を実証したとしない。

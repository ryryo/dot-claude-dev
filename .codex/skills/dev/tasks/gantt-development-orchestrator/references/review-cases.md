# 改訂時の回帰確認

代表的な架空入力で、読む資料、判断する担当、次の操作、停止・終了条件を確認する。文言一致、文字数、ケース数、lintの指摘数は、意味や実動作の合格基準にしない。製品作業に新しい監査やGateを追加する資料ではない。

## 1. 起動文と読む範囲

全管理8 ID、正本完了2 IDのカテゴリが、通常接続の残る`entry-C`を新PMへ配置する。旧owner、未担当、供給待ちも8 IDに含める。

カテゴリはtask-launch.mdの入力と本文から、残6/8 ID・25%（2/8 ID）の4列配置表を作成前に示す。起動者は同資料のPM入力にplaying-manager.mdの本文を展開する。そこに含まれる5列表はPM自身が具体化し、提示→正当なCLI着手→実装の順で進む。起点やsource_thread_idから報告義務を作らない。

カテゴリ、PM、通常担当、自動配送ワーカー、手動配送ワーカー、点検タイマーを、各正本のブロックから組み立てる。未置換入力、表の列、本文の二重挿入を調べ、実際の送信文を読んで権限と責任を比較する。PMの通常実行でカテゴリの起動・点検資料一式を読ませず、タイマーには新規起動本文を混ぜない。

同IDの通常再開では完全な既存表と差分を使う。正式後継は読取受領から始め、所有移管後に自分の5列表で実編集する。所属や許可が不明なら依存する起動だけ保留し、既成果を消さない。

## 2. 部分成果と工程終了

`entry-C`でhelperは通ったが実入口と必須認可試験が残っている。PMは別IDへ移らず、同じchatで接続と試験を進める。既証拠は対象版・環境が一致する範囲で再利用する。

必要な利用動作と検証が成立した後、将来対応や内部関数名を追認する試験を追加しようとする変種を与える。PMは原条件外の拡張を終了条件に加えず、次の原checkまたはCLI更新・commit・受渡しへ進む。新しい認可不良が見つかった変種では修正を続け、時間や試験件数で必須検証を省略しない。

## 3. 未担当・循環・効かない是正

`read-C`と`store-I`が相手ID全体のdoneを待つ。型は固定済みだが、認可された実読取と資源寿命が未成立で、供給工程に担当がいない。

発見カテゴリは割当の解決を持ち、関係カテゴリが既存ID内の最小供給と受取接続を順序付ける。独立TDDの開始と実接続の成立を分け、型・fixture・予定・形式依存の通過を実供給としない。

次に実能力が成立しても旧CLIが開始を拒否する変種を与える。CLI維持担当が正当な開始を通し、能力なしの実接続、不正owner、原条件不足の完了を引き続き拒否することを確認する。依存削除、偽done、詳細行への迂回はしない。

是正版が別branchにしかない、受取環境が古い、更新競合、未配達、client停止の各変種では、現物に応じて次操作を変える。同じ是正文を送って済ませず、受取版での成果受入と、同じ元ID/checkの作業再開を確認する。未変化の外部待ちは静かに保持する。

## 4. カテゴリ判断と共有試験枠

2カテゴリが比較していた共有読取案に、第三カテゴリの認可条件が関係すると分かる。PMは共有仕様の判断を所属カテゴリへ戻し、全関係カテゴリが同じ版・案・原必須条件を見る。責任カテゴリが選べるのは、全条件を満たした局所技術案だけである。

成立性が不明なら最小試験へ進み、無応答を合意や所有解放にしない。合意不能の間は依存する共有変更だけ止め、両立不能な保証変更が必要になった場合だけ利用者へ戻す。

共有serverの先行利用が終わる変種では、対象入力、process終了、資源解放、次利用者を確認して引き渡す。次担当はカテゴリのACKを待たない。HEADだけで共有WIPを固定済みとせず、影響する入力だけ調整する。架空の排他API、全体上位、全員同報は追加しない。

## 5. 配送・回収・引取り

同じ担当成果を、自動で最終回答が直接PMへ届くワーカーと、自動配送のない独立chatのワーカーに当てはめる。前者は最終回答一つ、後者は手動受渡し一度と自chatの結果参照を使う。必要な途中判断や入力解放の相談は残し、同じblocked全文を二重送信しない。

未着不明、通知なしcompleted、古い依頼回の重複、commit後の中断を与える。指示元は実成果と処理済み工程を確認し、到着済みの再送や二重commit・doneを避ける。配送と親の再開・検収は別に判断する。

品質上の2回の修正後にも条件不足が残る変種では、指示元が既存基準で引き取る。環境不足は品質回数に数えない。引取り時は停止指示だけで編集せず、実終了を確認し、有効な差分・証拠・修正履歴を保持する。

## 6. 移管・通常モード・タイマー

複数IDを持つ旧PMにWIP、untracked、未回収ワーカー、未実施OS条件がある。後継は読取受領から始め、旧編集終了と正当なtransferを確認する。結果不明なら照会し、残WIPを無担当にしない。原条件と履歴は保持し、main全集約やarchiveは別の許可なしに実行しない。

通常モードでは近い複数IDを一担当へ渡せる。通常の実行本文だけを使い、大規模の4列配置表やIDごとの新chatを要求しない。依頼内の一IDが外部待ちなら全体を完了にしない。

依頼済みタイマーはexecution-review.mdの入力と短い読取本文で組み立て、現在の点検手順へ進む。手順を読めなければ未実施とし、旧全文を代用しない。同じ対象を重複作成せず、全管理IDと必要な正式化が完了した時、または利用者の停止指示時に実停止を確認する。配送時刻だけで指定間隔の点検・割込みを保証しない。

## 確認結果の扱い

構造検査、作成者の机上判断、独立評価、実client・製品CLI・実サービス・OS検証を分けて報告する。静的組立てはチャット作成・配送・タイマーの実動作を証明しない。実検証は別途許可された対象と設定で行い、実製品IDを試験用に偽doneにしない。

CLIを試す場合は隔離fixtureで、旧edge互換、工程開始可・元完了不可、能力欠如、版・環境変更、循環、不正owner、同時revisionを確認する。任意の統合集約も隔離した対象で、差分の保護とM開始の実対応を調べる。

原条件や権限の欠落、証拠・WIPの破棄、二重正式化、機械判定の迂回、所有奪取は不合格とする。rollbackでも成果と正本履歴を消さない。少数の実IDでの試行は元ID完了と再開、不要な上位待ち・重複検収を確認し、部分成果だけで完遂や速度改善を実証したとはしない。

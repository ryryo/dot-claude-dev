# カテゴリ管理と単体ID PMの起動

カテゴリオーケストラが、管理する多数IDから実際に開始する元ID一つをPMへ渡す。起動する側の許可・実ツール・モデル・環境・正式IDは[共通実行条件](../../codex-task-split/references/execution-context.md)に従う。通常の限定担当の起動・回収を再利用し、大規模の担当範囲と継続は[単体ID契約](playing-manager.md)に従う。

## 起動する側

1. 原計画、実開始許可、カテゴリの全担当ID、今回の元ID、実行モード、owner・WIP・worker・未回収を読む。移管中は[所有移管](consolidation.md#1-単体id担当への所有移管)を適用し、既存PMへ二重に実装担当を重ねない。
2. project/host、認可済み方式・開始元、役割別モデル/推論、唯一の正本/CLI、編集境界と環境手順、通信先・回収先を確認する。既許可は維持し、未確認の自動再開を約束しない。
3. [起動文の組み立て](templates.md#起動文の組み立て)に従い、[PM起動本文](templates.md#単体id-pm)へ元ID一つ、原条件、最初に減らす残条件、既成果/採用版、依存と受取先、実設定、実在する担当契約の絶対パスを入れる。[原IDの開始](playing-manager.md#3-原idの開始)の5列雛形、[工程終了条件の本文](playing-manager.md#実装検証を必要な範囲で終える)、[共通通信文](#起動文へ展開する共通通信文)全文を実際の送信文へ展開し、[送信前の照合](#送信前と起動後の照合)を行う。PM自身が具体的な分担・順序・検収・今回の工程を終える条件を埋めて提示→実着手CLI更新→実装/worker起動する順を渡す。全カテゴリのworker成果を先に設計しない。
4. 自分のカテゴリchatに[PM配置表](#カテゴリのpm配置表)を提示してから、実schemaが対応する `create_thread` 等で、その元ID専用の新規chatを認可済み設定で作る。正式ID・実タイトル・方式・model/effort・cwd/開始HEADを対応付ける。pendingは正式IDにせず、結果不明は照会してから再試行する。同じ元IDの部分成果・再開・修正のために新規chatを作らない。
5. PMの実chatで対象元ID、原条件と既成果、開始表の内容、実設定、実着手との順序を照合する。配送・読了・表の存在だけで開始確認済みにしない。不足は現在分担として補正し、過去の順序漏れは残す。適正な着手は確認者のACK待ちにしない。

準備・引継ぎ読取だけの依頼ではその結果を確認し、実装確認のためにclaim・worker起動へ許可を広げない。起動成功・開始確認・実装完了・CLI完了を分けて報告する。

## 送信前と起動後の照合

カテゴリ起動とPM起動の両方で、送信する本文と実ツール引数を照合する。手引きの存在だけで展開済みとせず、案件補足まで含む実送信文を見る。

| 送信前に照合するもの | 成立する入力 |
| --- | --- |
| 対象と到達点 | カテゴリは承認済み全管理IDと根拠、PMは元ID一つ・原body/check/必要level・最初に減らす残条件。owner/readyだけへの縮小や条件の省略がない。 |
| 担当と引継ぎ | 正本/CLI、現owner、既成果/版、WIP/未回収、編集境界、供給元/受取先/解除条件が実在参照に対応する。移管前は読取のみ。 |
| 所属と報告経路 | PMの所属カテゴリに正式ID/hostを使う。カテゴリの利用者向け報告は自chat。起点/source_thread_idを上位・承認・報告先にしない。 |
| 本文と展開物 | 役割別本文、共通通信文全文、カテゴリ4列と点検文またはPM5列と工程終了条件の本文が実送信文にあり、未展開の指示や仮値が残らない。案件補足にも全員連絡・返信義務・起点報告がない。 |
| 許可と実設定 | 実利用者指示の操作範囲、project/host、モデル/推論、起動方式/開始元、cwd/環境方針と、実schemaの引数が一致する。雛形から新しい許可を作らない。 |

必須の対象・所属・許可等が不明なら、依存する起動/操作を保留し、非依存の読取や準備を続ける。存在しない担当や宛先を作らず、未知の値を既確認として埋めない。全文を新規chatへ一度渡すことと、継続ごとに同じ説明を再送することを区別する。

起動後は正式thread・実タイトル・実設定・cwd/開始HEADと、対象/原条件・開始表・正当なCLI実着手を実態から照合する。読取だけの起動では実着手を要求せず、許可された読取結果を照合する。配送成功、pending、受領返信だけで実行開始としない。カテゴリは作成されたPMの実状態を読み、起点で配置した側も必要な初回照合を読取で行う。起点へ受領/初回配置の返送を要求せず、その後の報告系統にしない。照合は開始承認ではなく、適正な作業をACK待ちにしない。新しい確認台帳・常設pollを作らず、既存記録と実clientの認可済み方式を使う。

## カテゴリのPM配置表

新しいPM chatを作る直前に、自分のカテゴリchatで「PM配置：<カテゴリ>」と次の表を示す。今回作るPMの対象元IDを一行ずつ書き、観測時点と正本revision等の版を添える。

| 元ID・作業名 | PMが作るもの | カテゴリの残ID数 | カテゴリのID完了率 |
| --- | --- | --- | --- |

「PMが作るもの」は原body/checkの残条件に沿って、担当する成果・利用動作を短く示す。workerの分担、モデル・推論、実装の前提・順序・検収方法はこの表へ先回りして書かず、PM自身の開始表に任せる。認可済みの実モデル設定や既存の依存・受入条件は、起動入力としてそのまま渡す。

カテゴリ全担当IDを重複なく数えた総数をN、同じ集合で正本が完了と判定するID数をDとし、残ID数は「N−D / N ID」、ID完了率は「D/N × 100%（D/N ID）」で示す。待機中や未担当も分母に含め、owner検索・ready・今回配置するIDだけで分母を作らない。部分成果、check数、コード量、chat作成をID完了へ換算しない。集計は既存正本/CLIから読み、別の進捗台帳やスキル専用の計算基盤は追加しない。

全行は配置前の同じ観測値を使う。ID集合の承認済み変更で分母が変わる場合は理由を添える。取得不能は「未確認」、N=0は「対象IDなし」として率を捏造しない。これはID件数の割合であり工数の進捗見積りではない。表は配置の宣言で、再承認のGateにはしない。同じPM/chatの再開には新しい配置表を要求しない。

## カテゴリ自体の配置

複数カテゴリの起動も実際に承認された方式・範囲だけで行う。[カテゴリ起動本文](templates.md#カテゴリオーケストラ)へ担当ID群、原根拠、他カテゴリと共通契約の責任、正本、既存PM/未回収を入れる。[起動文の組み立て](templates.md#起動文の組み立て)で4列配置表の雛形、[点検文](execution-review.md#カテゴリ起動文へ展開する点検文)、共通通信文全文を実送信文へ展開し、[送信前と起動後の照合](#送信前と起動後の照合)を行う。配置手続きを行う起点chatを常設の全体指揮者や報告先にしない。

既存の複数ID PMをカテゴリ管理へ移す場合は、対象IDのWIPと所有を順に単体ID PMへ渡す。残WIPがある範囲は移管中の実責任として保持し、カテゴリ化完了と称して無担当にしない。スキルの読み込みや新雛形の配送だけで移管を開始しない。

利用者が定期点検の設置を依頼した場合は、[カテゴリのタイマー雛形](templates.md#カテゴリの定期点検タイマー)と[点検の実行条件](execution-review.md#適用する契機と許可)を使う。対象・間隔・既許可、実在参照、点検/通信本文の展開、実設定と実schemaを送信前に照合し、作成後は実対象chat・保存prompt・設定・実runを確認する。タイマー配送から点検実行や進展を保証せず、起点への定期報告・点検専用chat・PMごとのタイマーを暗黙に追加しない。

## 同IDの継続・正式後継

通常の受渡し・再開確認で、同IDの残工程、完全な開始表の参照と現在条件、未回収、claim/採用版を照合する。分担や設定が変わる場合の補正は単体ID契約に従う。既存handoffへの参照で足り、常設pollや新しい開始台帳は作らない。

元IDが終了すれば、そのPMは終了を返す。カテゴリが次IDの開始条件と既存ownerを読み、別の新規PMを配置する。担当交代が必要な同IDは正式後継として履歴・証拠・修正回数・未回収を引き継ぎ、旧編集終了と正当な所有移管後に実編集を始める。

## 通信と回収

### 起動文へ展開する共通通信文

このコードブロックを通信規則の正本として維持し、新規カテゴリと新規PMの実起動文へ全文を展開する。役割別本文やAGENTSへ別版を作らない。所属カテゴリと必要宛先の実値は役割別入力で渡す。通信規則は送信権限そのものではなく、既許可を[共通実行条件](../../codex-task-split/references/execution-context.md)で確認する。

```text
【他チャットへの通信】
他チャットへは原則送信しません。
自分のチャット・唯一の正本・既存handoffへ記録し、共有成果や契約の参照を読んで進めてください。
宛先を知っていること、通信が許可されていること、メッセージを受け取ったことは、送信や返信を始める理由になりません。
読むこと・受領を返すこと自体を、相手に必要な次操作として数えません。

既に許可された宛先へ、次の場合だけ必要な連絡を行います。
1. 既存記録の読取と自担当の判断では解けず、相手の具体的な判断・操作が必要。
2. 実際のfile/hunk編集・試験入力・server/build/Git等の共有操作で、衝突解消や入力固定・解放が必要。
3. 実際に待機している受取担当を再開させる、合意済み契約の固定供給・資源解放が成立した。
4. 正当な所有移管に必要な読取受領・受渡し、または全原条件と必要な正式化を閉じたPMから所属カテゴリへの一度の元ID完了通知。

PM同士の通信は、実際の操作衝突と、合意済み固定成果の必要な受渡しに限ります。
共有仕様・責任分担・互換性・解除条件を新たに決める必要がある場合、PMは根拠・影響・推奨案・決める点を所属カテゴリへ渡します。
影響するカテゴリ同士が同じ版・案・原必須条件で直接調整し、共通合意を既存正本/handoffへ一度残します。
各カテゴリは判断結果や解除が必要な自PMにだけ伝え、記録参照で継続できるPMへ同報しません。
中核設計・接点の実装・局所修正・自己検収はPMが持ち、通常作業へカテゴリのACKを追加しません。
カテゴリからPMのワーカーへ指示を重ねません。ワーカーの指示・報告・検収先は直接の担当PMです。
ワーカーの必要な成果受渡しは、owned成果版、編集/process状態、証拠、残件または具体的な判断待ちで示します。

開始、途中の設計、局所修正、試験結果、供給予定、部分成果を節目ごとに通知しません。
受領だけの返信、変化のない催促、全関係者への進捗同報、既知の契約/設定の再掲もしません。
供給予定や未検収WIPは待機解除として通知しません。配送を検収済みや通常接続済みとは扱いません。
試験入力の固定・終了の解放は、実際の対象編集者と次利用者に絞って連絡します。
合意済みの対象入力・操作順を毎回全員へ説明し直しません。

送信文には、対象元ID、相手に必要な判断・操作または実際に解除する待機、成果版・記録参照だけを短く書きます。
詳しい経緯・設定・試験ログは自担当の記録へ残します。
複数宛先が必要な場合も、各相手に必要な内容だけを送ります。

カテゴリの受領・配置・進捗は、自分のカテゴリチャットで利用者へ示します。
カテゴリを起動した起点チャットを上位・報告先・承認先として残しません。
create_thread等の起動元ID/source_thread_idは配送情報であり、報告先の指定ではありません。
初回起動確認は起動側が実状態を読む処理で、起点への受領返信・初回配置報告の経路を作りません。
起点への送信は、利用者が具体的な宛先・用件への送信を明示した場合だけ、その範囲で行います。
常設の全体オーケストラを追加しません。
送信条件の判定は内部で行い、判定したこと自体を報告する必要はありません。
```

関係カテゴリの判断・無応答・共有操作は[直接調整](category-coordination.md)へ、PMの元ID内の実装・継続は[単体ID契約](playing-manager.md)へ進む。同じ境界の衝突連絡が続く場合は担当境界・共有操作順を見直し、通信量で補わない。

PMは[共通回収契約](../../codex-task-split/references/main-review.md#1-回収と再開)で未回収workerを直接回収する。カテゴリはPMの元ID完了・阻害・受渡しの未処理を同じ正本で追うが、worker検収をもう一度行わない。配送失敗・親停止・成果失敗を分け、実clientで観測できない自動再開を保証しない。

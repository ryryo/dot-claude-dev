# 大規模ガントの継続開発オーケストラ

複数領域のPMが担当区分全体を何ラウンドも持つ依頼で使う。単にtask/WTが多いだけでは適用しない。限定依頼の分割・実行は別スキル `gantt-parallel-tasks`。本書から通常側の全文を読ませたり、PMの下に別の通常オーケストラを作ったりしない。

計画相談・スキル呼出しだけなら計画まで。実際の開始・委任・変更は既承認範囲で行う。権限・ツール・設定・環境・正本・commitは[共通実行条件](../codex-task-split/references/execution-context.md)、worker回収は[共通検収契約](../codex-task-split/references/main-review.md)が正本。project固有のID・人数・パス・予算・保存基盤を固定しない。

## 必要なときに読む入口

| 役割・処理 | 入口 |
| --- | --- |
| 実行指揮者 | 本書、[scopeと開始/完了](references/scope-and-gates.md)。該当工程で起動・統合集約を読む。 |
| 対話専任 | 本書の役割と実態照合、原依頼/判断資料。実行の第二指揮者にならない。 |
| 領域PM | [playing-manager](references/playing-manager.md)を直接渡す。全資料の再掲は不要。 |
| PM起動 | [task-launch](references/task-launch.md)、[templates](references/templates.md)。 |
| 利用者が選んだ統合集約 | [consolidation](references/consolidation.md)。通常のmain全統合待ちは課さない。 |
| スキル改訂の試行 | [review-cases](references/review-cases.md)。各製品taskへ追加Gateを作らない。 |

## 1. 一つの指揮系統と対話役

| 役割 | 責任・権限 |
| --- | --- |
| 対話専任（分ける場合） | 要求・方針・選択肢を整理し、code/diff・実thread・正本・証拠へ直接到達する。製品編集・task完了変更・workerへの並行指示はしない。実行役へ判断根拠/差戻しを渡す。 |
| 実行オーケストラ | 全原scope、owner、能力依存、共有境界、採用/統合、未回収・停滞の責任。承認済みの統合差分と正本の共有調停を扱う。 |
| 領域PM | 区分全体の中核設計・実装・統合・検収、原ID更新、必要なLuna成果の分解・回収、次ID選定を自律実施する。 |
| worker | 明確なowned成果の調査・局所設計・実装・試験。指示元PMへ返す。原則未commitで、共有台帳や上位契約を変更しない。 |

実行指揮者は一つ。対話役は追加承認階層ではない。技術上の局所判断・受入・次ID・同worker修正をRoot/userの逐次承認へ戻さない。製品の利用動作、phase、権限・費用上限、破壊的操作など、利用者が選ぶ事項だけを区別して返す。

対話役がsnapshotしか読めない場合は、その取得版と制限を明示する。PM報告の転送だけで独立した実態確認ができるとは扱わない。読取のために秘密や顧客stateを共有しない。

## 2. 承認済み計画を原scopeへ対応させる

[scope契約](references/scope-and-gates.md)で原依頼・実送信launch・承認移管と正本を双方向照合する。初回だけ、ownerだけ、readyだけ、今の成果数から全分母を推測しない。設定、通常入口、保存、後続検証などの責任を含め、欠落は元IDとownerへ戻す。

合意済み計画は作り直さず、食い違う部分だけ調停する。担当区分は責務・共有file・依存・検収負荷で決め、固定人数にしない。実行設定・開始元・共通能力の供給/利用・次の通常接続・共有編集の窓口を決める。各PMの後続全worker成果を事前設計することを開始条件にしない。

外部実行が必要な案件では、projectが定める許可・接続条件・費用制約を早めに確認し、不足を担当付きで整理する。実装を止める範囲は、その条件に依存する操作へ限定する。

## 3. 起動と初動を確認する

[task-launch](references/task-launch.md)で全scopeと既成果、[原ID開始手順](references/playing-manager.md#3-原idの開始)と5列雛形を実際の起動・再開文へ渡す。実thread/起動方式/設定/cwd/HEAD・初動のscope対応に加え、実chatの完全な開始表と実着手の順序を照合する。正式化前のpendingを稼働済みとしない。実委任は宣言や子の件数ではなく、正式threadとowned成果・回収先で判断する。

PMが全scopeと最初の分担を示した後、承認済み着手をRootの受領ACK待ちにしない。共有localか明示Worktreeかは既認可を引き継ぐ。専用環境はproject手順を使用し、共有正本は一つのままにする。

## 4. 実態を直接読み、必要な介入だけ行う

| 契機 | 照合するもの | 処置 |
| --- | --- | --- |
| 起動・再開・移管 | 原scope、正本revision、実thread、既成果、未回収、統合版、開始表と実着手の順序 | 漏れ・重複所有・古い前提・取りこぼしを調停。配送だけで開始確認済みにしない。 |
| 後続IDへの移行・分担変更を観測 | 新しく着手した元ID、担当chatの開始表、実設定・編集境界 | 第3節へ戻って提示した現物を確認。既存handoffへ発言参照/未確認を残す。 |
| 部分供給・受入 | 固定Source/owned差分、consumer版、元checkと証拠 | 使える能力と進む原IDを確定し、通常入口の接続担当を置く。 |
| 停滞・待機 | 実turn/必要出力、HEAD/index/WIP、worker状態、残check、次ID | 能力待ち、回収待ち、機械拒否、判断待ち、担当不在を分けて解く。 |
| 状況照会 | 問われた期間の必要履歴、正本変更、成果差分、実試験記録 | 自己報告を入口に使うが結論にしない。未取得期間を未確認として示す。 |
| 外部実行が必要な場合 | projectの実行条件、既存許可、対象版、必要証拠 | 不足を解消する担当と次の作業を決める。 |

一覧/cursorから必要なthread/差分へ絞る。毎回の全code・全suite・全履歴再演、定期コピー、専用監視は不要。稼働時間を経過時間やcommit数から推定しない。正本・実差分・実threadに到達できなければ、その不足を先に示す。

状況照会には「結論／根拠／処置／担当／改善確認」を返す。例：未回収成果をPMが回収し、原checkの証拠を更新して次IDへ移ったかを次の受渡しで確認する。「規則を守る」「Lunaを使う」で終えない。

## 5. 部分供給・能力判定・継続

PMは[担当契約](references/playing-manager.md)で原check→既成果→採用版→証拠→不足→次IDを更新し、次の実着手・再開を同契約第3節へ戻す。同ID継続の省略には整合する既存表の特定が必要。全体役は共通成果がどの原条件を減らし、誰の通常呼出元へ接続されるかを見る。詳細だけ増える場合は、欠けている通常接続や独立可能な実装の担当を調整する。

必要能力が対象版で成立しCLIも正当に開始を許すなら、相手担当全体doneやmainへの全統合を待たない。CLIが契約と異なる場合は[是正手順](references/scope-and-gates.md)で担当・最低変更・受入・再評価まで持つ。依存削除/偽done/詳細化迂回はしない。

PMとworkerの回収・再開は共通契約に従う。全体役も待機/再開時に未回収のPM成果を照合し、実completedと未commitを拾う。親終了後の自動再開は実client対応・明示有効化された方式を確認し、Goal/heartbeat/永続daemonを仮定しない。通常のPM同士のACK往復・短間隔pokeで継続を作らない。

## 6. 採用と全体完了

供給元のbase・owned差分と統合先を比較し、既採用/後続版、必要前提、今回成果、未受入を分ける。共通能力の供給検収は一度、各consumerは変わる通常入口・結合境界を検収する。証拠は差分・依存・環境・対象が一致する場合だけ再利用し、失敗・疑義・変更に集中する。project必須CI/Gateは維持する。

生成側→保存/再読→利用側の意味（ID/digest/版/認可/資源寿命等）を照合する。fixture・export・型一致だけで通常接続としない。selector、実対象件数、自然終了結果、failed/cancelled/skipを区別し、成功診断ログを足して失敗した結合を打ち消さない。

最後は全原scopeと元check、採用版、通常経路、必要level、実サービス/OS/配布等の必須Vを再照合する。部分成果、供給可能、consumer受入、main採用、担当完了、全体完了を分ける。未証明Vを削除したり保証を弱めて完了にしたりしない。

利用者が統合集約を選んだ期間は[任意の移行手順](references/consolidation.md)を優先し、全体完了を待たず現最小成果で区切る。スキルの導入だけでPM回収・CLI・WT・実clientの問題が解決済みにはならない。

# 大規模ガントのカテゴリ別オーケストラ

多数IDの管理と一つの元IDの完遂を分ける依頼で使う。「カテゴリオーケストラ→元ID一つごとの新規chatのPM→限定ワーカー」の3役を維持し、常設の全体オーケストラ・全成果の承認上位を置かない。通常の限定成果群は[gantt-parallel-tasks](../gantt-parallel-tasks/SKILL.md)を使い、そちらの担当まで1 IDに制限しない。task数だけでモードを変えない。

計画相談・スキル呼出しだけなら計画まで。実行許可・実ツール・モデル・環境はproject契約と[共通実行条件](../codex-task-split/references/execution-context.md)から引き継ぐ。文書の読込みをチャット起動・通信・移管・Worktree・課金・タイマー設置の許可にしない。

## 手順の正本と入口

各行の正本が詳細を持つ。役割の入口から必要な工程へ進み、参照元へ戻って同じ手順を再実行しない。展開本文は[起動文の組み立て](references/templates.md#起動文の組み立て)だけで合成し、別版を手書きしない。

## 1. 役割と決定権

カテゴリは全管理IDの配置・順序・依存・未担当・未回収・供給待ちを持つ。PMは元ID一つの設計・中核実装・必要な通常接続・worker回収・自己検収・正当なCLI完了と正式化を持つ。workerはPMのowned成果を担当し、指示・報告・検収先は直接のPMだけ。カテゴリはPMの実装/全検収を重ねず、workerへ並行指示しない。

カテゴリの管理ID群とPMの正当な実作業claimを分ける。元IDのownerは一意とし、局所修正・通常の完了・空いた試験枠への着手に上位ACKを加えない。設計・最終採否・検収を名目上workerへ移して役割別モデル指定を回避しない。

起点chatは配置手続きをしただけで上位・報告先・承認先にならない。source_thread_id等から報告義務を作らず、受領・初回配置・定期進捗を起点へ送らない。利用者との対話を分けても第二指揮系統にはしない。製品範囲・両立不能な保証・権限・費用等、担当の既存権限外の変更に限って利用者へ戻す。

## 2. 全管理IDから必要な配置を行う

原依頼・実launch・承認移管を唯一の正本へ双方向照合し、全管理ID集合を保持する。旧owner・待機・未担当も含め、owner/readyや現成果だけで分母を作らない。カテゴリ間の合計で全原scopeを覆い、重複・未割当を元IDのまま解消する。

責務・共有file・供給・検収負荷から担当境界を決める。共通契約には供給/維持責任カテゴリと受取元IDを置き、consumer開始前は受取カテゴリが責任を保持する。合意済み計画を全面再設計せず、必要な差だけ当事者で調整する。

新規PM作成前はtask-launchの4列配置表をカテゴリ自身のchatへ提示する。元ID一つを新規PMへ渡し、具体的な中核実装・worker分担・工程終了条件はPM自身の5列開始表で決める。同IDの部分成果・修正・阻害解除は同じchat、交代は正式後継への所有移管とする。

実装中・阻害中・未回収をWIPとして扱い、projectの許可・利用枠・共有資源・回収能力内で配置する。待機ごとにchatを増やさず、固定人数・別進捗DB・汎用スケジューラ・毎成果の承認表を追加しない。

## 3. 観測から原工程への復帰まで持つ

起動/移管、供給成立、停滞/反復、状況照会で必要な実thread・差分・証拠・正本を読む。一覧/cursorから疑いのある元IDへ絞り、全履歴監査・全試験再演をしない。PMの自己報告や配送だけで開始・受入・再開を確認済みにしない。

局所問題はPMが共通実行ループで解く。カテゴリは配置・横断供給・共有契約の解決担当と受取担当を結び、是正の指示で終わらず、実成果の受入と元IDの実再開を追う。効かなければ現物から未実施・供給不足・版/環境・CLI・配送/再開を分け、次操作を修正する。変化のない外部待ちは静かに保持する。

定期点検は利用者が依頼した時だけ既存カテゴリchatに設定する。保存promptは現行手順を読み直す入口とし、旧手順全文を周期ごとに再実行する正本にしない。実ツールがない継続・割込みを保証しない。

## 4. 供給と全体完了

供給I、consumer C/V、main採用、元ID完了は別。元条件に必要な通常入口・権限・保存/再読・資源寿命を検収し、型/fixtureやCLIの形式依存だけで実能力成立としない。有効な供給検収は再利用し、consumerの変わる結合境界を検収する。必須CI/Gate・実サービス/OS・必要levelは保持する。

PMは自分の全原条件と必要な正式化を閉じて終了し、原条件外の全consumer完了まで延長しない。カテゴリは受取先と残C/Vを追う。最終統合・横断検証・リリースはその元条件を持つIDのPMが行い、他IDの承認者にはならない。

全体完了は単一正本の全管理IDと必須統合条件・V・必要正式化の充足で判断する。カテゴリが設定済みの点検タイマーは全管理範囲完了または利用者の停止指示で実停止を確認する。文書改訂だけでclient・CLI・実運用の問題を解消済みにしない。

# 大規模ガントのカテゴリ別オーケストラ

多数IDの管理と、一つの元IDを完了まで持つ実装担当を分ける大規模・継続開発で使う。カテゴリ別オーケストラ → 単体ID PM → 限定実装workerの3役とし、常設の全体Rootや全成果の承認上位を置かない。単にtask/WTが多いだけでは適用しない。通常の限定成果群の分担は別スキル [gantt-parallel-tasks](../gantt-parallel-tasks/SKILL.md)であり、そちらの全担当を1 IDへ制限しない。

計画相談・スキル呼出しだけなら計画まで。開始・通信・移管・変更は既承認範囲で行う。許可・実ツール・モデル・環境・正本・commitは[共通実行条件](../codex-task-split/references/execution-context.md)、worker回収は[共通検収契約](../codex-task-split/references/main-review.md)が正本。project固有のカテゴリ、ID、人数、パス、予算、保存基盤を固定しない。

## 必要なときに読む入口

| 役割・処理 | 入口 |
| --- | --- |
| カテゴリオーケストラ | 本書と[scopeと開始/完了](references/scope-and-gates.md)。横断案件は[カテゴリ間調整](references/category-coordination.md)。 |
| 単体ID PM | [単体IDの担当契約](references/playing-manager.md)を直接渡す。全体の手引書の再掲は不要。 |
| 起動・再開 | [task-launch](references/task-launch.md)、[templates](references/templates.md)。 |
| 既存担当の移管・任意の統合集約 | [consolidation](references/consolidation.md)。所有移管とmain集約を区別する。 |
| スキル改訂の確認 | [review-cases](references/review-cases.md)。製品taskへの追加Gateではない。 |

## 1. 役割と決定権

| 役割 | 責任・権限 |
| --- | --- |
| カテゴリオーケストラ | 担当ID群の配置・順序・能力依存・未担当・未回収・供給待ちと、関係カテゴリとの直接調整。通常の中核実装・各IDの最終検収を兼務しない。 |
| 単体ID PM | 元ID一つの原条件の残工程を、自分の新規chatで設計・実装・必要な通常接続・worker回収・自己検収・正当なCLI完了まで持つ。 |
| worker | PMが切り出したowned成果の調査・局所設計・実装・試験。指示・報告・検収先はそのPM。原則未commitで共有進捗や上位契約を変更しない。 |

カテゴリの管理範囲は、PMの実作業claimとは別。各元IDの実作業ownerは一意にし、管理側が全IDをclaimしたりworkerへ並行指示したりしない。局所修正・同worker修正・通常の完了・空いた試験枠への着手にカテゴリのACKを挟まない。設計・最終採否・検収を名目上workerへ移して役割別モデル指定を回避しない。

利用者との対話を分ける場合も、要求・判断根拠を整理する補助にとどめる。実態を直接読める範囲を示し、第二指揮系統や承認階層にはしない。製品範囲・保証・権限・費用・破壊的操作など、既存権限で決められない事項だけを利用者へ返す。

## 2. 全原scopeと担当範囲を対応させる

[scope契約](references/scope-and-gates.md)で、原依頼・実launch・承認移管と唯一の正本を双方向照合する。カテゴリの担当ID群の合計で全原scopeを覆い、未割当・重複を元IDのまま解消する。owner/ready/現在の成果だけから分母を作らない。承認済み計画を作り直さず、食い違う部分だけ当事者で調整する。

カテゴリ境界は責務・共有file・能力供給・検収負荷から決める。共通契約には供給・維持の責任カテゴリを特定し、consumer側の受取ID/PMまたは開始前の受取責任カテゴリを決める。責任カテゴリは全体上位者ではなく、その契約の限定された責任を持つ。

既存の順序表/正本に原ID、原条件の残件、採用版、担当、必要能力と解除条件を対応させる。日次コピー・別進捗DB・毎成果の承認表は追加しない。後続全IDの実装設計や全worker成果を完成させることを初動の条件にしない。

同時に実装する数は、projectの許可・利用枠・共有資源・回収能力に合わせて当事者が決める。阻害中IDと未回収成果も未完WIPとして数え、待機のたびにchatを増やさない。スキル固有の固定上限や汎用スケジューラは作らない。外部実行の不足は担当と次の対応を置き、非依存の実装まで止めない。

## 3. 元ID一つのPMを起動する

[起動手順](references/task-launch.md)で現在のowner・WIP・未回収を確認し、元ID一つにつき新規chatへ担当契約を渡す。新しい別IDは別PM chatとし、カテゴリが次の配置を選ぶ。同IDの修正・部分成果後の継続・阻害解除は同じPM chatを使う。交代は同IDの正式後継として移管する。

実thread・実設定・cwd/HEAD、初動の原条件対応と[開始表](references/playing-manager.md#3-原idの開始)を照合する。pendingを稼働済みにせず、結果不明は再照会して重複作成しない。適正な着手は受領ACK待ちにしない。確認は実態照合であり開始承認ではない。

## 4. 実態から必要な調整だけ行う

| 契機 | 読むものと次の処置 |
| --- | --- |
| 起動・再開・移管 | 原ID、正本revision、実thread/設定、所有差分、既成果、未回収、開始表と実着手を照合し、重複所有・古い前提を解く。 |
| 部分供給・受入 | 供給版・consumer版・元check・証拠を照合し、受取責任と解除後の同ID再開を追う。 |
| 停滞・待機 | 必要なturn、HEAD/index/WIP、worker状態、原残条件を読み、供給・回収・CLI拒否・未決契約・担当不在を分けて処置する。 |
| 状況照会・終了 | 問われた範囲の正本変更、実差分・試験記録を読む。結論・根拠・処置・担当・改善確認と未取得範囲を返す。 |

一覧/cursorから必要箇所へ絞り、毎回の全code・全suite・全履歴再演、定期コピー、常設監視は行わない。読めない現物は確認済みにせず、稼働時間を経過時間やcommit数から推定しない。

原checkが減らず部品だけ増えるなら、当該PMが不足する接続・検収・正式化へ戻る。カテゴリはその仕事を引き取って重ねず、未割当や横断供給を解く。必要能力が成立してもCLIが拒否する場合は[是正経路](references/scope-and-gates.md#5-cli不一致を閉じる是正経路)を同じ元IDの再開まで追う。

## 5. 供給・継続・全体完了

共通能力の供給検収は再利用し、各consumerは変わる通常入口・結合境界を検収する。対象版・依存・環境・対象が一致する証拠だけを再利用し、必須CI/Gate・実サービス/OS検証は保持する。部品/fixture/export/型一致を通常経路の成立と混同しない。

供給Iとconsumer C/Vの完了は別。PMは自分の原条件と必要な受渡しを満たせば正当に完了でき、全consumer完了まで無制限に担当を延長しない。カテゴリは受取先と残C/Vを追い、開始可能になれば対応する元IDのPMが着手・再開する。原条件に反する供給不良はその元IDの修正経路へ戻す。

カテゴリは全担当IDの原body/check/必要level・採用版・残件を同じ正本で確認する。最終統合・横断検証・リリースは、それを元条件として持つIDのPMが担当し、全成果の承認上位にならない。全体完了は全カテゴリの原scopeと必要な統合条件・必須Vの充足で判断する。部分成果・main採用・一カテゴリ完了だけで代替しない。

親終了後の自動再開は実client対応と既承認方式を確認し、配送成功から保証しない。確認できない場合は実際の再開点と不足を残す。文書改訂だけで担当移管・CLI・clientの問題を解消済みと扱わない。

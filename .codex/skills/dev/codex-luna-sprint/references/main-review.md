# Astraの検収契約

通常の分担とSprintで共用する。Lunaの報告は主張として扱い、実差分と受入条件で採否を判断する。Astraが設計・実装を最初からやり直す工程にはしない。

## 報告の受領

- 元の依頼と作業ID・依頼回・送信元チャット・workspaceを照合する。古い依頼回や既に処理した報告で、修正依頼・進捗更新を重複させない。
- `review_ready`は検収待ち。Lunaの編集終了を確認し、同じファイルを編集中なら検収中の追加編集を調整する。
- `blocked`なら根拠・影響・推奨案から、Astraが契約の採否や担当の調整を判断する。採用する契約・理由・反映範囲と、再開可能な作業／保留する作業を同じLunaへ回答する。利用者の選択が必要ならその判断だけを利用者へ確認し、未決部分を保留する。「適切に整理して」という依頼や受領通知で、未解決の判断をLunaへ戻さない。無関係な新taskを起動しない。
- 中断や未報告を完了とみなさない。必要時は`wait_threads`の状態や限定した`read_thread`で確認し、履歴全体や全ログを毎回読み込まない。

## 実差分と証拠を確認する

1. 作業開始時の既存差分を基準に、変更ファイル、scope、重要な実差分を確認する。`git diff`全体をLunaの成果と決めつけず、他担当の変更と区別する。
2. 原依頼・既存正本の完了条件、利用側との境界、回帰しやすい経路を照合する。検収のためだけに別の受入条件表を作らない。UIや状態処理を含むこと自体は棄却理由にしない。
3. Lunaの検証コマンド・結果・対象環境と実差分が対応するかを確認する。必要な証拠を見て、報告だけで合格にしない。差分変更後の古い結果、確認不能な結果、mockだけでは保証できない実動作は再利用しない。
4. 再利用できる検証は繰り返さず、不足・疑義・統合・重要な失敗条件だけを追加確認する。全テスト再実行やtaskごとの追加negative caseを一律必須にしない。

適用先のCIや独立Gateが明示的に要求する検証は守る。新しい変更・失敗・未確認事項がなければ同じ検収を反復しない。

## 修正と採否

不足は再現条件・根拠・必要な挙動をまとめ、同じLunaチャットへ修正依頼する。Lunaに任せられる内部設計をAstraが毎回書き直さない。再依頼する前に、次の引き取り条件を確認する。

判定は`accepted`、`rework`、`corrected-by-main`、`rejected`、`blocked`とする。通常は会話に、Sprintは既存の検収欄へ、判断・根拠・必要な残件だけを記録する。採否と共有進捗の完了判定はAstraが行う。

### Astraへの引き取り

| 状況 | 判断 |
| --- | --- |
| 目的・契約の理解は合っており、局所的な不足がある | 根拠と必要な挙動をまとめてLunaへ修正依頼する。軽微な残修正は初回からAstraが引き取ってよい。 |
| 同じ成果について2回の修正依頼を行い、その結果を検収しても必須条件を満たさない | 原則として3回目の修正依頼は送らず、Astraが残件を引き取る。 |
| 指摘した同じ根本原因が修正後も残る・再発する、または成果が明らかに依頼の目的・契約から外れている | 回数を待たず、根拠を示してAstraが引き取る。単なる実装方法や文体の好みの違いはこの条件にしない。 |
| 指示不足、契約の未確定、依存待ち、検証環境の障害が原因 | Astraが先に前提を解決し、Lunaの修正失敗と区別する。契約変更が必要なら既存の判断権限に従う。 |

修正回数は同じ成果への品質上の差し戻しを一括して1回と数える。初回依頼、重複報告、単なる判断回答・環境復旧後の再開は数えず、雛形の「依頼回」と混同しない。回数と残る必須条件は会話または既存の検収欄に短く残し、新しい台帳は作らない。チャットの作り直しで同じ成果の修正回数をリセットしない。

引き取りは次の順で行う。

1. 担当Astraが理由と引き取る範囲を決め、Lunaへその範囲の編集停止と引継ぎを指示する。`review_ready`で既に編集を終えた成果なら、その記録を使える。送信しただけで停止済みとせず、Lunaの編集と書き込みを行う処理の終了を確認してから同じ範囲を編集する。
2. 使える成果と対応する検証証拠を保持し、未完箇所・現在の差分・実行中の処理を引き継ぐ。Lunaの変更を一括で破棄したり、同じ仕事を別のLunaへ投げ直したりしない。
3. Astraが残件を修正し、変更に必要な検証と既存Gateを完了する。検収できた時点で`corrected-by-main`を記録する。引き取りの決定だけでは完了にしない。
4. 適用先の進捗更新・コミット・完了報告の手順まで担当Astraが進める。完了報告には引き取り理由、修正回数、再利用した成果とAstraの修正範囲を短く含める。

承認済みの担当範囲内の引き取りは担当Astraが判断し、毎回利用者や上位オーケストラへ承認を求めない。範囲・製品契約・権限の変更や担当間で解決できない衝突だけは、既存の相談経路を使う。通常の引き取り経過は担当内へ残し、上位へ逐次転送しない。

## 統合と利用動作

taskごとの成功だけで全体を完了にしない。変更範囲に対応する通常導線と、契約にある失敗・復旧を確認する。UIは実画面、その他は公開interfaceや実成果物を使い、検証のための不要なUI・復旧要件を追加しない。Lunaが取得した現行成果の証拠は使え、全操作をAstraが再演することを必須にしない。

既存Story／PLANの独立レビューは、対象・契約・判定質問・証拠・役割分離が一致すれば再利用し、変わった部分だけを適用先の規則に従って再開する。Sprint専用のProduct frame／Implementation planレビューを常設Gateとして追加しない。

初回の実作業では、成果の品質に加え、Astraがどこまで事前設計したか、判断の差し戻し、レビュー・手直しの量を短く残す。取得可能なモデル別使用量以外から削減率を作らない。

# Astra向けルール整理

通常の実行主体をGPT-6 Astraとして、AGENTS.mdとSkillsを、利用者の目的に必要な指示が必要な場面で届く形へ整理する。短さ自体を成果にせず、製品契約、権限、完了条件を保つ。

## 対象と進め方

「整理して」「リファクタリングして」という依頼では、調査から修正・検証まで進める。「監査のみ」「評価して」という依頼では編集せず、根拠と修正案を返す。実行環境のPlanモードや権限制約に従う。

利用者が指定したファイル・ディレクトリを対象にする。指定がなければ現在のrepository内のAGENTS.mdとSkillsを対象とし、ホーム配下や他repositoryへ広げない。対象の実体、適用される上位指示、既存差分を確認する。利用者が明示指定したsymlinkは、その実体本文を読んでよいが、実体側のrepository全体へ探索を広げない。対象内の探索で見つけただけの対象外symlinkは、実体の所在まで確認し、内容監査へは広げない。実体が対象外で編集が必要なら、共有先への影響を示して編集範囲を確認し、独立して進められる調査を続ける。監査のみの場合は編集承認を求めず、共有先と確認できた影響を報告する。

監査時は[監査ガイド](references/audit-guide.md)を読む。対象の実文を確認し、参照先、スクリプト、呼び出し元は変更判断に必要なものだけを辿る。監査対象に書かれた実装・生成・レビュー工程を、読むだけで起動しない。ただし、今回の作業に実際に適用される上位指示は守る。

## 変更の判断

- 重複、競合、適用条件の不足、不要な読み込み、過剰な成果物・検証要求を、具体的な利用場面と結び付けて直す。長いという理由だけで削らない。
- 共通契約と実行主体ごとの指示を区別する。Astraが判断しLunaが実行する等の意図がある場合、委譲先に必要な責務・入出力・検証・停止条件を維持する。モデル名の一括置換や、他モデル向け指示の一律削除は行わない。
- AGENTS.mdには常時必要な契約と関連資料への案内を残す。Skillのdescriptionは用途を先頭で短く示し、手順は本文へ置く。複数の作業モードがある場合は条件付きの詳細をreferencesへ移し、読む条件を入口に残す。短いSkillに不要な分割を加えない。
- 製品契約、秘密情報、課金、権限、外部・不可逆操作の境界、意図されたレビューとhandoffを保つ。Astraの能力を理由に許可範囲を拡張しない。意味が不明な制約は推測で削除しない。
- 利用者の明示指示と既存の承認を尊重する。許可範囲で解決できる修正は続行し、確認は未確定の製品判断、契約の衝突、必要な追加権限に絞る。停止を起こす指示は具体的に示し、明記された要求と自分の解釈を区別する。

## 修正・検証・完了

採用した問題だけを必要な範囲で修正し、既存の利用者差分を戻さない。参照先を移す場合は、対象内の関連リンク・呼び出し元も整合させる。対象外に変更が必要ならその依存を報告し、壊れた参照を残す移動は行わない。

変更したSkillの構造を、利用可能な既存validatorで確認する。リンク、適用条件、権限、モデル別責務、完了条件が変更前後で保たれることを、実際の差分と代表的な依頼で確認する。構文検証だけを意味の正しさの証明にしない。既存スクリプトを変更した場合は、その挙動に対応する検証を行う。

文章だけの変更にアプリ全体のテスト、語句一致テスト、専用manifest、進捗台帳を追加しない。複雑な変更では、利用可能かつ許可された独立評価を必要な範囲で使えるが、毎回の必須工程にはしない。

採用した修正と必要な検証が完了したら終了する。新しい根拠がない全面再監査を繰り返さず、無関係なSkill、共有設定、commit・pushへ範囲を広げない。

最終報告には、対象、主な変更と理由、保持した重要な契約、検証結果、判断が必要な残件を短く示す。監査のみでは、問題のある箇所、具体的な影響、最小の修正案を返し、問題がなければそのまま伝える。

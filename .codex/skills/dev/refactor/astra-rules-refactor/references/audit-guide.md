# 監査ガイド

対象の利用場面に当てはまる観点を使う。全ファイルに同じ工程や項目数を要求しない。

## 根拠の扱い

公式資料で確認できる仕様、モデルの傾向、個別環境での改善仮説を区別する。

- [Skillsの公式資料](https://learn.chatgpt.com/docs/build-skills)：名前と説明で選択し、採用時に本文を読む仕組みと、説明が短縮され得ることを確認できる。
- [GPT-6 Astraの公式モデルガイド](https://developers.openai.com/api/docs/guides/latest-model#gpt-6-astra-behavior)：指示への感度、確認のための停止、過剰な検証が起こり得るという傾向を説明している。

これらは「指示を減らせば必ず改善する」「テストや承認が不要」という保証ではない。モデル特性や製品仕様の新しい主張に依存する変更では、該当する公式資料を確認する。単なる重複・リンク修正のたびに全資料を読み直す必要はない。資料を取得できなければ未確認とし、その主張に依存しない整理だけを進める。

## 情報の置き場所

| 状況 | 判断と修正 |
| --- | --- |
| descriptionが工程や機能の列挙になっている | 主な利用場面を先頭へ置く。詳しい担当基準や手順は本文へ移す。必要な対象外条件は短く残す。 |
| 関連語に触れただけでSkillを起動する | 実際に必要な依頼へ用途を絞る。依頼していない監査や実装を開始させない。 |
| AGENTS.mdとSkillに同じ手順がある | 正本を一つにして参照する。独立した作業環境でも必要な指示に到達できるか確認する。 |
| 大きなSkillに複数の作業モードが同居する | 共通契約と選択条件を入口へ残し、条件付き詳細をreferencesへ分ける。移動した全文を毎回読ませない。 |
| 短いSkillで内容が一つの作業にまとまる | そのまま保つ。分割やファイル追加を成果としない。 |
| 類似Skillや同名Skillがある | 用途、実体、利用者、呼び出し元を確認する。同名だけで統合・削除・無効化しない。 |

## 適用範囲と手順の強さ

固定手順が必要な理由を確認する。脆い操作、正確なプロトコル、費用や外部状態を扱う手順には具体性が必要になる。単なる作業例や過去の一度の失敗を、すべての作業の必須工程へ拡張している場合は条件を絞る。

「毎回repository全体を読む」は、変更する契約と利用側を判断できる必要十分な探索へ置き換える。ただし正本を読まずに仕様を推測してよいとはしない。「必ず全テストを実行する」は、変更の失敗条件と影響に対応する検証へ絞る。ただしCIやreleaseの明示契約は勝手に削らない。

進捗文書、manifest、validatorには利用側や失敗防止の役割があるか確認する。形式を維持するだけの負担と、機械的な保証を与える仕組みを区別する。利用側を確認せずに削除しない。

「現在の停止位置」等の時点情報は現行の正本と照合する。古そうという推測でGateを解除しない。状態管理の正本へ参照を集約する場合も、現在有効な停止条件を失わせない。

## モデルごとの責務

Astraを通常の実行主体としながら、意図的な他モデル利用にはそのモデル向けの指示を適用する。

例：Astraが仕様を決定し、Lunaへ固定済みの変換処理を委譲する運用では、Lunaの入出力、許可された変更範囲、未確定判断を戻す条件、Astraの検収責務を残す。Astra自身の通常作業に、そのleaf向けの制限を誤適用しない。

モデル名の存在だけで不要と判定しない。選択の意図が不明なら適用箇所を確認し、現在の役割を保持する。新しい委譲方式やモデル切替を勝手に導入しない。

## 停止と完了

| 状況 | 期待する進め方 |
| --- | --- |
| 承認されたローカル修正でテストが失敗した | 許可範囲内で原因調査、修正、影響した検証まで続ける。 |
| 実装が一度できたが必要な画面確認が残る | 完了条件に含まれる確認と修正を続ける。 |
| 意図された別タスクへのレビュー依頼が完了した | handoff契約どおり終了する。自律性を理由に待機や次工程を追加しない。 |
| 製品契約が衝突し、どちらを採用するか未確定 | 衝突箇所と必要な判断を示す。契約を黙って変更しない。 |
| 未承認の課金や外部変更が必要になった | 依存しない準備を進め、必要な権限を具体的に確認する。 |
| 承認済み操作にSkillが再承認を要求する | 承認の対象と有効範囲を確認し、適用される上位指示の下で不要な再確認を整理する。 |

## 意味の検証

変更に関連する代表的な依頼を当てはめ、選択されるSkill、読む資料、編集範囲、実行主体、停止位置が妥当か確認する。独立評価を行う場合は、依頼と最小の入力資料を渡し、期待する答えや疑いを先に教えない。共有設定や外部サービスには作用させず、一時環境の成果を観察する。

構造validatorの成功と実行結果は別々に報告する。実行していないシナリオを「動作確認済み」としない。確認できた範囲を示し、一般的な性能向上や誤選択の解消を保証しない。

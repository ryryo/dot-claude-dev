# migration-refactor

移植元の利用動作を把握し、移植先の構造を先に設計してから、機能単位で移植とリファクタリングを完了する。維持する対象は利用者の目的・動作・データ契約であり、旧実装の構造そのものではない。

基本順序は **既知の見逃しの分類（該当時） → 範囲と根拠の確定 → 動作と構造の調査 → 移植先の設計・アドバイザーレビュー → 機能単位の実装 → 新旧比較と構造検収 → 再監査・アドバイザーレビュー**。既に移植が進んでいても、現在の実装だけを正本にせず、この順で不足を回復する。

## 適用と守る境界

- 対象範囲の限定は、範囲内の機能・操作・UI・データ・保存・復旧の省略や簡略化を許可しない。概念や代表的な操作が似ているだけでは移植済みとしない。
- 合意済みの変更と、維持する動作を分ける。既知の不具合修正は再現条件と期待結果を明示する。旧仕様の改善も検討するが、未合意の仕様変更を内部整理や既知不具合の修正と呼んで通さない。
- 旧実装は比較基準として保護し、変更が明示的に依頼された範囲以外は書き換えない。作業開始時の既存差分と他担当の変更も保護する。
- 調査・計画のみの依頼なら設計と未決事項までで終了し、実装を始めない。実装依頼なら、許可済みの修正と検証を続ける。設計の記録を、毎回の承認依頼に置き換えない。
- 主担当とは別のアドバイザーエージェントによるread-onlyレビューを、設計時と完了判定前に行う。主担当は設計・実装・採否・検証に責任を持ち、レビュー依頼を実装委譲や外部送信の許可へ拡大しない。最初のレビュー依頼前に[アドバイザーレビュー](references/advisor-review.md)を読み、実施方法と利用できない場合の扱いに従う。

## 0. 既知の見逃しがある場合は、先に分類する

移植漏れの是正、途中からの立て直し、過去の失敗を基にした進め方の改善では、個別修正やルール追加の前に、会話の訂正・監査記録・不具合・完了撤回を棚卸しする。最新の症状だけで代表させず、初期の機能欠落から修正後の回帰、設計・検証・完了判断の誤りまで拾う。

[確認観点の先行分類](references/coverage-guide.md#0-既知の事例を原因と検出方法へ対応付ける)に従い、**具体的な事例 → 種類 → 原因 → 検証の穴 → 予防する工程 → 検出条件・証拠** を結び付ける。発生した問題、原因の分析、未確認の懸念、合意済みの変更を区別する。

分類から各事例へ戻り、既知の全件に具体的な予防・検出の対応があることを確認する。「GUI確認」「コード確認」といった見出しの存在だけで対応済みにしない。事例一覧と対応は既存の作業記録へ統合し、その結果を以下の調査・設計・検収へ渡す。

過去に起きた事例だけを対象にすると未知の漏れが残るため、次の移植元起点の調査も独立して行う。過去事例のない新規移植では架空の失敗一覧を作らず、次節から進める。

## 1. 範囲と比較基準を確定する

依頼、これまでの会話の訂正・合意、既存の仕様・計画、移植元と移植先、作業中の差分を確認する。過去の「完了」という報告も検証対象であり、完了の根拠にはしない。

対象の利用目的、入口、関連する共通処理、範囲外、意図した削除・変更とその根拠を明確にする。後続機能に依存する入口や保存項目は、今回維持すべき接続契約まで追う。隣接しているだけの未対象機能を丸ごと移植しない。

比較基準として移植元の版・該当コード・テスト・確認用データを特定する。新旧で異なる実行環境、認証、ライブラリ、保存基盤なども記録し、環境差を機能差や意図した変更と混同しない。実装・資料・実動作が食い違う場合は、合意した目的と再現結果に照らして扱いを決める。

## 2. 動作と構造を一緒に調べる

[確認観点](references/coverage-guide.md)を読み、対象に存在する観点を一巡する。代表画面や主要関数だけで一覧を作らない。入口から呼出先、利用側、状態遷移、データ形式、永続化、通知、外部作用まで追い、旧テストと実動作も照合する。

コード調査はファイル名の列挙や検索ヒットの確認で済ませない。対象の動作を成立させる定義・適用条件・利用側を辿り、条件分岐、既定値、共有設定などを新旧の対応へ落とす。GUIではcomponentだけでなく、DOM構成、CSSの読込・継承・上書き、media query、ライブラリの既定styleと状態による属性も追う。読んだファイルの一覧を調査完了の証拠にせず、各要件を成立させる経路と未追跡部分を示す。コードで判定できる欠落・差分を、後の実操作で発見する前提にしない。

移植元を根拠に、要件ごとの **条件・操作・期待結果 → 移植元 → 移植先 → 差分の扱い → 検証方法・結果** を対応付ける。メニュー、キー操作、暗黙の既定値、共有処理、エラー時の動作にも対応先を持たせる。欠落だけでなく、移植先が追加した操作負担・禁止状態・制約も調べる。対象に存在しない観点は理由付きで非適用にできるが、未調査を非適用としない。

同時に、責務の混在、ルールの重複、状態の二重所有、暫定分岐、依存方向、実行環境との結合、検証しにくい境界を調べる。指摘は具体的な経路・問題・影響と結び付ける。ファイルの大きさや命名だけで分割を決めない。

複数の旧アプリや入口に似た機能があれば、各実装を移す前に利用目的、入出力、データの意味、状態・更新規則、保存・失敗・復旧の差を比較する。本当に必要な差と歴史的な重複を区別する。同じ意味のデータと処理は同じ保存形式・共通実装へ揃え、必要な業務差だけをcodecや操作判定へ残す。共通化しない箇所には利用動作に基づく理由を示す。旧ディレクトリごとに新パッケージを作ったり、重複した仕組みを共通インターフェースで包むだけで共通化済みとしない。

## 3. 実装前に対象全体の構造を再設計する

最初の製品コードを変更する前に、指定された移植範囲とそれが依存する境界を、一つのシステムとして見直す。共通化、関数抽出、ファイル分割は実現手段の一部であり、それだけをリファクタリング工程にしない。既に移植済みの部分も、旧構成を引き継いだ結果や修正の積み重ねを含めて対象にする。調査用の再現や既存動作を固定するテストは先行できる。

まず、入口から出力・保存・復旧までの現状を、責務・依存・データ・状態遷移・副作用の流れとして示す。[構造の確認観点](references/coverage-guide.md#2-対象全体の構造を再設計するための問い)を一巡し、個別の不具合以外にも、迂回した処理、過剰な層、密結合、不要な状態、重複変換、複雑な順序制御がないか評価する。

次に、利用目的と維持する契約から移植先の構成を設計する。旧ファイル・クラス・パッケージの区切りを前提にせず、**残す・統合する・分解する・削除する・置き換える**判断を行う。局所修正で足りる案と、処理経路・データモデル・状態管理を組み替える案を、問題に応じて比較する。変更量を減らすためだけに不健全な構造を残さず、逆に変更件数のために健全な実装を書き直さない。

実装へ渡す設計には次を揃える。

- **全体の改善目標**: どの構造が、どの利用動作・変更・失敗処理を難しくしているか。組み替え後に不要になる仕組みや、明確になる責任と検証方法。
- **移植先の構成**: データモデル、業務ルール、UI、状態遷移、永続化・通知、外部実行の責務と依存方向。正常系だけでなく、失敗・競合・中断も同じ構成で説明できること。
- **状態・副作用の設計**: 正本と派生値、編集中・送信待ち・確定済み状態の所有者、識別、寿命、受渡し・退役条件。同期、再試行、復旧に必要な順序と不要にできる調停。
- **現状からの変更判断**: 各責務・経路を残す/統合/分解/削除/置換する理由、再利用する実装、必要な互換処理と撤去条件。問題なしとする観点も実経路を根拠にする。
- **移行と実装順**: 維持契約、意図した変更、データ移行・復旧、依存順、段階的な切替と最終構成の検収条件。

旧仕様・保存方式・処理経路が利用目的に対して過剰なら、簡素化も候補にする。仕様が変わる案は、変更前後、得る効果、失う動作、既存データへの影響、検証方法を具体化し、既存の合意で採用できるか判断する。未決の製品判断だけを利用者へ返し、その判断に依存しない調査・作業は進める。

対象全体の構成と各要件の実装先を説明でき、構造上の問題の採否、最終構成への到達条件、未決事項の影響範囲が揃ったら、別のアドバイザーへ移植元・要件対応・構造設計のレビューを依頼する。根拠のある漏れ・矛盾を解消し、変更が影響する箇所の再レビューを受けてから実装へ進む。局所改善案の一覧だけではこの工程を通過しない。調査・設計のみの依頼はこのレビューまでを対象とし、実装・最終実装レビューへ進まない。対象外の全面改修や用途のない汎用基盤は追加しないが、対象内で必要な構造の組み替えを「移植だから」「変更が大きいから」と後回しにしない。

## 4. 一連の利用動作が通る単位で実装する

全体設計から依存順に実装単位を切り出し、入口・UIからルール、保存、再表示・復旧まで検収できる形で進める。小さく実装することと、局所的にしか設計しないことを混同しない。ファイルをコピーした順や、画面だけ・保存だけの完成を機能の完成としない。段階実装の途中状態は未完了として扱う。

設計した責務へ健全な旧処理を再利用し、同じ操作の検証・更新規則をGUI・CLI・MCP等の入口ごとに増やさない。編集・生成の業務ルール、表示・操作状態、永続化・通知、外部実行を分離し、共通の業務ルールからブラウザー・Worker・Node等の実行環境へ依存させない。アプリ間の内部実装への直接依存や、異なる責務を一つの共通ユーティリティへ集める構造を避ける。

対象単位の重複や役目を終えた暫定処理も同時に除く。互換アダプター・暫定分岐や保存経路・状態所有者の二重化が必要なら、理由、適用範囲、切替条件、互換性、撤去条件を決めてから導入する。移植と無関係な一括依存更新や、旧二系統を温存するためだけの汎用基盤は追加しない。

発見した不具合は再現条件と期待結果を決め、所有者・順序・契約の原因から修正する。非同期処理の開始だけで一時状態を捨てたり、古い応答で後続操作を上書きしたりしない。遅延、フラグ、表示の固定などを局所に追加して症状だけを隠さない。同じ状態を読むコピー、履歴、別画面などの利用側にも影響を追う。

新しい根拠によって範囲・契約・所有者の前提が変わったら、要件対応と構造設計を更新してから依存する実装を進める。設計を固定したまま例外分岐だけを増やさない。

## 5. 動作と構造を別々に検収する

**動作の検収**では、旧コード・データ契約・旧テストの振る舞い・実際の操作を組み合わせ、維持要件と意図した変更をそれぞれ確認する。新実装から作った期待値やテスト成功だけを同等性の根拠にしない。利用動作と失敗条件を観測する既存テストを再利用し、不足する保証にだけテストを足す。

GUIが対象なら、同じデータ・選択・権限・画面サイズ・操作段階の新旧ブラウザーで、構成、配置、表示、操作を比較する。保存後の静止画だけでは、入力や非同期処理の途中の品質は分からない。操作開始、継続、終了、保存待ち、確定・失敗までの表示と操作可能性を連続して確認する。遅延・失敗・競合を挟み、後続操作や画面切替を重ねた場合も、対象の状態遷移に応じて確認する。

非同期のGUIを変更した場合は、該当する応答を保留・失敗させて途中状態を観測する回帰テストと、実ブラウザーでの連続操作の両方を行う。既存テストが同じ条件と観測を保証するなら再利用し、形式だけの追加テストは作らない。

一瞬の巻き戻りやちらつきは、実ブラウザーの連続操作に加えて、中間フレーム・動画・座標や描画状態の計測など、現象を観測できる手段を使う。最終値の一致で代用しない。既存のブラウザー機能とテスト環境を優先し、不足する能力が明確な場合だけ追加ツール・依存を検討する。追加する場合は、既存手段との役割と導入理由を説明する。

**構造の検収**では、統合後の対象全体を現状図・移植先の設計と比較し、実際の入口から出力・保存・復旧まで追い直す。責務と依存、データモデル、状態遷移、失敗処理が設計どおりに機能し、不要になった経路・状態・変換・調停が除去されたことを確認する。各局所修正が成功していても、全体に迂回や二重管理が残れば完了しない。「coreへ分離した」「ファイルを分けた」という説明だけでは通さない。性能に影響する変更や改善主張は、同条件の操作とデータで必要な指標を比較する。

対象に必要なテスト、型・lint・build、プロジェクト必須の確認を実行する。実ブラウザーに届かないテストをGUI検証と呼ばず、イベント模擬を実機確認と呼ばない。取得できない証拠は、代替確認と残る未確認事項を区別する。

## 6. 要件へ戻って再監査し、完了を判定する

各単位の修正後は影響する経路を確認し、統合後に対象範囲の要件一覧と移植元へ戻る。新コードや修正済みの指摘だけを見直して終えない。

- 移植元の各要件に、実装と検証の対応先があるか。
- 移植先の差分に、維持・合意した変更・既知不具合修正としての根拠があるか。
- 調査で見つかった対象内の構造問題を整理し、採用した設計が実経路で機能しているか。
- 修正から、新たな動作差、重複状態、迂回処理、検証漏れが生じていないか。

見逃しが判明したら、それを生んだ調査不足も特定する。同じ原因が届く入口・状態・利用側へ検査を広げ、要件一覧と必要な回帰検証を補う。範囲内の未実装を事後的に「対象外」にしたり、根拠なく「意図した改善」に置き換えたりしない。新しい変更や根拠がない合格項目は引き継ぎ、無関係な全面監査を反復しない。

不具合を発見した手段と、事前に検出できた根拠を区別する。実画面で発見しても、原因となる定義・条件が旧コードに存在したなら、どの追跡や新旧対応が欠けたかを記録する。「ブラウザーで発見した」を「コードでは分からなかった」へ読み替えず、実行結果の確認とコード調査の不足を別々に扱う。

主担当の再監査後に、別のアドバイザーへ、移植元からの要件対応、実装と検証根拠、設計からの差分、残件のレビューを依頼する。指摘は根拠と影響を確認して是正し、その変更が届く経路を検証・再レビューする。指摘の採否と理由を記録し、自己確認を独立レビューの代わりにしない。

完了には **対象内の動作の維持または根拠ある変更、必要な構造改善の検収、必要な検証、アドバイザーレビューでの必須指摘の解消確認** のすべてが必要である。未解決・未確認の必須項目があれば移植完了としない。残る事項と依存を明示し、許可済みで実行可能な是正は続ける。

## 記録と既存スキルとの関係

複数単位や再開を伴う作業は、既存の計画・要件対応表を更新する。必要なら[記録の最小構成](references/work-record.md)を使う。調査・計画・旧コード参照の公開範囲、保存先、再開・共有方法はプロジェクトの方針に従う。非公開とする資料は公開予定のGit履歴へ一時的にも持ち込まない。会話全文、日付違いの複製、別台帳の二重管理を増やさない。

本スキルは新旧対応と移植の統合判断を担当する。詳細な構造監査が必要なら [architecture-refactor-loop](../architecture-refactor-loop/SKILL.md)、フロントエンド構造の深掘りなら [front-end-refactor-loop](../front-end-refactor-loop/SKILL.md)を、該当範囲に限って利用できる。これらの挙動維持を目的とする監査と、移植に伴う製品仕様の採否を混同しない。複数スキルの手順・台帳・レビューを機械的に重ねない。

最終報告は、対象範囲、維持した動作と意図した差分、整理した構造、実施した検証と限界、未解決事項を示す。実装済み・検証済み・未確認を分け、テスト件数だけで「すべて完了」を主張しない。

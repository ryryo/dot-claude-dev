# 移植の確認観点

調査開始時に一巡し、対象に存在する動作から検証を選ぶ。これは機能名を増やすためのチェックリストではなく、入口・状態・利用側の見落としを探すための観点である。対象にない基盤を先行実装しない。

## 0. 既知の事例を原因と検出方法へ対応付ける

先に、記録された個別事例を列挙する。その後に共通点を分類する。先に数種類の箱を決めて例を一つずつ入れる方式では、箱に合わない事例が再び落ちる。事例の件数と失敗の種類数は区別し、一つの事例が複数の境界に関わるなら関連付ける。

次の三層を分ける。

1. **製品上の事象**: 何がなくなった・変わった・壊れたか。下の動作観点に沿って、具体的な条件と期待結果を示す。
2. **調査・設計・実装の原因**: なぜその変更をした、または要件を落としたか。コードや会話から確かめた事実と原因の分析を区別する。
3. **検証・完了判断の穴**: なぜ確認しても検出できなかった、または未確認なのに完了としたか。観測対象・時点・比較基準へ落とす。

| 進め方の失敗 | 次の作業で変える判断 | 対応したと言える条件 |
| --- | --- | --- |
| 範囲の誤読・主要経路だけの調査 | 機能名や代表CRUDから範囲を推測せず、旧入口・利用側・契約を調べる | 既知の各欠落に要件と実装・検証先があり、範囲変更の根拠も示せる |
| 設計を後回しにしたコピー・部分的な分離 | 対象全体の責務、共通化、所有者、整理対象を製品コード変更前に決める | 採用した設計を実際の呼出経路で確認でき、重複・暫定処理の削除や残す理由も示せる |
| 新実装だけの期待値・不適切な観測 | 旧動作を比較基準にし、欠落する値や途中状態を観測する | 元の事例が起きれば失敗を検出できる条件になっている。成功後だけの確認へすり替わっていない |
| 指摘された箇所だけの修正 | 同じ原因が届く入口・状態・利用側を追う | 最初の再現例以外にも影響経路を調べ、結果または非適用の根拠を示せる |
| テスト成功を全体完了へ拡大 | 要件別の実装済み・検証済み・未確認を分ける | 動作と構造の必須証拠が揃い、過去の完了報告や件数に依存しない |
| 最近の症状・特定の語だけのルール化 | 全事例から再発原因を抽出し、適用条件・工程・観測方法を定める | 分類から元の全事例へ逆照合でき、語句や操作が違っても同じ原因を拾える |

「注意する」「詳しく見る」を対策にしない。いつ、何を根拠に、何が違えば不合格にするかを定める。例えば誤った上限を追加した事例なら、schemaを見るだけでなく、旧版で有効な最大入力や負の値を移植先でも扱えることが観測条件になる。

合意済みの削除、旧側の不具合を直す変更、未確認の懸念を、発生した移植漏れと混ぜない。資料の公開範囲・共有やツール選定に関する意図の読み違いは、製品不具合とは別の進め方の問題として扱う。既知の事例の対応を確認した後も、以下の移植元からの調査で未知の経路を探す。

## 1. 移植元を起点に動作を拾う

利用者の目的ごとに、入口から結果が再利用される場所まで追う。例えば「編集できる」は、入力、確定、保存、再表示、取消、別の操作から値を読むところまで分解する。仕様書にないから不要、テストにないから未定義とは判断しない。

| 観点 | 移植元で確認すること | 見逃しを露出させる条件・証拠 |
| --- | --- | --- |
| 入口と導線 | 一覧からの作成・再開、URL、メニュー、右クリック、キー、検索、CLI/APIなど実在する入口 | 同じ操作への入口違い、戻る・再訪、空検索。画面にない項目がキーから実行されないか |
| 利用手順と禁止状態 | 自動/明示の確定、編集開始・終了、操作同士の併用、入力から結果までに必要な手順 | 移植先だけで追加された保存ボタン、待機・確認、操作禁止がないか。基盤の変更を理由に余計な操作を要求していないか |
| 入力と編集 | 既定値、上限・単位、書式、IME、貼付、確定時点、自動保存、入力内Undoと全体Undo | 未確定入力、最大の有効値、空値、欄の切替、入力中のキー。変換後の値も保存制約を満たすか |
| GUIの構成と知覚 | DOMとclass/属性の適用条件からCSSの読込順・継承・上書き・reset・ライブラリ既定値、media query、表示状態を追い、配置/寸法/余白/開閉/操作可否を新旧対応させる | コード上の条件別対応を確認したうえで、新旧同条件の空・通常・多数・長文・狭幅等を実画面比較。focus/scroll/zoom/重なり/キー操作・アクセシビリティも確認 |
| 複合操作と参照 | コピー、複製、移動、グループ、削除、取消で変わるID・親子・順序・参照 | 親だけ・子だけ・混在選択、共有・使用中データ、保存待ち直後のコピー。見た値と利用先が読む値の一致 |
| データ契約 | 省略時の意味、明示値、未知・古い形式、無効値、順序、精度、書式、参照整合性、意味的な同値 | 旧保存データの読込→編集→保存→再読込。配列からDBへの変更で暗黙の順序等が落ちないか。表現だけの差で不要な保存や履歴を発生させないか |
| 永続化と外部作用 | 自動・明示保存、原子性、検証の時点、通知順、保存成功の定義 | 途中失敗、部分書込、応答喪失、成功後の再取得失敗。事前に判定できる無効入力で副作用が残らないか |
| 寿命・履歴・復旧 | 一時入力、履歴、cache、復旧情報の所有者と保持範囲 | blur、別対象へ切替、画面往復、再読込、再接続で、残すものと退役させるものを比較 |
| 競合と非同期順序 | 排他、版、再試行、重複操作、古い応答・通知、取消・結果不明 | 操作Aの待機中に操作B、同じ対象と別対象、応答順の逆転、切断復帰。他者・新操作の値が保護されるか |
| 実行環境と運用 | ブラウザー/サーバー/CLIの依存、設定・権限・エラー、導入・起動・データ移行 | 対象環境で同じ目的を達成できるか。代替環境での検証と本来の環境での確認を区別 |
| 依存・権利・資料 | 共有処理の他の利用者、移すコード・素材の出典やライセンス、公開情報の境界 | 削除・置換する依存の役割が残っていないか。第三者表示を落とさず、私的な計画・参照が公開側へ混入しないか |

全組合せの総当たりは要求しない。異なる状態遷移、所有者、失敗原因、利用結果を区別できる条件を選ぶ。代表例を通しただけで、未調査の経路まで検証済みにしない。

## 2. 対象全体の構造を再設計するための問い

既存部品の整理から始めず、利用目的を達成するために必要なデータと処理の流れを描く。その構成と現状を比較し、下記を一巡してから実装案を選ぶ。共通化だけで終えず、問題がない観点にも現在の経路に基づく理由を持つ。

| 構造の観点 | 再設計で問うこと |
| --- | --- |
| システムの分割と依存 | 現在のアプリ・パッケージ・クラス・component境界は利用目的と変更理由に合うか。統合/分解/再配置で結合や循環、過剰な層を減らせるか |
| データモデルと表現 | 同じ意味のデータを複数形式・複数正本で扱っていないか。識別・関係・順序・不変条件をモデルで表し、重複変換や例外を減らせるか |
| 業務処理とアルゴリズム | 必要な結果までの処理が迂回していないか。分岐の追加ではなく処理方式の置換で簡素にできるか。データ量・計算量も妥当か |
| 状態遷移と並行処理 | 暗黙の順序や複数フラグの組合せを、明確な遷移・所有者へ置換できるか。入力、確定、通知、再取得の順序を局所ごとに調停していないか |
| 副作用と失敗処理 | 検証・書込・通知・後処理の境界は適切か。成功/拒否/結果不明を一つのerrorへ潰していないか。再試行・中断・復旧を経路全体で扱えるか |
| UIの構成と状態 | 表示・入力・ナビゲーション・コマンドの責任が混ざっていないか。入口ごとの重複や派生状態を減らし、表示と実行が同じ規則を使えるか |
| ライフサイクルと検証性 | 接続・timer・editor・cacheの生成から破棄まで責任が明確か。状態の組み合わせや実行時の挙動を外から観測・検証できるか |

以下の問いも実経路へ結び付ける。抽象化やファイル分割の件数を成果にしない。

- 同じ利用目的を実現するルール・データ・保存処理が複数あるか。必要な差を残しながら、一つの規則・所有者へ統合できるか。別々の仕組みをそのまま包む必要は本当にあるか。
- 旧構造は旧製品・旧基盤の制約で複雑になっていないか。その制約が消える移植先でも仕組みを残す理由はあるか。
- 業務ルールをUI、HTTP、DB、外部SDKから独立して判断できるか。同じ操作のGUIとCLIで制約や更新結果が違わないか。
- 各状態の正本はどこか。編集中・送信待ち・確定済み・表示用の区別は必要か。派生値を独立して更新する二重管理を増やしていないか。
- 誰が状態を生成し、識別し、引き継ぎ、退役させるか。対象・操作・世代を取り違えず、古い非同期処理が新しい状態を消さないか。
- 状態を読む利用側をすべて追ったか。画面の表示だけを直して、保存、コピー、履歴、別画面が旧値を読む構造が残っていないか。
- 検証、更新、保存、通知の順序と失敗時の責任が明確か。同期を保つべき処理を分割して、かえって調停を増やしていないか。
- 互換分岐・変換・二重経路は何のために必要か。適用範囲と撤去条件を説明できるか。
- 不具合を境界で再現・観測できるか。テスト用に内部を固定するより、利用動作と状態遷移を観測する境界を作れないか。

単にコピーせず考えることと、旧仕様を自由に変更することは別である。仕様改善候補は変更前後と損失まで示し、合意と検証の対象にする。健全な処理はそのまま再利用できる。

## 3. GUIを時間の流れで比較する

操作ごとに「各段階で見えるべき状態」「途中でも変わってはいけない状態」「失敗時に戻す／保持する状態」を決める。

| 段階 | 観測すること |
| --- | --- |
| 開始前・開始 | 対象、選択、focus、入力可否、表示位置、初期値。最初の入力や移動が落ちないか |
| 操作中 | 追従、書式、寸法、選択・scrollの維持。他の更新を受けても操作対象を取り違えないか |
| 操作終了・保存待ち | 編集結果を保持するか、待機をどう示すか。旧保存値へ一瞬戻らないか |
| 確定・通知・再取得 | 値と待機状態が矛盾なく切り替わるか。古い応答で後続操作を巻き戻さないか |
| 拒否・失敗・結果不明 | 入力・表示・通知・再試行の対応。保存済みか不明な状態を成功や失敗と断定していないか |
| 中断・切替・再開 | 入力の所有者、履歴、復旧情報が意図した範囲で保持されるか。前の処理の終了が次の処理を消さないか |

待機が関係する操作では、通信・編集権取得・保存など該当境界を遅らせ、実際にその中間状態へ到達したことを確認してから別の操作を重ねる。単なる固定時間のsleepで、狙った競合を再現したとみなさない。成功、拒否、結果不明は別の結果として扱う。

表示上の不変条件には、画面座標、寸法、選択、focus、入力末尾、scroll、操作可否などから必要なものを選ぶ。フレームごとの観測が必要な現象は連続画像・動画・描画計測で確認し、検証自身の「保存完了まで待つ」が不具合の時間帯を隠さないようにする。許容誤差や期待する補間があれば先に定める。

例えばドラッグ後の巻き戻りなら、位置の最終一致に加え、解放から確定までの表示、確定前の次のドラッグ、表示座標を読むコピーなどを調べる。これはドラッグ専用ルールではなく、**同じ状態の生存期間と利用側を調べる**ための例である。

## 4. 根拠の強さと限界

- 旧テストは、守る振る舞いを読み取って移植先の契約へ結び付ける。実装依存のassertionまで機械的に複製しない。合意済みの変更では期待結果と理由を更新する。
- 静止画像は構成・表示の証拠、連続操作は時間変化の証拠、保存データは永続化の証拠であり、互いを代用しない。GUIではブラウザー比較とコード比較のどちらも必要である。
- 旧環境を起動できない場合は、原因を解消できる範囲で対処し、コード・旧テスト・保存データ等で確認を進める。新画面のスクリーンショットだけで新旧比較を済ませず、取得できない証拠と影響する要件を未確認として残す。
- 検証できるようになる前の「動くはず」、一つの修正後の「他も同じはず」、件数の多いテストの成功を、全範囲の完了根拠にしない。
- 見逃しを追加発見したら、欠けていた観点・入口・状態を要件対応へ戻す。発見手段とは別に、事前に読めた定義と未追跡だった経路を特定し、同じ原因の未検査経路を閉じる。実画面での発見を、静的に検出不能だった根拠にはしない。

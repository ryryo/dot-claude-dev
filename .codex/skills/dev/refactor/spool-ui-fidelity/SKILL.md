# Spoolの新旧UI比較と改修

旧 `spool-flow` の `magnific-node-fidelity` を下地に、利用者が基準に指定した旧UIの見た目と操作を新Spoolへ揃える。部品を置き換えただけ、静止画が似ただけでは完了にしない。調査依頼は比較と方針提示まで、改修依頼は合意した範囲の実装と検証まで進める。

## 比較の基準と作業先

- 基準は旧spool-flowの対象ノードの実画面・実操作とする。新Spoolの現状を承認済みデザインや意図的な差分とみなさない。Magnificの過去資料は考え方の参考であり、今回の基準をMagnificへ変更したり、外部認証・有料生成を始めたりする理由にしない。
- 現行の製品契約、対象版、担当、作業先・branchを確認する。R1の配置・担当構成は内部資料の `docs/OPERATIONS/parallel-release-development.md` に従う。旧repoは参照元として保持し、新側の対象worktreeだけを改修する。スキルを使っただけで別担当や会話を起動しない。
- 技術選定・保存・生成・権限の新側契約は別に照合する。旧部品ライブラリや旧保存実装のコピーはUI再現の要件ではない。意図的な差分の根拠は利用者の判断か現行契約に求め、実装の難しさで正当化しない。
- 既存のUI移植仕様・対象ノード設計を入口にし、既存の該当資料を更新する。旧repoを参照する比較・設計・検収記録は内部資料へ置き、公開製品資料へ持ち込まない。スキルへ個別案件の進捗・一時URL・素材・認証情報を蓄積しない。

## 同じ状態で観測する

正規Browserツールのスキルに従い、接続Host・タブ・URL・対象Workflowを識別する。確認用ブラウザの成功を利用者のMacタブの成功へ読み替えない。画面取得できない範囲は明記し、ソースやDOMの読取をスクリーンショットの目視確認と呼ばない。

同じ素材・内容・モデル条件、viewport、ブラウザ倍率、Canvas倍率を揃えるか、その違いを記録する。Canvas拡縮後の画素寸法とCSS寸法を区別する。モデル未対応や設定の違いで項目・ポートが出ない場合、UIの機能欠落と即断せず、対応モデルの条件とコードを照合する。必要な比較用データは複製先へ用意し、制作原本を書き換えない。

対象の操作loopから、差分に関係する状態を選んで両画面で操作する。全ノードや無関係な状態の総当たりを必須にしない。

| 観点 | 観測すること |
| --- | --- |
| 通常・選択・hover | カード、画像、名称、本文、設定の表示量。幅・高さ・余白・文字・色・枠・角丸・アイコン。選択枠、操作バー、hoverで現れる操作と位置 |
| クリックとCanvas | 単クリック・ダブルクリック・右クリック・空白クリックの結果。選択、パネル、編集、プレビューのどれが始まるか。cursor、文字選択、ドラッグ・パンとの競合 |
| 名称・本文編集 | カード上の名称も直接操作し、編集開始、フォーカス、Enter・外側クリック・Escapeの結果を見る。右パネルでの編集だけで行内編集の代替としない。IMEやUndoは変更が影響する範囲で確認 |
| 設定パネル | 項目・順序・初期値・候補・条件付き表示・disabled・補助文。開始時の選択/開閉状態→操作→対象/開閉/内容。別ノード選択、閉じた後の再選択、幅とCanvasの移動・縮小・重なり |
| 画像と候補・プレビュー | 候補を見る入口、採用中表示、画像のfitと切れ方、拡大、メタデータ・履歴・ダウンロード。閉じる・Escape・外側クリックでCanvasへ戻るまで。別メディアの構造を画像へ推定しない |
| 接続・実行・復帰 | 入出力ポート、接続素材、次工程、設定反映、実行入口、確認画面、結果・失敗・再試行。過去結果の保持と操作可能範囲。今回の許可なしに費用の掛かる実行をしない |
| 確定・保存 | 保存される変更と画面だけの状態を分ける。編集を試した複製先で保存・再読込、取消・Undo等を必要な範囲で確認し、CLI対応済みの操作は同じ確定結果を維持する |

対象状態の全景と詳細を撮影・目視し、描画済みDOM/computed styleで寸法やcursorを補う。ボタンの存在、クリック結果、保存・再読込の成功は別の証拠とする。調査で開いた表示は元へ戻し、一時的な編集を制作原本へ残さない。

## 差分と機能衝突の判断

簡潔な比較表に「対象と開始状態／操作／旧側の観測／新側の観測／分類と根拠／対応」をまとめる。少なくとも次を区別する。

- **見た目・操作の再現不足**：同じ機能を保って、配置・密度・表示タイミング・入口等を旧側へ揃えられる。
- **機能不足**：旧側の利用動作が新側にない。別の入口があるなら、その到達性や結果も確認する。移植範囲と現行契約を照合し、表示を隠して同等扱いしない。
- **機能契約の衝突**：旧側へそのまま揃えると、新側の実行確認・保存の所有・候補採用・権限等と両立しない、または現行契約や既存の利用動作を変える必要がある。
- **合意済みの意図的差分**：利用者の判断または現在有効な契約を具体的に示せる。今回指定された旧UI基準と衝突するなら再確認の対象にする。
- **未確認**：操作未観測、条件不一致、読込失敗等で判断できない。機能不足や合格へ読み替えない。

衝突があれば、該当する動作を変える前に、利用者が判断できる解消方針を用意して確認する。

1. 旧側でできること、新側で必要なこと、両立しない具体的な場面を示す。
2. 根拠と、維持・変更する見た目/操作/データ契約、代替案と推奨案、利用者への影響を示す。必要なら複製先の試作で判断できる形にする。
3. 判断してほしい点を絞って尋ね、回答を同じTask・現行仕様へ反映してから当該部分を実装する。既に決まったことを繰り返し確認しない。

例：旧側の「実行」ボタンの位置・外観は揃えられても、新側が必要とする生成内容や費用の確認を黙って省略しない。旧側の入口から新側の確認へ進める案などを提示し、どの操作を採用するか確認する。

衝突が出ても、独立した比較・合意済み修正・検証は続ける。機能を削る、新規provider対応へ広げる、保存契約を置き換えるなどの方針を無断で決めない。一方、今回合意した範囲の余白・色・文言等や技術判断ごとに確認待ちを設けない。

## 改修と受け渡し

改修するときは対象component・event・state・保存経路を追い、見た目と状態遷移の責務に沿って直す。共有部品は影響する利用箇所を確認する。機能移植や構造変更へ踏み込む場合は該当する移植手順も適用し、UI差分だけを根拠に保存・実行の別実装を増やさない。

大きなUI変更や未合意の試作は現行の並行開発方針に従う専用worktree・ポート・stateで見せ、制作Hostを切り替えない。小さな合意済み修正に不要な環境を追加しない。

変更した状態を再操作・再撮影し、通常幅と影響のある狭い幅で確認する。近いテストで操作結果と必要な保存・復帰を検証し、CSS文言の一致だけを保証にしない。機能が変わらない表示修正でCLI全件や全OSの再演は行わない。

報告は、主な見た目/操作の差分、機能不足、衝突と合意した方針、確認した画面・操作・保存、未確認と次の作業を分ける。技術検証済み、利用者の体験レビュー、mainへの採用、元Task全体の完了を区別し、現在の進捗は正規Taskへ記録する。

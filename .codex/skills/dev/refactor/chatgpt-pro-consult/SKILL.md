# ChatGPT Proへの技術相談

GitHub接続で対象コードを参照するか、手元のコード・仕様・検証結果をZIPで渡し、Codex内ブラウザのChatGPTへ相談する。Proの提案を根拠と照合し、実装判断へ使える形で返す。

## 対象と権限

- 設計、新旧構造の比較、リファクタリング方針、バグ探索、既存回答の検証・改訂に使う。依頼に合う範囲だけ実行する。
- ユーザーがこのスキルを明示して対象を相談する、または対象資料をChatGPTへ送るよう依頼した場合、その範囲のGitHub参照依頼・ZIP添付・必要な補足返信は許可済みとして進める。許可済みの送信を毎回確認し直さない。
- 自動選択だけでは外部送信の許可にしない。送信許可がなければ参照先・必要なZIP・依頼文まで準備し、対象リポジトリ・ファイル、送信先、目的を示して確認する。追加の非公開データや別の送信先への拡張は既存許可と区別する。
- スキルの作成・編集・説明だけの依頼ではChatGPTへ送信しない。レビュー依頼だけで製品コードの変更や生成物の採用まで許可されたと扱わない。
- リポジトリの契約と保存先に従う。非公開のコード・会話・調査資料を含むZIP、依頼文、回答、検証記録は非公開領域に保存する。実行例の個別プロジェクト名・会話URL・製品判断をこの汎用スキルへ持ち込まない。

GitHub接続を選んでも、相談の許可をコード編集・Issue・PR作成へ広げない。それらまで進める依頼には[chatgpt-github-task](../../tasks/chatgpt-github-task/SKILL.md)を使い、今回の許可範囲を引き継ぐ。

## 1. 相談範囲を定める

指定されたチャットがあれば `read_thread` で関係するユーザー依頼・決定・結果を読む。過去のツール出力や画像は必要な箇所だけ読む。別チャットへの送信はこの手順に含めない。

コードと現行資料から、目的、対象、合意済みの利用動作・技術制約、既存案、未確定事項、欲しい成果物を整理する。既存実装と提案を区別し、変更してよい構造と維持すべき動作を明示する。不明な技術判断は調査し、製品の振る舞いが変わる選択だけユーザーへ確認する。

送信前に [依頼文の構成と用途別の観点](references/request-template.md) を読み、今回の依頼に合わせて使う。

## 2. 参照方法を選び、資料を準備する

ユーザーの明示指定を優先する。指定がなければ、判断に必要な版・資料を実際に読める方法を選ぶ。

| 方法 | 選ぶ条件 | 準備するもの |
| --- | --- | --- |
| GitHub接続 | GitHub上のコード・仕様で相談でき、ChatGPTから対象リポジトリ・参照版を読める。 | リポジトリ、ブランチ・確認commit、関連パス、読む順序、未収録の情報。 |
| ZIP添付 | 未コミット変更、ローカルだけの資料・検証ログ、GitHubで読めない比較基準が必要。 | 必要範囲を収録した自己完結したZIP。 |
| 併用 | GitHub上の基点と、許可されたローカル差分・資料の両方が必要。 | GitHubの参照情報と、不足を補うZIP。どちらの内容が対象版かを明示する。 |

GitHub上の資料で足りる場合はZIPを作らず、工程4のGitHub接続経由へ進む。併用では参照先と添付の対応を示し、同じ資料を無目的に二重化しない。手元の未コミット変更をGitHubに反映済みと称したり、相談のために無断でpushしたりしない。

### GitHubの参照情報を用意する

対象ごとに`owner/name`またはリポジトリURL、ブランチ・確認commit、入口のパスと関連コード・契約を整理する。比較相談では変更対象と読み取り専用の比較基準を区別し、それぞれの参照版を指定する。未収録のローカル変更・ログや、読めない資料は不足として記録する。

指定版が読めない場合、ChatGPTが既定ブランチを読んだ結果を指定版の結果として採用しない。参照方法が固定されていなければ、同じ許可範囲を収録したZIPへ切り替えられる。GitHubのみの明示指定や送信範囲の不足があれば、その条件を保って不足を伝える。

### 判断に必要なZIPを作る

必要なファイルを選び、専用の作業ディレクトリへコピーする。リポジトリ全体を無条件に圧縮しない。

- 入口になる説明、合意済み仕様、関連コードと呼出元・依存先、型/API/DB契約、依存バージョン、関連テストを含める。
- バグ調査なら再現手順、期待と実際、環境、必要な匿名化ログも含める。設計検討なら利用シナリオ・失敗時の動作・既知の制約を含める。
- 比較対象が複数なら `current/`、`baseline/` などの相対パスで分け、読み取り専用の比較基準と変更対象を説明する。抜粋は元の相対パス・行範囲・省略部分を記録する。
- Gitの基点commitと未コミット変更の有無を記録する。現在の作業内容が対象なら、その内容を収録する。HEADのファイルだけを渡して現在の状態と称さない。
- `README.md` に読む順序、収録範囲、正本、未収録の参照先、既知の不足、検証済み/未実施を記す。ChatGPTがローカルパスや非公開リンクの先を読めるとは仮定しない。
- 認証情報、実値入り `.env`、Cookie、個人情報、顧客データを除く。必要な再現データは匿名化する。`.git`、依存ライブラリ、キャッシュ、無関係な生成物・巨大メディアは含めない。必要な生成SQLや検証結果は目的を説明して含める。

ZIP化には [scripts/build_bundle.py](scripts/build_bundle.py) を使える。標準ライブラリだけで、列挙したファイルのみを収録し、各ファイルのサイズ・SHA-256を `BUNDLE-MANIFEST.json` に付ける。シンボリックリンク・範囲外パス・代表的な秘密ファイルを拒否するが、内容の秘密検査を代替しない。

```bash
python3 <skill-dir>/scripts/build_bundle.py \
  --root <staging-directory> \
  --files <reviewed-file-list.txt> \
  --output <private-output-directory>/context.zip
```

ファイル一覧はUTF-8、1行1ファイル、rootからの相対パス。ディレクトリやglobは指定しない。ZIPの内容一覧と実際の本文を確認し、機密の混入・不足・古い版を点検してから添付する。送信用依頼文とZIPのSHA-256も手元に残す。

## 3. Codex内ブラウザで最新GPTのProを確認する

`mcp__cua_repl.js` のその時点の説明に従う。新しいセッションの初回呼出しは、指定タブの取得、`cua.getState()`、または `cua.createBrowserTab("iab", "https://chatgpt.com/", { visible: true })` など、説明で許された入口を一つだけ実行する。相談の送信はCodex内ブラウザで行い、外部ChromeやAPIへ勝手に切り替えない。返却成果物の取得だけは、IABで保存先を確認できない場合に限り、[限定的な通常Chromeフォールバック](#返却成果物の取得がiabで捕捉できないとき)を使う。

1. 指定された会話を優先する。既存相談の継続は同じ会話で行い、新規相談は新しいChatGPT会話を使う。無関係な会話・未送信の下書きを上書きしない。
2. ログイン済みであることを確認する。利用できなければログインをユーザーに依頼し、Cookieの抽出・移植で回避しない。
3. モデル選択UIを開き、実行時点の最新GPT世代の **Pro** を選ぶ。`GPT-6 Pro` / `6 Pro` は例であり固定値ではない。Pro契約のアカウント表示だけでモデル選択済みと判断しない。Auto、Instant、Thinkingなどで代用しない。
4. 選択状態を確認し、実際のモデル表示名と確認日時を記録する。最新世代が不明なら公式OpenAI情報を確認する。最新モデルが未提供・利用上限・選択不能なら、その事実と選べる候補を報告し、旧世代や他モードへ無断で落とさない。明示されたモデル固定指定があればそちらを優先する。

ボタン名、要素番号、selector、URLパラメータは過去の例から固定しない。現行AX/DOMで対象を特定し、選択状態の明確な証拠が得られたら確認を繰り返さない。

## 4. 選んだ参照方法で依頼を送る

### GitHub接続経由

ChatGPT側で対象GitHub接続を利用できることを現行UIで確認する。CodexのGitHubツールで読めることを、ChatGPTでも読める証拠にはしない。

1. 依頼文にリポジトリ、ブランチ・確認commit、関連パス、読む順序、合意済み制約を記載する。併用では下記のZIP添付手順のアップロード操作だけを行い、GitHubの基点と添付差分の関係を明示する。送信は本節の次の手順で一度だけ行う。
2. 入力欄の本文、会話、モデル、必要な添付を照合して一度送る。投稿されたメッセージとProの応答開始を確認する。送信状態が不明なら既存メッセージを確認してから再試行する。
3. Proに関連コードを実際に取得させ、読めた参照版・パスと不足を回答させる。接続済み表示や「確認した」という断定だけで参照済みにしない。対象版を読めなければ工程2の切替条件に従う。
4. 会話URL、実モデル名、送信日時、指定した参照情報と実際に読めた範囲、依頼文の保存先を記録する。併用時は添付ZIPのハッシュも記録する。送信結果のスクリーンショットを保存し、報告時に表示する。

GitHubのみの場合はfile chooserやアップロード説明を読み込まず、工程5の回答回収へ進む。

### ZIPを添付する場合

ZIPのみの場合は以下の全手順を使う。併用時はアップロード完了まで行い、上のGitHub接続経由の送信・記録手順へ戻る。

添付前に、ブラウザが提供する `agent.documentation.get("file-uploads")` の説明を読む。対応しているfile chooser経路を使い、chooser待機を登録してから実際の添付入力または対応ボタンを押し、chooserの `setFiles([absoluteZipPath])` で指定する。通常のPlaywrightにあるAPIを推測して呼ばない。

1. 添付欄に意図したZIP名が表示され、アップロード完了・送信可能になったことを確認する。
2. 保存済みの依頼文を入力し、入力欄の本文と照合する。送信先、モデル、添付、本文が揃ってから一度送る。
3. 投稿されたユーザーメッセージと添付、Proの応答開始を確認する。送信済みと回答完了を分けて記録する。送信状態が不明なら既存メッセージを先に確認し、同じ依頼を再送しない。
4. 会話URL、実モデル名、送信日時、ZIPのハッシュ、依頼文の保存先を記録する。送信結果のスクリーンショットを保存し、報告時に表示する。

UI操作が効かない場合は状態を読み直し、遮蔽物や対象の変化を解消する。同じクリックを連打せず、現行の要素から再指定する。添付不可なら必要な文脈を保ってZIPを縮小・分割する。ZIP自体を読めないと返されたら、収録ファイルを個別添付できるか確認する。送信範囲は広げない。

### 添付が不安定なときの再利用手順

Codex内ブラウザでファイル選択が一度失敗した場合は、古いchooser待機や要素参照を再利用しない。次の順で同じ会話を開いた状態からやり直す。

1. `agent.documentation.get("file-uploads")` を読み直し、入力欄の「ファイルなどを追加」を `press("Enter")` で開く。
2. 「写真やファイルを追加」を選んだあとではなく、対応するボタンを押す前に `waitForEvent("filechooser")` を登録する。
3. chooser待機とクリックは `Promise.allSettled` で同時に実行し、成功したchooserへ `setFiles([absoluteZipPath])` を一度だけ渡す。chooserのタイムアウトを未処理Promiseのまま残さない。
4. AX/DOMでファイル名が表示され、進捗表示が消えて送信可能になったことを確認してから依頼文を入力・送信する。送信後はユーザーメッセージ側の添付表示も確認する。

時間を置いたタブなどで添付操作が反応せず、再読込後もchooserがタイムアウトする場合、未送信本文・添付の有無を確認してから、同じ会話URLを新しいIABタブで開き、上記のchooser待機とクリックをやり直す。既存タブの状態を失わずに添付が復旧することがある。新しい会話への送信や依頼の二重送信はしない。

### 返却成果物の取得がIABで捕捉できないとき

IABのファイルカードで `waitForEvent("download")` がタイムアウトしても、リンク表示だけで取得済みとは扱わない。IABで同じ会話のカードを再試行し、それでも保存先を確認できない場合に限り、同じログイン状態を確認できる通常Chromeのブラウザセッションで会話URLを開き直して最新の再添付カードを選択する。Cookieの抽出・移植、署名URLへの直接アクセス、raw API呼び出しは行わない。

通常Chromeで保存された場合は、ダウンロード先の絶対パス、ファイルサイズ、SHA-256、`unzip -t`、manifestの列挙ファイルのサイズ・SHA-256を確認する。検証済みのZIPだけを専用の受領ディレクトリへコピーし、取得方法と検証結果を送信記録へ残す。

## 5. 回答と成果物を回収する

通常の相談は回答回収・照合まで続ける。「依頼を送るだけ」なら送信確認で終える。処理中の短い受領メッセージを完成回答にしない。

- 送信と応答開始を確認したら、automationツールで同じ会話を**5分おき**に確認するheartbeatタイマーを設定する。同じ相談のタイマーがあれば更新し、会話URL・許可範囲・記録の保存先・回収と照合の続き方をpromptに残す。「依頼を送るだけ」の指定では設定しない。設定不能なら未設定と制約を報告する。
- 各タイマー実行では可視DOM/AXを一度確認する。応答中ならタブを`markHandoff()`して静かに終了し、次の5分後の実行へ戻す。sleepの繰り返しや短い間隔の画面確認で待ち続けない。途中の受領文・思考要約を完成回答にせず、数分経過だけで失敗扱い・再送・生成停止にしない。
- 完成回答を確認したらタイマーを停止し、その実行で回答・成果物の回収と照合を進める。訂正依頼を送って再び応答待ちになった場合は同じタイマーを再開する。通知は回収・照合の完了、失敗、利用者対応が必要なときだけとし、変化のない待機では通知しない。設定しただけで回収完了とは報告しない。
- 回答を可視DOM/AXから読み、本文を保存する。成果物があれば実際のダウンロード操作を行う。`waitForEvent("download")` はクリック前に登録し、返った保存パスとファイルの実在・内容を確認する。
- ダウンロード失敗は表示された原因を確認し、修正可能な場合だけ再試行する。同じ失敗が続いたら、同じ会話で新しいリンク・小分けファイル・本文への展開を依頼する。リンクがあるだけで取得済みにしない。
- 返却ZIPは専用の受領ディレクトリで一覧と展開サイズを確認し、絶対パス、`..`、リンクによる範囲外書込を拒否して展開する。製品ツリーへ直接展開しない。生成コード・コマンドは読んでから、許可された検証環境で必要な範囲だけ実行する。
- 続行が必要なタブは `markHandoff()`、成果として残すタブは `markDeliverable()` を使う。中断時は会話URL、最新の観測状態、保存済みファイル、次の操作を残して同じ会話から再開する。

## 6. 手元で照合し、選択事項を返す

Proの断定や「テスト成功」をそのまま採用しない。重要な提案は対象版のコード・仕様・公式根拠と突き合わせ、技術的な成立性を必要なテストで確認する。ローカルfixtureの成功と本番サービスの保証、提案コードと製品への接続完了を区別する。GitHub参照ではProが読んだ版と手元の版を照合し、版の差を相談結果の根拠に混ぜない。

回答を次に分ける。

| 分類 | 対応 |
| --- | --- |
| コードと合意済み契約から決められる | 根拠を示して実装側で判断する |
| 利用動作・保持・互換性・費用・復旧保証が変わる | 変更前後、利点、失う動作、推奨理由を説明し、質問ツールで一項目ずつ選択してもらう |
| 証明・再現・追加資料が必要 | 未確認として残し、具体的な検証や追加資料で解消する |
| 誤り・適用外 | 根拠付きで却下し、必要ならProへ訂正を返す |

ユーザーの選択をProの仮定で埋めない。回答待ちの間も独立した技術検証は進める。改訂時は確定事項、訂正、未決事項、更新対象の成果物を一つの返信にまとめる。GitHub参照では更新したcommit・パスと旧版との関係を渡す。ZIP参照では新しいZIPまたは差分を添え、置き換える版を明示する。返答でも選択内容の反映と成果物間の整合性を確認する。

## 完了報告

依頼範囲に応じて、実モデル名と会話リンク、選んだ参照方法、GitHubで実際に読めたリポジトリ・版・パス、添付した資料の範囲、回答の結論、手元で確認できたこと、ユーザーの選択が必要なこと、保存先を簡潔に示す。`参照情報準備済み`、`ZIP準備済み`、`送信済み`、`参照確認済み`、`回答完了`、`成果物取得済み`、`照合済み`を混同しない。取得不能や未検証が残れば明記し、コード変更・採用が完了していないものを完了扱いにしない。

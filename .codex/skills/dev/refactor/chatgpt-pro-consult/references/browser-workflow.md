# Pro相談のブラウザ送信・回収

CodexがChatGPTへ依頼を送り、回答を回収するときの共通手順。`chatgpt-pro-consult`と`chatgpt-github-task`から、現在の工程を読む。対象、送信・書込権限、終了する工程は呼出元の依頼で決め、この資料を読むだけでは操作を開始しない。Proとして直接受け取ったGitHub作業では、別のProへ再送するためにこの手順を使わない。

## 1. 会話と実モデルを確認する

`mcp__cua_repl.js`の実行時点の説明に従う。新しいセッションの初回は、指定タブの取得、`cua.getState()`、または`cua.createBrowserTab("iab", "https://chatgpt.com/", { visible: true })`など、説明で許された入口を一つだけ実行する。

相談の送信はCodex内ブラウザで行い、外部ChromeやAPIへ無断で切り替えない。通常Chromeを使えるのは、後述する返却成果物の取得でIABの保存先を確認できない場合だけである。

1. 指定会話を優先する。継続相談は同じ会話、新規相談は新しいChatGPT会話を使い、無関係な会話や未送信の下書きを上書きしない。
2. ログイン状態を確認する。利用できなければ利用者へログインを依頼し、Cookieの抽出・移植で回避しない。
3. モデル選択UIで、実行時点の最新GPT世代のProを選ぶ。`GPT-6 Pro` / `6 Pro`は例であり固定値ではない。Pro契約のアカウント表示だけで選択済みとせず、Auto、Instant、Thinkingなどで代用しない。
4. 実際の選択状態、モデル表示名、確認日時を記録する。最新世代が不明ならOpenAI公式情報で確認する。未提供・利用上限・選択不能なら、その事実と選べる候補を報告し、旧世代や他モードへ無断で変更しない。利用者によるモデル固定指定を優先する。

ボタン名、要素番号、selector、URLパラメータを過去の例で固定しない。現行AX/DOMから対象を特定し、選択状態の明確な証拠があれば確認を繰り返さない。

GitHubを使う依頼では、ChatGPT側の接続を現行UIで確認する。CodexのGitHubツールで読めることは、ChatGPTでも読める証拠にはならない。Proの実取得による版・パスの照合は、回答回収時にも行う。

## 2. 必要な添付を確認して、一度送信する

GitHub参照ではリポジトリ、ブランチ・確認commit、関連パス、読む順序、合意済み制約を依頼文へ記す。GitHubとZIPの併用なら基点と添付差分の関係も示す。

ZIPがある場合だけ、[添付操作](attachments.md#2-zipを添付する)でアップロードを完了する。GitHubのみならfile chooserやアップロードの説明を読まない。ZIPのみ・併用のどちらも、送信は次の一手順に統一する。

1. 依頼文を入力し、準備した本文と照合する。送信先の会話、モデル、必要な添付が揃い、アップロード完了・送信可能であることを確認する。
2. 一度送信し、投稿された利用者メッセージ、必要な添付、Proの応答開始を確認する。送信状態が不明なら既存メッセージを先に調べ、同じ依頼を重複送信しない。
3. 会話URL、実モデル名、送信日時、指定参照情報を既存の相談記録へ残す。`chatgpt-pro-consult`では依頼文の保存先と送信結果のスクリーンショットも残し、報告時に画像を表示する。ZIPがあればSHA-256も記録する。実際に読めた範囲はProの取得結果で補う。

UI操作が効かなければ状態を読み直し、遮蔽物や対象の変化を解消する。同じクリックを連打せず、現行の要素を指定し直す。

「依頼を送るだけ」の指定なら、ここで終了する。送信確認と回答完了は別の状態として報告する。

## 3. 回答待ちと再開を記録する

通常の依頼は、回答回収と呼出元の照合まで続ける。処理中の受領メッセージや思考要約を完成回答としない。

- 送信と応答開始を確認したら、automationツールで同じ会話を5分おきに確認するheartbeatタイマーを設定する。同じ相談のタイマーがあれば更新し、会話URL、許可範囲、記録の保存先、回収と照合の続き方をpromptに残す。設定不能なら未設定と制約を報告する。「依頼を送るだけ」では設定しない。
- 各実行で可視DOM/AXを一度確認する。応答中ならタブを`markHandoff()`して静かに終了し、次回へ戻す。sleepの繰り返しや短い間隔の画面確認で待ち続けない。数分経過だけで失敗扱い・再送・生成停止にしない。
- 完成回答を確認したらタイマーを停止し、その実行で回収・照合を進める。訂正依頼で再び応答待ちになれば、同じタイマーを再開する。通知は回収・照合・許可された登録の完了、失敗、利用者対応が必要なときだけにし、変化のない待機では通知しない。タイマー設定だけを回収完了と報告しない。

## 4. 回答と必要な成果物を取得する

回答を可視DOM/AXから読み、本文を呼出元が定める保存先へ残す。GitHub参照では、Proが実際に読んだ版・パスと不足を照合する。接続表示や「確認した」という断定だけで参照済みにしない。

返却ファイルがある場合だけ、次を行う。

1. 実際のダウンロード操作を行う。`waitForEvent("download")`はクリック前に登録し、返された保存パス、ファイルの実在と内容を確認する。リンク表示だけでは取得済みにしない。
2. 失敗原因を表示から確認し、修正可能な場合だけ再試行する。同じ失敗が続けば、同じ会話で新しいリンク・小分けファイル・本文への展開を依頼する。IABで保存先を確認できない場合は、[限定的な取得復旧](attachments.md#4-iabで保存先を確認できない場合)を使える。
3. ZIPは[受領ZIPの確認](attachments.md#3-受領zipを確認する)に従う。生成コード・コマンドを読まずに実行せず、許可された検証環境で必要な範囲だけ実行する。

続行するタブは`markHandoff()`、成果として残すタブは`markDeliverable()`を使う。中断時は会話URL、最新の観測状態、保存済みファイル、次の操作を残し、同じ会話から再開する。

取得後は呼出元のコード照合、訂正、許可された成果登録へ戻る。回答・ファイル取得を、コードの採用や実装完了と取り違えない。

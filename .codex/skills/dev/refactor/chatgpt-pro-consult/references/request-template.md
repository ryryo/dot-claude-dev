# 依頼文の構成

今回の目的に合わせて構成し、不要な観点は削る。本文は原則日本語とし、役柄や称賛よりも目的・証拠・成果物を具体的にする。

## 参照方法の指定

使う方法の冒頭を選び、その後に共通本文を続ける。GitHubのみの相談にZIP添付を要求しない。

### GitHub接続経由

```text
GitHub接続から <owner/repository> の <ブランチ・確認commit> を読んでください。
入口は <関連パス・シンボル>、読む順序は <順序> です。必要な呼出元・依存先・契約も確認してください。
比較基準は <別リポジトリ・参照版・パス、または該当なし>、変更対象は <範囲> です。
実際に読めた参照版・パスを示し、取得できない資料を読んだと仮定しないでください。
GitHubにないローカル変更・資料は <未収録の内容、または該当なし> です。
指定版を読めない場合は、既定ブランチで代用せず、不足を示してください。
今回の依頼は相談です。リポジトリの編集やIssue・PR作成は行わないでください。
```

### ZIP添付

```text
添付の <ZIP名> を展開し、README.mdとBUNDLE-MANIFEST.jsonを入口に、今回の判断に関係する資料・コードを読んでください。
```

### GitHubとZIPの併用

```text
GitHub接続から <owner/repository> の <ブランチ・確認commit> を基点として読んでください。
添付の <ZIP名> は <ローカル差分・仕様・検証ログ等の補足範囲> です。README.mdとmanifestで収録範囲を確認してください。
GitHubと添付の対応は <同じ基点か、上書きする対象パスと版の関係>、比較基準は <対象> です。
対象版には <どの内容を使うか> を適用し、未コミット差分をGitHubに反映済みとは扱わないでください。
実際に読めた参照版・パスと未収録の不足を区別してください。今回の依頼は相談です。
```

<維持する動作、技術方針、対象外>

<現在の実装、既存案、未解決の問題、自由に再検討できる構造>

<実行済みの検証、その環境、未実施、未収録の参照先>

未合意の仕様変更は、変更前後、利点、失う動作、影響を示す提案として扱い、決定済みにしないでください。

実ファイルが必要な成果物は、内容の整合したファイル一式とダウンロードできるZIPで返してください。本文にも主要な結論・未解決点を残してください。

## 設計・再設計

- 利用シナリオと失敗条件から責務・依存方向・状態・副作用の所有者を設計する。
- 現案のテーブル数、層、命名、偶然の実装差を正当性の前提にしない。単純化のために必要な動作や失敗時の保証を落とさない。
- 推奨案と現実的な代案、採用理由、トレードオフ、未解決の製品判断を示す。
- 必要に応じてAPI/型/スキーマ、主要処理、競合・再試行・取消・復旧、段階導入、検証方法を具体化する。図だけで契約を省略しない。

## リファクタリング方針

- 保持すべき観測可能な動作を示し、重複状態、依存の逆転、責務の混在、過剰な中間層を根拠付きで特定する。
- 削除・統合・維持・変更を、その理由と影響範囲付きで示す。抽象化やファイル分割そのものを目的にしない。
- 段階ごとの変更範囲、利用動作の確認方法、戻せる境界を示す。仕様変更を挙動維持のリファクタリングに混ぜない。

## バグ探索・原因調査

- 提供された症状と関連する到達可能な経路を優先する。呼出元・認可・状態遷移・失敗処理まで確認する。
- 各指摘に発生条件、再現手順または具体的な実行順序、期待と実際、影響、根拠パス、修正方針、回帰検証を付ける。
- 確認済みの不具合、再現待ちの疑い、設計上の懸念を分ける。指摘数を目標にせず、問題を発見できなければ確認範囲と未確認条件を報告する。

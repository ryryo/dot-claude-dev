# ③ 外部で仕事・復旧を管理

InstaboxとローカルPCの両方が止まっても残る場所へ、起動役と仕事の状態を置く。開発を行うエージェントはInstabox側で動かし、外部は起動判断・状態照合・次ジョブ選択だけを担う小さな構成から試す。

## 構成を選ぶ

既存の管理基盤・永続ストレージ・スケジューラーを先に調べる。利用できるものがなければ、外部の起動処理、永続状態、Instabox内の一件ずつ実行する処理を最小案として示す。追加構築そのものが今回の許可範囲と上限に収まるか確認し、未許可のサービス契約や本番展開を実験に含めない。

特定のクラウド製品は必須にしない。実装するサービスに合う公式資料・利用可能なスキルを読み、定期起動の保証、同時実行、永続化、秘密の保存、費用を確認する。長いモデル処理やビルドを外部の短時間起動処理へ押し込まない。

Instabox側は [API overview](https://instabox.sh/docs/api)、[Machines](https://instabox.sh/docs/machines)、[SDK](https://instabox.sh/docs/sdk)、[Operations](https://instabox.sh/docs/api/operations) を読む。状態照会が暗黙の起動を伴うか、どの操作に冪等性があるか、コマンド再送の意味を確認する。API詳細をこの参照の記述から推測しない。

## 最小の責務と記録

| 場所 | 役割 |
| --- | --- |
| Instabox外の永続状態 | 承認済みの仕事、開始条件、実行・待機・完了、停止意思、試行との対応を保存する |
| 外部の起動役 | 実行を望む仕事がある時だけ、状態と進行中operationを照会し、必要な起動と照合を行う |
| Instabox内の実行処理 | 既存の実行を確認してから一件を引き受け、実行器を起動し、工程・ログ・成果と終了状態を記録する |
| 人間が戻るUI | 進捗・待機理由・差分・検証結果を表示し、実行器が要求する承認や再開を正規の経路で行う |

ジョブID、入力・基点commit、試行ID、マシンID、実行器のSession等のID、最後に完了した工程、成果物、起動operation、待機理由を対応付ける。複数の起動役が同じ仕事を取得しない仕組みと、古い実行を区別する識別情報を設ける。全操作の完全な一回実行を保証したとは言わない。

## 最小の試行

1. 開発タスク1件と受入条件を登録する。最初は実行の追跡・停止・回収を確かめ、次ジョブ管理が目的の場合だけ独立した次の仕事を追加する。生産用バックログを無制限に投入しない。
2. ローカルPCやそのheartbeatに依存せず、外部起動役が動くことを確認する。②のクラウド内の開発実行に、外部からの状態確認を接続する。
3. 実験用の対象で許可された休止・停止を行い、operationの完了を追う。復旧では、マシン→Host→既存ジョブ→完了工程・成果物の順に照合し、続行・再試行・人間待ちを決める。
4. 状態確認の重複、起動要求の応答喪失、古い実行の復帰など、対象実装に関係する失敗を試す。同じジョブが二重に実行・採用されないか、結果不明で停止できるか確認する。
5. 人間が止めた仕事を、定期起動が勝手に再開しないことを確認する。理由不明の停止や台帳と実機の不一致は照合待ちにする。
6. 実際の開発成果と原票を回収し、外部管理を足したことで減った介入と、増えた構築・運用負荷を評価する。

## 再開権限と停止条件

VMを起こす権限と実行器の仕事を再開する権限を分ける。DSHの利用版の [Goal](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/goal/goal/README.md)・[継続driver](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/goal/goal-round-driver/README.md)・[Schedule](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/docs/user/guide/schedule.md) の契約を確認する。リンクは0.2.1-rc.2用で、別版では対応する資料に読み替える。

停止中のDSH Goalを自動で再開できない場合、外部はHostまで復帰させ、人間の再開待ちを記録する。予約指示を人間の直接指示として扱ったり、別CLIで同じ仕事をやり直して承認条件を回避したりしない。独立した仕事を通常のCLIへ渡す場合も、その実行の許可・認証・停止条件を維持する。

認証・承認・上限待ちでは、原因が変わるまで起動や実行を繰り返さない。許可期間・試行回数・利用量の上限、ユーザーの停止、未照合の実行がある場合は次の投入を止める。後片付けでは、今回だけの外部タイマー・待ちジョブ・接続も保持方針に沿って停止する。

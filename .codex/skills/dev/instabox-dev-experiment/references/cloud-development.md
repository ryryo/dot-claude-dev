# ② Instaboxで開発を継続

開発を進める実行器・作業リポジトリ・進捗保存をInstabox側へ置く。手元は開始・方針変更・承認・レビュー用の端末にし、ローカル不在中も有限の仕事が進むかを試す。

## 準備と資料

- PC不在中も生きる司令役を明示する。ローカルのCodexからSSHコマンドを投げただけで、この構成が成立したとしない。
- 実行器はタスクに合い、正規に利用できるCodex CLI、DSH Host / Webなどから選ぶ。[Codex Remote connections](https://learn.chatgpt.com/docs/remote-connections)、[Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)、またはDSHの利用版の公式資料で、切断・承認・Session再開の契約を確認する。接続UIと無人継続の能力は別に確かめる。
- DSHで複数ラウンドの開発を試すなら、状態を保存するGoalだけでなく、継続driverと必要な構成の有無も確認する。[0.2.1-rc.2のGoal](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/goal/goal/README.md) と [round driver](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/goal/goal-round-driver/README.md) は対象版の参照先。別版では対応する資料を読む。
- [Instabox SDK](https://instabox.sh/docs/sdk) と実機で、実効タイムアウト・アイドル休止・アカウントの制御権限を照合する。長い推論やCPU使用が休止を防ぐかは、仕様で分からなければ実測する。見かけのアクセスを送り続けて制限を回避する実験にしない。

## 最小の試行

1. 完了条件のある小さな開発1件を選び、調査→修正→検証など後続工程を含める。基点commit、対象ファイル・機能、許可操作、停止条件、受入条件を渡す。
2. クラウド側の専用作業先と永続領域へ、Session / Goalまたは実行ID、工程の時刻、差分・ログ・終了結果を残す。初回は独自キューや専用管理UIを追加しない。
3. 正規認証と既存の承認条件のもとで開始し、クラウド側の最初の工程が動いたことを確認する。
4. 切断・ローカル不在を試す時刻と範囲を記録してから、依頼された範囲で接続を閉じる。実際のPCスリープ・停止をユーザーが行う必要があれば、その操作だけを依頼する。エージェントがユーザーのPCを無断停止しない。
5. 再接続後、クラウド側の時刻付き記録で、不在中に後続工程が開始・完了したかを確認する。単一コマンドの継続だけを、継続的な開発の証明にしない。
6. タスクの成果を検証してレビュー可能な形で回収する。止まっていたら、休止・Host停止・モデル失敗・認証・承認・上限待ち・完了を区別する。

## 復旧試行と評価

VM休止・Host再起動まで試すのは、対象が実験用と分かり、その操作が許可範囲にある場合だけにする。再開後は既存プロセス、保存済み工程、Git状態、成果物を先に照合する。

DSH 0.2.1-rc.2ではGoal状態の永続化と継続許可が分かれ、再開・fork・Host再起動後などは人間が許可した明示的な再開を要する。保存されたactive表示だけで稼働中と判定せず、利用版の契約に従う。自動復旧が必須なら③を検討するが、Goalの再開条件は維持する。

不在中の後続工程、人間の介入時間、再接続後に現在地を把握する時間、成果の受入条件を測る。短時間の試行を一晩の継続やVM停止後の自動復旧の根拠にしない。切断のみを試した場合、PC停止は未検証と明記する。

# Journey検証と結果記録

実画面・実サービス・releaseで条件を確認するとき、または状態と証拠を更新するときに読む。検証は[実装後独立レビューGate](implementation.md#実装後独立レビューgate)通過後に行い、固定済み条件の実結果を判定する。新しい要件を探索する工程にはしない。

## 開始状態と判定方法を揃える

対象USの条件IDと`例:`から、通常入口、開始状態、操作、完了点、必要な証拠を定める。状態遷移、失敗・取消・再試行、再読込・再訪、keyboard・狭幅、外部サービス・費用・権限は、対象条件に必要なものだけ含める。

既存PLANに検証方法があれば使い、不足分だけを一時領域または実行中PLANへ補う。恒久的なverification briefや、条件の複製台帳は作らない。

UIを含むUSは通常入口から実画面で確認する。外部操作と費用は既存の明示承認に含まれる範囲なら再承認を求めず実行し、範囲外の作用だけを停止する。未実施の実検証をmockやfixtureで代替して完了にしない。

## 実結果を判定する

各条件の`例:`について開始状態、操作、観測結果、成功／失敗、未実施理由を記録する。固定条件と異なる結果はその条件の失敗とする。途中の改善案や別の利用者成果を、現在のJourneyや後続taskへ追加しない。

## 失敗を担当Gateへ戻す

| 観測した問題 | 戻す先 |
| --- | --- |
| 固定済み実装が現在契約を破る | 実装Gate |
| oracle、activation、rollback等、同じ条件を確かめる手順が不足する | 該当PLANの検証Gate |
| 既存契約が衝突し、どちらを正とするか判断が必要 | [実装の停止条件](implementation.md#停止条件)の契約判断 |

検証担当はその場で新しい製品挙動を考案・実装しない。手順の修正は同じ条件を判定する最小範囲に限る。修正後のGateとJourneyの再開は[入口の規則](../SKILL.md#gateの再開と状態)に従う。同じ仮説の外部変更・deploy・Journeyを繰り返しても新しい証拠が得られない場合は、安全な状態へ戻して停止する。

## 状態と証拠を更新する

記録工程では新しい品質条件を追加せず、固定条件と実際の結果を対応付ける。状態は[入口の状態定義](../SKILL.md#gateの再開と状態)に従い、全条件を必要な水準で確認した場合だけ`verified`にする。自動テストだけで十分なUSは、その根拠を検証欄へ記録する。

- 条件のチェック欄は、その`例:`を確認した結果で更新する。未チェック条件IDを`未確認条件`へ過不足なく列挙し、残件がなければ`なし`とする。
- 実サービス、目視品質、費用、外部job、重要な失敗復旧の証拠が必要なら、台帳と同じscopeの`EVIDENCE/_TEMPLATE.md`を使う。
- 証拠名は`EVIDENCE/YYMMDD_US-XX_{slug}.md`とする。成果物本体や秘密情報は文書へ埋め込まない。

台帳・PLAN・EVIDENCEを更新したらrepository rootから実行する。

```bash
python3 .codex/skills/dev/develop-user-story/scripts/validate_story_ledger.py <resolved-ledger-path>
```

validatorは構文、条件ID、具体例、未確認条件、文書参照、EVIDENCE metadataを検査する。失敗した箇所を修正して再実行し、通すためにIDを採番し直したり未確認をcheckedにしたりしない。最終報告は対象US、到達状態、主要検証、証拠、未完了条件を短く示す。

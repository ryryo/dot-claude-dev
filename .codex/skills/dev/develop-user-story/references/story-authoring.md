# ストーリーの作成と独立レビュー

ストーリーを追加・精緻化するとき、またはストーリー独立レビューGateを担当するときに読む。[入口](../SKILL.md)で解決した台帳の雛形を使い、利用者成果と合否をPLANの入力として確定する。

## 利用者の成果を定める

`きっかけ`に、誰がどの場面で何に困ったか、根拠となる依頼・観察を書く。根拠がなければ利用者へ確認し、実装や機能一覧からストーリーを逆算しない。

- 台帳の「利用者の活動」を確認・更新し、ストーリーをその活動へ結び付ける。
- 一度で完了できる利用者成果を一件にする。タイトルには達成する状態、目的には得られる成果と避けたい困りごとを書く。PLAN数や条件数から分割を決めない。
- 通常導線の開始と完了を定める。失敗、取消、再試行、再読込、復元は、その操作に存在するものだけを対象にする。
- 共通ルールは参照し、各ストーリーには固有の条件を記載する。
- 新規US IDは既存最大番号の次とし、欠番を埋めたり既存IDを採番し直したりしない。

## 受け入れ条件を観測可能にする

一つの状況、一つの操作、一つの観測結果を一条件にする。独立した操作や結果が混ざる場合に分割し、読点や特定の語の有無だけで判定しない。「適切に」「安全に」などの評価語だけで合否を済ませず、利用者が見る内容と保持される対象を示す。内部型、内部ID、実装pathはPLANへ置く。

各条件へ`US-XX-01`形式のIDと、具体値を含む`例:`を付ける。既存IDは同じ意味を保ち、新しい意味の条件は末尾へ新IDを追加する。値が未確定なら`例: 未確定（決めるべき値）`と明記し、確認済みにしない。

台帳の書式は次を守る。

```markdown
- [ ] `US-XX-01` 一つの状況で一つの操作をすると、観測結果になる。
  - 例: 対象、操作、期待結果を具体値で示す。
```

検証欄の`未確認条件`には未チェック条件IDを過不足なく列挙し、残件がなければ`なし`とする。PLAN／EVIDENCEは台帳に存在する条件IDを参照する。状態とvalidatorの扱いは[結果記録](journey-verification.md#状態と証拠を更新する)に従う。

## ストーリー独立レビューGate

PLANや実装の入力として固定する前に、作成者とは別のエージェントを1名以上立ち上げ、`$review-gate`で確認する。判定質問は「PLANの入力として、利用者成果と合否が確定しているか」。共通のReview Inputと役割は[入口](../SKILL.md#レビューへ渡す契約)に従う。

レビューでは、上の成果・条件が利用者の依頼に忠実かを確認し、次のうち実際に適用する境界を調べる。

- 通常導線と例外導線の完了・失敗・保持・再試行。取消可能なら取消、永続化するなら再読込／復元、利用者や領域を切り替えるなら切替後の結果。
- 権限、プライバシー、外部状態、費用が操作結果を変える場合の境界。
- 同じ名前付き契約、不変条件、handoffを共有するストーリーとの重複、矛盾、順序依存、責務や必須成果の欠落。

`fix-here`は成果の混在、scopeの矛盾、観測不能な条件、明示導線の欠落、関連契約の衝突に限る。保存方式、API、retry等の実装機構は受け入れ条件へ追加せず、次の規則で振り分ける。

| 状況 | 振り分け |
| --- | --- |
| 初回Story Gateで、固定した成果を実現する方法の判断が必要 | `plan-input` |
| 再レビューで、固定PLAN・名前付き実装Gate・owner・handoff契約が揃う | `implementation-risk` |
| どちらにも該当しない将来用途や一般的な改善 | `非適用` |

mainは採用した`fix-here`を台帳へ反映し、後工程への入力は受け入れ条件と分けて引き継ぐ。技術上の懸念を理由に成果を追加・分割しない。必要な再確認を終えたらGateを閉じ、Story追加だけの依頼ではここで終了する。

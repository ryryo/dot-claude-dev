# PLANの実装と停止条件

実行PLANの実装・再開、または実装後独立レビューGateを担当するときに読む。実装者は開始条件から、reviewerは実装後独立レビューGateから確認する。[入口](../SKILL.md)の製品契約とGate再開規則を共通の前提とする。

## 開始条件と実行範囲を確認する

指定された実行PLANの最初の未完了項目から依存順に進める。進行PLANは開始可能な実行PLANの選択とhandoffの確認に使い、実装scopeにはしない。複数PLANではParallelization Topology GateとPLAN独立レビューGateのPASSを確認する。

並行laneのwrite scope、port、生成物、外部状態が衝突しない実行contextを計画外で割り当てる。直列実行で足りる場合は不要な分離を作らない。参照資産を採用したPLANでは、コード・テスト編集前に[実装開始時の再確認](reuse-assessment.md#実装開始と前提変更時に再確認する)を行う。

PLAN全体の実行依頼では、担当するPhase、Gate、Journey、証拠、handoffまで継続する。通常のテスト失敗や作業量だけで終了せず、許可範囲内の原因調査・修正・検証を進める。レビュー送信が停止Gateなら、実際に送信し、成功を確認した時点で終了する。レビュー待ちで起動し続けない。

## 検証方法を選んで実装する

テスト編集前に、対象の合否をどの方法で確かめるか決める。

| 対象 | 検証 |
| --- | --- |
| 公開behavior、interface、状態遷移、失敗・復旧、protocol、保存形式、実際のアクセシビリティ契約 | 振る舞いの自動テスト |
| 静的HTML・文言・style・layout、prompt本文、画像・映像の内容や目視品質 | 実画面または実成果物 |
| 両者が混在する変更 | 操作・状態遷移だけを自動テストへ分け、見た目は実結果で確認 |

見た目の代理としてDOM文字列、class、CSS値、assetの存在をテストしない。視覚条件をテストするためだけにrole、aria-label、test idを追加しない。keyboard、focus、accessible name／state自体が契約なら、アクセシビリティの振る舞いとして検証する。strong oracleの要求もこの境界を越えない。

自動テストに適する変更は、担当条件または再発条件を表すテストを先に追加し、意図した失敗を確認して最小限の実装へ進む。条件の`例:`は公開behaviorの入力・期待値にできる場合だけ使う。自動テストに適さない成果だけならREDを省略する。

focused testと、変更リスク・PLANに応じたtypecheck、build、統合テストを行う。必要な確認が通ったら、新しい変更・失敗・未確認の根拠がない検証拡大や反復は行わない。到達する失敗・状態保持・外部コストを点検し、一般的なhardeningへ実装を広げない。

## 停止条件

次の場合は、契約を変える迂回実装の前に停止する。

| 理由 | 必要な対応 |
| --- | --- |
| 台帳、PLAN、適用指示、現行実装、外部仕様が衝突し、Goal・scope・条件・実装契約の意味を変える必要がある | 衝突と最小の変更案を示し、利用者の判断前に契約を変更しない |
| 未承認の外部変更・課金・秘密情報の利用・破壊的操作、または利用者だけが決められる製品判断が必要 | 既存承認の範囲を確認し、不足する権限・判断だけを求める |
| 必須dependency・credential・外部状態が利用できず、安全な調査とPLAN内の代替手段を尽くした | 利用できない条件と試した範囲を示す |
| 必要なoracleを成立させられず、条件を弱めるか未確認を完了扱いするしかない | 未確認を残し、検証方法の判断へ戻す |

停止時は実証できた項目だけをcheckedにする。停止項目／Gate、証拠、試した解決、続行に必要な判断、完了済みと未完了を短く報告する。隠れたfallbackやテスト削除で合格を作らない。

## 実装後独立レビューGate

PLAN内の実装と通常の自動検証が完了したら、`implemented`への更新と最初の実画面Journey・実サービス検証より前に行う。実装者、ストーリーレビュー担当、PLANレビュー担当のいずれとも異なるエージェントを1名以上立ち上げる。既存PLANの記載が後ろにあってもこの順序を優先する。

原則としてPLAN全体で一度行う。中間レビューは、PLANが到達可能な高リスク境界と判定質問を明示する場合だけ設ける。

判定質問は「現在の変更と自動検証は、ストーリー台帳とPLANを満たしており、未実装を隠さずJourneyへ進めるか」。`$review-gate`でレビュー済み台帳・PLAN、実際のコード・テスト・設定・差分・検証結果を照合する。

- 全担当条件IDと`例:`について実装根拠があり、Journey待ちと未実装を区別しているか。
- 公開interface、通常導線、適用される例外・復旧・切替がPLANの責務と一致するか。条件の抜けや実装都合の迂回、未確認を成功にするfallbackがないか。
- 自動テストが公開behaviorと再発条件を確かめ、生成側と利用側で値の意味が一致するか。静的内容やmockで必要な実結果を代用していないか。
- 変更から到達する範囲に、未承認の作用・費用、秘密情報や個人情報の露出、不要な依存、既存契約を破る性能退行がないか。

担当契約を破る再現可能な問題を`fix-here`とする。変更行や優先度だけで対象を限定せず、PLANから漏れた現在契約の違反も扱う。新しい要件、設計の好み、別US、到達しない将来リスクは追加しない。mainは採用した修正を一括で反映し、契約同士が衝突する場合は[停止条件](#停止条件)へ戻す。

## 条件を分類して次工程へ渡す

Gateの結論前に全条件を根拠付きで分類する。

| 条件の分類 | 扱い |
| --- | --- |
| `実装済み` | 担当する実装・自動検証の根拠がある |
| `実装済み・Journey／実サービス待ち` | コードは成立し、必要な実検証が残る |
| `未実装` | `doing`のまま、許可範囲内の実装を続ける |
| `契約判断待ち` | 停止条件に従って利用者へ返す |

全条件が前二種類で、review-gateの必要な確認を通過し、未解決blockerがなければGateを通す。コードと必要な自動検証の成立を`implemented`とし、[Journey検証](journey-verification.md)へ進む。自動テストとレビューだけで`verified`にはしない。指定された停止Gateがあればそこでhandoffする。

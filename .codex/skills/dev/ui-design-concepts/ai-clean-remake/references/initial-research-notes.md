## 調査時の問題設定

対象は、AI 画像の反復編集や低品質な再生成によって生じる次のような劣化だった。

- 輪郭のジャギー、二重線、白黒のハロー
- 過剰シャープ、リンギング、圧縮残渣
- 髪、布、草木、背景などの不自然な微細ノイズ
- 意味のない疑似テクスチャや描き込みの増殖
- 顔、手、小物、建築線などの局所的な破綻
- 編集を重ねるほど既存の破綻まで参照特徴として引き継ぐ現象

単純なシャープ化やアップスケールでは、壊れた高周波情報も強調され得る。そのため初案では、劣化画像をそのまま補正するだけでなく、いったん情報量を落とした制御画像から全面を再生成する発想を調べた。

## 調査で得た中心仮説

当時の中心仮説は、元画像の情報を次のように分けることだった。

- **WHAT / WHO**: 人物、顔、衣装、物体、画風、意味内容
- **WHERE**: 構図、配置、スケール、重なり、奥行き、色面
- **HOW**: 個々のピクセル、輪郭の荒れ、ノイズ、壊れた微細テクスチャ

低情報量の中間表現は `WHERE` を残し、破損した `HOW` を弱める制御信号として使えるのではないか、という考えである。

初期回答では、これを「元画像を最終生成に渡さず、構図マップだけで新規生成する」と強く解釈していた。しかし、それでは `WHAT / WHO` に必要な顔、固有デザイン、画風、細かな意味情報まで失われる。後の比較実験を受け、現在は次の役割分担へ修正されている。

- 元画像: `WHAT / WHO` と画風・意味・細部の正本
- 補助マップ: `WHERE` と低周波構造を安定させる追加制御
- テキスト: 各参照の責務と、継承しない劣化特徴を指定

## 候補として検討した方式

初期調査では次の中間表現が候補に挙がった。

| 候補 | 残そうとした情報 | 想定した弱点 |
|---|---|---|
| 約30色の構図マップ | 大きな色面、シルエット、配置、重なり | 顔、画風、小物、局所意味の消失 |
| SLIC Superpixel | 色領域、境界、構図 | モザイク状の形を画風として模倣される可能性 |
| coarse structure | 大きな輪郭、姿勢、物体境界 | 疎すぎる線やノイズ線が誤誘導になる可能性 |
| relative Depth | 前景・中景・背景、空間順序 | 平面絵、鏡、透明体、細い手足などで誤推定し得る |
| blurred low-frequency image | 大きな明暗、色、構図 | 物体境界や意味が曖昧になり得る |
| 白黒 storyboard / blockout | カメラ、人物配置、ポーズ | identity と固有の画風を保持できない |
| semantic layout | 物体カテゴリと配置 | 作成コストが高く、細かな構図が失われ得る |

この一覧は優劣が確定した方式表ではなく、比較候補の棚卸しである。

## プロンプトのみの修復との区別

調査中には、元画像へ直接「高解像度」「滑らかな線」「ジャギー、圧縮、ノイズを除去」「構図や顔を固定」と指示する実務例も挙がった。

直接修復は比較対象として有用だが、重い劣化ではモデルが残すべき構造と捨てるべき破損画素を分離できない可能性がある、というのが当時の懸念だった。一方、補助マップだけでは identity とテイストが落ちる。したがって現行設計では、次を同条件で候補生成し QC する。

- 元画像だけを使う Direct 候補
- 元画像と有効な補助マップを併用する hybrid 候補

会話内で提示された長い英語・日本語プロンプトは、複数の公開例を踏まえて当時のアシスタントが再構成した案であり、特定の公開手法からの逐語引用でも、普遍的に有効と確認された確定プロンプトでもない。

## 当初想定した4方式

### Method 1: Superpixel + Depth

写真・フォトリアル向け候補として、色領域と相対奥行きを別々に抽出する案。Depth Anything V2 Small 級の relative-depth 推定器で、metric depth ではなく大まかな前景・中景・背景の保持を狙った。

### Method 2: Superpixel + Coarse Structure

イラスト向け候補として、色領域に太い構造線を追加する案。縮小、ぼかし、Sobel または DoG、閾値処理、小領域除去、軽い膨張・平滑化、元サイズへの拡大を想定した。

### Method 3: Superpixel Only

SLIC などで近傍色を領域化し、細かなノイズを落としながら、構図、色面、主要シルエットを残す案。

### Method 4: 約30色 Composition Map

提示された「かし子式」として調査を始めた baseline。denoise、Gaussian blur、色量子化、dithering 無効化、小さな色島の整理を想定した。「30色」は経験的な目安として扱い、普遍的な最適値とはみなさなかった。

当初は写真を Method 1、イラストを Method 2 へ自動振り分ける案だったが、後の実験で Method 2 はイラストを誤誘導したため、現行の既定ルートは異なる。

## 前処理スクリプト案

初案では、Codex が実行ごとに画像処理コードを書かないよう、次を Skill に同梱する案が出た。

```text
scripts/
├── bootstrap.py または check_dependencies.py
├── prepare_image.py
├── make_superpixel.py
├── make_depth.py
├── make_structure.py
├── make_30color_map.py
└── inspect_outputs.py
```

責務の想定:

- `prepare_image.py`: EXIF orientation、RGB/RGBA、カラープロファイル、長辺、PNG 化、aspect ratio の統一
- `make_superpixel.py`: SLIC とプリセットの固定
- `make_depth.py`: relative-depth モデル取得、キャッシュ、推論
- `make_structure.py`: ぼかし済み画像から大きな境界だけを抽出
- `make_30color_map.py`: 再現可能な色量子化
- `inspect_outputs.py`: palette 数、edge 密度、depth のレンジ、出力寸法などの機械チェック

現行実装では YAGNI と共通処理の整理により、`make_controls.py` と `make_depth.py` に統合している。このファイル分割案そのものは現行契約ではない。

## 初期パラメータ案

以下は実画像で調整する前提の初期仮説であり、固定値ではない。

| 処理 | 当時の候補値 |
|---|---|
| Superpixel 数 | 約1MPで 180〜450 |
| 写真 preset の例 | segments 350、compactness 10 |
| イラスト preset の例 | segments 250、compactness 15 |
| structure の縮小率 | 25〜40%（例 0.33） |
| structure | Gaussian blur → Sobel/DoG → threshold → small-component removal |
| composition map | 48 / 32 / 30 / 24 / 16 色を比較候補にする |
| quantization | dithering なし、小さな色島を整理 |

パラメータを CLI 引数にし、失敗原因に応じて限定的に再試行する案も含まれていた。

## 依存関係と実行負荷に関する検討

初期 Skill は Depth 推定器と `scikit-image` が環境に存在する前提で書かれており、実行時に「Depth 推定器がない」と止まった。この失敗から次の設計要件が出た。

- Skill の指示にライブラリ名を書くだけでは依存関係は導入されない。
- 再現性が必要な処理はスクリプト化し、実行環境を宣言する。
- Depth モデルは初回に取得し、その後はキャッシュを使う。
- Depth が使えなくてもタスク全体を止めず、別候補へフォールバックする。
- 不足依存を利用者へ丸投げしない。

当初想定した依存候補は Python、Pillow、NumPy、OpenCV、scikit-image、PyTorch / Transformers、Depth Anything V2 だった。現行実装は Apple Silicon での負荷を抑えるため Core ML と `uv` の一時実行環境を採用し、巨大な PyTorch 環境を必須にしていない。

後のローカル計測では、通常の Apple Silicon Mac で制御マップ生成と Small depth 推論は現実的な時間に収まり、総所要時間は前処理より画像生成候補数に支配された。ただし、これは単一の M2 / 16GB 環境での測定であり、全 Apple Mac を保証する値ではない。

## 後の実験で修正された点

2026-08-16 のローカル比較では、写真1例と2Dイラスト1例について Direct、map-only、元画像＋補助マップの hybrid を比較した。その結果を受け、初案を次のように修正した。

| 初案の仮説 | 後の判定 |
|---|---|
| ガビガビを避けるには元画像を最終入力から外す | 棄却。顔、画風、小物、意味情報が失われた |
| 構図マップだけで同じ画像を再構築できる | 一般化不可。map-only は現行方式で禁止 |
| イラストは Method 2 が既定 | 棄却。疎い構造線が誤誘導した例がある |
| Depth は重いが精度向上のため必要 | 未確定。写真では Method 2 とほぼ同等で、Depth 固有の上積みは未証明 |
| 30色は固定の最適値 | 未証明。比較用 baseline / 調整可能な目安 |
| 全方式を毎回実行する | 不採用。画像種別と QC に応じた小さな候補 portfolio を使う |
| 外部依存がある場合は利用者へ確認する | 修正。自動準備または安全な fallback を行う |

ローカル実験の詳細は Skill 外の一時評価資料であり、Skill 配布物の恒久的な一次資料とはしていない。重要なのは、元画像を Reference 1 として常に残し、補助マップを代用品ではなく追加制御に限定するという再発防止ルールである。

## 現行設計へ残した考え方

初期調査から現行 Skill へ残ったのは次の部分である。

- 壊れた高周波ピクセルをそのまま sharpen せず、全面を fresh render する。
- 元画像と補助マップの役割をプロンプトで明示する。
- 前処理は deterministic な同梱スクリプトへ寄せる。
- Superpixel、Depth、structure、30色 map は補助制御として比較可能にする。
- 補助マップ自体を目視 QC し、不正な map を生成へ渡さない。
- Direct を対照候補として残し、方式名ではなく結果の QC で選ぶ。
- 顔、画風、構図、物体、照明を守りながら artifact 除去を評価する。
- 依存関係の不足や Depth 失敗でタスク全体を止めない。
- 再試行回数を制限し、画像生成コストを無制限に増やさない。

## 未検証の論点

今後検証する価値があるが、現時点では断定しない項目:

- 長い反復編集履歴を持つ実画像でも hybrid の優位が再現するか
- 複数人物、顔の極端な小ささ、小さな文字、複雑な衣装での identity 保持
- 写真で Depth が coarse structure より有効になる具体的な条件
- 平面イラスト、透明体、鏡、建築、極端な遠近での Depth QC 基準
- 色数、Superpixel 数、blur 量を画像別に最適化する価値
- 生成候補数を増やしたときの品質向上と費用・待ち時間の釣り合い
- 自動指標が顔、画風、意味保持の人間評価をどこまで代替できるか

これらを検証する場合も、初期仮説を正しい前提にせず、Direct と hybrid を同条件で比較し、失敗例を含めて判断する。

# 実アプリの検証手順を作る

[Codexでの実行規則](../../execution.md)を読んでから使う。

コードと資料から、利用者の操作面、起動方法、既存の操作工具、取得できる証拠、並行実行の分離を調べる。複数の面があれば主な面と他を示す。起動はrepoの手順、操作は既存のPlaywright、PTY、HTTP等を優先する。観測できない製品判断だけ利用者へ確認する。

既存版が起動できなければ先に許可範囲で直すか具体的に報告する。検証用の一時資源を補う場合はその用途と終了時の削除を明示する。共有インスタンスを二重操作して状態を壊さない。

`.agents/skills/verify-<app>/SKILL.md` にアプリ・操作面・用途が分かるfrontmatterを書き、実際の調査から次を定める。

- 起動: 正確なコマンド、準備完了の観測、終了方法。短命のCLIは各操作を隔離したセッションで実行する。
- 診断: 正しい版・所有プロセス・ポート・認証を読み取りだけで確かめる。
- 操作: 実際のセレクタやコマンドを使う。座標より安定したラベル等を優先する。
- 証拠: 実際の利用経路で操作と結果、副作用を取得する。内部setterや試験専用入口を代用しない。外部境界だけ必要なモックを使う。dry-runが何を省略するかは実際のファイル・通信・Git参照で確認する。
- 後片付け: 自分が起動したものだけ終了する。名前による一括killをしない。証拠は削除しない。
- 補助: 実行可能なスクリプトと呼出方法を本文に示す。

`features/README.md` と利用者向けの主要3〜5機能を [機能一覧の例](feature-map-example/README.md) に沿って作る。各機能に何をするか、利用者がどう到達するか、工具でどう操作するか、観測できる完了状態、注意点を記す。他の入口も一覧にあるなら便宜的な一経路だけで全体検証済みにしない。

作った手順を起動・診断・一機能の操作・証拠取得・後片付けまで一回実行し、証拠が残ることを確認する。失敗ごとにも残った実行資源を片付ける。未実行なら下書きと報告する。保守には `maintain-verification-skill` を案内し、周期は依頼がある場合だけ提案する。

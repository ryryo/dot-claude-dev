# 仕組みと理由を会話で説明する

[Codexでの実行規則](../../execution.md)を読んでから使う。

会話から相手が知りたいことと既に分かっていることを読み、確認試験のような質問で知識を測らない。変更、レビュー、調査、初学のどれが目的かに合わせて深さを決める。

`how` で動作、`why` で理由を実際に調べる。許可されれば独立に並行し、同じ調査を親が重ねない。小さい変更なら一方だけで足りることもある。`why` は限定した問いと出典に絞り、省略理由はその規則に従って残す。説明の言い換えでも確信度を変えない。

最初に、何であるかと今回の用途を一、二文で説明する。仕組み、理由、境界のケースは相手の返答に合わせて加える。関数と定数の列挙ではなく、操作に伴い実際に何が起きるかを示す。「要点」「核心」などの型だけの導入を増やさない。

講義や演出にせず、相手の進め方に合わせる。言い返しや小テストを求めず、理解が難しいと先回りで決めつけない。一回の返答で終える場合は説明を完結させ、必要な次の話題を末尾へ置く。

図が理解を助ける場合はコード、差分、debuggerや図を示す。三つ以上の部分があるなら、全体を一度に出すより、前の図を描き直して一部分ずつ加える。流れや構造はMermaid、空間・配置・重なり・画面比較は利用可能な画像生成を使い、短いラベルで表す。単一の点に図は要らない。

`unslop` を使い、同僚へ話す自然な日本語で具体的な機構を説明する。比喩や予告で置き換えず、同じ概念を同じ名前で呼ぶ。本文は説明そのものとし、何をしたかの作業報告にしない。

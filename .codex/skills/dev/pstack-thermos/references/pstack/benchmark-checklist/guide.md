# 性能測定の根拠を検査する

[Codexでの実行規則](../../execution.md)を読んでから使う。

`principle-explain-the-number` を読む。変更前後、回帰、反復改善、ライブラリや設定の選定で得た数値を、実行の証拠で確認する。利用者が単なる概算を求めた場合は一回でもよいが、失敗と処理の実施は確認し、一回と明示する。選択肢の採用判断は概算ではない。

報告したい主張を先に書き、計測コードが何を測り、数え、除外するか読む。`uptime` とLinuxの `nproc` またはmacOSの `sysctl -n hw.ncpu` で負荷とCPU数を確認する。雑音を止められなければ両側を交互に測り、その条件を報告する。

1. 制限要因を調べる。報告用でない実行でプロファイル・CPU・I/O・システムコールを見てコードへ対応させる。負荷生成側が先に飽和していないかも見る。
2. 両側を本番相当のビルド、設定、データ、版、バッチ、トランザクション、接続、キャッシュで調整する。一方が既定設定なら実装比較とは言えない。調整できなければ、その測定で採用の勝者を選ばない。
3. 帯域、CPU、操作あたりの費用、変更箇所の元の時間と数値を照合する。物理限界や元の時間を超える改善は測り方を調べる。
4. エラー、タイムアウト、処理漏れを数える。失敗して短く終わった処理を性能改善に数えない。
5. 各側を少なくとも5回、A・B・A・Bのように交互に実行し、中央値と範囲を報告する。実行ごとの変動より小さい差は測定できた差としない。近い場合は順位和検定や測定基盤の統計も使う。複数回の分布を調べ、順序・ウォームアップ・負荷・キャッシュを揃える。偶然の一値を改善として採用しない。
6. 利用者の実際の経路に関係するか、部分測定の改善が全体にも現れるかを見る。
7. 意図した仕事が本当に実行されたか、入力件数・出力・チェックサム等で確認する。キャッシュ、省略、最適化による除去を除外する。

測定スクリプト、設定、入力、回数、ばらつき、エラーと処理件数、制限要因の証拠を数値と一緒に残す。`perf-issue` は基準と変更後の数値、`hillclimb` は測定条件を固定する前と各採用・撤回で使う。

報告は高速化・低速化・測定できる差なし・未確定の判定を先にし、単位、回数、範囲、制限要因を示す。制限要因が不明、片側が未調整、失敗と処理の実施を確認できない場合は未確定とする。PR本文の主要数値は一つにし詳細を証拠へリンクする。

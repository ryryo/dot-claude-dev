# 設計候補担当への指示

主担当が目的、調査結果、専用作業先、出力先を埋めて渡す。worktreeまたは候補ごとのディレクトリで独立させる。起動は委譲が許可された場合だけ行う。

まず **architect** 全文を読む。一候補の型、関数シグネチャ、モジュール図、[設計理由](rationale-template.md)を作る。

- 呼び出し元のREADMEと二、三の実例を先に書き、型を導く。使い方と型を一致させる。
- 主要なアクセスをデータ構造へたどる。「後で索引やキャッシュを足す」なら構造を見直す。
- 小さい公開面の内側へ機能と方針を集める。転送用の型を公開せず、境界内でドメイン型へ変換する。
- 二者が同じ状態へ書いたら何が起きるか問う。影響があれば各担当の状態へ分け、読取境界で統合する。
- 未実装の本文は `not implemented`、難しい処理は `// TODO` の疑似コード、コメントには意図と不変条件を示す。型とシグネチャだけで入力から出力を追えるようにする。
- 誤用しにくい型、実行時検査、説明の順で不変条件を守る。
- 外部境界で検証し、内部は型を信頼する。業務処理を純粋関数へ、外側を薄くする。
- 一つの不変条件には一つの正本を持ち、同期でなく導出する。
- 二回実行、途中失敗、再実行を考え、状態遷移を冪等にする。
- 呼び出しが三ファイルを越えて理解を散らすなら階層を浅くする。

他案へ遠慮して中間案に寄せず、自分の最良の設計を出す。案の違いが比較の材料になる。

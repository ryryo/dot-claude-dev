# 設計案を退ける兆候

統合前に各案を確認する。兆候があれば修正か不採用の理由を検討する。

## 薄いモジュール

公開する操作が多いのに、隠す複雑さが少ない。公開面の大きさに対して内側が引き受ける機能・方針を評価する。深いモジュールと長い呼び出し鎖を混同しない。前者は一つの入口へ知識を集め、後者は理解を分散する。

呼び出し元が一操作のために複数のメソッドを調整する、公開オプションが内部段階を露出する、インターフェースを学んでも実装を学ぶ必要がある場合は見直す。

## 内部情報の漏れ

同じ表現・方針・プロトコルの判断が複数モジュールへ広がり、変更に同時編集が必要になる。転送用の型を公開APIへ再公開しない。外部データは内部でドメイン型へ変換し、保存形式、フレームワーク、プロトコルの詳細を隠す。

## 時間順の分割

load、validate、transform、saveという実行順だけで分けると、一つの表現と不変条件が境界ごとに重複する。知識と所有でまとめる。同じ判断を守るメソッドなら、違う時点に動いても一モジュールに属せる。

## 素通しのメソッド

同じ形の引数をそのまま別メソッドへ渡すだけの層は消すか、操作を完結できる側へ責務を移す。方針、変換、別の抽象を提供する境界なら残す。

# 証拠と確信の扱い

コードから動作は読めても、存在理由は直接読めない。理由はcommit、PR、チケット、資料、会話にあり、欠落や矛盾を含む。筋の通る説明を後から作って事実にしない。

## 五段階

| 段階 | 条件 | 書き方 |
|---|---|---|
| Direct | 作者が理由を明示した文章。PRの目的、顧客要望、上限を説明するコメント、設計の採否など。 | 理由を断定できるが、すぐ隣に引用元を置く。 |
| Supported | 複数の間接証拠が一致する。perfのPR・ラベル・同じ経路のcommitなど。 | どの証拠から導いた判断か示し、複数の出典を付ける。 |
| Inferred | 文脈からの合理的な読みだが明示した根拠がない。 | 「AとBから、DのためCだった可能性が高い」と推論の鎖を示す。 |
| Speculative | あり得るが証拠が薄く、他の説明も同程度に成立する。 | 「一つの可能性だが直接の証拠はない」と明記し、競合仮説へ置く。 |
| Unknown | 調べても分からない。 | 対象、期間、検索語、調べた資料、結果を具体的に示す。 |

「理由は」「〜のため設計した」「解決した」「チームが決めた」はDirectまたはSupportedの根拠が必要。推論には「示唆する」「可能性が高い」「整合する」を使う。「当然」「明らか」「単に」は不確かさを隠しやすい。

作者が正しかったと仮定して正当化しない。反復パターンが意図的だったとは限らず、言及がないことを懸念がなかった証明にしない。利用者の「性能のため？」も仮説の一つとして独立に調べる。

矛盾するPRとチケットは両方を引用する。動機と作者の説明の違いか、どちらかの誤りかを勝手に決めない。未発見は有用な結果であり、問い、資料、検索語、関連情報しかなかったことを示す。

提出前に各主張を確認する。引用があるか、表現が確信段階へ合うか、コード自身を意図の証拠にしていないか、不明な点を隠していないか。根拠がなければ推論・仮説・不明へ移す。

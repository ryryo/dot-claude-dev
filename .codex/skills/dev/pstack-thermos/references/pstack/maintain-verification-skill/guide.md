# 検証スキルと機能一覧を保守する

[Codexでの実行規則](../../execution.md)を読んでから使う。

対象の検証スキルを特定する。複数なら確認し、なければ `create-verification-skill` を案内する。成果は全機能のコードと実動作を確認した `clean`、証拠のある修正を行う `changed`、網羅できない `blocked` から選んで明示する。

編集は検証スキル自身のSKILL.md、機能一覧、所有する補助に限る。製品コードを直さない。製品の回帰を資料で隠さず報告する。

索引の不足・重複・古い参照を直す。許可された並列調査では各機能に読み取り担当を一人割り当て、概要、コードの入口、ずれの候補、実動作の操作案を回収する。子はアプリを操作せず編集しない。全機能の結果を統合し、候補の根拠を確認する。未掲載の機能は具体的なコード経路が必要である。

コードが正常に見えても全機能を実際に操作する。親が操作を所有し、サーバー・UIは一つの長命インスタンスを順に操作し、短命CLIは各回を分離する。初回、異常後、新セッションでは診断する。UIの固着を診断できなければ既知の状態へ戻すか再起動する。証拠は毎回の後片付け後も残し、操作で始めた不要な資源を残さない。

診断手順のずれなら所有範囲で直し、その修正で無効になったものだけ再起動して一回再試行する。到達不能は認証・権利・OS・外部状態の具体的な前提と試した経路を示す。前提が一覧に抜けていれば資料のずれである。操作補助の修正は実動作で再検証してから届ける。

説明の違いは資料、動く機能を操作できない問題は補助、実際の製品不具合は残件として分ける。`changed` は許可された範囲で一つのPR、`clean`・`blocked` はPRを作らず網羅性を正直に報告する。最後に実行資源を終了し証拠を残す。短い実行メモは一時場所へ置く。

# 型で不正状態を表せなくする

[Codexでの実行規則](../../execution.md)を読んでから使う。

型検査を使い、不正な状態、意味の異なる基本値の混同、未処理の状態をコンパイル時に防ぐ。すべての型付き言語に適用し、TypeScriptでは `typescript-best-practices` で具体化する。

選択肢は直和型で表す。TypeScriptの判別共用体、Rust等の値を持つenum、sealed class等を使い、任意項目の組合せで矛盾する状態を許さない。`completed` と `completedAt` を別々に同期する代わりに、一つの状態から導出するか `{ kind: 'open' } | { kind: 'done'; at: Date }` にする。

型は制限だけでなく構築方法で設計する。非空リストは先頭と残り、時間範囲は開始と期間、偶数長はペアの列など、不正値を作れない形を選び、呼び出し元が必要とする操作を公開する。

`UserId` と `OrderId` のような意味の違う基本値はブランド型・newtype等で区別し、生成時に一度検証する。RPC、JSON、IPC、CLI、設定、環境変数、DB行は境界で未型付きの入力として解析する。

型の断言、unsafe変換、検査しないassertで型検査を欺かない。検証・絞り込み・モデルの修正で証明する。状態の選択肢を追加したとき、未処理の分岐がコンパイルエラーになる網羅性を使う。TypeScriptは `never`、Rustは `match`、Haskellは `-Wincomplete-patterns` 等を使う。

Protocol Buffers、OpenAPI、GraphQL、DB移行、デザイントークンなどが形を定義しているなら、その取得元から型を導出する。手書きの別版を増やさない。

型を強めるのは操作が未定義になり得る場所に限る。空列の `sum` は0で全域なら通常の列、空列の `head` は値を返せないので非空型にする。正確さだけを目的に型を複雑化しない。

項目の組合せの妥当性をコメントで説明していないか、同じ基本型で意味の異なる引数がないか、`any`・`as`・`assertNotNull` がどの境界から来たか、新しい状態を型検査が知らせるか、他の取得元の形を複製していないかを点検する。

例えば `UserId` と `OrderId` を区別し、読み込み中・成功・失敗を判別unionで表すと、取り違えと不正な組合せを型検査で防げる。

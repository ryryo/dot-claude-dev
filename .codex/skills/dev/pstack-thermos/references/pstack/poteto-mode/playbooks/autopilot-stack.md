[Codexでの実行規則](../../../execution.md)に従う。担当は親の設定を継承し、書き手の作業場所を分離する。採用・公開・定期実行は利用者の許可範囲で行う。

# 検証したPRを直列に届ける

実装と検証を自律的に進め、利用者が採用する一本のPR列を作る。マージは担当しない。

1. `autopilot-full.md` の担当進行を使う。各担当は実装、最初のpush、自己検証前の許可されたPR、検査とCI、botの反証、コード整理、`no-comments`、`babysit` を所有する。独立作業は並列化し、約15分以内の判断記録・snapshot・PRと、子担当の記録を維持する。利用者のdraft指定を優先する。
2. 親は実行中およそ30分ごとと完了時に手順・目的・全担当・子担当・実際の成果を監査する。将来の監査は対応する永続機能と明示依頼を要し、sleepで代用しない。停滞の対応はfull版に従う。
3. 計画の提示依頼と開始許可を分ける。開始後は全体の目的を記録し、停止は全担当への書込み停止として直ちに反映する。
4. 担当はcode-ready SHA、検査後の `STACK-READY` と正確なheadを示す。親はfull版と同じ、実動作・回帰・差分監査を含む独立判定を各反復へ行う。未検証のPRを列へ入れない。
5. 合格したPRを検証順または利用者指定順で一本のbase-branch列へ追加する。担当はマージ、auto-merge、終了を行わない。
6. 構成を変更する書き手は親一人とする。担当は自分のブランチだけpushし、tip、現在のbase、意図する親を報告する。親は指定parentをfetchし、その正確なtipへchildをrebaseしてlease付きpushを行い、PRのbaseをparentブランチへ設定する。rootだけtrunkを対象にする。Graphiteへ列を登録しない。
7. trunkの変更は親が下から上へ取り込む。担当範囲の競合はその担当が直し、親が結果をpushする。書き換わったSHAの判定をそのまま使わず `shipping.md` のpatch-id規則で確認する。無効なら再検証し、patchが同じでも新headのCIとmergeabilityは再実行する。固定値の新たな緩和はfull版の親承認を要する。
8. 一本の列を下から確認できる形で渡し、各PRの本文またはコメントに検証判定を残す。利用者が自身の操作で採用する。

独立PRの採用権限まであるならfull版、事前の利用者レビュー・順序依存・採用権限なしならstack版を選ぶ。rootとtip、各PRの判定、保留・除外と理由を返す。

コード変更のレビューは [レビューの進行](../../../review.md)へ進む。計画・設計の反証と、実動作・性能の検証は、それぞれの対象に応じて行う。

# 確認できる小さなPRを作る

他の手順の最後で、利用者とrepoに許可された範囲のPR作成を行う。

状態を先に確認し無関係な変更を保持する。書き手に専有ブランチとWorktreeを用意し、正確なパスと基準SHAを依頼へ渡す。起動だけで分離されない。占有された作業場所をreset・cleanしない。所有ブランチだけをrebaseし、許可されたremote書換は現在のSHAと明示的なleaseを使う。

コミットを小さく一目的にし、説明できる順に整える。直前の同じ目的の修正はamend、独立の変更は別コミットにする。commit前に利用できる `deslop`、レビュー前に `no-comments` を行う。PRとコミット文には `technical-writing` のDiátaxis以外の規則と `unslop` を使う。

題名は `type(scope): subject` のConventional Commitsで、feat、fix、docs、refactor、test、chore、perfから選ぶ。変更領域をscopeにし、短い動作と実際の記号を示す。末尾の句点は付けない。

本文は作業日誌ではなくレビューの説明にする。目的、方法、必要な範囲、気になる代案、影響、実施した証拠を伝える。squash本文として約40行を大きく超えるなら詳細を別の証拠へ移す。

見出しは目的と方法、範囲、比較した代案、影響、検証の順とし、内容のない欄を省く。範囲は実際の記号・パス、renameは両側を示す。影響は誰・何にどう影響するか、安全または危険の根拠を1〜3文で示す。性能は主要な一数値を単位付きの変更前→後で記し、その他の証拠へリンクする。

証明になる画像・動画を添える。SHA一覧、担当別の長い報告、ファイルごとの作文、合格宣言だけを本文へ貼らない。repoのテンプレートを優先し、SummaryやTest planを形だけ足さない。本文をshellへ埋め込まずファイルで渡す。

最初のPR操作前にGitHub CLIまたは解決できるOriginを選び、作成・編集・確認・監視・採用を一貫させる。Graphiteを必須にしない。

大きい一PRより狭い複数PRを選ぶ。依存する列のrootはtrunk、childはparentの正確なtipへrebaseし、PRのbaseもparentブランチにする。独立作業だけtrunkから分岐する。大きい列作業前にtrunkとの基準を整える。

完成成果は許可されたready、未完成はdraftにする。既存のdraft指定や他の所有者の公開状態を勝手に変更しない。状態を述べる前に実際のPRを読む。

PR作成だけでbabysitを始めずURLを返して実装を続ける。段階または列が完成して利用者が依頼したら別の確認として行う。子はinterrogate・deslop・no-commentsとURLを返して親へ戻る。full・stackの所有者だけは依頼された進行に従いcode-ready後にbabysitを行いmerge-readyまたはSTACK-READYを返す。

コード変更のレビューは [レビューの進行](../../../review.md)へ進む。計画・設計の反証と、実動作・性能の検証は、それぞれの対象に応じて行う。

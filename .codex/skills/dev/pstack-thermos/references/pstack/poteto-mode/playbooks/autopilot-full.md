[Codexでの実行規則](../../../execution.md)に従う。担当は親の設定を継承し、書き手の作業場所を分離する。採用・公開・定期実行は利用者の許可範囲で行う。

# PRごとの担当が実装から採用まで進める

親はPRの実装ではなく独立判定・承認記録・監査を担当する。一PRの担当が実装からマージまで責任を持つ。親自身が採用し子はマージしない `orchestrate` とは分ける。

1. 利用者が自分で操作すると指定した項目は利用者へ残す。計画を述べるだけの依頼なら提示して待ち、明示された開始から実行する。依頼された場合に全体の目的を記録し、対象が完了するまで維持する。
2. GitHub CLIを既定とし、Originが導入済みでrepoを解決できる場合だけ一貫してOriginを使う。Graphiteを必須にしない。一PRに一担当、専有ブランチと作業場所を割り当てる。担当は実装、最初のpush、PR、実物の自己検証、botの反証、`deslop`、`no-comments`、現trunkへのrebase、`babysit`、許可されたマージまで扱う。
3. 約15分以内に `decisions.tsv`、最初のブランチsnapshot、許可された公開状態のPRを用意する。PRを自己検証前に開いてURL・判断・検査を記録に残す。元版のready運用より、利用者のdraft指定と公開権限を優先する。子を起動したら `children.tsv` にID、予想時間（同種の過去最長以上）、状態を記す。両TSVは未コミットで回収する。
4. code-ready前に一度rebaseする。修正反復ではその基準を維持し、採用準備、trunkとのmerge-tree競合、trunk由来のCI故障の場合だけ再rebaseする。コード整理後のcode-ready SHAと、以後patchを変えたpushのSHAを報告する。親の検証と自己検証・CI・babysitを並行する。push前に対象のAGENTS等が求める検査をコミット済みheadへ実行し、hookの合格で代用しない。自分のremoteブランチの書換は許可範囲で `ls-remote` と明示的な `--force-with-lease` を使い、共有ブランチを強制pushしない。
5. 独立PRはmainから分岐し並列に進め、依存作業は採用後に次を分岐する。実際に重なる部分だけ直列化する。真に依存する一変更の分割だけ短い専用stackを許す。
6. code-readyとpatchを変えるpushごとに、親がそのSHAへ独立した `swarm` 検証を行う。対象SHAの必須検査、実際の操作面で主要動作、PR説明を信頼しない差分監査を行う。監査は少なくとも二つの担当に、利用者の挙動一致、寿命・競合、データ・設定安全性等の主題を分ける。
7. 現trunkで同じ主要シナリオを実行する。trunkに新機能がない場合はその事実を残し、差分の追加動作と利用者が待つ最終状態を確認する。実動作担当が欠けた判定は合格ではない。採用可能報告の証拠を先に監査し、採用headのpatchと一致する反復の合格が必要である。
8. 問題は注記扱いの不具合も含め、証明できた全件を一回で担当へ返す。同じ不具合がある全箇所を再現するRED、無理なら再現記録を要求し、次のレビュー条件にも加える。新headは新しい検証を要し、再利用は `shipping.md` のpatch-id条件だけを使う。
9. 合格後、担当は検証が開始された後に採用準備を行い、直前に最新trunkへrebaseし新headを報告する。そのheadでCIを通し、patch-idで判定の有効性を再確認する。trunkが再度動いた場合も同じ規則を使う。許可と親の合格が揃った自分のPRをsquashで採用し、次の独立項目へ進む。利用者指定の項目は採用可能までで止める。
10. 既存予算や固定検査値の新たな緩和は、検証の証拠と親の新しい承認記録を要する。工具やホスティング側の承認を迂回しない。mainに採用済みの値を取り込むことは新たな緩和ではない。
11. 親は実行中およそ30分ごとの監査期限を置き、担当の完了時には早める。将来の無人監査は明示依頼と永続実行機能を要する。監査で手順の版・パスと目的を読み直し、ずれを直す。全担当と `children.tsv` の状態を確認し、進捗はコミット、push、PR・検査の変化、成果物等の実結果で判断する。
12. 予想時間を超えて成果がないかエラーになった担当は、実際の正常な長処理と区別して停滞を調べ、停止と限定した後任の配置を行う。停止が完了する前に同じ書込先へ後任を重ねない。停止できなくても停滞と必要な作業を記録し、仕事を合格や不要扱いにしない。全子担当を回収し、まとめて採用した後は振り返りと採用後のbot指摘を確認する。最後のマージ後も子担当を残さない。
13. 利用者の停止指示は全担当へ直ちに書込み停止として伝える。解除まで依頼を保持する。

各PRの担当・状態・head、各反復の判定と検証担当、採用結果と次の項目、承認記録、利用者待ち、回収した判断記録を返す。

コード変更のレビューは [レビューの進行](../../../review.md)へ進む。計画・設計の反証と、実動作・性能の検証は、それぞれの対象に応じて行う。

# pstack-thermos

依頼に合う手順を選び、求められた成果を実際の利用経路で確かめる。開発はpstack、コード変更のレビューはthermosの手順で進める。

## 依頼から手順を選ぶ

最初に [実行条件](references/execution.md)を読む。下の表から必要な入口へ進み、その入口が指定する資料だけを読む。

| 依頼・作業の段階 | 読む手順 |
| --- | --- |
| 調査、設計、実装、修正、自律開発 | [pstackの作業選択](references/pstack/poteto-mode/guide.md) |
| PR・ブランチ・作業ツリーのコードレビュー、開発後の変更レビュー | [レビューの進行](references/review.md)、続いて [thermos](references/thermos/guide.md) |
| 計画・設計・検証資料の反証レビュー | [レビューの進行](references/review.md)、続いて [interrogate](references/pstack/interrogate/guide.md) |
| 初回設定、設定の不足・競合、担当の検出失敗 | [セットアップ補助](references/setup.md) |
| 特定のpstack手順を指定 | [内部手順の索引](references/pstack/index.md)から該当手順 |

内部手順は参照資料として使う。`$thermos` や `$interrogate` などの別スキルが導入されていることを前提にしない。子担当には、この配布物の該当ファイルの絶対パスと固定した対象を渡す。

## 開発とレビューをつなぐ

実装後は、変更範囲と検証結果を固定してthermosへ渡す。採用した指摘を許可された範囲で修正し、影響する検証とレビューを更新する。計画レビュー、コードレビュー、実動作検証は、それぞれの対象と実施証拠を持つ。

小さな変更には必要な手順だけを使う。文言や書式だけの変更でコードの動作が変わらない場合は、内容・参照・表示の確認で完了を判断する。利用者やリポジトリが指定する必須レビューは維持する。

## 担当を使う前に確認する

委譲の許可、実際に使えるツール、並列枠、担当の一覧を確認する。書き手には専有するファイルと実行資源を割り当て、レビュー担当は読み取り専用にする。主担当が実物・差分・検証結果を回収する。

専用担当が未設定なら、[セットアップ補助](references/setup.md)で診断する。使える汎用担当へ必要な指示を渡せる場合は、その経路でも進められる。担当設定の配置と、Codexでの検出・起動成功を区別する。

## 完了を判断する

求められた成果、実際の変更、検証結果、残る指摘を照合する。未実施・判定不能・利用できない機能を区別し、担当の自己申告だけで合格にしない。

返答は成果から伝え、確認できた範囲と、残る作業があれば具体的な次の操作を示す。レビューの合格は、マージ・公開・外部操作の許可を追加しない。

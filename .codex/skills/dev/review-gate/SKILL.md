# Review Gate

現在の成果を次工程へ渡してよいかを、契約と直接証拠で判定する。

このレビューで揃えるのは、細かな入力値や操作順の全組合せではない。**同じ成果を別の根本原因から壊し得る、独立した観点**である。具体例や反例は観点を確かめるために使い、件数を増やすこと自体を完全性の根拠にしない。

一件の問題でNO-GOが見えても探索は終えない。初回レビューでは、適用する観点をすべて一巡してから、根本原因ごとにまとめた指摘を一度だけ返す。

## 用語を混同しない

### 見逃し

レビューした成果の同じ状態に、現在契約を破る到達可能な問題がすでに存在していたにもかかわらず、完了したレビューの指摘と判定へ含めなかったことをいう。

次は見逃しに含めない。

- レビュー後の修正が新しく生んだ回帰
- レビュー後に追加または変更された契約への不適合
- 初回レビュー時には取得できず、`未確認`として明示していた証拠が後で得られた場合
- 現在の契約や到達経路に入らない改善案

修正後の再確認で別の問題を見つけた場合は、問題が初回レビュー時の成果にも存在したかを確認する。存在していたなら`初回レビューの見逃し`、修正によって生じたなら`変更由来の回帰`と報告する。根拠なく後者へ分類しない。

見逃し防止とは、細かな全組合せを列挙することではない。初回レビューで異なる根本原因を探す観点を揃え、全観点を一巡してから指摘をまとめることである。

### 過剰レビュー

現在Gateの判定に必要な範囲を越えて、調査、反例、証拠、再レビューを増やすことをいう。次のいずれかに該当するものは過剰レビューである。

- 現在契約、到達可能な因果経路、既存handoffのいずれにも結び付かない対象を調べる
- 同じ根本原因を、入力値、時刻、browser、file、event順ごとのcaseへ分割して網羅しようとする
- 変更の影響を受けない観点を、修正のたびに最初から調べ直す
- 文言、記録、review tool、schemaの変更だけを理由に、成立済みの実装観点を再レビューする
- 機械で確かめられる事実を利用者へ断言させる、または一つの事実を複数の証拠で過度に重ねる
- 現在Gateの結論に使わないreview履歴、case台帳、移行表、巨大なhandoff表をPLANへ蓄積する

一方、到達頻度が低くても、現在契約を破る因果経路があり、別の根本原因を代表する確認は過剰レビューではない。難しい問題かどうかではなく、現在Gateの成立可否に必要かで判定する。

### 過剰実装

現在契約を成立させるため、または採用済み`fix-here`を直すために必要な最小範囲を越えて、製品挙動、構造、UI、運用、外部作用を追加・変更することをいう。次のいずれかに該当するものは過剰実装である。

- 現在の条件にない自動検知、監視、heartbeat、fallback、設定項目、診断機能を追加する
- 後工程や別Storyが所有する内部実装を先取りする
- reviewやJourneyで見つけた改善案を、新しい利用者要件として実装する
- 検証harnessや証拠作成のために、判定に不要な製品UIや挙動を作り込む
- release／Journey担当が、条件不成立をその場で新しい製品挙動へ置き換える
- 到達可能な反例と破られる現在契約を示さず、一般的な堅牢化だけを理由に実装する

PLANにこのような作業を必須項目として先取りすることは、過剰実装を予約する過剰計画である。現在契約を破る到達可能な問題を最小範囲で直し、必要な振る舞いの回帰テストを加えることは過剰実装ではない。

## 1. レビュー対象を固定する

深く調べる前に、依頼、Story、PLAN、差分などの一次情報から、一時的なReview Inputを作る。

- Gate固有の判定質問
- 対象成果と、同一性を確認する方法
- 担当する条件IDと現在の公開契約
- 意味を変更した箇所、公開状態、出力、外部作用
- 通常導線と、現在の契約に実在する例外導線
- OpenCap全体の不変条件のうち、変更経路が影響し得るもの
- 対象外
- 既存の後工程へ渡す場合は、Gate、担当、handoff契約

PRでは、最初に実差分のfile一覧を取得し、Review Inputの`target_artifacts`へ過不足なく入れる。PR以外では、判定対象となる実装、文書、外部状態などを同じ欄へ入れる。Briefでは各成果物を、現在契約へ届くsurfaceへ対応付けるか、対象外の理由を付けて除外する。file数をレビュー品質の目標にはしないが、見ていないfileを暗黙に無視しない。

Review Inputを、実装内容、既知の指摘、reviewerの改善案から逆算しない。main Codexが正本と意味を照合する。validatorは構造を検査できても、この意味上の忠実性までは判定できない。

次はレビュー対象へ入れない。

- 現在の契約から到達しない将来用途
- 一般的なbest practiceや「より良い設計」だけを根拠にした改善
- 別Storyや後工程の内部実装
- 現在Gateが所有しない製品要件の追加

PLANレビューでは、実行項目が現在Gateの利用者成果または必要なhandoffへ直接結び付くかも確認する。後工程の責務は、現在Gateが渡す境界を一つのhandoffとして記載すればよく、後工程の条件表や実行手順を先取りしない。

Review Input、Brief、manifestなどのレビュー管理物は一時成果物とする。修正と再確認のcycleが閉じるまではtask-localにbaselineとして保持し、閉じた後は永続成果物にしない。Story、PLAN、EVIDENCEへ、レビュー履歴、case台帳、一時path、branch、commit SHA、worktreeやsessionの識別子を保存しない。

## 2. 適用範囲Gateを通す

対象範囲は、次の二方向を別々に辿って作る。

1. 利用者が観測する結果と条件から、生成側へ遡る。
2. 変更したsurface、共有状態、外部作用から、既存の利用側と観測結果へ進む。

現在の成果から観測結果まで因果経路があり、破られ得る既存契約と探索を止める境界を示せるものだけを`適用`とする。契約上必要な配線や状態遷移が存在しない場合は、その欠落自体を到達可能な経路として扱う。

既存のhandoffへ実際に値や状態を渡す場合は、その境界を`適用`観点として確認し、後工程の内部へ入らない。後工程はReview Inputのhandoffとして別に記録する。契約にもhandoffにも結び付かない候補は`非適用`とし、指摘や追加計画へ昇格させない。判断に必要な一次情報を取得できない場合は`未確認`としてHOLDする。

適用範囲Gateは、次を満たした場合だけ通過する。

- 判定質問、対象成果、現在契約、対象外が固定されている
- 上流方向と下流方向の候補が`適用`または`非適用`に分類され、未確認がない
- すべての`適用`に、契約、到達可能な因果経路、探索を止める境界がある
- 後工程は、正本に既存の名前付きhandoffだけである
- `非適用`には、現在の契約または到達経路へ入らない理由がある
- Review Inputの全成果物が、適用surfaceまたは理由付きの対象外へ一度だけ分類されている

## 3. 独立した観点を先に揃える

深い探索や指摘の確定より前に、一時的な「レビュー観点一覧」を作る。観点は、**異なる根本原因を見つけ得るか**で分ける。同じ原因を入力値、条件ID、file、browser、時刻、event順ごとに分割しない。

次は観点を考える入口であり、常に全項目を採用する固定チェックリストではない。

- 利用者成果と公開契約
- 状態遷移とデータの保持・復元
- 所有権、resource lifecycle、非同期処理、競合
- 失敗、取消、再試行、cleanup
- consumer、統合境界、認証・分離、外部作用
- 証拠とoracleが実際に保証できる範囲

現在の変更に適用するものだけを選ぶ。因果経路と根本原因が同じものは一つにまとめる。複数の機構が実際に接続する境界だけは、観点をまたぐ確認を一度行う。全観点の直積や、理論上あり得る全interleavingは作らない。

各観点には、次を持たせる。

- IDと、答える質問
- 守る現在契約
- `契約 → 生成側 → 状態・外部作用 → 利用側 → 観測結果`の因果経路
- 探索を止める境界
- 代表となる正常例または反例
- 最小で十分な観測方法と、その証拠が保証する範囲
- `未着手`、`成立`、`違反`、`未確認`の状態

さらに、各観点の因果経路を、次の3種類の確認点（`coverage point`）へ分ける。

- `origin`: 現在契約、入力、producerなど、経路の入口
- `mechanism`: 状態、resource、非同期処理、変換、外部作用など、結果を生む仕組み
- `observation`: consumer、公開出力、cleanup後の状態、証拠など、合否を観測する出口

これはcase表ではない。入力値、操作順、browserごとには分けない。同じownerが同じ開始・前進・失敗・退役経路で管理するものは一つにまとめる。一方、ownerまたは退役経路が異なる状態、resource、非同期処理は、同じ観点の中でも別の`mechanism`として残す。代表例の一つが通っただけで、別ownerの仕組みまで確認済みにしない。

最初の観点一覧を作った後、深い探索に入る前に別の文脈から一度だけ見直す。問いは「同じ利用者成果、または同じ変更経路を、別の根本原因で壊す観点が欠けていないか」とする。独立reviewerを使える場合はこの見直しを任せ、main Codexが重複を統合して一覧を固定する。

この見直しでは、次の三つを一度ずつ記録する。

1. 条件と観測結果からproducerへ遡った結果
2. 変更surfaceからconsumerと外部作用へ進んだ結果
3. 同じ成果を別の根本原因で壊す観点が残っていないかの確認

この時点で行うのは観点の不足確認であり、細かな反例の列挙ではない。観点数、test件数、file数はレビュー品質の目標にしない。

編集ドメインでclock、scheduler、queue、retry、resource lifecycle、serializationを変更した場合は、適用する観点について`.reference/`の対応source、consumer、test、修正履歴を確認する。参照実装の機能全体をレビュー範囲へ取り込まない。

## 4. 指摘を保留して全観点を探索する

固定した各`適用`観点を調べ、`成立`、`違反`、`未確認`へ更新する。問題候補は別に保持し、全`適用`観点を終えるまで確定した修正指示や最終NO-GOを送らない。

- 一件目の指摘で止めない
- 複数reviewerを使った場合は、全員の完了を待つ
- reviewerの報告を並べるだけでなく、main Codexが観点間の重複と隙間を確認する
- 同じ根本原因の候補をまとめる
- test件数や「全体を読んだ」という自己申告を証拠にしない
- 各`coverage point`を`成立`、`違反`、`未確認`へ分類し、直接根拠を残す
- 一つでも`違反`なら観点全体を`違反`、`未確認`が残れば観点全体を`未確認`とする

証拠は`実行して観測`、`静的に確認`、`既存証拠を照合`のいずれかを明示する。人へ確認するのは、聞こえ方、見た目、操作感など人にしか判定できない結果に限る。mute設定、時刻、routing、保存値など機械で観測できる事実を、人の回答で代用しない。

探索中に本当に別の観点が必要だと分かった場合は、候補をすぐ指摘へせず、適用範囲Gateへ一度戻る。既存観点と異なる根本原因である理由を確認し、観点一覧へ加えてから残りを探索する。単なる値違い、順序違い、追加例は新観点にしない。

## 5. 三つのGateで完了を判定する

実装を含むPR／Gateレビューでは、[Review Gate manifest](references/manifest-schema.md)とvalidatorを使う。「USや変更影響へ範囲を限定する」という依頼は、manifestを省略できる限定レビューを意味しない。純粋な文言確認など、状態、resource、外部作用、複数成果物を持たない単純な確認だけは省略できる。manifestは観点の完了を忘れないための一時チェックであり、細かなcase台帳ではない。

### 適用範囲Gate

第2節の条件を満たし、全成果物の分類、二方向の追跡と独立原因の確認、レビュー対象、観点、各確認点の境界が探索前に確定していることを確認する。

### 探索完了Gate

次をすべて満たすまで探索完了にしない。

- 固定した全`適用`観点が`成立`、`違反`、`未確認`のいずれかである
- 各観点に、因果経路、探索境界、観測方法、直接根拠がある
- 各観点の全`coverage point`に直接根拠があり、その集約状態と観点の状態が一致する
- 観点をまたぐ接続境界が実在する場合は、その境界を確認している
- すべての問題候補が観点へ結び付いている
- 対象成果が探索開始時から変わっていない
- 担当reviewerが完了している。続行不能なら残りを引き継ぐか、未確認として理由を残している

一件のblockerはGateの結論を早く決めても、探索完了を意味しない。このGateが、指摘を一件ずつ小出しにすることを防ぐ。

### 指摘採用Gate

探索完了後に、各候補を次の四軸で判定する。

1. 到達可能な反例、破られる現在契約、一次根拠があるか。
2. 現在Gateの成立可否を変えるか。
3. 現在の依頼と権限内で、契約を変えずに修正できるか。
4. 提案する修正が現在契約に必要な最小境界に収まり、新しい製品挙動や後工程の実装を増やさないか。

結果は`fix-here`、`later-gate`、`契約判断待ち`、`非適用`へ分ける。

- `fix-here`: 現在Gateの契約を破り、現在の範囲と最小境界で直せる
- `later-gate`: Review Inputに既存のhandoffと一致する
- `契約判断待ち`: 現在適用される契約同士が衝突し、利用者の判断が必要
- `非適用`: 現在の指摘、修正、後続作業にしない

全候補を分類し、同じ根本原因を統合してから、採用した全指摘を一つの修正指示へまとめる。レビューだけを依頼された場合は成果物を変更しない。

validatorの成功は構造上の完了だけを示す。main Codexは、契約、到達経路、探索境界、証拠の意味、観点の粒度を一次情報で確認する。レビュー中にvalidatorやschemaが更新されても、開始時に固定した版で成立したレビューを失効させない。新しい規則が現在の成果に具体的な未確認を示した場合だけ、その観点を再開する。

## 6. 修正後は影響した観点だけを再確認する

修正後の依頼は、新しい全面レビューではない。初回レビューの観点一覧と完了証拠をbaselineにし、まず変更影響を整理する。

- 何の公開状態、出力、外部作用が変わったか
- どの因果経路と観点へ影響するか
- 影響しない観点では、契約、境界、証拠の前提が保たれているか

影響した観点だけを再び開き、修正と回帰を確認する。影響しない観点は、前提が不変である根拠を添えて引き継ぐ。次のいずれかが変わった場合だけ、観点一覧を作り直して全面探索する。

- Gateの判定質問または現在契約
- 対象となる利用者成果や変更surface
- 利用側までの因果経路または探索境界
- 独立した観点の集合そのもの

文言、見た目、証拠の記録、進捗、review toolだけの変更は、それが契約や因果経路を変えない限り全面レビューを発生させない。検証は変更リスクに比例させる。

再確認中に、修正前から存在した別観点の問題を見つけた場合は、通常の追加findingとして一件だけ追送しない。これは初回レビューの見逃しである。

1. その場では候補として保留する。
2. 既存観点の探索不足か、観点選定の不足かを特定する。
3. 同じ不足から残り得る観点を一度だけまとめて確認する。
4. 見つかった全件を、見逃しの原因とともに一括で報告する。

この回復確認を、新しい入力値や理論上の全順序を増やす口実にしない。対象も契約も変わっていない成果へ、理由なく別の全面レビューを繰り返さない。

実Journeyやrelease確認で条件を満たさない場合、検証担当が新しい製品挙動を考案して実装しない。固定済み実装が契約を破るなら実装Gate、oracleや外部反映手順だけが不足するなら該当PLANの検証Gate、既存契約が衝突するなら契約判断へ戻す。検証手順の修正は同じ条件を判定する最小範囲に限る。同じ仮説の外部変更やdeployを繰り返しても新しい証拠が得られない場合は、安全な状態へ戻して停止する。

## 7. 最終報告

最終報告は短くまとめる。

1. Gate質問へのGO／NO-GO
2. 適用範囲Gate、探索完了Gate、指摘採用Gateの結果
3. 根本原因ごとに統合した指摘。なければ「なし」
4. 未確認事項と、現在の範囲に残るリスク
5. 既存handoffへ残す責務

GOにできるのは、未解決のblockerと合否に必要な未確認がなく、Gate質問へ直接証拠でYesと答えられる場合だけである。
